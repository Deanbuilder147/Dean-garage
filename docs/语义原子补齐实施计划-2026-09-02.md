## 一、已验证的核心机制（本方案的基石）

### 1.1 完整链路（5 步，全部经代码核实）

```
① 前端 atomGroups 定义原子
   { grp, key, label, effectType: '<handlerKey>', fields: [...] }
        ↓
② 加载时拉 /combat-glossary/atom-meta，自动回填 semantic
   GlossaryStudio.vue L550-565 / GlossaryHubNew.vue L553-560
   byHandler: handlerKey → semantic；a.semantic = byHandler.get(a.key) || byHandler.get(a.effectType)
        ↓
③ 落库：type = a.semantic || effectType
   GlossaryStudio.vue L1465  →  { type, atom_key, _semantic, ...params }
        ↓
④ 引擎执行：atomRegistry.resolveAll() 翻译 + 应用 paramMap
   skillExecutor.cjs L1461  →  { type: handlerKey, ...引擎字段, _semantic }
        ↓
⑤ 回读：按 atom_key → semantic → effectType 三级匹配，取原子面板的 fields
   GlossaryStudio.vue L1155-1175；L1178: fields = (def && def.fields) || EFFECT_FIELDS[e.type] || []
```

### 1.2 关键结论

| # | 结论 | 证据 |
|---|---|---|
| 1 | **前端 effectType 必须写「后端 handlerKey」**，semantic 会自动回填 | L559 `byHandler.get(a.effectType)` |
| 2 | **`paramMap` 仅对语义名生效**，写 handlerKey 走直通不翻译 | `atomRegistry.resolve()` L58-70；测试 `integration.test.cjs:60-63` |
| 3 | **回读优先用原子面板的 fields**，`EFFECT_FIELDS` 只是兜底 | L1178 → 新增原子只要在 `atomGroups` 定义了 fields，回读即可用，**无需补 EFFECT_FIELDS** |
| 4 | 两副本（Studio / HubNew）**都已实现** atom-meta 回填 | Studio L553、HubNew L553 |
| 5 | **存量数据完全干净**：`target_selection`/`spawn_items`/`cost_*`/`trigger_entry`/`resolve_target`/`remove_buff` 在 `glossary-skill-config.json` 中**均 0 次** | 实测 |

> ⚠️ **修正此前判断**：前端**已消费** `/combat-glossary/atom-meta`（用 `apiClient.get` 直调，非 `glossaryAPI.getAtomMeta` 封装）。

## 三、⚠️ 三个决策点（需你拍板）

### 决策点 1：`trigger_entry` 语义名冲突（必须解决）

`B_ENTRY` 与 `B_HIT_CALLBACK` 的 handlerKey **同为 `trigger_entry`**。
现有回填逻辑（`byHandler.set(m.handlerKey, m.semantic)`）是 Map 覆盖，**后注册的 `B_HIT_CALLBACK` 会覆盖 `B_ENTRY`**。

后果：若新增两个原子都用 `effectType:'trigger_entry'`，回填后两者的 `semantic` **都会变成 `B_HIT_CALLBACK`**，
导致 `B_ENTRY` 的 `entry_type` 参数在 `paramMap` 中无映射而丢失。

| 选项 | 做法 | 评价 |
|---|---|---|
| **A（推荐）** | 新增 2 个原子 + 改回填逻辑为**硬编码优先**：`if (a.semantic) return` 放在赋值前（1 行改动，两副本各 1 处）；atomGroups 里显式写 `semantic:'B_ENTRY'` / `'B_HIT_CALLBACK'` | 语义精确，1 行改动，风险低 |
| B | 只加 1 个"词条联动"原子（fields 同时含 `entry_id`/`entry_type`/`on`），接受映射到 `B_HIT_CALLBACK` | 最省事，但 `B_ENTRY` 语义丢失 |
| C | 只加 `B_ENTRY`，不做命中回调 | 功能不全 |

**推荐 A**。改动示意：
```js
atomGroups.forEach((g) => g.atoms.forEach((a) => {
  if (a.semantic) return                                    // ← 新增：已显式声明则不覆盖
  const sem = byHandler.get(a.key) || byHandler.get(a.effectType)
  if (sem) a.semantic = sem
}))
```

### 决策点 2：`target_selection` vs `resolve_target`（语义不同，勿混为一谈）

| | `target_selection`（W 组，现有） | `resolve_target`（`B_TARGET`，新增） |
|---|---|---|
| 定位 | 编辑器**目标定义** | 引擎**运行时目标解析** |
| 落点 | 写回契约字段 `draft.target.type` | 写 `context.resolvedTargets`，供后续 DO 原子消费 |
| 后端 | **无对应 handler**（引擎侧不执行） | 已真实实现 |
| 关联代码 | L1088 / L1237 / L1790（与 `draft.target.type` 绑定） | — |

真相源（`原子记录` L13）说「WHO 降级为 DO 段首置前导原子 `B_TARGET`」，
但前端现有的 `target_selection` 承担的是**目标定义落库契约**，与运行时解析不是一回事。

| 选项 | 做法 | 风险 |
|---|---|---|
| **A（推荐）** | **新增** `resolve_target` 作为独立原子（W7 或归入 DO 组），**保留 W 组现状**，并在注释中区分两者定位 | 低。两套并存，各司其职 |
| B | W 组 6 个原子 `target_selection` 全改为 `resolve_target` | **高**。会破坏 `draft.target.type` 落库契约，且 6 个原子的 `target_type` 枚举（SINGLE_ENEMY/ALL_ENEMIES/…）与 `B_TARGET` 的 `scope`（self/enemy/ally/…）取值不同，无法直接映射 |
| C | 不新增 `resolve_target` | 放弃运行时目标解析能力 |

**推荐 A。**

### 决策点 3：改动同步范围（3 处必须同步）

`atomGroups` 现有**三份副本**，改动必须全部同步，否则共享内核与单体页会漂移：

仅做三处同步；如需收敛副本，建议作为独立任务处理。
