# 思想纪要：开发设计哲学与协作纪律（2026-08-04 提炼）

> 本文档提炼自用户在本轮开发对话（C 文档核对 → 核销 → T5 清单落地 → 部署）中
> 反复表达的设计意图与协作偏好，作为长期决策参考。非代码手册，是「为什么这么做」的思想记录。

---

## 一、文档治理：草案与落地真相分离

**核心原则**：开发前夕的核对稿/草案**必须长期保留**，但要与落地后的真实代码划清界限，
防止后人或未来的 AI 被草案里的过时描述误导。

**具体做法（用户亲自指定的范式）**：
- 草案移入 `docs/` 长期保留，不删不覆盖。
- 文件**最顶部**追加「`[YYYY-MM-DD 落地核销说明]`」区块，用「以当前代码为准」的语气
  明确点出草案与落地的出入（几处、哪几行、正确事实是什么）。
- 正文草案原文**保留**，但被推翻处用删除线就地标注 + 落点图按真实契约修正，
  形成「草案原貌 + 顶部核销 + 错位标注」三位一体的可读记录。
- 核销说明的措辞要具体（字段名、英文值、映射方向），不写空泛的"以代码为准"。

**设计动机**：草案是思考过程的痕迹，有史料价值；但落地后代码是真相。二者不能混为一谈，
否则后人看草案会当成规范去实现，酿成二次错误。用户明确说"防止后人被草案里的 type 误导"，
说明他把文档当**会误导人的活物**来防，而非静态存档。

## 二、架构取舍：零回归与历史兼容优先

**核心原则**：在「优雅但高风险的方案」与「朴素但零回归的方案」之间，选后者。

**实证（T5 强引用决策）**：
- 方案 A（快照副本 + 绑定 `skill_key`）：选中即把全局词条字段灌入单位技能副本，记锚点。
  → 战斗结算零改动、历史旧单位天然兼容。
- 方案 B（纯引用 `skill_key`，运行时回查全局）：永远最新，但需改 `makeUnitSkill`+战斗链路，
  且旧局 JSON 全失效，回归面大。
- **用户拍板方案 A**：认可"单位技能自给自足、战斗结算零改动、历史兼容好"的论据。

**设计动机**：宁可接受"词条更新需手动同步"的小瑕疵，也不碰战斗链路与历史数据。
稳定性 > 理论纯净度。这对一个已有线上战局的项目是正确权衡。

---

## 三、交互设计：绑定即生效

**核心原则**：用户操作要"所见即所得、绑定即落地"，不要只记一个引用等别处消费。

**实证**：下拉「从全局词条选择」选中后，**立即灌入** `name` + 映射后的中文 `type`，
`skill_key` 随行记录。不是"仅记 key 让用户继续手改"。

**设计动机**：强引用的价值在于省去重复手填。若选中只记 key 不灌字段，用户仍要手动补
name/type，强引用就贬值了。灌入即"绑定生效"的明确反馈。

---

## 四、容错哲学：绝不破坏现有数据

**核心原则**：新功能回退旧数据时，匹配不上就**静默降级**，绝不报错、绝不丢数据。

**实证**：旧单位技能只有 `name`、无 `skill_key`。T5 落地后按 `name` **精确匹配**全局词条补全
`skill_key`；匹配不上则保留原手填副本、`skill_key` 留空（降级为软关联），不破坏现有单位。

**设计动机**：线上已有大量历史单位，任何"找不到就崩/就清"的逻辑都是生产事故。
精确匹配而非模糊匹配（用户选精确），因为模糊匹配会有误绑风险——宁可少绑不可错绑。

---

## 五、协作节奏：核对确认后直接推进

**核心原则**：核对类任务，结论确认后即"继续执行计划"，不重复追问、不回退重议。

**实证**：
- 我指出 C 文档 2 处错误 + 提议正文删除线标注增强 → 用户"确认保留"（接受增强，未要求回退）。
- "然后开始按照内容继续执行计划" → 我按已落地清单逐项核验、收尾未完项、部署，全程无二次确认。
- 部署节点用户只回"需要"一字，即授权标准部署流程。

**设计动机**：用户把"核对"和"执行"分两段。核对阶段他要严格挑错；一旦确认，就信任结论、
把执行交出去。AI 不应在确认后还反复问"真的要这么做吗"。

## 六、运维红线（用户长期强调，本轮再次遵守）

1. **单一入口 8081**：所有前端改动构建进 `mecha-frontend`（nginx 反代 `/api`→gateway、
   `/socket.io`→comm），严禁新建子端口验证。验收口径 = 资产哈希匹配 + 新增文案在线。
2. **绝不动 `mecha-battle-db`**（PostgreSQL 容器）：任何操作避开它。
3. **shared-kernel 改动纪律**：单体仓库共享内核改动须先在服务器 `npm run build`（ESM+CJS
   双产物）出 dist，再 rsync + 重建 gateway/frontend，否则改动不生效。
4. **容器重建避孤儿冲突**：`docker compose up -d --no-deps <svc>`，不连带重启未改的服务。
5. **gateway 运行时真相**：战斗逻辑真实在 `.cjs`（经 `createRequire` 加载），容器内
   `/app/dist/*.js` 是 gateway 自身 TS 死代码，核查必须查 `.cjs` 路径。

## 七、一句话总结用户工程人格

> **先严格核对挑错，确认后信任结论直接推进；架构上零回归与历史兼容压倒理论优雅；
> 文档上把草案当会误导人的活物来防；运维上守单一入口与不动数据库的红线。**
