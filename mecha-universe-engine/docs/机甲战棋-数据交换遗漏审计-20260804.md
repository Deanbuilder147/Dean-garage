## 一、确证遗漏（必须修）

### 遗漏 1：单位技能进战场被 `mapSkills` 强制白名单重建，丢失关键字段

**链路**：`NewUnitEditorView.makeUnitSkill` → units 表五列（`main_skills` 等）→ `rooms.ts` 聚合 → `mapSkills()` → `pendingUnits` → 部署 → 战斗引擎

**断点位置**：`backend-gateway/src/routes/rooms.ts:18-20`（强制 import）+ `:504`：
```ts
// rooms.ts:18-20
import { mapSkills } from '../services/excel-schema-normalizer.js';
// rooms.ts:504
try { skills = mapSkills(mergedRaw); } catch { skills = []; }
```

`mapSkills`（`excel-schema-normalizer.ts:215-238`）是**白名单重建**函数，只输出固定字段集。
前端 `makeUnitSkill`（`NewUnitEditorView.vue:931-943`）精心产出的字段，被丢弃/改写如下：

| 字段 | 前端产出（有值） | `mapSkills` 后 | 后果 |
|------|----------------|---------------|------|
| `skill_key` | L942 透传（T5 强引用锚点） | **丢失** | 见遗漏 4：强引用在进战场瞬间被抹除 |
| `prerequisite` | L940 透传（词条前置条件） | **丢失** | 技能前置依赖失效 |
| `id` | L933 用 `crypto.randomUUID()` | **被 L222 `uuidv4()` 覆盖** | 前端持有的 skill_id 与战场内 id 对不上（前端选中技能点敌人时匹配错位） |
| `cast_range` / `min_cast_range` / `range` / `range_max` / `rangeLabel` | L937-938 透传 | **全部丢弃**（L233-235 注释"严禁透传"） | 见遗漏 2 |
| `category` | 前端不产出 | L217 由 `resolveSkillCategory(s)` 从中文 `type` 推导 | 此跳为**补全**，非丢失 |

**根因**：`mapSkills` 本是为 Excel 导入器写的（把混乱的中文 Excel 列归一），被复用到"开战部署"路径，
但二者数据质量不同——UI 编辑的单位技能字段是干净结构化的，不该走 Excel 的白名单清洗（其 `uuidv4()` 强覆 `id`、丢弃 `skill_key/prerequisite/cast_range`）。

**完整修复方案（遗漏 1，P0）**：
1. **新增部署专用透传函数** `mapUnitEditorSkills(rawSkills)`（置于 `backend-gateway/src/services/excel-schema-normalizer.ts` 或新文件 `unitEditorSchema.ts`），**不复用** Excel 的 `mapSkills`：
   ```ts
   function mapUnitEditorSkills(rawSkills) {
     return (rawSkills || []).map((s) => {
       const cat = resolveSkillCategory(s);
       const absRange = s.cast_range ?? s.max_range ?? s.range;
       return {
         id: s.id || uuidv4(),              // 保留用户/编辑器给的 id，仅缺失时补
         skill_key: s.skill_key || null,    // ★ 强引用锚点保留（修遗漏1核心）
         name: s.name,
         type: s.type,                       // 中文 type（由绑定灌入）
         category: cat,                      // 英文 category
         prerequisite: s.prerequisite ?? null,
         action_type: s.action_type,
         damage_kind: s.damage_kind,
         // 射程：绝对射程→相对 bonus_range（加法模型，见遗漏2）
         ...(absoluteToBonusRange(cat, absRange) != null
             ? { bonus_range: absoluteToBonusRange(cat, absRange) }
             : {}),
         // 其余字段按需透传，绝不复活 cast_range 绝对字段
       };
     });
   }
   ```
2. **`rooms.ts:504` 改调用** `mapUnitEditorSkills(pendingUnit.skills)` 替代 `mapSkills(...)`。
3. **保留 `prerequisite`/`id`**：不再被 `uuidv4()` 强制覆盖，保证后续"技能解锁链"与"强引用回写"（取舍4）有稳定主键。
4. **验收**：开战后 `GET /state` 该单位 `skills[]` 含 `skill_key` 且与编辑器录入一致；射程由 `bonus_range` 派生正确。

### 遗漏 2：技能绝对射程在进战场后丢失，全按分类兜底

**链路**：编辑器填 `cast_range` → `makeUnitSkill` 透传 `cast_range: max`（L938）→ units 表 → `mapSkills` 丢弃（L233-235）→ 战场按 `category` 兜底

**证据**：
- 前端产出：`NewUnitEditorView.vue:938` `cast_range: max`（用户填的射程原样透传）
- 网关丢弃：`excel-schema-normalizer.ts:233-235` 注释"⚠️ 严禁透传任何绝对射程字段(cast_range/range/max_range/...)"
- 战场射程：`shared-kernel/src/hexMath.ts` 的 `getSkillRangeFields` 按 `category` 兜底（远程=3）

**现象**：用户在单位编辑器某技能填 `cast_range=5`，进战场后该技能射程变回分类默认值（远程=3）。
与《思想纪要》"普通攻击删除后射程只来自技能自身词条"的设定**直接冲突**——
因为 `cast_range` 在部署环节就被摘掉了，战场根本读不到。

**关联**：这也是为什么记忆里反复强调"旧战局 cast_range:1 需重开新局验证"——
旧战局残留值本就不可靠，而新战局因 `mapSkills` 丢弃，连用户新填的值也进不去。

> ⚠️ **修复方向关键修正（2026-08-05 补）**：战斗引擎采用「**射程加法模型**」——`shared-kernel/src/hexMath.ts::getSkillRangeFields` 由 `category` 基准 + `bonus_range` 派生，`combat.ts` 红线**严禁读取 `cast_range` 绝对字段**（仅作兼容兜底、非真相源）。
> 因此"保留 `cast_range` 透传"是**错误方向**。正确做法是：**部署转换时把用户填的绝对射程折算成相对 `bonus_range`**（如远程填 5 → `bonus_range = 5 - 3 = 2`；近战填 2 → `bonus_range = 2 - 1 = 1`），引擎自然按 `基准 + bonus_range` 派生出正确射程，与 Excel 词条 / glossary 词条完全同源。

**完整修复方案（遗漏 2，与遗漏 1 同改文件）**：
1. 在 `backend-gateway/src/services/excel-schema-normalizer.ts`（或新建 `unitEditorSchema.ts`）新增 `mapUnitEditorSkills`，不复用 Excel 的 `mapSkills`。
2. 该函数在部署前把单位技能绝对射程转为 `bonus_range`：
   ```ts
   function absoluteToBonusRange(cat, absRange) {
     if (absRange == null) return undefined;
     const base = cat === 'ranged' ? 3 : cat === 'auto' ? 0 : 1; // 与 DEFAULT_RANGE_BY_CATEGORY 一致
     const b = Math.max(0, Number(absRange) - base);
     return b > 0 ? b : undefined; // 0 加成则不写字段，走纯基准
   }
   ```
3. 转换结果只输出 `bonus_range`（绝不复活 `cast_range` 绝对字段），与 Excel 词条、`glossary` 词条共用同一加法派生真相源。
4. 前端 `NewUnitEditorView.vue:938` 的 `cast_range: max` 保留（编辑器录入用绝对语义即可），由部署转换负责折算；前端预览射程展示仍走 `getSkillRangeFields`（hexUtils 镜像），无需改。

### 遗漏 3：单位 HP 三套公式并存，前端展示值 ≠ 后端战场实际值

**三套公式**：
1. **前端展示**（单位编辑器计算属性）：`NewUnitEditorView.vue:728` `mainHP = 结构*10`；`:730` `royroyHP = 结构*3`
2. **后端 Excel 通道**：`excel-schema-normalizer.ts:14,154` `hp = 结构*5+20`
3. **后端 UI 单位通道**：`rooms.ts:507-521` `baseHp = stats.hp（缺省100）→ applySizeHp(baseHp, size)`（体型系数 s-10%/m0/l+5%/xl+10%）

**不一致点**：
- 前端展示用 `结构*10`，后端 Excel 用 `结构*5+20`，UI 通道用 `stats.hp(默认100)*体型`——**三套完全不同**。
- 用户在编辑器看到的 HP（结构*10）与战场上实际血量（stats.hp*体型，默认100）往往对不上。
- 若用户在单位编辑器**填了结构但没意识到 HP 由另一套公式算**，会困惑"我结构堆到 90 怎么血量才 100"。

**完整修复方案（遗漏 3）**：
目标：前端单位编辑器展示的 HP == 后端战场实际 HP（含体型系数），彻底消灭三套公式。
落地步骤：
1. **确立唯一真相公式**：以 `rooms.ts:507-521` 的 UI 通道为准——`baseHp = stats.hp（缺省100）→ applySizeHp(baseHp, size)`。Excel 通道的 `结构*5+20`（normalizer.ts:154）与前端 `结构*10/结构*3`（NewUnitEditorView.vue:728/730）一律视为"录入辅助预览"，而非真相。
2. **前端展示改为消费后端回传值**：单位编辑器保存单位后，后端 `rooms.ts` 已算好 `stats.hp` 并经 `applySizeHp` 得到最终 HP。前端把"保存返回的单位对象"里的 `stats.hp` 作为展示源，废弃 `mainHP/royroyHP` 的本地 `*10/*3` 计算属性（或仅在"未保存草稿态"用本地预览，保存后切真实值）。
3. **结构→HP 映射对齐**：若坚持"结构驱动 HP"，则统一为单一公式（推荐 `结构*系数 + 体型`，系数与后端 normalizer 一致），并让 `rooms.ts` 部署时使用同一公式写 `stats.hp`，消灭 normalizer 与 rooms 的双公式。
4. **验收**：同单位同结构值，编辑器展示 HP == 开战后首回合 `GET /state` 该单位 `currentStats.hp`。

**优先级**：P1（小改，前端改展示源 + 后端统一一处公式即可）。

## 二、设计取舍（非 bug，但需文档明示）

### 取舍 4：强引用 `skill_key` 有"身份匹配"消费，但缺"回查全局词条回写"消费

> ⚠️ **事实更正（2026-08-05 复核）**：原审计称"skill_key 存而不用"——**不准确**。
> 复核 `combat.ts` 全文，`skill_key` 在 **5+ 处**作为技能身份匹配候选被实际消费：
> - L1325 / L1571：`(s.id===k || s.key===k || s.skill_key===k)` 武器机动加成定位
> - L1436-1440：`unitHasSkill(u, key)` 反应技能（tactical_overwatch）归属判定
> - L1693-1697：`resolveSelectedSkill` 选中技能归属 + 取 `skillKey = owned.key||owned.skill_key||...`
> - L1984-1988：inlineDef 构建时按 `skill_key` 回查归属技能
>
> 因此 `skill_key` 是**活着的身份锚点**（与 key/id/name 并列参与匹配），并非"无消费方"。
> 真正缺失的是 T5 方案 A 承诺的"**强引用回写**"——即部署/使用时按 `skill_key` 回查全局 glossary 词条，
> 刷新单位技能副本的 `name/type/category/cast_range` 等字段。当前战斗引擎只"认锚点"，不"读锚点指向的词条内容"。

**性质**：这是 T5 方案 A 的**有意设计边界**（《思想纪要》明确否决方案 B 纯引用回查，用户拍板"战斗结算零改动"）。
`skill_key` 当前定位=**身份锚点（有消费）**，但不驱动"词条内容同步"。

**风险**：因缺回写消费，"词条更新→单位不同步"是**结构性必然**（非临时缺口）。
但身份锚点已落地，未来做"一键同步"不必再补锚点，只需补"回查 + 重写副本"逻辑。

**完整修复方案（取舍 4，P2 可选增强）**：
1. **前置依赖**：先修遗漏 1，让 `skill_key` 活到单位副本持久层（不被 `mapSkills` 丢弃）。
2. **新增回查消费点**（推荐在 `excel-schema-normalizer.ts` 的 `mapUnitEditorSkills` 内，复用全局 glossary 配置）：
   ```ts
   import { getGlossaryConfig } from './glossary.js'; // 已有 configLoader 出口
   function enrichFromGlossary(unitSkill) {
     const key = unitSkill.skill_key;
     if (!key) return unitSkill;
     const g = getGlossaryConfig()?.skills?.[key];
     if (!g) return unitSkill;
     // 强引用回写：以全局词条为准刷新副本展示/分类字段（不覆盖用户显式 override 的字段）
     return {
       ...unitSkill,
       name: unitSkill.name ?? g.name,
       type: unitSkill.type ?? g.categoryCN,        // 中文 type
       category: unitSkill.category ?? g.category,  // 英文 category
       // 射程：优先用户填的绝对射程→折算 bonus_range（见遗漏2），否则用全局词条
     };
   }
   ```
3. **同步按钮（编辑态）**：在 `GlossaryHub` 或 `NewUnitEditorView` 加"按全局词条同步"动作，调用同一 `enrichFromGlossary` 重写所选单位技能副本并落库。
4. **验收**：改全局词条 `name/type` → 单位副本经同步后展示同步更新；未同步则保持快照（兼容历史）。

**说明文档要求**：在产品文档/使用说明中明确"强引用当前=身份绑定+可选同步，非自动实时同步"，消除用户误以为改全局即改单位的预期。

## 三、已澄清（非遗漏，消除误报）

### 澄清 5：阵营角色 `role` 透传正确
- `rooms.ts:522-524` 把 `faction` 与 `role: assignedRole` 都写入 pendingUnit。
- `combat.ts` 的 `resolveUnitRole`（L266-276）通过 `battle.factionRoles`（由 `reconcileFactionRoles` 从 faction 重建，L123-167）决定单位角色。

- ⚠️ 注意：单位技能对象本身**不应**带 role（role 是战场轮转概念，非技能属性），前端 `makeUnitSkill` 不设 role 是正确的。

## 三·五、用户复发关注点：词条库更新 → 战斗管道（🔴 未接通，综合性致命遗漏）

> 2026-08-05 用户复查时质疑"之前说的词条库更新到战斗管道的问题好像也没改好"，经代码核查——**确认未接通，用户直觉正确**。
> 此问题横跨遗漏 1 + 取舍 4（断点 A/B），并多出一个"已开战局零触达"断点 C，故单列。

### 断点 A：保存的 `skill_key` 锚点在部署入战场时被抹除
- `SkillsEditor.vue:127-134` `onGlossaryBind` 正确灌入 `skill_key`（强引用锚点✓）。
- `NewUnitEditorView` `makeUnitSkill` 透传 `skill_key` 进 `units` 表 ✓。
- **但 `rooms.ts:504` 部署时复用 Excel 导入器的 `mapSkills`，白名单丢弃 `skill_key`** → 锚点进战场瞬间消失（= 遗漏 1，未修）。

### 断点 B：即便锚点留存，战斗结算不回查全局词条库
- `combat.ts:1984` `(s.key === skill_key || s.skill_key === skill_key)` 只是**身份匹配**——在"已开战局的单位技能副本"里定位"谁拥有该技能"。
- 它**从不**读 `getGlossaryConfig().skills[skill_key]` 去刷新 name/type/射程。
- 即：战斗管道全程消费的是**单位副本里的旧快照**，与词条库当前值无关。
- `enrichFromGlossary` 回写逻辑（取舍 4 方案）**当前不存在**——全代码库搜 `skill_key` 仅 `glossary-excel-parser.ts`（Excel 解析）与 `combat.ts`（身份匹配）两处，无任何回查消费点。

### 断点 C：已开战局单位副本对词条库更新零触达
- `glossary.ts:432` `PUT /hub-config/:key` 只写存储 A，**落盘后无广播 / 无刷新 / 无回调**去碰已开战局或单位副本。
- 故即便 A/B 修好，已开战局仍是开战那一刻的快照，词条库更新对它无效（除非重开战局）。

### ⚠️ 靶场 vs 正式战斗的关键差异（易误判）
- 靶场 `glossary.ts:490` `POST /test-skill` **直接读存储 A** `stored.skills[key]` → 靶场能看到词条库更新 ✓。
- 正式战斗 `/attack` 走的是单位副本 `exeCaster.skills`（= 部署时 `mapSkills` 产物）→ 看不到词条库更新 ✗。
- 这正是"靶场改了生效、实战改了不生效"错觉的来源，必须分清。

### 完整修复方案（遗漏 8，P0 综合）
**层 1（修断点 A，复用遗漏 1 方案）**：`rooms.ts:504` 改调 `mapUnitEditorSkills`，保留 `skill_key`。
**层 2（修断点 B，落地取舍 4）**：
- 在 `mapUnitEditorSkills` 内联调用 `enrichFromGlossary`（开战时按 `skill_key` 回查存储 A 刷新 name/type/射程为 `bonus_range`），使"开新局"即拿到词条库最新值。
- 在 `combat.ts` 的 `/attack` 解析 `owned` 后，可选加一次轻量回查：若 `owned.skill_key` 命中存储 A 且字段比副本新，以全局为准覆盖派生态（保证"词条库改了，下一发攻击即生效"）。
**层 3（修断点 C，已开战局触达）**：`PUT /hub-config/:key` 落盘后，向 comm 广播 `glossary-updated`（携带 key）；战斗服务监听后，遍历进行中战局 `battle.units[].skills`，对有该 `skill_key` 的副本就地 `enrichFromGlossary` 刷新（仅刷新 name/type/分类/bonus_range，不动运行时状态如 currentHP/statusEffects）。
- 验收：改全局词条 name → ① 开新局该单位显示新名；② 已开战局收到广播后该单位下一发攻击用新 name/新射程；③ 靶场始终最新（已有）。

**依赖**：层 1/2 依赖遗漏 1 的 `mapUnitEditorSkills` + 取舍 4 的 `enrichFromGlossary`；层 3 依赖 comm 广播通道（已存在 `internal-token` 同步机制可复用）。
