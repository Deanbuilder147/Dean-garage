## 一、现状诊断：两套系统的运行方式差异

### 1.1 架构全景

```
┌─────────────────────────────────────────────────────────────┐
│                    VisualGlossaryView.vue                    │
│  ┌──────────────┬───────────────┬────────────────────────┐  │
│  │  Tab: 编辑器  │   Tab: 词条库   │                        │  │
│  │ ┌──────────┐ │ ┌───────────┐ │                        │  │
│  │ │HexCanvas  │ │ │GlossaryView│← 内嵌旧中枢            │  │
│  │ │(射程/打击)│ │ │(万能语法)  │                        │  │
│  │ ├──────────┤ │ └───────────┘ │                        │  │
│  │ │TierForm   │ │               │                        │  │
│  │ │EffectStack│ │               │                        │  │
│  │ ├──────────┤ │               │                        │  │
│  │ │JsonCompiler│ │              │                        │  │
│  │ └──────────┘ │               │                        │  │
│  └──────────────┴───────────────┴────────────────────────┘  │
└─────────────────────────────────────────────────────────────┘
```

### 1.2 核心差异对照表

| 维度 | **可视化编辑器** | **词条库中枢（旧）** |
|------|-----------------|---------------------|
| **数据流向** | **纯单向写入 (write-only)** | 读→改→写（全量 CRUD） |
| **读取** | ❌ 无。硬编码 reactive 初始值，不调用 `getConfig()` | ✅ `GET /api/combat-glossary/config` → `hydrateSkill()` 水合 |
| **写入** | `POST /api/combat-glossary/config` `{skills:{[key]:obj}}` 单条增量 | 同 API 但 `{_meta, skills:全量序列化, _delete_skills}` 全量覆盖 |
| **二次编辑** | ❌ 不可能。无加载回填逻辑，改词条必须从零重画 | ✅ 手风琴内联编辑 + key 重命名 |
| **保存后行为** | `alert()` 弹窗，不刷新列表 | `await loadConfig()` 回读确认 |
| **目标存储** | 存储B (`backend-gateway/data/glossary-skill-config.json`) | 存储B（同文件） |
| **战斗引擎读取** | — | **存储A** (`services/combat-service/.../glossary-skill-config.json`) ← **两者互不同步！** |

### 1.3 字段模型冲突（关键阻塞点）

| 编辑器产出字段 | 中枢展示字段 | 对齐状态 |
|---------------|-------------|---------|
| `entryType` (`skill\|special\|faction`) | 无此字段（仅推断读取） | ⚠️ 中枢无展示位 |
| `name` | `name` | ✅ 唯一完全对齐 |
| `category` (`melee\|ranged\|auto`) | `category` | ✅ 对齐 |
| `bonus_range` + `min_range` | `cast_range: {min, max}` | ❌ **模型冲突**：编辑器 delete cast_range；中枢 serializeSkillToContract 强制注入 `{min:0,max:0}` |
| `effects[]`（4类堆栈: damage/recovery/status/displacement） | `dice_branches[]` + `status_effects[]` + `base_damage` | ❌ **完全不兼容**：中枢无 effects 渲染分支 |
| `target: {type, filter}` | `target_scope`（enemy/ally/...） | ❌ 枚举不同（`SINGLE_ENEMY` vs `enemy`），落入未命中兜底 |
| `map_cannon.directions`（六向立方坐标数组） | `range_type` + `beam_width` | ❌ 六向坐标数组无展示位 |
| `aoe: {center, spread}` | `aoe_radius`（纯数字） | ❌ 结构不兼容 |
| `ap_cost` | `ap_cost` | ✅ 对齐 |
| `prerequisite` / `faction` / `trigger` | 无编辑位 | ❌ 不展示 |
| — | `damage_kind` / `skill_shape` / `has_dice` / `dice_type` | 编辑器**显式删除**这些字段 |

### 1.4 双存储路径与脑裂风险

**真实架构**（代码实测确认）：

```
configLoader.cjs (combat-service)
├── CONFIG_PATH = services/combat-service/src/config/glossary-skill-config.json  ← 存储A
├── getGlossaryConfig()  → combat-service 与 gateway 共享读取
└── saveGlossaryConfig() → gateway 经 nodeRequire 直接调用，写入存储A

glossary.ts (backend-gateway)
├── GLOSSARY_CONFIG_PATH = backend-gateway/data/glossary-skill-config.json  ← 存储B
├── GET /config  → 独立读取存储B（不经由 configLoader）
└── POST /config → 独立写入存储B（不触发 configLoader.saveGlossaryConfig）
```

**问题根因**：存在**两条写路径**——
1. gateway `combat.ts` 经 `configLoader.saveGlossaryConfig()` 写存储A（战斗引擎读取）
2. gateway `glossary.ts` 经 `fs.writeFileSync(GLOSSARY_CONFIG_PATH)` 写存储B（中枢读取）

两条路径**互不同步**，导致：
- 编辑器（glossary.ts）新建的词条只进存储B，战斗引擎读存储A 看不到 → **引擎侧缺失**
- 存储B 当前**不存在**（首次 POST 才 mkdirSync 创建）→ 中枢只看到 6 条 CORE_SKILLS fallback
- 多节点/容器运行时，两条路径时机错配 → **双库脑裂（Split-Brain）**：gateway 落了 B，combat-service 仍读旧 A

**修正方向**（详见 3.3 节）：**单一写入口**。所有词条写操作统一经由 `configLoader.saveGlossaryConfig()` 写入存储A；存储B 不再是独立权威源，降级为存储A 的只读镜像（或直接在 glossary.ts 中改读 configLoader 的 CONFIG_PATH）。

## 三、改造方案

### 3.1 总体架构：从「Tab 切换」到「四区域同屏」

**现状**：VisualGlossaryView 用 tab 在「编辑器」和「词条库」之间切换，两者互不相通。

**目标**：合并为单一「词条库中枢」视图，四区域实时联动。

```
改造后架构:
┌─────────────────────────────────────────────────────────────┐
│                   GlossaryHub.vue (新)                      │
│  ┌────────┬────────────────────┬──────────────────────────┐ │
│  │        │                    │                          │ │
│  │ SkillList│  HexPreview      │  DetailPanel             │ │
│  │ (区域1) │  (区域2)          │  (区域3)                 │ │
│  │        │  316×275 只读渲染  │  TierForm + EffectStack  │ │
│  │        │                    │  (可读写)                │ │
│  ├────────┴────────────────────┼──────────────────────────┤ │
│  │        BattleTest (区域4)    │                          │ │
│  │        接入 NewBattleView     │                          │ │
│  └─────────────────────────────┴──────────────────────────┘ │
└─────────────────────────────────────────────────────────────┘
```

### 3.2 各区域详细设计

#### 区域1：词条库列表（SkillListPanel）

**布局**：
- 顶部三分类按钮：`[技能] [特殊] [阵营]`，样式复用现有 `.vg-tab` / `.vg-badge`
- 下方为词条列表，每项显示：key + name + entryType badge + category
- 点击选中 → 联动区域2（渲染该词条的射程/打击范围）+ 区域3（显示该词条参数）

**数据来源**：`GET /api/combat-glossary/config` 返回的全量 skills

**分类过滤逻辑**：
```js
// 按 entryType 过滤
const filteredSkills = computed(() => {
  if (activeCategory.value === 'all') return allSkills
  return allSkills.filter(s => entryTypeOf(s) === activeCategory.value)
})
```

**新增操作**：
- 右键/长按菜单：「在编辑器中打开」（跳转到编辑模式修改该词条）
- 「复制为新词条」（基于当前词条创建副本）

**🛡️ 保护状态与版本视觉标牌**：

列表渲染时，除 `[技能]`/`[特殊]`/`[阵营]` Badge 外，追加以下标识：

| 标牌 | 样式 | 含义 | 交互 |
|------|------|------|------|
| 🔒 核心保护 | 灰色锁图标 | 该词条属于 6 个 CORE_SKILLS，**不可彻底从数据库抹除**（只读防覆写） | 可查看/复制，不可删除 |
| ⚡ 未同步草稿 | 黄色圆点 | 当前词条在本地 `draftSkill` 中有修改但未落库（未 PUT） | 提示用户点击「保存」 |
| ✅ 已落库 | 无标记（或淡绿勾） | 草稿与存储A 一致 | — |

实现：`SkillListPanel` 对比 `draftSkill.key` 与已保存 config 的 hash，不一致则显示 ⚡；`CORE_SKILLS.includes(key)` 则显示 🔒。

#### 区域2：图层窗口（HexCanvasPanel）

**双模式设计**：区域2同时具备「只读预览」和「交互式绘制」两种能力，由模式开关切换。

| 模式 | 触发方式 | 行为 |
|------|---------|------|
| **只读预览** | 区域1点击词条后默认进入 | 渲染选中词条的射程/打击范围，禁用所有绘制交互（仅允许 camera 平移/缩放检查） |
| **交互式绘制** | 点击区域2右上角「✎ 绘制」按钮，或区域3处于「编辑态」时自动联动 | 用户在格子上点击绘制射程环/打击范围，绘制结果实时写回区域3的 `design.range` 状态 |

**尺寸（放宽硬限制，响应式外框）**：
- 描绘格子区域**最小尺寸** `min-width: 316px; min-height: 275px`（不再死板限制为固定 316×275）
- 工具栏/模式切换按钮/绘制控件放在区域外部或上方独立条，**不计入** 此最小区域
- Canvas 容器随右侧面板宽度**自适应扩展**（如 17×17 大网格时自动放大，避免单格仅 15~20px 难以精准点击）
- 提供 **[🔍 放大/缩小]** 缩放控件，供用户在超大网格下微调视图
- Canvas 物理像素 = 容器实际尺寸 × devicePixelRatio，保证高分屏清晰

**只读预览功能**：
- 接收区域1选中词条的 `category` + `bonus_range` + `map_cannon` + `aoe` 数据
- **射程层**：根据 `category`(melee/ranged/auto) + `bonus_range` 渲染绿色可达范围环
- **打击范围层**：根据 `map_cannon.directions`（地图炮）或 `aoe.{center,spread}`（AOE）渲染红色命中格
- 双层叠加显示（绿色底 + 红色顶层）
- 保留 camera 平移/缩放（Ctrl+滚轮）供用户检查细节

**交互式绘制功能**：
- 复用现有 `HexCanvasEditor` 的全部绘制能力：射程起点/终点环输入、地图炮六向绘制/补全/清除、AOE 落点+扩散
- 绘制变更通过 `v-model` 实时写回 `design.range`（区域3的共享状态）
- 切换到只读预览或切换选中词条时，自动从当前 `design.range` 重新渲染

**技术方案**：
- **不抽取独立 HexRenderer**，直接复用 `HexCanvasEditor.vue` 原组件
- 新增 `mode` prop：`'preview' | 'edit'`
  - `'preview'`：组件内部禁用 pointer/touch 绘制事件，仅渲染传入的 `range` 数据
  - `'edit'`：保持现有全部交互逻辑不变
- `GlossaryHub` 根据状态决定传入 `mode`：
  - 区域1选中词条但未点「编辑」→ `mode='preview'`
  - 点击「编辑」或「✎ 绘制」→ `mode='edit'`，同时区域3解锁
- 这样最大程度复用现有代码，避免渲染与编辑逻辑分裂导致的 bug

#### 区域3：词条参数 & 效果堆栈（DetailPanel）

**核心变更**：从「编辑器输入态」变为「选中词条展示态 + 可选编辑态」

**布局**：沿用现有 TierDimensionForm + EffectStackBuilder，但增加两种模式：

| 模式 | 触发方式 | 行为 |
|------|---------|------|
| **浏览态**（默认） | 区域1点击词条 | 所有表单 disabled/只读，显示该词条完整参数 |
| **编辑态** | 点击「编辑」按钮或双击区域 | 表单解锁，可修改，修改后「保存」写回 |

**🔗 双向响应式状态共享（State Sharing 红线）**：

编辑态下，区域2（画布）与区域3（表单）**必须共享同一个 `reactive(draftSkill)` 响应式对象**，禁止各自维护副本。

| 用户操作 | 响应 |
|---------|------|
| 在区域2 绿色图层涂抹射程环 | 区域3 的 `category` / `bonus_range` / `min_range` 表单字段**实时变动** |
| 在区域3 修改 `bonus_range` 数字 | 区域2 画布绿色外环**实时重绘** |
| 在区域2 点击红色格设置 AOE 落点 | 区域3 的 `aoe.center` / `aoe.spread` **实时同步** |
| 在区域3 效果堆栈增删 `effects[]` | 区域2 打击范围图层**实时重算**渲染 |

实现方式：`GlossaryHub` 持有 `const draftSkill = reactive({...})`，通过 props 同时传给 `HexCanvasPanel`（v-model:range）与 `DetailPanel`（v-model:skill），任一侧变更经 Vue 响应式系统自动驱动另一侧重渲染。

**展示内容（全面采用编辑器维度）**：

```
┌─ 通用维度 ─────────────────────────┐
│ name: ____________________         │
│ description: ________________       │
│ ap_cost: [___]                     │
│ entryType: [skill▼]                │
└────────────────────────────────────┘
┌─ 特殊维度（entryType=special时显示）─┐
│ trigger: [none▼] value: ____       │
└────────────────────────────────────┘
┌─ 阵营维度（entryType=faction时显示）─┐
│ limited_to: [all▼]                  │
│ limit_count: [faction_once▼]        │
│ stance: [attack▼]                   │
└────────────────────────────────────┘
┌─ 目标维度 ─────────────────────────┐
│ target type: [SINGLE_ENEMY▼]        │
│ filter unit_types: [☑ mech]...     │
│ filter status: [none▼]              │
└────────────────────────────────────┘
┌─ 效果堆栈 ─────────────────────────┐
│ [damage] fixed_rate: 1.0  ...  ↑↓  │
│ [buff] status: ATK_UP  value:3 ... │
│ [+ 添加效果]                        │
└────────────────────────────────────┘
```

**弃用的旧版字段**（不再展示）：
- ~~damage_kind~~ → 由 effects[].action:'damage' 替代
- ~~skill_shape~~ → 由 map_cannon/aoe 替代
- ~~cast_range{min,max}~~ → 由 category + bonus_range 替代
- ~~has_dice / dice_type / dice_branches~~ → 由 effects[] 替代（如需骰子效果可在堆栈中添加）
- ~~target_scope~~ → 由 target.type 替代
- ~~compat 分区 11 项~~ → 全部移除
- ~~automation 分区 13 项~~ → 仅保留 ap_cost，其余由 effects[] 替代

#### 区域4：战场测试栏（BattleTestPanel）

**目标**：接入战场系统，对已保存的技能进行实战模拟测试

**设计方案（分阶段）**：

##### Phase 1：轻量化单回合靶场模拟器（本次改造）

> 无需完整嵌入战场引擎，仅做「单回合靶场日志模拟器」。

```
┌─ 战场测试（靶场） ──────────────────────────────────┐
│ 施法者: [基准机甲 ▾]   目标: [木人靶 ▾]              │
│ 选择技能: [区域1选中词条 ▾]   [🎯 触发测试]          │
│                                                      │
│ ┌─ 结算日志 ─────────────────────────────────────┐  │
│ │ > 投掷 成功！                                  │  │
│ │ > 对 木人靶 造成 12 点伤害                      │  │
│ │ > 附加 [DEBUFF: 受到伤害+5] 持续 1 回合         │  │
│ │ > 木人靶 剩余耐久: 38/50                        │  │
│ └───────────────────────────────────────────────┘  │
└──────────────────────────────────────────────────────┘
```

**实现思路**：
- `BattleTestPanel.vue` **不渲染六角战场画布**，仅两个桩位 + 日志文本框
- 预置桩位：`施法者`（基准机甲，固定 ATK/DEF 预设值）与 `木人靶`（标准防具，固定耐久 50）

### 3.3 数据流统一方案（单一写入口 + 单向兼容）

#### 问题根因

当前存在**两条写路径**导致脑裂（详见 1.4 节）：
1. `glossary.ts` 独立 `fs.writeFileSync(存储B)` —— 中枢读写，但战斗引擎不读
2. `combat.ts` 经 `configLoader.saveGlossaryConfig()` 写存储A —— 战斗引擎读写

编辑器/中枢新建的词条只进存储B，战斗引擎永远读不到。

#### 统一策略：以编辑器维度为唯一真相源 + 单一写入口

```
┌────────────┐                                              ┌──────────┐
│ 可视化编辑器 │                                              │  词条中枢  │
│ (write)    │    全部经 configLoader.saveGlossaryConfig()   │ (read)    │
└─────┬──────┘                 ↓ 唯一写入路径                └────┬─────┘
      │                          ┌──────────┐                     │ GET /config
      │   POST /api/combat-glossary/config                  ┌─────┴──────┐
      └────────────────────────→│  存储A    │←─────────────│ glossary.ts │
                                 │ (config   │  读 configLoader  (改为读存储A，
                                 │  Loader)  │  CONFIG_PATH     不再独立写B)
                                 └────┬─────┘
                                      │ getGlossaryConfig()
                                      ↓
                                ┌──────────┐
                                │ 战斗引擎  │  ← skillExecutor 直接消费新 Schema
                                │ (consume) │    (effects[] / category+bonus_range /
                                └──────────┘     map_cannon / target.type)
```

**核心原则**（架构红线）：
- ✅ **单一写入口**：所有词条 CRUD 统一经由 `configLoader.saveGlossaryConfig()` 写入存储A。
- ✅ **单向兼容**：`skillAdapter.cjs` 只做 `legacyToEditor`（旧→新）解析，供迁移脚本与运行时读取旧词条用。**禁止 `editorToLegacy`**（防止旧污染字段回潮）。
- ✅ **引擎直读新 Schema**：`skillExecutor.cjs` 直接消费 `effects[]` / `category+bonus_range` / `map_cannon` / `target.type`（上次阶段已落地的 `effectExecutor.cjs` + `skillToTagConverter.cjs` 已支持，本次不再倒退）。
- ❌ **废弃手动 sync 按钮**：不新增 `sync-to-combat` 端点，消除双库脑裂的人为风险。
- ⚠️ **存储B 降级**：`glossary.ts` 改为直接读取 `configLoader.getGlossaryConfig()`（即存储A），不再独立维护 `backend-gateway/data/glossary-skill-config.json` 为权威源（可保留为缓存镜像，但写入一律走存储A）。

**具体措施**：

1. **中枢彻底弃用旧版字段**：`serializeSkillToContract` 重写，不再补回 `cast_range`/`dice_branches`/`damage_kind`
2. **中枢直接透传编辑器产物**：`normalizeSkillForSave()` 保持 `effects[]`/`map_cannon`/`target`/`faction` 完整
3. **glossary.ts 改读存储A**：`GET /api/combat-glossary/config` 内部调用 `configLoader.getGlossaryConfig()`，删除独立的 `GLOSSARY_CONFIG_PATH` 读写分支
4. **glossary.ts 写入走 configLoader**：`POST /api/combat-glossary/config` 内部调用 `configLoader.saveGlossaryConfig(merged)`，CORE_SKILLS 只读防覆写
5. **运行时单向桥接**：`skillAdapter.cjs` 暴露 `legacyToEditor()` 供迁移脚本与「读旧词条」使用；`skillExecutor` 直接消费新 Schema，**不调用任何 editor→legacy 转译**

#### 后端 API 变更清单

| 端点 | 方法 | 变更 | 说明 |
|------|------|------|------|
| `/api/combat-glossary/config` | GET | **改** | 内部改读 `configLoader.getGlossaryConfig()`（存储A），不再独立读存储B |
| `/api/combat-glossary/config` | POST | **改** | 内部改走 `configLoader.saveGlossaryConfig()`（写存储A）；`normalizeSkillForSave` 不再删除/覆写 `effects[]`/`map_cannon`/`target`，不再注入 `cast_range` |

### 3.5 存储A 9条业务词条的新字段适配方案

**核心问题**：存储A 当前有 9 条业务词条（block/sweep/throw/execute/duel/snatch/focused_fire/lucky/reactivate），格式为旧版万能语法（扁平特化字段）。它们无法在区域3以编辑器维度展示、也无法在区域2渲染。

**适配策略**：提供「一次性迁移脚本」+「运行时转译器」双保险，不破坏现有战斗引擎。

#### 3.5.1 字段映射规则

| 旧版字段（存储A） | 编辑器维度（区域3展示） | 转换逻辑 |
|------------------|----------------------|---------|
| `label` | `name` | 直接映射 |
| `type: 'active'\|'passive'` | `entryType` | `active → 'skill'`，`passive → 'skill'`（被动技能仍是技能类，特殊/阵营暂不使用） |
| `category` (melee/ranged/auto) | `category` | 直接映射 |
| `min_range` / `max_range` | `bonus_range` + `map_cannon`/`aoe` 推导 | `bonus_range = max_range - 3`（ranged），`min_range` 单独保留为 `min_range` |
| `bonus_range` | `bonus_range` | 直接映射（注意：负值是削减射程，区域2倒推需兼容负值） |
| `aoe_radius` | `aoe: {center, spread}` | `spread = aoe_radius`，center 默认中心点 |
| `description` | `description` | 直接映射 |
| `action_type` (attack/heal/buff/debuff/passive) | `effects[].action` 推导 | 决定效果堆栈首项谓语 |
| `base_damage` / `reduction` / `bonus` / `value` 等扁平数值 | `effects[]` 数组 | 按 `action_type` 包装为对应 effect 对象 |
| `trigger` | `trigger: {type, value}` | `trigger` 非空 → `{type: trigger, value: ''}` |
| `target_filter` (self/enemy/ally/all) | `target.type` | `self→SELF`，`enemy→SINGLE_ENEMY`，`ally→SINGLE_ALLY`，`all→ALL_UNITS` |
| `damage_kind` | `effects[].damage_kind`（可选） | 包装进 damage effect 的扩展字段，仅供展示 |
| `deterministic` / `requires_unmoved` / `requires_stealth` / `sector_angle` 等引擎内部字段 | **保留不转换** | 存入 `engine_meta` 扩展字段透传，战斗引擎继续读取 |

#### 3.5.2 逐条适配示例

**block（格挡）**：
```json
// 旧版
{ "type":"passive", "label":"格挡", "category":"melee", "reduction":2,
  "trigger":"on_attacked", "target_filter":"self", "action_type":"passive" }
// 新版（区域3展示）
{ "entryType":"skill", "name":"格挡", "category":"melee", "ap_cost":0,
  "description":"受攻击时伤害-2",
  "trigger": { "type":"on_attacked", "value":"" },
  "target": { "type":"SELF", "filter":{ "unit_types":[], "status":"none" } },
  "effects": [ { "action":"buff", "status":"DEFENSE_DOWN_NEGATE", "value":2, "duration":0 } ],
  "engine_meta": { "deterministic":true, "reduction":2 } }
```

**sweep（扫射）**：
```json
// 旧版
{ "type":"active", "label":"扫射", "category":"ranged", "sector_angle":60,
  "bonus_range":-1, "damage_modifier_precise":-2, "target_filter":"enemy",
  "base_damage":-2, "action_type":"attack" }
// 新版
{ "entryType":"skill", "name":"扫射", "category":"ranged", "ap_cost":1,
  "description":"扇形2格范围攻击...",
  "bonus_range":-1, "min_range":1,
  "aoe": { "center":{ "q":8,"r":8 }, "spread":2 },
  "target": { "type":"SINGLE_ENEMY", "filter":{ "unit_types":[], "status":"none" } },
  "effects": [ { "action":"damage", "flat_value":-2, "armor_pen":0 } ],
  "engine_meta": { "sector_angle":60, "damage_modifier_precise":-2 } }
```

**throw（投掷）**：
```json
// 旧版：min_range:1, max_range:3, effect:"damage_amp", value:5, aoe_range:2
// 新版
{ "entryType":"skill", "name":"投掷", "category":"ranged", "ap_cost":1,
  "bonus_range":0, "min_range":1,
  "aoe": { "center":{ "q":8,"r":8 }, "spread":2 },
  "target": { "type":"SINGLE_ENEMY", "filter":{ "unit_types":[], "status":"none" } },
  "effects": [ { "action":"debuff", "status":"DAMAGE_AMP", "value":5, "duration":1 } ],
  "engine_meta": { "max_range":3 } }
```

**execute / duel / snatch / reactivate / lucky / focused_fire**：同理映射（详见迁移脚本 `migrate-legacy-skills.cjs`）

#### 3.5.3 迁移脚本设计

**文件**：`scripts/migrate-legacy-skills.cjs`（新建）

**逻辑**：
1. 读取存储A（configLoader CONFIG_PATH）的 9 条业务词条
2. 逐条应用 3.5.1 映射规则，生成编辑器维度对象
3. 经 `configLoader.saveGlossaryConfig()` **写回存储A**（单一写入口，不独立写存储B）
4. **保留** `engine_meta` 扩展字段（引擎内部特化逻辑继续读取，但已不再作为展示字段）
5. 不覆盖 CORE_SKILLS（6条核心技能已在新格式中，脚本跳过只读保护 key）

**幂等性**：脚本检查存储A是否已存在该 key 且已是新 Schema（含 `effects` 字段），存在则跳过（除非 `--force`）

**触发时机**：Phase 1 部署时执行一次（先跑脚本 → 再重构 UI → 打通数据流）

#### 3.5.4 运行时转译器（单向兼容，禁止倒退）

> ⚠️ **架构红线**：**只做 `legacyToEditor`（旧→新），坚决不写 `editorToLegacy`（新→旧）**。
> 我们在之前阶段好不容易把 `cast_range`/`damage_kind` 等污染字段清零，若在此倒退回旧 Schema，
> 会破坏已收敛的加法射程模型与 Effect Stack 架构。

在 `combat-service/src/skillAdapter.cjs` 增加**单向**桥接：

```js
// skillAdapter.cjs（新建，单向）
function legacyToEditor(legacySkill) {
  /* 3.5.1 映射规则：旧扁平字段 → 编辑器维度 effects[]/category+bonus_range/map_cannon/target */
  // 供：① 迁移脚本 ② 运行时读取尚未迁移的旧词条（兜底）使用
}

// ❌ 不提供 editorToLegacy —— 新 Schema 是终点，引擎直接消费，不存在回退路径

function getSkillForEditor(key) {
  const cfg = getGlossaryConfig()
  const raw = cfg.skills[key]
  // 若仍是旧格式（无 effects），运行时单向转译给前端展示用
  return raw.effects ? raw : legacyToEditor(raw)
}
```

**引擎侧消费**：
- `skillExecutor.cjs` 直接读取 `effects[]` / `category + bonus_range` / `map_cannon` / `target.type` 进行结算（上次阶段已落地的 `effectExecutor.cjs` + `skillToTagConverter.cjs` 已支持）。
- 不再有任何「新→旧」转译环节，架构单向向前。
