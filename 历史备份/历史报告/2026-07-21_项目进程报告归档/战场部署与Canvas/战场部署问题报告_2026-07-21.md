# 战场部署问题分析报告

**日期**：2026-07-21
**现象**：进入战场后棋子无法部署到场上，控制台持续报错：
```
index-p0sZKu1c.js:38 [factions] 加载失败: AxiosError: Request failed with status code 404
index-p0sZKu1c.js:38 AxiosError: Request failed with status code 400
```

---

## 一、已确认 Bug A：`/api/units/factions` 路由被劫持 → 404

### 根因（高置信度，已服务器实测复现）
`backend-gateway/src/routes/units.ts` 中，**带参数的路由 `GET /api/units/:unitId` 定义在前，`GET /api/units/factions` 静态路由定义在后**。Express 按定义顺序匹配，导致 `/api/units/factions` 被 `:unitId` 路由抢先匹配成 `unitId = 'factions'`，执行单单位查询后查无结果，返回 `404 UNIT_NOT_FOUND`。

### 关键代码
`units.ts`
```ts
// ❌ 第 51 行：鉴权中间件（对所有 /api/units 生效）
router.use('/api/units', authenticate, requireAuth);

// ❌ 第 89 行：参数路由定义在「前」—— 会劫持 /api/units/factions
router.get('/api/units/:unitId', authenticate, requireAuth, (req, res) => {
  const { unitId } = req.params
  const userId = req.auth?.userId
  const row = db.prepare('SELECT * FROM units WHERE id = ? AND owner_id = ?').get(unitId, userId)
  if (!row) {
    return res.status(404).json({ error: 'UNIT_NOT_FOUND', message: '单位不存在或无权访问' })
  }
  // ...
})

// ✅ 第 204 行：静态 factions 路由定义在「后」—— 永远命中不到
router.get('/api/units/factions', authenticate, requireAuth, (req, res) => {
  const rows = db.prepare('SELECT DISTINCT faction FROM units').all()
  const factions = rows.map(r => r.faction).filter(Boolean)
  res.json({ success: true, factions })
})
```

### 受影响调用点
- 前端 `frontend/src/api/client.js` 的 `hangarAPI.getFactions()` → `GET /api/units/factions`
- `NewUnitEditorView.vue:477` `loadFactions()` → 控制台精确报错 `[factions] 加载失败: AxiosError 404`（即用户粘贴的第一条）
- `NewBattleView.vue:1108` `loadFactionLogos()` → 战场端阵营 Logo 加载失败（仅影响贴图，回退矢量，不直接阻断部署）

### 服务器实测（伪造 admin token 复现）
```
$ GET /api/units/factions        → HTTP 500（我的假 token 缺 userId，参数路由内部 SQL 抛错）
$ GET /api/units/12345           → HTTP 500（同一参数路由处理器）
```
两条路径都落到**同一个参数路由处理器**，证明 `/api/units/factions` 并未命中静态路由，而是被 `:unitId` 抢匹配（真实用户携带有效 token 时该处理器查 `id='factions'` 无结果 → 返回 `404 UNIT_NOT_FOUND`，与用户控制台一致）。

### 建议修复（待您确认后实施）
将静态 `factions` 路由**移到** `:unitId` 参数路由**之前**，或改用无歧义路径（如 `/api/units/meta/factions`）：
```ts
// 放在 router.get('/api/units/:unitId', ...) 之前
router.get('/api/units/factions', authenticate, requireAuth, (req, res) => { /* ... */ })
```

## 二、关于 `400` 的分析（中高置信度，建议补充证据以 100% 定位）

网关日志**不会记录 400 响应**，且用户战斗的部署日志完全不在其中（仅存在 `unit-inject-*` 测试战斗的成功部署记录），说明该 400 请求确实到达了网关但未被记录。

### 最可能的 400 来源：`POST /api/combat/:battleId/deploy-unit` 的参数校验
`backend-gateway/src/routes/combat.ts:547`
```ts
router.post('/api/combat/:battleId/deploy-unit', authenticate, (req, res) => {
  const { battleId } = req.params
  const { unit_id, q, r, unit_data } = req.body || {}
  if (!unit_id || q === undefined || r === undefined) {        // ← 命中此处即 400
    res.status(400).json({ error: 'INVALID_DEPLOY', message: 'unit_id, q, r 必填' })
    return
  }
  // ...
})
```
前端调用 `frontend/src/api/client.js`：
```js
deployUnit: (id, data) => apiClient.post(`/combat/${id}/deploy-unit`, data)
```
`NewBattleView.vue` 的 `deployToHex(q, r)` 构造：
```js
await combatAPI.deployUnit(route.params.id, {
  unit_id: String(unit.id),
  q, r,
  unit_data: unit
})
```
> 注：由于 `String(unit.id)` 对 `null/0/undefined` 都会生成非空字符串（`"null"`/`"0"`/`"undefined"`），单纯「单位 id 缺失」反而会变成 `404 UNIT_NOT_IN_POOL` 而非 400。因此 400 更可能由 **`q`/`r` 未定义** 或 **`unit_id` 为空字符串 `""`** 触发，需结合 Network 实际请求体确认。

### 重要背景：`battleStore` 为内存态，网关重建即清空
战局（`battleStore` 中的 `pendingUnits`/已部署单位）全部保存在**网关进程内存**中。本项目近期多次 `docker compose build --no-cache mecha-gateway` 重建，会导致**历史战局全部丢失**。

`NewBattleView.vue:2723-2780` 的兜底逻辑：
```js
try {
  const { data } = await combatAPI.getBattleState(route.params.id)
  battleState.value = data.battle || data
} catch (e) {
  // 自动创建战斗会话
  try {
    const res = await combatAPI.createBattle({ battlefield_id: 1 })   // ⚠ 硬编码 1
    // ...
  } catch (createErr) { console.warn('[BattleInit] auto-create failed:', createErr.message) }
}
```
已知坑（见 MEMORY）：`createBattle` 的 `battlefield_id` 在 `maps` 表中是 **UUID**，硬编码 `1` 会导致：
- 若 `maps` 无 `id=1` → `404 BATTLEFIELD_NOT_FOUND`（被吞掉）→ `battleState` 为空/异常 → 部署池为空 → 无法部署；
- 若 `getBattleState` 成功但战局来自被清空的旧会话 → `pendingUnits` 丢失 → `getDeployPool` 返回空 → 同样无法部署。

### 次要疑点（已被排除）
- `setPendingUnits(battleId, { units: [...] })`（NewPreparationRoom.vue:306）调用时**只传 `units`**。后端 `pending-units` 实际只校验 `Array.isArray(units)`（combat.ts:179），故**不触发 400**，部署池可正常写入。此路非 400 元凶。
- `createBattle({ battlefield_id: 1 })` 中 `battlefield_id=1` 为真值，不会命中 `!battlefield_id → 400`（combat.ts:50）。

## 四、结论与下一步建议
1. **Bug A（404 factions）已确认且修复简单**：调整 `units.ts` 路由顺序即可彻底消除 `[factions] 加载失败`。
2. **400 的机制已锁定为 `deploy-unit` 的参数校验**，但「具体哪个参数缺失」需以下任一方式确认：
   - 用户在浏览器 **Network 面板** 中找到那条 `400` 的请求，提供 **URL + Request Body**（最关键）；或
   - 我可在网关加临时请求日志（记录 400 请求的 URL 与 body），重启后复现抓取。
3. 同时建议排查**战局内存态丢失**问题（`battleStore` 重建即空 + `createBattle` 硬编码 `battlefield_id:1`），这是「棋子无法部署」的另一大潜在根因。

**等待您的下一步指示**：是否先修复 Bug A 的路由顺序？是否需要我加临时日志来精确定位 400 的请求体？
