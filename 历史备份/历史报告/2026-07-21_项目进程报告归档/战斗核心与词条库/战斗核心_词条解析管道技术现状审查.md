## 一、当前管道工作流现状

### 1.1 词条配置从哪来：静态 JSON，每次同步重读

- `configLoader.cjs` 暴露 `getGlossaryConfig()`，每次被调用时**直接 `fs.readFileSync` 磁盘上的 `glossary-skill-config.json`** 并 `JSON.parse`。
  - 优点：无缓存失效问题，编辑器 POST 保存后下次请求立即生效。
  - 缺点：**无内存缓存/无 Schema 校验**，任何非法 JSON 或字段缺失都会让该次请求抛错；配置结构完全依赖约定。
- 词条按 5 个顶层分组组织：`skills`(14)、`terrains`(10)、`damage_kinds`(5)、`action_types`(5)、`systems`(3：ambush/fog_of_war/crit)。
- **结论**：读取层是「单一静态 JSON 真相源」，不是散落各处的硬编码——这点设计是对的。问题出在**解析/消费层**。

### 1.2 解析与消费层：两层硬编码调度，配置只在「简单技能」路径生效

数据流（一次技能释放）：

```
combatResolver.executeSkill(ctx)                ← 入口，按 skillId 大 if/else 分流
   ├─ 命中具名处理：executeCounter / executeBlock / executeSniper / executeSweep
   │              / executeAssist / executeStable / executeGuard / executeScout
   │              / executeThrow / executeBlockade / executeSupply / executeUnit ...
   │        → 各自**自带一套硬编码结算逻辑**，仅挑选个别字段读配置
   └─ 未命中 → skillExecutor.executeSkill(skillData, ctx)   ← 「万能」通用路径
              → getDamageType() 定伤害种类 → buildSkillContext() 合并字段
              → executeUniversalSkill() 读 base_damage/accuracy_mod/... 计算
              → DamagePipe.calculate(damageType, rawDamage, defender, ctx)
```

**关键事实 1 —— `damage_kind` 在管道里是「死字段」：**
- `skillExecutor.getDamageType(skillData, attacker)` 返回 `skillData.attack_type || attacker.weaponType || 'kinetic'`。
  - 配置里根本没有 `attack_type` 字段（只有 `action_type`，语义是「攻击/治疗/增益…」），所以 `skillData.attack_type` 恒为 `undefined`。
  - 于是伤害种类**永远取 `attacker.weaponType`，技能配置的 `damage_kind` 被完全忽略**。
- `combatResolver` 在调用 `DamagePipe.calculate(...)` 时只注入了 `dice_type / success_line / height_bonus`，**没有把技能的 `damage_kind` 传进去**；`DamagePipe` 又只认 `attacker.weaponType` 作为伤害种类键。
- **影响**：在词条编辑器里把某技能设为 `beam`（光束）或 `kinetic`，普通攻击/万能路径结算结果与设 `kinetic` 毫无差别——编辑器该字段形同虚设。

**关键事实 2 —— 具名处理器的配置读取是「挑着读」，且带硬编码兜底：**
- `executeBlock` 读 `reduction / damage_multiplier`（配置有就生效）；
- `executeCounter` 读 `reduction / bonus / mobility_reduction`；
- 但 `combatResolver` 里 `sniper` 的机动削减写死字面量 `2`、**`counter` 的 `_extractSkillBonuses` 写死 `value:2`**（与 `executeCounter` 读配置形成双份真相）；
- 这些「读配置」字段在**前端编辑器里没有对应控件**（见《词条编辑器属性编辑逻辑报告》），所以编辑器即便有入口也改不到它们，默认值优先。

**关键事实 3 —— 字段漏传/错位汇总（管道内部）：**

| 字段 | 配置里有 | 管道是否消费 | 现状 |
|---|---|---|---|
| `damage_kind` | ✅ | ❌ | 被 `weaponType` 覆盖，死字段 |
| `base_damage` | ✅ | ⚠️ | 仅万能路径/部分具名读；具名写死时忽略 |
| `accuracy_mod` / `evasion_mod` | ✅ | ⚠️ | 万能路径读，具名常忽略 |
| `height_bonus` | ✅ | ✅(但仅注入具名) | 仅在 `combatResolver` 注入 `DamagePipe`，万能路径未注入 |
| `status_effects` | ✅ | ⚠️ | 万能路径经 `effectExecutor` 消费；具名按需手写 |
| `dice_type` / `success_line` / `success_bonus` | ✅ | ⚠️ | 仅在具名 `DamagePipe.calculate` 注入；万能路径走另一套 |
| `range_type` / `beam_width` / `aoe_radius` / `min_cast_range` | ✅ | ❌ | 仅描述性，结算层基本不读（范围判定在别处） |
| `reduction` / `bonus` / `damage_multiplier` / `mobility_reduction` | ✅ | ⚠️ | 仅个别具名处理器读，无通用机制 |

**小结**：读取层是干净的单源；但解析层是 **「两层大 if/else + 万能路径」三轨并行**，配置只在最简单那一轨真正驱动计算，中高级机制（counter/block/sniper/sweep/duel/snatch/focused_fire…）仍由分散的硬编码函数承载，且字段对齐混乱（漏传 `damage_kind`、`beam`/`energy` 错配、多个写死常量）。

## 二、识别与处理极限盘点

### 2.1 后端「能」动态识别并计算什么

**A. 能纯配置驱动的（万能路径 / 通用字段）：**
- 伤害数值：`base_damage`（经 `executeUniversalSkill` → `DamagePipe`）。
- 命中修正：`accuracy_mod` / `evasion_mod` / `height_bonus`。
- 状态效果：`status_effects[]`（经 `effectExecutor` 落地 `applyStatusEffect`，支持 `type/value/duration/stackable/chance`）。
- 暴击：`systems.crit` 全局参数驱动（33.3% 触发，倍率取自配置）。
- 被动触发门槛：`requires_hp_below` / `requires_unmoved` / `target_on_terrain` / `requires_stealth`（经 `ConditionEvaluator.evaluateFlat`）。

**B. 能「半配置驱动」的（具名处理器挑字段）：**
- `counter` / `block` / `sweep` / `assist` / `stable` / `guard` / `snatch` / `duel` / `focused_fire` / `reactivate` / `lucky` 等：函数内逻辑硬编码，但部分数值（如 `reduction`、`bonus`、`damage_multiplier`、`mobility_reduction`、`success_bonus`）从 `skillData` 读取——即「结构框死、数值可配」。

**C. 完全硬编码、配置改不动的：**
- `sniper` 机动削减（`=2`）、`counter` 反击加成（`_extractSkillBonuses` 写死 `value:2`）、各技能的掷骰判定线上限。

### 2.2 复杂词条 / 条件分支 / 区间判定 —— **当前架构做不到动态解析**

**1）触发条件（能否发动）：已支持结构化，但仅限「门槛门控」**
- `ConditionEvaluator` 支持两种格式：
  - 平铺式：`{ requires_unmoved: true, requires_hp_below: 50 }`（白名单 `flatConditionKeys` 仅 4 个键）。
  - 结构化：`{ required:[...], any:[...], not:{...} }` 或 `{ check, value, ref, operator }`，支持 AND/OR/NOT。
- **但**：这些条件只回答「**这个技能现在能不能触发**」，不回答「**触发后按什么分支结算**」。

**2）效果分支 / 区间判定（如「骰出 1-4 点则伤害 +3」）：** **当前架构不支持**
- 配置 schema 里**没有**任何「分支 modifiers」字段。掷骰系统只有 `dice_type / success_line / success_bonus`——`success_bonus` 是「命中后统一加值」，不是「区间分段 +3/+5」。
- 用户举例的「`1-4点伤害+3`」这类**按掷骰结果分段选择不同修正**的模式，在代码里**不存在对应数据结构**，只能靠为每个技能单独写一段 `if (roll >= 1 && roll <= 4) dmg += 3` 的硬编码。这正是 `sniper`、`counter`、`focused_fire` 里残留硬编码的根源。
- `ConditionEvaluator` 的 `compare` 能做数值区间比较，但**它只用于触发门控，没有被复用到「结算分支选择」**。

**3）多状态选择（同一技能在不同局势选不同效果）：** 同上，**无机制**。目前多状态效果要么靠 `status_effects[]`（固定全上），要么靠具名函数手写不同分支。

**4）新增一个全新机制（如「反击时反弹 50% 伤害」）：** **必须改代码**
- `combatResolver` 用 `skillId` 大 `if/else` 分流；skillExecutor 也有 `EXECUTORS` 映射。两者都是**按 id 硬编码分发**，不是按配置里的 `mechanic` / `handler` / `effects` 字段分发。
- 因此**仅靠前端传 JSON 无法引入新机制**：必须有人在 `combatResolver`/`skillExecutor` 里加一个具名函数并登记 id。这是当前管道最大的「非数据驱动」瓶颈。

### 2.3 极限小结

| 能力 | 现状 |
|---|---|
| 简单伤害/命中/状态 | ✅ 配置驱动 |
| 被动触发门槛 | ✅ 配置驱动（4 个键 + 结构化） |
| 机制数值微调 | ⚠️ 部分字段可读配置，但编辑器无控件 |
| 区间/分支修饰（掷骰分段） | ❌ 不支持，需硬编码 |
| 多状态/多分支效果选择 | ❌ 不支持，需硬编码 |
| 新增全新机制 | ❌ 必须改代码（id 分发硬编码） |

## 三、映射接口契约（JSON 协议）—— 前端结构化配置要被无缝执行，后端需做什么

### 3.1 当前 JSON 协议（glossary-skill-config.json，skill 条目）

当前每个 skill 实际生效的字段大致为：

```jsonc
{
  "id": "counter",
  "label": "反击",
  "category": "战术",
  "type": "active",            // active / passive
  "icon": "...",
  "description": "...",
  "target_filter": "enemy",
  "cast_range": 1,
  "range_type": "radial",      // radial / directional_beam / cone
  "min_cast_range": 0,
  "aoe_radius": 0,
  "beam_width": 0,
  "base_damage": 0,
  "dice_type": 2,              // 掷骰面数（残留）
  "success_line": 6,
  "success_bonus": 0,
  "accuracy_mod": 0,
  "evasion_mod": 0,
  "height_bonus": 0,
  "damage_kind": "kinetic",    // ⚠️ 当前管道忽略
  "attack_stat": "melee",
  "action_type": "attack",     // 攻击/治疗/增益/减益/被动
  "status_effects": [ { "type": "stun", "value": 1, "duration": 1, "stackable": false, "chance": 1 } ],
  // 以下为具名处理器专用，无通用语义：
  "reduction": 0, "bonus": 0, "damage_multiplier": 1, "mobility_reduction": 0
}
```

**缺口**：没有「效果操作序列」`effects`，没有「分支」`branches`，没有「触发条件」`trigger`（被动条目有局部 `trigger` 但非通用），没有「机制类型」`mechanic` 让后端按字段分发。

### 3.2 若前端要传「主谓宾 + 触发条件 + 分支 modifiers」，后端需的改动

要让后端**无缝接收并执行**一种结构化协议（例如）：

```jsonc
{
  "id": "...",
  "mechanic": "universal",          // 后端按 mechanic 选执行器，而非按 id 写死
  "trigger": { "required": [ {"check":"requires_unmoved","value":true} ] },
  "target": { "filter": "enemy", "range": 1, "shape": "radial" },   // 主谓宾里的「宾」
  "effects": [                       // 主谓宾里的「谓」= 有序操作序列
    { "op": "damage", "amount": {"base": 4, "kind": "beam"} },
    { "op": "apply_status", "status": "stun", "value": 1, "duration": 1 }
  ],
  "branches": [                      // 分支 modifiers（区间/多状态）
    { "when": { "check": "dice_range", "value": [1,4] },
      "then": [ { "op": "damage_mod", "amount": 3 } ] },
    { "when": { "any": [ {"check":"target_hp","value":3,"operator":"<="} ] },
      "then": [ { "op": "damage_mod", "amount": 5 } ] }
  ]
}
```

后端需做以下改造（按优先级）：

**契约层（必须新增/规范）**
1. 引入 `mechanic` 字段替代 `combatResolver` 的 `skillId` 硬编码分发（或保留 id 但增加 `mechanic→executor` 映射表）。
2. 规范 `damage_kind` 为唯一伤害种类真相，删除 `attacker.weaponType` 的优先级（或加显式映射层）。
3. 新增 `effects[]`（有序操作：`damage`/`heal`/`apply_status`/`modify_mobility`/`teleport`/`summon`/`draw`…）——后端需一个**通用 effect 解释器**遍历执行，取代散落的具名函数。
4. 新增 `branches[]`：`{ when: <ConditionEvaluator 结构>, then: <effects> }`——后端在结算时遍历 `branches`，用 `ConditionEvaluator.evaluate(when, ctx)` 决定套用哪条 `then`。
5. 将 `trigger` 标准化为所有技能通用的 `ConditionEvaluator` 结构（被动已有雏形，需上提到所有 skill）。

**解释器层（需重构）**
6. 把 `executeCounter/executeBlock/executeSniper/...` 逐个**降解为 `effects + branches` 声明**，逐步从 `combatResolver` 的 if/else 中移除。
7. `DamagePipe.calculate` 必须接受显式 `damage_kind`（而非派生 `weaponType`），并与 `equipmentDurability` 共用同一套伤害种类枚举。
8. `ConditionEvaluator` 需扩展可评估的上下文键（如 `dice_range`、`roll_result`、`target_hp` 已在，但需暴露给分支选择而不仅是触发门控），并提供 `evaluateBranch` 语义。
9. `effectExecutor` 已有 `applyStatusEffect`，需扩充为 `executeEffects(effects, ctx)` 通用循环，并把 `status_effects` 与未来 `effects` 合并为一种数据模型。

**契约健壮性（建议）**
10. `configLoader` 增加轻量 Schema 校验（至少 `id/mechanic/effects` 存在性），避免非法 JSON 直接让结算崩溃。

## 四、需要重构的痛点清单（按等级）

### 🔴 P0 — 阻断「配置真正驱动战斗」的真 bug
- **P0-1 `damage_kind` 死字段**：`skillExecutor.getDamageType` 用 `attacker.weaponType` 覆盖配置；`combatResolver` 调 `DamagePipe` 不传 `damage_kind`。→ 编辑器设光束/动能无效。修复：在 `getDamageType` 与 `DamagePipe.calculate` 中改用 `skillData.damage_kind`。
- **P0-2 `beam`↔`energy` 术语错配**：配置伤害种类是 `beam`，但 `equipmentDurability` 涂层/全覆式判定用的是 `weaponType === 'energy'`，且全覆式/涂层减伤写死 `-2`（配置设计为 `-3`）。→ 抗性涂层对光束永不触发，且与设计不符。修复：建 `damage_kind → weaponType` 映射层，统一枚举，减伤改回 `-3`。

### 🟡 P1 — 半硬编码，配置只能「部分」生效
- **P1-1 `combatResolver` 按 `skillId` 大 if/else 分发**：新增机制必改代码。→ 引入 `mechanic` 字段 + 映射表，走向数据驱动。
- **P1-2 `sniper` 机动削减写死 `2`**（`combatResolver`）、**`counter` 反击加成写死 `value:2`**（`_extractSkillBonuses`）：与读配置的 `executeCounter` 双份真相，编辑器改动无效。→ 全部迁到配置字段。
- **P1-3 `height_bonus` 仅在具名路径注入 `DamagePipe`**，万能路径未注入 → 万能技能不吃高度加成。

### 🟠 P2 — 架构性缺失（动态分支/多状态）
- **P2-1 无「分支 modifiers」机制**：区间判定（如「1-4 伤 +3」）只能硬编码。→ 引入 `branches[]` + `ConditionEvaluator` 分支语义。
- **P2-2 `ConditionEvaluator` 仅用于触发门控**，未复用到结算分支选择 / 多状态效果选择。
- **P2-3 无通用 `effects[]` 操作序列**：每个机制一套手写函数，无法由 JSON 描述「主谓宾」。

### 🟢 P3 — 协议与健壮性
- **P3-1 `status_effects` vs `effects` 双模型并存**，建议统一为 `effects[]`。
- **P3-2 `configLoader` 无 Schema 校验**，非法配置直接抛错。
- **P3-3 编辑器缺 `terrains/damage_kinds/action_types` 入口**（见编辑器报告），协议扩展后需补 UI。
- **P3-4 `action_type` / `category` / `type` 语义三重叠**，建议明确：category=分类标签、type=active/passive、action_type=攻击/治疗/增益/减益。

## 五、一句话结论

当前管道**读配置是干净的（单一静态 JSON），但解析是「三层硬编码 + 万能路径」并行，配置只在最简单一轨真正生效**。它能数据驱动「简单伤害/命中/状态/被动门槛」，但**区间分支、多状态选择、以及任何全新机制都做不到纯配置驱动**——必须改 `combatResolver` 的 id 硬编码分发、补 `effects[]`/`branches[]` 通用解释器、并先修掉 `damage_kind` 死字段与 `beam`/`energy` 错配这两个阻断性 bug，才能让前端传来的「主谓宾 + 触发条件 + 分支 modifiers」被无缝执行。
