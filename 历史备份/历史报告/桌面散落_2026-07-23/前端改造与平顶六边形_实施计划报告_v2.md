## 2. ★ 核心逻辑关联风险排查（本次重点）

> 原则：**坐标/距离数学层（axial/offset 距离、hexDistance）与渲染层（尖顶/平顶/等距）正交，本身不受影响**；真正的风险点在「**邻居方向集合是否前后端一致**」与「**边界判定是否还残留 width/height**」。以下逐项列出函数、位置、语义、改造影响、风险、动作。

### 2.1 距离计算 `hexDistance`（核心，低风险但需清单化）
| 实现位置 | 公式 | 语义 | 改造影响 |
|---|---|---|---|
| `services/combat-service/src/state/battleState.js:147` | `max(\|dq\|,\|dr\|,\|dq+dr\|)` | axial/cube 距离 | 与渲染无关，**不受影响** |
| `services/map-service/src/utils/hexUtils.js:85` | `(|dq|+|dq+dr|+|dr|)/2` | 同上（等价） | 不受影响 |
| `backend-gateway/src/routes/combat.ts:315` | 调用 `hexDistance` | 攻击距离判定 | 不受影响 |
| `skillExecutor._hexDistance` (`combatCore/skillExecutor.cjs:965`) | 内部调用 | 技能/伤害距离 | 不受影响 |
| `DamagePipe.calculateHexDistance` (`factionSkillRegistry.cjs:82/220/315`) | (q,r) 距离 | 技能射程/受击判定 | 不受影响 |

**结论**：`hexDistance` 全部基于 (q,r) 坐标，**平顶/等距/固定画布均不改变距离值**。无需改公式，但建议**统一为单一实现**（目前 3+ 份重复实现），避免未来某一处被误改。

### 2.2 ★ 邻居方向一致性矩阵（最高危）
| 消费方 | 位置 | 当前方向定义 | 坐标语义 |
|---|---|---|---|
| 前端高亮/范围预览 | `frontend/src/utils/hexUtils.js:256` `getHexNeighbors` | **Even-R offset 奇偶行方向表** | 把 (q,r) 当 offset |
| 前端平顶备用 | `frontend/src/utils/hexUtils.js:288` `getHexNeighborsFlatTop` | **Even-Q offset 奇偶列表方向表** | 平顶备用，**当前未启用** |
| 网关寻路 | `backend-gateway/src/routes/combat.ts:67` `tsFindPath` dirs | `[1,0],[1,-1],[0,-1],[-1,0],[-1,1],[0,1]` | **axial 固定方向**（不区分奇偶行） |
| combat-service 寻路 | `battleState.js` `findPath` / `terrainMovement.cjs:281` `getReachableHexes` | 需核对是否 axial 或 offset | 待确认 |
| map-service | `map-service/hexUtils.js:94` `getNeighbors` | axial 固定方向 | axial |

**⚠️ 已识别矛盾（须验证）**：前端 `getHexNeighbors`(2,3) 在奇数行产出 `{1,2}` 邻居；而网关 `tsFindPath` 对 (2,3) 用 axial dirs 产出 `{3,2}` 邻居。两者**集合不一致**。这说明系统内部 (q,r) 的「axial vs offset」语义在前后端并不统一——要么前端渲染把 (q,r) 当 offset（则 tsFindPath 应改用 Even-R 方向），要么后端把 (q,r) 当 axial（则前端 `getHexNeighbors` 应改用 axial 固定方向）。

**风险**：在「保守平顶」下，前端高亮范围与后端实际可达范围可能**已经存在偏差**（只是战场地图小、玩家不易察觉）。一旦启用全局平顶（Even-Q），前端若切 `getHexNeighborsFlatTop` 而后端不改，偏差将**彻底错乱**。

**决策（阶段 B 必做 · 2026-07-23 复核修正）**：统一到 **Even-R Offset 语义**，且**改动点在后端，不动前端**。

> ⚠️ 复核结论：原 v2「推荐前端 `getHexNeighbors` 改用 axial 固定 6 方向」是**错误**的。
> 原因：前端 `(q,r)` 是 Even-R Offset 坐标，渲染（`pointyTopCenter`）与点击（`pointyTopToHex`）全部走 offset。
> 若把前端 `getHexNeighbors` 改成 axial 向量 `[[1,0],[1,-1],[0,-1],[-1,0],[-1,1],[0,1]]`，
> 前端高亮/范围会与**前端自己的渲染**错位——同一个 `(2,3)`，axial 邻居含 `(3,2)`、offset 邻居含 `(1,2)`，
> 二者在屏幕上并不相邻，棋子会"跨格跳"。要做到"全 axial"必须连渲染管道
> （`pointyTopCenter`/`pointyTopToHex` 全部换成 axial→像素）+ DB 序列化一起迁移，属另一项大改造，
> 与此 plan「跳过阶段 C、低风险」立场矛盾。因此正确做法是**以后端迁就前端这条已落地的渲染真理源**。

**动作**：
1. 写单测：对同一 `(q,r)`，断言前端 `getHexNeighbors`（Even-R offset）与网关 `tsFindPath` 实际产出的邻居集合相等。当前不等（后端 axial 多出 `(3,2)`、缺 `(1,2)` 之类），需修复。
2. 后端 `tsFindPath` 的 `dirs` 改用 **Even-R offset 方向表**（与前端 `getHexNeighbors` 完全一致，含奇偶行分支），并同步 `combat.ts:1130` Royroy 重定位的 `dirs`、以及 `combat-service`/`terrainMovement.cjs` 的 `getReachableHexes` 若用 axial 则一并改 offset。
3. `map-service` 的 `getNeighbors`(axial) 仅用于地图编辑/静态寻路；若其 `(q,r)` 也来自同一 offset 数据源，需同样改为 offset 或显式转换，否则保持并加单测区分。
4. 固化单测：前后端邻居集合相等 + `tsFindPath` 在 offset 语义下可达集合与前端高亮一致。

### 2.3 移动范围公式一致性（高危，已存在分歧）
| 路径 | 公式 | 位置 |
|---|---|---|
| 网关 `/move` + 前端高亮 | `max(1, round(rawMob/10))` | `combat.ts` / `NewBattleView.drawBattleScene`（工作记忆红线固化） |
| combat-service AI / 旧路径 | `Math.floor(mobility/2)` | 评估报告 §2.4 载明 |

**风险**：若 `combat-service` 的 `Math.floor(mobility/2)` 路径仍参与实时战斗结算（AI 移动、自动战斗），则与网关 `round(rawMob/10)` 给出的可走格数**不一致** → 玩家看到的高亮范围与 AI 实际走的格数不同，且两端「够不够得着」判定冲突。

**动作（阶段 B）**：
1. 确认 `combat-service` 的 `getMoveRange`/`Math.floor(mobility/2)` 是否仍在实时链路；若是，统一为 `max(1, round(rawMob/10))` 或显式分流（AI 用独立公式需文档说明）。
2. 前端高亮与 `tsFindPath(maxRange)` **必须同源**，加单测断言同一 `mobility` 下两者 maxRange 相等（防止再次出现 `moveRange=0 → 无法移动` 的 NaN 类 bug）。

### 2.4 寻路与可达 / 边界判定（固定画布直接关联）
| 函数 | 位置 | 边界判定现状 | 固定画布改造动作 |
|---|---|---|---|
| `tsFindPath` | `combat.ts:58` | 仅 `cellSet`（已适配 ✓） | 已 OK；但需确认 `cellSet` 由 `cells` 而非 `width/height` 构建 |
| `battleState.findPath` | `battleState.js:85` | 含 `width/height` 矩形边界（评估报告 §4.7） | **迁移为 cellSet 成员判定** |
| `getReachableHexes` | `terrainMovement.cjs:281` | 待查 | 同步迁移边界 |
| `map-service.findPath` | `map-service/hexUtils.js:155` | 用 `getNeighbors`(axial) + `heuristic=hexDistance` | 距离/邻居不受影响；边界若用 width/height 需迁 cellSet |
| `getHexesInRange` | `map-service/hexUtils.js:108` | axial 范围环，无边界 | 不受影响（范围计算与渲染无关） |

**风险**：固定画布后，「地图外」格子不再由 width/height 矩形定义，而由 `cells` 集合定义。任何残留 `0<=q<width && 0<=r<height` 的判定会导致：在 100×100 画布上，原本「地图外」的空白区域被错误地当作可移动/可部署。

**动作（阶段 A）**：全局搜索 `.width`/`.height` + `width/height` 边界判定（评估报告 §9 关键词），逐个迁移到 `cellsSet.has(key)`；并在 `createBattle`/`battleStateFactory` 固化 `width=height=100`（评估报告 §4.6）。

### 2.5 命中 / 点击（pixelToHex）
- 当前：`pointyTopToHex`（`frontend/src/utils/hexUtils.js:191`，尖顶逆推）。挤出行模式命中仍用顶面中心逆变换（综合方案 §3.2e）。
- **保守平顶下**：尖顶逆推与渲染（尖顶压扁）一致，点击精准 ✓。
- **若启用全局平顶（阶段 C）**：必须把点击逆推切到 `flatTopToHex`，且顶点/倒角轴同步（否则「平顶顶点与倒角轴不同步 → 瓷砖横扁」+ 点击错位，综合方案风险表 §380）。
- **动作**：阶段 B 加单测 `pointyTopToHex(pointyTopCenter(q,r)) === {q,r}` 已验证；阶段 C 加 `flatTopToHex(flatTopCenter(q,r)) === {q,r}` 并核对点击命中。

### 2.6 攻击 / 技能范围（与渲染无关，低风险）
- `getHexesInRange`（axial 范围环）、`range_type: radial/directional_beam/cone`、`DamagePipe.calculateHexDistance` 全部基于 (q,r)，**不受平顶/等距/固定画布影响**。
- **唯一关联**：范围预览若用 `getHexNeighbors` 逐层扩散（前端 `drawBattleScene` L1617/1640/2029），则其正确性**依赖 §2.2 邻居方向一致性**。邻居统一后范围自然正确。

### 2.7 单位锚点与朝向
- 挤出模式：单位精灵锚点需对齐「该格顶面中心」（`NewBattleView.drawBattleScene` 已做顶面中心 + 脚底投影椭圆）。
- **保守平顶下**：顶面中心 = 尖顶压扁后的中心，已对齐 ✓。
- **若启用全局平顶**：顶面中心坐标改为 `flatTopCenter`，且单位朝向/七视图锚点 `_defaultRenderH` 可能需重校准（`unitSpriteResolver.js`，综合方案 §3.6）。

### 2.8 渲染性能关联（固定画布放大风险）
- 固定 100×100 = 10,000 格；若战场 `:use-terrain-cache="false"`（当前 `NewBattleView` 模板），挤出行每帧重绘约 1 万立柱 → 中低配掉帧（综合方案已知风险）。
- **动作（阶段 D）**：固定画布后强制开启地形缓存（缓存 key 含 `extrude+ISO`），或评估 `use-terrain-cache` 默认 true。

### 2.9 用户补充排查决策（2026-07-23 复核）
用户提交三项补充建议，经代码核查后结论：
1. **邻居统一为 Axial（改前端 `getHexNeighbors`）→ 采纳方向、修正操作**：统一到单一语义正确，但操作应为**后端迁就前端 Even-R offset**（改 `tsFindPath` / Royroy 重定位 `dirs`），而非改前端为 axial 向量。原因与正确做法见 §2.2 决策块——改前端会令高亮与自身渲染错位。真正「全 axial」需渲染管道 + DB 序列化大迁移，不在此 plan。

3. **跳过阶段 C（维持保守平顶）→ 完全采纳**：理由见阶段 C 决策块。

## 3. 修订后分阶段实施计划

### 阶段 A — 固定画布 100×100 + cells 边界（数据层，必做，评估报告 §7.1）
1. 后端 `sqlite.ts`：`maps` 表 `width/height` → nullable / 默认 100。
2. 后端 `maps.ts`：create/update 忽略 `width/height`，返回 `cells`；`combat.ts` `createBattle` + `battleStateFactory` 固化 `width=height=100`。
3. 后端 `battleState.js` / `terrainMovement.cjs` / `map-service`：边界判定 `width/height` → `cellSet.has(key)`。
4. 前端 `NewBattlefieldView`：移除 width/height 输入框（L121-130/237-238/626-650），固定 100×100 画布，画笔边界 `0–99`。
5. 前端 `HexGridCanvasEngine`：`updateVisibleRange`/`isInViewport`/渲染循环/点击边界改为 cells bbox 或 `0–99`。
6. 前端 `NewBattleView`：`gridData` 构造适配；边界判定 `cellMap.has(q,r)`。
7. 数据迁移（旧地图平滑兼容）：`maps` 表 `cells` 永远是数组（默认 `'[]'`），旧地图"有 width/height 但 cells 为空数组"会渲染成全空白。在 `maps.ts` 各 GET 端点（`/api/map/list`、`/api/map/battlefields`、`/api/map/battlefields/:id`）解析 `cells` 后加平滑补丁：
   ```js
   // 旧地图兼容：cells 为空数组但存在 width/height → 按矩形自动补全为全量 cells
   let cells = JSON.parse(map.cells || '[]')
   if ((!cells || cells.length === 0) && map.width && map.height) {
     cells = []
     for (let r = 0; r < map.height; r++) {
       for (let q = 0; q < map.width; q++) {
         cells.push({ q, r, terrain: 'moon' })   // 数组元素 {q,r,terrain}，非 dict/下划线 key
       }
     }
   }
   ```
   ⚠️ 注意 `cells` 是 **`{q,r,terrain}` 对象数组**（`combat.ts` 用 `cells.map(c => \`${c.q},${c.r}\`)` 构建 cellSet），不能用 `{"q_r": {active:true}}` 这类 dict / 下划线 key（会让 cellSet 构建崩溃）。编辑器渲染回退 `cell?.terrain || 'moon'`，默认填 `moon` 视觉安全。
8. 单测 + 部署。

### 阶段 B — ★ 核心逻辑一致性专项排查（必做，本次重点）
1. **邻居方向一致性**（§2.2）：单测断言前端 `getHexNeighbors` 与 `tsFindPath` 邻居集合相等 → 定位 axial/offset 语义分歧 → 统一并固化。
2. **移动范围公式**（§2.3）：确认 `combat-service` 的 `floor(mobility/2)` 是否实时链路；统一为 `max(1, round(rawMob/10))`；前端高亮 vs `tsFindPath(maxRange)` 同源单测。
3. **距离计算**（§2.1）：统一多份 `hexDistance` 为单一实现；单测坐标正逆 round-trip。
4. **边界残留扫描**（评估报告 §9）：全局搜 `.width`/`.height`/`pointyTop`/`Even-R`/`sqrt(3)`/`1.5 *`/`getHexNeighbors`/`HEX_WIDTH`/`HEX_HEIGHT`，建检查清单逐条销账。
5. **命中/点击**：`pointyTopToHex(pointyTopCenter) === identity` 单测（已有）+ 挤出命中单测。

### 阶段 C — 全局平顶六边形切换（可选，高风险，评估报告 §7.2）
