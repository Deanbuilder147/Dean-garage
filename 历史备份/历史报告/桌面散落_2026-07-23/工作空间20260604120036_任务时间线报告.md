## 五、走过的弯路汇总（Detours & Course-Corrections）

梳理全程，最显著的"绕路"集中在 **架构方向反复、并行实现浪费、部署工程踩坑、同类 bug 反复复发** 四类。以下按主题归纳（均可在对应日期日志中查证）。

### 1. 架构方向类弯路（最重，投入大但被废弃/回退）

- **❌ 剧情战役模式从大建到全废（Phase 15 → 19-E → 22 → 23 焦土清仓）**
  06-21 起大建 CampaignView / campaignManager / campaign.js / virtualPlayerAgent（单机沙盒、教学关卡、AI 战术引擎、三关配置）；06-22 又做"剧情×正常战场 100% 同壳复刻"（注入 is_campaign/campaign_battle_id + battleApi 分流器）。到 06-22 Phase 23，总监裁决"放弃剧情模式"，物理删除 4 个文件、回退到 Phase 16 纯净联机战场。**整条剧情线基本是净废弃投入。**
  - 教训：多态 ID 同壳复用引发 `[object Object]` UUID 冲突 + 404 截瘫，为此又堆出 9 层防护墙（Phase 21-ABCDE），最终仍走不通。

- **❌ 两套并行战斗实现（TS skillExecutor vs .cjs combatCore）**
  Phase 29 大一统后，运行网关自带一份 **TS 版** skillExecutor，而 `services/combat-service` 的 **.cjs** 引擎并行存在却互不生效。07-20 才发现：之前对 .cjs 的契约/注册表/多分支解析器（Step1-6）改动**根本没在生产生效**；投骰多分支等功能此前不可用。直到用 `combatBridge.ts`（createRequire）把 .cjs 接入网关才真正落地。
  - 教训：早期大量"战斗功能"改动是**无效劳动**，根因是部署架构未让网关引用 combat-service。

- **❌ 七微服务 → 4 容器单体的反复（焦土退守）**
  早期 9 个微服务（auth/hangar/map/combat/comm/online-battle + PG + 网关），经历多次网络/代理/数据卷错位（如 hangar-service Docker 构建卡死、数据库路径硬编码导致 `--no-cache` 数据丢失）。最终 Phase 29 全部废弃 legacy 微服务、收敛为 4 容器单体。
  - 牵连浪费：07-21 在 `hangar-service` 上做的 fix-import-fields / unify-owner 等改动，事后确认是 **legacy 死代码、对线上零影响**，仅为"双库代码一致性"。

- **❌ Royroy 实现方案回退（07-22）**
  先落地"独立浮游辅机 BattleUnit"（deploy-unit 生成 + /move 邻域约束 + createRoyroyUnit），用户澄清后回退为属性模型 `unit.royroy`（RoyroyState），前一套 spawn 逻辑被撤。
  - 教训：实现前未确认"部署时机与数据模型归属"，导致一次完整实现返工。

- **❌ 重型架构重组提案被否决（07-22）**
  用户提的 Core/Adapter/View 三层 + Camera 类 + TS 接口的"零额外工期"提案，经实地核查（hexUtils 非纯数学、引擎已解耦、TS 引入构建摩擦）被判定为"零额外工期是假的"，驳回，改采轻量解耦。
  - 教训：提案中的工作量评估不可轻信，需对照现状核账。

### 2. 部署 / 工程类弯路（反复踩，固化成"红线"）

- **🔁 镜像名陷阱 + 重建遗漏（多次）**
  `docker compose build mecha-gateway` 产出 `mecha-universe-engine-mecha-gateway`（非 `mecha-gateway:latest`）；只 `restart` 会复用旧镜像，导致"改动看不到"。前端也曾多次"只 `npm run build` 不重建镜像"失效。此类问题在 06-25、07-21（两个镜像名导致 smoke-test 失败）、07-22 多次复现。

- **🔁 Python 补丁脚本锚点依赖（多次回退）**
  反复用 Python 补丁针对远程路径打补丁，锚点不在则全链崩溃（如 Phase 16 的 terrainMap 缺失导致 17 处引用未定义）。催生了"红线资料库 #1-#8"这类对**反复同类故障**的总结性防御。

- **🔁 Canvas 居中/旋转多轮横跳（06-29 ~ 07-03）**
  - 06-29 CanvasTrueCenter 给 CTM 加 `ctx.rotate(rotation)` → TrueFinal 第 4 轮又**物理删除**（rotate 破坏逆矩阵、鼠标错位），rotation 交还 hexUtils。
  - 07-03 Phase 30 把 ISO shear 放进 `ctx.transform` 导致与 hexUtils 双重挤压畸变 → 紧急热修剥离，确立"CTM 只管 scale+translate，ISO 由 hexUtils 逐顶点施加"原则。
  - 同一"左上角切边/鼠标错位"问题历经 CanvasTrueCenter → TrueFinal → DOM_Purge → ParitySync 多轮才稳定。

### 3. 功能 / 数据类弯路（需求理解偏差或坑反复）

- **🔁 Excel 导入 400 / VALIDATION_ERROR 多轮诊断（07-21）**
  根因层层暴露：① A4 未精确填"主机体"或其别名；② axios 全局 `Content-Type: application/json` 干扰 FormData → multer 收不到文件（先后试过手动写 multipart 无 boundary、删头、最终 `instanceof FormData` 删除头）；③ 预览嵌套结构不匹配（最终用 `_importPayload` 字符串方案绕过 JSON 丢失）；④ 主图上传静默 `catch` 吞错。
  - 教训：前端 axios 默认头与 FormData 的冲突是**经典反复坑**。

- **🔁 硬编码导致的 404 链路（多次）**
  `battlefield_id: 1`（maps 表用 UUID）、`API_BASE='http://localhost:3004'`（应走 Nginx 相对路径）、`/api/hangar/` 旧前缀（应 `/api/units/`）、`deploy-pool` 路径缺 `/api/` 前缀……均为硬编码写死真实路径，触发 404 后排查耗时。

- **🔁 单位数值体系反复（06-20 ~ 07-22）**
  shield 长期固定 0、`equipManager` 加成系统是孤儿代码（Excel 归一器未写这些字段）；Excel 设定器 v1（行号硬编码）与 v2.1（A 列驱动）两版格式打架；07-22 又因"攻击差额/防具分担"规则重新核算数值底层并写迁移脚本。

### 4. 弯路的共性规律（给后续工作的提醒）

1. **先定架构与部署模型，再写功能**：剧情模式、双战斗引擎、微服务拆分三件大事都因"后期才统一架构/部署"而返工。
2. **改动必须验证"运行态"而非"构建成功"**：镜像名陷阱、网关 dist 旧上下文、`??` 不捕获 0 等，都因只看 build 成功而漏掉真实生效验证。
3. **同类故障应一次性资产化**：红线资料库 #1-#8 与九层防护墙本质是"反复踩同一坑"的补丁堆，最好在首个坑就固化检查表。
4. **需求确认先于实现**：Royroy（数据模型归属）、同壳复用（多态 ID）、重型重构提案三例，均因未先与现状/用户对齐而走弯路。
5. **配置/路径单一真相（single source of truth）**：两版 Excel 格式、TypeScript 与 .cjs 双实现、combat-service 与 gateway 配置分叉，都是"多份真相"导致的错位。

> 总体评价：弯路主要不是"技术写错"，而是**架构方向（剧情模式、微服务、双引擎）与部署模型在后期才收敛**带来的返工，以及**同类工程坑（镜像重建、FormData 头、硬编码路径、Canvas 时序）反复复发**。功能性 bug 大多在当日内即被修复并部署验证，未长期遗留。
