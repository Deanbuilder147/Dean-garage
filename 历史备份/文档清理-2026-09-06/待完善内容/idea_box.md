**涉及核心功能：** 用户登录、新用户注册、Token 自动持久化。

**跨服务协同关联：**

- `mecha-auth (3001)` → 保持不动，作为唯一的账号验证源，继续向大一统 `apiClient` 签发 7 天有效期的 JWT Token。

### 2. 🗂️ 房间数据大厅（3006 独裁执政）

**涉及核心功能：** 创建联机房间、加入/离开房间、修改房间配置、天梯配对队列。

**跨服务协同关联：**

- `mecha-online-battle (3006)` → 升级为核心命令写入端。全量负责房间创建与销毁的 HTTP 请求，将状态刚性写入本地 `better-sqlite3` 持久化库中。
- `mecha-comm (3005)` → 物理交出数据主权。废弃其内部重叠的房间 HTTP 写入端点，不再进行任何内存 Map 房间记录。
- `frontend/src/api/client.js` → 将原本属于 `commAPI` 的房间控制方法，其请求根路径（baseURL）全量无损迁移到 3006 端口代理的 `onlineBattleAPI` 骨架下。

### 3. 📺 5-10 秒微信小程序观战流（3005 读写分离缓冲）

**涉及核心功能：** 实时战局推流、微信无感知异步观战、网络并发防踩踏。

**跨服务协同关联：**

- `mecha-combat (3004)` → 战局流源头。战棋引擎在战场中每次发生棋子移动或交火时，异步向 3005 端口实时推送当前的 `BattleState`（战局快照）。
- `mecha-comm (3005)` → 缓冲与微信输入端。内部维护一个内存 FIFO（先进先出）队列，对收到的战局快照挂载 5-10 秒的 `setTimeout` 延迟阻尼，通过其原生的 Socket.io 通道，专职为未来的微信观战小程序提供平滑的延迟数据推流。

### 4. 🧭 不可变地图模板与剧情战役（沙盒物理隔离）

**涉及核心功能：** 地图编辑器无损保存、玩家自定义 JSON 上传、战场内格子的破坏性焦土演变、剧情战役固定关卡加载。

**跨服务协同关联：**

- `mecha-map (3003)` → 只读模板库。无论是官方剧情关卡还是玩家导出的 `custom_map.json`，在文件系统中一律作为不可变资产（Immutable）处理，任何游戏行为绝对无法修改污染它。
- `mecha-combat (3004)` → 动态沙盒演变层。开战（出击）瞬间，调用 3003 接口将地图 JSON 整个拉过来，在自己的 PostgreSQL 数据库内针对当前 `battle_id` 注入一份深拷贝（Deep Copy）。游戏中地形被大炮轰塌、战役剧情触发的桥梁断裂，100% 仅修改并读写本局对应的 PostgreSQL 记录，实现与原始地图文件的完美隔离。

## 🛠️ 一、架构师建议：对四级权限的"打补丁与微调"

### 1. 游客层（Guest）── 【建议增加：本地暂存（LocalStorage）】

**现状分析：** 游客可以编辑，但保存需要登录。

**架构增益：** 强烈建议增加一个"游客本地沙盒暂存"功能。当游客花了半小时编辑了一个极度精美的机甲或者地图，点击保存时，前端并不报错，而是将其以 JSON 形式存入浏览器的 `localStorage`。同时弹窗提示："由于您是游客，内容已暂存本地，注册/登录后即可一键永久同步到云本格纳库。" 这样能把"游客到注册用户"的转化率直接拉满。

### 2. 普通用户与裁判层（User / Referee）── 【建议增加：观战大厅特权】

**现状分析：** 游客只能通过"输入房间号"精准观战；普通用户可以正常游玩；裁判可以新建房间并设置内容。

**架构增益：**
- **游客：** 只能精准输入房号观战（防止游客白嫖服务器带宽，刷爆观战列表）。
- **普通用户：** 可以解锁"观战大厅（房间大厅）"，自由浏览当前所有正在进行的公开对局。
- **裁判（Referee）：** 除了新建房间，裁判应该天然拥有"强制全屏观战/无延迟实时观战"的上帝视角权限，用于在组织比赛时进行公正裁决（区别于微信观战小程序的 5-10 秒延迟机制）。

### 3. 管理员层（Admin）── 【建议增加：审核队列锁与版权标记】

**现状分析：** 管理员可以审核词条和地图，并在作者授权下将其设置为"公用 Copy"。这个"Copy 机制"极其高明，完全杜绝了后续如果删除玩家账号导致公用棋子直接消失的分布式断层 Bug！

**架构增益：**
- **防撞锁：** 当两个管理员同时在线时，需要引入一个"审核队列"。当 A 管理员点开某张地图审核时，该地图在后台自动锁定 5 分钟，防止 B 管理员重复操作引发持久层 SQLite/PG 冲突。
- **版权溯源：** 被复制成公用的资产，其底层 Schema 需要追加 `original_author_id`（原作者）和 `is_public_copy: true`。即使变成了官方公用资产，机甲面板上依然永远悬挂 *"由玩家 XXX 设计贡献"* 的勋章，极大刺激社区整活。

## 🗺️ 二、跨功能关联梳理：账号系统会对其他模块产生什么影响？

### 关联 1：对 mecha-auth（3001）与 JWT 的影响 🔐

**功能涉及：** 每次用户登录或验证时。

**协同逻辑：**
- 数据库的 `users` 表必须新增字段 `role`（整数或字符串：`guest, user, referee, admin, dominator`）。
- **核心机制：** 后端在签发 JWT Token 时，必须把这个 `role` 字段直接塞进 Token 的 Payload（荷载）里。这样前端大一统拦截器解密 Token 后，能瞬间知道当前是游客还是 Dominator，从而动态隐藏或显示"后台管理"或者"裁判新建房间"的按钮，不需要每次都去查数据库，性能极高。

### 关联 2：对 mecha-hangar（3002）与编辑器存储的影响 🤖

**功能涉及：** 保存单位、资产设置为公用。

**协同逻辑：**
- 普通用户的资产，其数据表中的 `user_id` 指向其真实 ID。
- **公用 Copy 机制：** 当管理员点击【设为公用】时，`hangar-service` 拦截该请求，在 `units` 表中物理插入一条一模一样的全新记录，但将其 `user_id` 设为 `0`（代表官方公用库），或者 `is_global: true`。这样，普通用户在格纳库读取公用资产时，直接 `SELECT * FROM units WHERE user_id = 0` 即可。

### 关联 3：对 mecha-online-battle（3006）房间创建的限制 🗂️

**功能涉及：** 新建房间、设置内容。

**协同逻辑：** 3006 端口的 `POST /api/rooms` 接口在被调用时，其底层的鉴权中间件不仅要看 Token 是否有效，还要硬性卡死一行代码：

```javascript
if (req.user.role !== 'referee' && req.user.role !== 'admin' && req.user.role !== 'dominator') {
  return res.status(403).json({ error: "权限不足：仅限裁判及以上级别创建房间" });
}
```

这样，普通用户和游客在绕过前端直接用 curl 或工具轰炸 3006 端口时，会被后端直接无情弹回，防线彻底焊死。

## 主框架 & 核心管道

### 🧭 一、绝对核心：大一统规则引擎的四大元数据组件

要吞噬一切 TRPG，底层的 7 个微服务将彻底退化为四大纯粹的元数据动力核心：

#### 1. 🗃️ 实体通用属性容器（Entity Attribute Matrix）── 对应 hangar-service

**底层重组：** 彻底淘汰 `units` 表中诸如"格斗、射击"等具体业务列。

**元代码设计：** 作战单位、挂件、甚至是战场上的一个建筑，在底层都是一个通用的 `Entity`。它只拥有一个动态的字典结构 `attributes: Map<string, any>`。引擎不关心字段叫什么，只提供通用的原子操作，如：`entity.getAttribute('WS')`、`entity.modifyAttribute('HP', -10)`。具体的属性定义完全由你导入的"规则配置文件（RuleManifest.json）"决定。

#### 2. 🎲 骰子解析树与算伤管道（DiceScript Pipeline）── 对应 combat-service

**底层重组：** 死锁 `dicescript` 引擎。

**元代码设计：** 所有的技能、武器开火效果，在底层代码里全部抽象为一行可解析的"算效脚本字符串（Action Script String）"。比如攻击动作的底层执行器只认这种元代码：

```
"roll(2d6) + attacker.get('mel') - defender.get('arm')"
```

无论是战锤的"判定投骰（To-Hit Roll）"还是跑团的"D100 大成功/大失败判定"，全部通过 `dicescript` 动态解释执行，后端核心不需要为任何具体游戏修改一行编译代码！

#### 3. 🕸️ 拓扑几何计算器（Topology Geometry Calculator）── 对应 map-service

**底层重组：** 彻底封杀和割裂"因具体游戏而异"的硬编码格子 Delta 计算。

**元代码设计：** 地图微服务退化为一个纯粹的"离散几何数学中心"。它只负责两件事：
1. 计算图论上的 A* 寻路权重；
2. 计算射线遮挡（Line of Sight）与多边形范围。

至于它是尖顶六角格、平顶六角格还是标准四向方格，纯粹是初始化时传入的拓扑矩阵参数（`GridTopologyParam`），底层计算公式完全归一化。

#### 4. 🎛️ 条件评估与断言状态机（Condition Assertion Machine）── 对应 conditionEvaluator.cjs

**底层重组：** 解决复杂技能的动态判定（如："当处于隐蔽状态且未移动时，射程+1"）。

**元代码设计：** 构建一个通用的断言器，它只负责解析 JSON 格式的逻辑门：

```json
{
  "condition": "AND",
  "statements": [
    { "field": "attacker.actionState", "operator": "EQUALS", "value": "stealth" },
    { "field": "attacker.has_moved", "operator": "EQUALS", "value": false }
  ],
  "effect": { "target": "weapon.range", "modifier": "+", "value": 1 }
}
```

## 形象生成

### 🧭 一、跨功能关联梳理：这四大举措如何影响全栈微服务？

#### 1. 🪙 积分/额度管控系统（涉及服务：mecha-auth 3001 + mecha-hangar 3002）

**涉及功能：** 每日配额发放、人肉后台赠送、超出按次付费。

**协同逻辑：**
- 数据库的 `users` 表需要追加 `credits`（当前剩余积分/额度数字）字段。
- **人肉+自动防薅羊毛机制：**
  - **自动：** 每日凌晨0点，服务器跑一个定时任务（Cron Job），根据账号权限等级（如普通用户刷新5点，裁判刷新20点）自动重置或累加积分。
  - **人肉：** 在 Dominator 后台或管理员面板，可以直接调用 `POST /api/auth/users/:id/gift-credits` 接口，手动给某个优质模型创作者定向赠送 50 积分。
- **扣减锁：** 玩家每次点击【开始 AI 生成】时，前端先调 `hangar-service`（3002）接口，后端判断 `if (user.credits <= 0)`，直接无情弹回并提示转入付费或等待明日发放，将算力成本死死控住。

#### 2. 📝 填空+随机的智能提示词引导（涉及功能：前端编辑器组件 NewUnitEditorView.vue）

**协同逻辑：**
- **前端 UI 刚性强约束：** 在"图生形"模式下，前端不只有一个单一的上传框，而是焊死四个独立的图片槽（正面、背面、左侧、右侧）。只有当 4 个槽全部 `hasImage === true` 时，【提交 AI 生成】的按钮才允许点亮。
- **"填空+随机"元表单：** 在"文生形"模式下，为了防止玩家胡乱输入导致 AI 生成一堆工业垃圾，设计结构化填空词条：
  - 头部样式：`[ 复合机械面板 / 单眼传感器 / 传统人形 ]`
  - 躯干风格：`[ 重装甲块 / 骨架外露 / 柔性流线 ]`
  - **随机键（Dice Roll）：** 旁边放一个摇骰子按钮，点击后利用前端随机数，自动从词库里抓取一套诸如 "铁锈涂装、肩部挂载双联导弹舱、尖顶六角底座" 的硬核描述填入表单，既有趣又能强行保证生成出来的机甲风格 100% 契合战棋世界观！

#### 3. 🎞️ 16帧基线与64帧承载（涉及功能：Canvas 渲染层 NewBattleView.vue）

**协同逻辑：**
- **底层时钟设计（Frame Ticker）：** 前端 Canvas 的作战单位渲染类中，绝对不把帧率写死。每个动作资产（Spritesheet）在加载时，都附带两个元数据：`totalFrames`（总帧数）和 `frameRate`（播放帧率）。
- **柔性兼容：** 当前端渲染前进动作时，代码逻辑是：
  ```
  currentFrame = Math.floor(elapsedTime * unit.action.frameRate) % unit.action.totalFrames
  ```
  当资产是 16 帧时，它就以 16 帧丝滑循环；未来升级了，直接把 64 帧的资产包往服务器一甩，前端一行代码都不需要改！

#### 4. ⚔️ 4轴核心动作集死锁（涉及功能：mecha-combat 3004 战斗引擎 + 动画状态机）

**协同逻辑：**
- **状态机契约收拢：** 作战单位的动态动画状态机（Animation State Machine）在底层原生支持无限扩展，但首发死锁四个合法状态：`['walk_forward', 'walk_backward', 'skill_01', 'skill_02']`。
- **带宽防爆：** 玩家在格纳库里如果想解锁第五个动作（比如"胜利嘲讽"），系统或者提示权限不足，或者需要消耗额外积分，从而在真机运行期把前端并发拉取精灵图的带宽压力直接砍掉 70%。

## 地图

### 🔬 一、翘翘板现象的底层三大病灶（为什么以前不能同时生效？）

#### 1. 交互事件的"精神分裂" 🧠

**病灶：** 在 Canvas 上点击一个六角格。
- 编辑器里的预期：把这个格子的地形修改为"高山"。
- 战场上的预期：选中当前格子的机甲，或者计算移动路径。

**以前的做法：** Agent 把这两种完全相反的点击逻辑，用大量的 `if (isEditor)` 和 `else` 乱七八糟地塞在同一个 Canvas 的 `onClick` 事件里。结果改动任何一个分支，都会因为变量污染导致另一个模式的点击判定失效。

#### 2. 状态机数据的"交叉污染" 🦠

**病灶：**
- 编辑器需要维护的是"当前选中的刷子类型（比如：墙壁、河流）"；
- 战场需要维护的是"当前回合、当前选中单位的剩余 AP、攻击范围"。

**以前的做法：** 没有将两者的状态完全隔离，导致战场组件无意间修改了全局的地图元数据（Template），从而引发了"打完一局游戏，原始地图文件直接被激光炮破坏污染"的恶性 Bug。

```
│       【中央底层纯净画布内核】          │
│         HexGridCanvasEngine           │
│  - 纯粹的无状态无意识渲染器           │
│  - 只管画地形 JSON、画棋子、画格子高亮 │
└──────────────────┬────────────────────┘
                   │ 注入 / 挂载
                   ▼
┌──────────────────────────┴──────────────────────────┐
▼                                                     ▼
┌─────────────────────────────────┐                 ┌─────────────────────────────────┐
│     【外壳 A：地图编辑器策略】    │                 │       【外壳 B：战场对战策略】   │

└─────────────────────────────────┘                 └─────────────────────────────────┘
```

**🛠️ 怎么做到同时修改、全球生效？**

1. **统一抽离出 `HexGridCanvasEngine`（内核）：** 这个内核代码死锁 0 修改。它的任务极其单纯，只要上层给它一套六角格数据，它就用 Canvas 2D/WebGL 把它画出来。如果以后升级了精美的皮肤、瓦片图，只需要在这个内核里改一次，编辑器和战场就会同时瞬间换装，绝对不产生任何翘翘板排异。

2. **事件派发制（Event Delegation）：** Canvas 本身不处理任何具体的业务点击。当玩家点击（x, y）时，内核通过 Even-R 坐标转换公式，算出点击的是哪个格子（q, r），然后化身为一个纯粹的喇叭喊一句："有人点击了 (q:3, r:5) 单元格！" 编辑器外壳听到这个广播，立刻去改地形；战场外壳听到这个广播，立刻拉取移动范围。两者的业务逻辑在物理文件上彻底各归各家。

### 🚨 三、跨功能关联梳理：地图大一统对其他模块的碰撞反应

#### 关联 1：对刚才确立的"不可变地图沙盒（剧情战役）"的无缝对接 🧭

**协同逻辑：**
- 当在地图编辑器里时，Canvas 内核绑定的数据源是 `map-service`（3003）直接读出来的只读 `TemplateJSON`。
- 当在真正对战里时，Canvas 内核绑定的数据源则是 `combat-service`（3004）存在 PostgreSQL 里的那一局动态 `BattleStateSandbox`（深拷贝沙盒）。
- **结果：** 内核不需要知道自己是在打游戏还是在编地图，它只负责看盘下菜。

### 📝 三、深度推演：一个词条多组"定状补"语句的动态叠加机制

**示例词条：【稳定射击特长】（包含两组定状补语句）**

**🟢 语句一（代价与静态加成层）**
- 【主谓宾】：我（主）攻击（谓）左上第4格的目标（宾）。
- 【定语（针对主语的限制）】：主语 `CONSUME(MOVE_ACTION)`（舍弃这回合的移动行动）。
- 【状语（掷骰环节）】：`DICE_ROLL(0)`（静态判定，不摇骰子，100% 触发）。
- 【补语（带来的结果）】：主语触发 `BUFF(命中率, +20%)`。

**🟢 语句二（动态随机暴击层，接续同一个主谓宾）**
- 【定语】：无（只要满足语句一即可）。
- 【状语】：运行时动态执行 `DICE_ROLL(1d6) === 6`（掷出了六点骰子）。
- 【补语】：本次攻击威力触发 `BUFF(DAMAGE_ENERGY, +5)`（使这次攻击增加 5 点能量伤害）。

**🔴 语句三（潜在的炸膛负面层，并发判定）**
- 【定语】：无。
- 【状语】：运行时动态执行 `DICE_ROLL(1d6) === 1`（意外掷出 1 点）。
- 【补语】：主语触发 `BUFF(CURRENT_ENERGY, -2)`（武器过热，反噬扣除自身 2 点能量）。

**微服务协同机制：** 当 3004 战斗引擎执行到这个技能时，`skillExecutor.cjs` 会把这三组"定状补"串联扔进循环：先扣移动力 → 挂上命中 Buff → 摇骰子 → 根据骰子数字同时分流触发语句二的伤害加成或语句三的过热扣能。玩家在前端看到的是一气呵成的连击体感。

## 🛰️ 首席架构师补遗：四大隐形骨架功能

### 🛠️ 1. 🎚️ 词元词条的"动态层叠与互斥池"（Clash & Stack Manager）

**缺失功能：** 在第七章里完美设计了"一个词条拥有多个定状补语句"。但漏掉了一个硬核 TRPG 频繁出现的场景：**词条与词条之间的冲突与层叠（Buff 覆盖逻辑）**。

**举例体感场景 A（层叠）：** 机甲开启了技能"专注射击"（伤害+5），同时战场上踩在了"高地地形"（伤害+2）。底层引擎怎么知道这两个补语是应该叠加成（+7），还是只取最高值？

**场景 B（互斥/免疫）：** 武器带有的词条是 `AP_ROUND`（无视防御），而防守方机甲带有的词条是 `SHIELD_PROT`（免疫任何无视防御效果）。

**架构师方案（必须追加）：** 在 `shared-kernel` 的词元定义中，必须增加一个"**优先级与互斥矩阵（Priority Matrix）**"。每一个补语动作（BUFF）都有一个层叠权重。当算伤管道（`damagePipe.ts`）运行时，会先拉取攻防双方的所有词条，扔进这个矩阵里进行过滤、去重、免疫判定，最后吐出纯净的数值，防止多词条由于交织触发引发计算死锁。

---

### 🛠️ 2. ⏳ 战局沙盒的"时光回溯器"（Action Log & Replay Engine）

**缺失功能：** 既然要支持 5-10 秒延迟的微信小程序观战，并且还要防止玩家中途断线重连（PVP 核心痛点），那数据库（PG库）里就绝对不能只存一个"当前的最新状态"。

**架构师方案（必须追加）：** 必须在 `mecha-combat`（3004）底层建立一个"**事件溯源（Event Sourcing）**"机制。做法：玩家在局内的每一次移动、每一次摇骰子（DICE_ROLL）结果、每一发技能造句，都会作为一条不可变的日志（ActionLog）物理写入数据库。

**收益：**
- **断线秒连：** 玩家打着打着掉线了，重新连进房间，核心引擎只需要把这局的所有 ActionLog 从头到尾在内存里快速"重放（Replay）"一遍，5毫秒内就能 100% 完美还原他掉线前的战场残局。
- **观战流天然适配：** 3005 端口的观战缓冲，只需要按照 ActionLog 的时间戳，每隔 5 秒向微信小程序吐出一条历史日志，小程序前端就能完美复刻一模一样的动态画面，连录像带文件都不用存！

---

### 🛠️ 3. 🛡️ UGC 内容的安全沙盒与"毒词条过滤器"（Content Jail）

**缺失功能：** 在四级权限里提到：管理员可以审核玩家上传的技能词条和自定义地图。但"人工审核"是有延迟的。如果一个坏脾气的普通玩家，在技能编辑器的"文生形"描述里输入了大量违规、辱骂词汇，或者在自定义 JSON 地图里写了一个死循环句子（例如定语是"无限消耗自己的移动力"），这会直接轰塌服务端算力。

**架构师方案（必须建议）：**
- **词法敏感词过滤（Clean Pipe）：** 在 `backend-gateway` 接收到玩家提交的文本或提示词时，前置过一遍敏感词本地字典，直接熔断不健康的内容。
- **抽象语法树（AST）死循环检测：** 在 `skillExecutor.ts` 动态解析定状补句子前，增加一个最大循环断言上限（Max Loop Step = 10）。一旦发现某个词条的条件判定连续执行了 10 次都没有跳出，断言机立刻触发"安全隔离（Sandbox Jail）"，判定该词条非法并强行下线，保护服务器不被玩家的"逻辑炸弹"烧毁。

### 🛠️ 4. 📦 规则包的"一键换装资产热更新"（Asset & Rule Hot-Swap）

**缺失功能：** 终极野心是"换套数据就能复刻所有 TRPG / 换个皮肤就能变成奇幻战棋"。但如果每一次换游戏，都需要登录腾讯云去修改代码、跑 `docker compose build` 冷启动，这就称不上是"生成器系统"，只能叫"多套项目混跑"。

**架构师方案（必须追加）：** 将整个系统的核心彻底解耦成"**引擎壳（Core Engine）**"与"**规则资产包（Rule Mod Pack）**"。
- **资产热更新：** 设计一个 `RuleManifest.json` 的上传网关。当想玩《战锤40K》时，直接在 Dominator 后台上传对应的 Zip 压缩包（里面包含战锤的词元配置、属性别名、机甲/士兵的 16 帧切图）。
- **内存无缝换装：** 前端 Canvas 内核（`HexGridCanvasEngine.vue`）和后端的断言机检测到新清单后，自动在内存中切换 KV 映射字典，100% 做到不需要重启任何 Docker 容器，整个网站秒变跨时代新游戏！
