## 〇、总体结论

这份 To-Do List 2.0 描述的是一套 **WebSocket 实时多人 + 四级权限（Dominator/GM/Player/Visitor）+ 战争迷雾 + 隐匿/奇袭** 的联机对战重构。但经过对当前项目代码的核对，**约 70% 的能力已在 Phase 29 等迭代中以不同命名/结构建成**。

直接"按阶段逐一攻克"会导致：
- 重复造轮子（房间/整备/stealth/迷雾已有实现）；
- 与既有实现冲突（双 stealth / 双 AP / 双迷雾状态机混乱）；
- 部署面扩大、维护双份逻辑。

建议采用 **"复用优先 + 增量补齐"** 策略（见第五节）。

## 二、我"不明晰"、需澄清的点

1. **角色命名映射**：报告用 `Dominator/GM/Player/Visitor`，现有 `UserRole` 是 `USER/REFEREE/ADMIN/DOMINATOR`（`shared-kernel`）。"GM" 指 `REFEREE` 还是新增？"Visitor" 是"未进房的观战者"还是新角色？
2. **`dean147` 硬编码 Dominator**：是示例占位，还是确实要锁死该用户名？现有 DB 已有 `DOMINATOR` role，硬编码 username 是安全反模式。
3. **战争迷雾语义**：1.3 的"按角色删 stealth 节点"是要**替换**现有 `fog_of_war` 战场级开关，还是**叠加**？
4. **Stealth 双轨**：4.1 的"玩家手动点击隐匿/消耗 AP"是要**复用**现有 `enter_stealth` 效果通道，还是**另开**手动 stealth（避免与词条 stealth 冲突）？
5. **联机 vs 单机模型**：现有 `combat` 是单 `battleId` REST + `activeFaction` 轮转（攻击→防守→偷袭）。报告的"多玩家各控一 faction 实时"是否要**取代**轮转模型？还是 REST 管单机、WebSocket 管联机并存？
6. **AP 消耗类型**：现有 AP 是**三类** `MOVE/ATTACK/DEFEND`（`battleStateFactory`）。4.1"消耗 2 AP"、4.2"预支剩余 AP" 指哪类？
7. **联机对战是否就是 Phase 29 的 `online-battle-service`(3006)**？若是，应复用房间/匹配而非重写。
8. **战报流数据来源**：掷骰结果经 WebSocket 广播，还是随 REST 响应返回？现有 `DiceService` 产出是否已在 `/attack` 回包里含 dice details？

## 三、与现有项目可能冲突 / 重复的地方（高风险）

**① 双 Stealth 机制并存（最危险）**
现有 stealth 是**词条/技能效果**：`enter_stealth` 带 `duration`、`stealth_ambush`（隐身攻击加伤）、`stealth_camouflage`（闪避）、`stealth_break`（暴露），且 `ConditionEvaluator` 白名单里的 `requires_stealth` 直接读 `unit.stealth`（`skillExecutor.cjs:242`）。报告 4.1 把 stealth 改成"玩家手动、消耗 AP、普攻即解除"的**状态机**。若两套并存：`unit.stealth` 的赋值/清除语义会打架，既有技能触发条件可能误判。必须二选一或明确分层。

**② 双 AP 模型冲突**
报告用单一"AP"概念（"消耗 2 AP""预支剩余 AP"），但现有是 `MOVE/ATTACK/DEFEND` 三类 + `markStandbyIfDone` 待机判定（`battleStateFactory`）。不定义 stealth/overwatch 消耗哪类 AP，会破坏现有待机/行动点结算。

**③ 双战争迷雾语义**
`combatResolver` 的 `fog_of_war` 是**战场级全有/全无**开关（`battles.js:41` 建场时设）；报告 1.3 是**角色级 stealth 节点剔除**。同名不同义，并存会混乱。

**④ `dean147` 硬编码 vs 现有 role 体系**
`rooms.ts:41` 已用 `requireRole` 限制 `referee/admin/dominator`。报告在连接参数里硬把 `username==='dean147'` 覆写为 Dominator，既绕过 DB role，又埋安全雷（任何人自称 dean147 即得最高权）。应改为读取 `req.auth.role`。

**⑤ GM 抽屉 vs 现有骰子工坊**
`DiceConfigView.vue`（`/dice-config`）已能热更新 `rollMult/critThreshold` 等全局参数。报告 3.3 的 GM 抽屉"实时调奇袭伤害倍率"会新增参数且与现有页面功能重叠，造成"两处调参"分裂。

**⑥ 宪法红线需守住**
报告全局指令"前端只读/指令下发、权限后端校验"与**宪法 v2.0 数据/视图解耦**一致（✅）。但任务 3.1 抽 Pinia、3.2 浮动底栏/观战层，须遵守：Canvas 是单向管道终点、等距变换走 `hexUtils`、`NewBattlefieldSelector` 必须 planar 恒等变换。新增的"全屏 WARNING 遮罩"属浮动层（z-index 高于 Canvas，pointer-events 按需），合规。

## 四、完成后可能存在的问题 / 风险

1. **跨容器状态一致性（架构硬伤）**：报告假设 WebSocket 广播 `battleState`，但当前战斗态在 **gateway 容器内内存**（`reactionHandlers` 注释"仅内存态 battleState"），`mecha-comm`(3005) 是独立容器。若 comm 直接广播自己持有的 state，会与 gateway 真实 state **分裂**。报告未提跨容器状态共享（Redis/DB/消息总线）。
2. **多人并发 vs 轮转**：现有 `activeFaction` 门控 `move/action`。若多玩家实时各控一 faction，轮转模型需重构为"每 faction 一连接"，否则会出现"非自己回合也能操作"或"锁死"。
3. **强制暂停全场（4.2）**："全场画面强制暂停"需全局 pause 锁；REST 轮询下客户端仍可能发指令，必须服务端在 paused 时拒绝命令，否则 pause 形同虚设。
4. **AP 预支无回收**：4.2"预支剩余 AP 设 overwatch"，若敌方永远不过 zone，预支 AP 是否退还？报告未定义，易成"死锁 AP"。
5. **战报透明性的数据契约**：要求"无论输赢显示掷骰"，需 `DiceService.roll` 产出可展示 log 条目并随结果返回/广播。若现有回包不含 dice details，需改 `damagePipe/skillExecutor` 回写结构（影响前端解析）。
6. **重复建设浪费**：1.1/1.2/1.3/2.1/2.2/2.3/4.1 若按报告从零写，会与 Phase 29 已上线代码形成"两套房间/两套 stealth/两套迷雾"，后续维护双份逻辑。
7. **部署影响面**：新增 WebSocket 鉴权/fog 逻辑若在 `mecha-comm`，需重建 `mecha-comm`；若动 gateway 战斗路由，需重建 `mecha-gateway`。注意**绝不动 `mecha-battle-db`**（红线），且前端改动需服务器 build（红线 AP-2）。
