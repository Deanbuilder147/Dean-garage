## 三、与单位编辑器 / 战场攻击系统的联动核查

### 3.1 词条 → 战场技能链路（✅ 通畅）

```
单位编辑器 (NewUnitEditorView.vue)
  └─ SkillsEditor 部件技能槽 → unit.skills[{name,type,attribute,effect,range,...}]
        ↓
战场 (NewBattleView.vue)
  ├─ glossarySkills ← glossary-skill-config.json (GlossaryHub 编辑的词条库)
  ├─ 战术面板按 ROLE_SKILLS[role] 分组展示 unit.skills
  └─ 选中技能 → executeUniversalSkill → skillExecutor (combat-service .cjs)
        ↓
伤害结算 damagePipe + DiceService（暴击倍率/投骰倍率全局随机）
```

- 单位编辑器技能名 → 单位 JSON `skills` → 战场 `unit.skills` + `glossarySkills[skill.type]` 匹配 → 调用 `skillExecutor`。**链路通畅**。
- ⚠️ **软关联**：单位编辑器技能 `type` 字段需与词条库词条 `type` 值人工保持一致（靠命名约定，非强外键引用）。建议后续在 SkillsEditor 下拉直接从 `glossarySkills` 拉取词条 key，建立强引用。

### 3.2 作用对象（target）联动（✅ 本次修复）

**修复前断点**：前端输出 `obj.target = {type, filter}`，但后端 `normalizeSkill` 只认 `src.target_scope/target_filter`，导致编辑器设的 `target.type`（如 SELF/AREA_ALLY）被忽略，全部回退 `enemy`。

**修复后**：`normalizeSkill` 新增 `TT_TO_SCOPE` 映射，从 `src.target.type` 派生 `target_scope/target_filter`，并给每个 effect 的 `target_type` 派生 `ef.target_scope`。`skillExecutor` 谓语处理器按 `uf.target_scope` + `unitRoleOf(u)` 判定敌我/落点，现在能正确区分 自身/友/敌/全体。

### 3.3 AOE / 地图炮联动（⚠️ 部分断链）

| 项 | 前端输出 | 引擎消费 | 状态 |
|----|----------|----------|------|
| AOE 范围 | `obj.aoe = {center, spread}` | `uf.aoe_radius`(skillExecutor 654/903/1028) | ✅ 本次修复：`aoe.spread → aoe_radius`, `aoe.center → aoe_center` |
| 地图炮六向 | `obj.map_cannon.directions` | `skillExecutor` 搜索 0 命中 | ❌ 引擎不消费 |

**地图炮断链说明**：`HexCanvasEditor` 绘制的"地图炮六向"图层数据（`directions: {left,right,up,...}`）会被编译保存，但 `skillExecutor` 当前**完全不读取 `map_cannon`**，因此战场中地图炮的范围命中判定不生效（仅前端可视化）。该字段本次已透传进 `normalizeSkill.out.map_cannon` 供未来接入，但**命中判定逻辑需另行开发**（超出本次"显示+引用"范围，列为待办）。

## 七、权限矩阵驱动鉴权改造方案（新增，2026-08-04）

### 7.1 背景与决策

经核查，后台「权限与用户」界面（`AdminPermissionsView.vue`）与等级-功能权限矩阵（`feature_permissions` 表 + `admin.ts` 的 `resolveRoleFeatures`）**已存在但未真正挂上业务接口**。所有写接口（glossary/units/maps）仍硬编码 `isAdminOrAbove = role === ADMIN || role === DOMINATOR`，导致在后台给 referee 勾选 `glossary.edit` 后，referee 保存词条仍被 403。

**用户决策（已确认）**：
1. **要**把矩阵驱动鉴权真正接上业务接口。
2. **dominator 自身仍硬编码永远拥有全部权限**（作为逃生通道，且不参与矩阵回退）。

### 7.2 鉴权现状（改造前）

| 写接口 | 当前鉴权 | 问题 |
|--------|----------|------|
| `glossary POST /config`（L203） | `isAdminOrAbove(role)` 硬判断 | 不读矩阵，referee 即便勾选 `glossary.edit` 仍 403 |
| `glossary POST /import-excel`（L270） | `requireAdmin`（旧数值 permission<3） | 仅认旧 permission 字段，与矩阵脱节 |
| `glossary POST /import-apply`（L313） | `requireAdmin` | 同上 |
| `glossary PUT /hub-config/:key`（L430） | `isAdminOrAbove(role)` | 同上 |
| `glossary DELETE /hub-config/:key`（L462） | `isAdminOrAbove(role)` | 同上 |
| `units` 写接口（L67/L419 `computeVisibility`） | `isAdminOrAbove` 控制 is_public/review_status | 矩阵无法让 referee 直接发布 |
| `maps` 写接口（L21 `computeMapVisibility`） | `isAdminOrAbove` | 同上 |
| `feature_permissions` 表 | `admin.ts` 内 `resolveRoleFeatures` 仅用于展示/回写 | **无业务接口消费** |

### 7.3 改造方案

#### 7.3.1 抽出共享权限查询函数

`resolveRoleFeatures` 当前是 `admin.ts` 的私有函数，需抽为可被路由层复用的模块级函数（建议放 `src/services/featurePermissions.ts` 或 `src/middleware/auth.ts` 内导出），供各写接口调用：

```ts
// src/services/featurePermissions.ts（新增）
import { get, run } from '../db/sqlite.js';
import { DEFAULT_FEATURE_PERMISSIONS } from '../routes/admin.js'; // 或抽到 shared

/** 读取某等级当前启用的功能 key 数组（缺表行回退默认并落库，幂等） */
export function resolveRoleFeatures(role: string): string[] {
  const row = get('SELECT enabled FROM feature_permissions WHERE role = ?', [role]) as any;
  if (row && row.enabled) {
    try { return JSON.parse(row.enabled); } catch { /* 脏数据回退 */ }
  }
  const def = DEFAULT_FEATURE_PERMISSIONS[role] || [];
  run('INSERT OR REPLACE INTO feature_permissions (role, enabled) VALUES (?, ?)', [role, JSON.stringify(def)]);
  return [...def];
}
```

> 注意：为避免循环依赖，建议把 `FEATURE_CATALOG` / `DEFAULT_FEATURE_PERMISSIONS` 抽到独立常量模块（如 `src/constants/features.ts`），`admin.ts` 与 `featurePermissions.ts` 共用。

#### 7.3.2 新增 `requireFeature` 中间件（`auth.ts`）

> ⚠️ **性能隐患与优化（用户补充）**：中间件每请求同步执行 `resolveRoleFeatures(role)` 会触发一次 SQLite `SELECT`（地图/词条编辑频刷时产生不必要 IO）。
> **优化**：在 `featurePermissions.ts` 内加一层进程内缓存，并在后台保存权限矩阵时失效对应 role。

`featurePermissions.ts` 增加缓存层：

```ts
// src/services/featurePermissions.ts（缓存层，与 resolveRoleFeatures 同文件）
const _featureCache = new Map<string, string[]>(); // role -> enabled[]
const _cacheSeq = new Map<string, number>();        // role -> 版本号（乐观失效）

export function clearFeatureCache(role?: string): void {
  if (role) { _featureCache.delete(role); _cacheSeq.delete(role); }
  else { _featureCache.clear(); _cacheSeq.clear(); }
}

export function resolveRoleFeatures(role: string): string[] {
  const cached = _featureCache.get(role);
  if (cached) return cached;
  const row = get('SELECT enabled FROM feature_permissions WHERE role = ?', [role]) as any;
  let enabled: string[];
  if (row && row.enabled) {
    try { enabled = JSON.parse(row.enabled); } catch { enabled = undefined; }
  }
  if (!enabled) {
    enabled = DEFAULT_FEATURE_PERMISSIONS[role] || [];
    run('INSERT OR REPLACE INTO feature_permissions (role, enabled) VALUES (?, ?)', [role, JSON.stringify(enabled)]);
  }
  _featureCache.set(role, enabled); // ← 命中缓存，避免下次查 DB
  return enabled;
}
```

`AdminPermissionsView.vue` 保存逻辑（后台 `admin.ts` 的 `PUT /api/admin/permissions`）在 `persistChanges` 落库后调用 `clearFeatureCache(role)`，保证矩阵修改即时生效、且不影响其他 role 的缓存。

```ts
// admin.ts PUT /api/admin/permissions 落库成功后
clearFeatureCache(role);
```

```ts
import { resolveRoleFeatures, clearFeatureCache } from '../services/featurePermissions.js';
import { UserRole } from '@mecha/shared-kernel';

/**
 * 功能权限中间件：除 dominator 硬编码永远放行外，其余等级查 feature_permissions 矩阵。
 * @param featureKey 功能键，如 'glossary.edit' / 'unit.publish' / 'map.create'
 */
export function requireFeature(featureKey: string) {
  return (req: Request, res: Response, next: NextFunction): void => {
    if (!req.auth) {
      res.status(401).json({ error: ErrorCode.AUTH_TOKEN_MISSING, message: '请先登录' });
      return;
    }
    const role = (req.auth.role || UserRole.USER) as UserRole;

    // ★ dominator 硬编码永远拥有全部权限（逃生通道，不参与矩阵回退）
    if (role === UserRole.DOMINATOR) {
      next();
      return;
    }

    const enabled = resolveRoleFeatures(role);
    if (!enabled.includes(featureKey)) {
      res.status(403).json({
        error: ErrorCode.ROLE_FORBIDDEN,
        message: `权限不足：当前等级未开放「${featureKey}」功能（请在后台「权限与用户」由主宰开启）`,
      });
      return;
    }
    next();
  };
}
```

**units/maps 的 `computeVisibility` 改造示例**（保留 dominator 永远放行语义）：

```ts
function computeVisibility(role: string, requestedPublic: boolean): { is_public: number; review_status: string } {
  // dominator 硬编码永远放行
  if (role === UserRole.DOMINATOR) {
    return { is_public: requestedPublic ? 1 : 0, review_status: 'approved' };
  }
  const enabled = resolveRoleFeatures(role);
  // 拥有 publish 功能 → 直接 approved；仅 create → pending；否则锁死
  if (enabled.includes('unit.publish')) {
    return { is_public: requestedPublic ? 1 : 0, review_status: 'approved' };
  }
  return { is_public: 0, review_status: 'pending' };
}
```

### 8.2 优化方案：为 skillExecutor.cjs 补齐六向地图炮判定

判定逻辑不复杂，等价于把 `aoe_radius` 的"圆心 + 半径"替换为"施法者/目标中心格 + 方向相对向量点集"：

```cjs
// skillExecutor.cjs 新增 _resolveMapCannonTargets(caster, target, skill)
function _resolveMapCannonTargets(caster, target, skill) {
  const cannon = skill.map_cannon;
  if (!cannon || !Array.isArray(cannon.directions) || !cannon.directions.length) return null;

  // 1. 计算施法者→落点的方位（六向之一）
  const dir = computeDirection(caster.q, caster.r, target.q, target.r); // 返回 'right'/'rightup'/...
  const vecSet = cannon.directions.find(d => d.dir === dir) || cannon.directions[0];
  const base = (cannon.anchor === 'target') ? target : caster; // 以施法者或落点为中心格

  // 2. 把相对坐标点集加到中心格，导出被命中的六角格数组
  const hitCoords = (vecSet.points || []).map(([dq, dr]) => [base.q + dq, base.r + dr]);
  // 3. 与 aoe_radius 同等效力：交由现有 AoE 落点解析器统一处理 (hitCoords 即命中格)
  return hitCoords;
}
```

> ⚠️ **数据格式兼容（高危 Bug，用户补充）**：前端 `JsonCompilerPanel.vue` L256 导出地图炮时写法为 `plain[dir] = arr.map(c => ({ q: c.q, r: c.r }))`，即 `directions[dir]` 存的是**绝对网格对象数组** `{q, r}`，且画布以 `CENTER = (8, 8)` 为锚点绘制。若直接 `(vecSet.points || []).map(([dq, dr]) => ...)` 解构，**dq 会被解构成整个 `{q: 10, r: 7}` 对象，计算结果直接沦为 NaN**。必须在解析时做相对坐标换算 + 格式容错：

```cjs
const CENTER_Q = 8, CENTER_R = 8; // 对齐 HexCanvasEditor 画布中心锚点

const hitCoords = (vecSet.points || []).map(p => {
  // 兼顾「对象 {q, r}」（前端 HexCanvasEditor 导出格式）与「数组 [dq, dr]」（人工/迁移格式）两种编译输出
  const dq = Array.isArray(p) ? p[0] : (p.q - CENTER_Q);
  const dr = Array.isArray(p) ? p[1] : (p.r - CENTER_R);
  return [base.q + dq, base.r + dr];
});
// 仅保留合法格（过滤 NaN / 非有限值）
const safeHit = hitCoords.filter(([q, r]) => Number.isFinite(q) && Number.isFinite(r));
```

## 九、fixed_rate_multiplier 死字段落地（隐患3）

### 9.1 现状评估（已执行核查，修正原假设）

> ⚠️ **落点纠错（执行阶段发现，2026-08-04）**：原 9.2 假设"在 `damagePipe.cjs` 接入"是**错误落点**。实际伤害结算链路如下：
> - `skillExecutor._executeAttackSkill`（L363）取 `const baseDamage = uf.base_damage || uf.damage_modifier_precise || 0`，**自行走 rollMult/机动/抗性公式，完全不调用 `damagePipe.calculate`**。
> - `damagePipe.calculate(config)`（`damagePipe.cjs` L431 `baseDamage = attacker.attack || 10`）是**另一条独立路径**（被 `effectExecutor` 等直接调用），技能伤害不经此。
> - `normalizeSkill`（`skillContract.cjs` L203）产出 `uf`：`out.base_damage = num(src.base_damage, 0)`，来自词条**顶层** `base_damage`；而 `fixed_rate_multiplier` / `flat_value` 是 **effect 维度**字段（`src.effects[].fixed_rate_multiplier`，如 `glossary-skill-config.json` L189/L628），`normalizeSkill` **未**提取到 `uf` 顶层、也未在 `base_damage` 计算里消费。
>
> **正确落点**：`fixed_rate_multiplier`/`flat_value` 必须在 **`skillExecutor._executeAttackSkill`** 计算 `baseDamage` 时接入，且需从 `uf.effects`（damage 类 effect）读取 —— 因为该字段位于 effect 维度，而非词条顶层。

### 9.2 优化方案：在 skillExecutor 攻击谓语接入倍率（含武器加成）

公式（与用户补充一致）：

$$
\text{EffectiveBase} = \max(0,\ \text{AttackerStat} \times \text{fixed\_rate\_multiplier} + \text{flat\_value})
$$

其中 `AttackerStat` = 机体属性 + 当前武器面板加成（见武器加成说明）。

```cjs
// skillExecutor.cjs _executeAttackSkill，替换原 L363 的 baseDamage 计算
const attackType = uf.attack_stat === 'ranged' ? 'ranged' : 'melee';

// 从 effect 维度读取固定倍率/固定值（fixed_rate_multiplier 是 effect 字段，非词条顶层）
const dmgEffect = (uf.effects || []).find(
  e => e.type === 'damage' || e.fixed_rate_multiplier != null || e.flat_value != null
);
const frm = dmgEffect ? Number(dmgEffect.fixed_rate_multiplier) : NaN;
const fixedMult = (Number.isFinite(frm) && frm > 0) ? frm : 1.0;   // 未配置/未传 → 1.0
const flat = dmgEffect ? (Number(dmgEffect.flat_value) || 0) : 0;

// legacyBase = 词条顶层 base_damage，已含网关侧 getEquipmentAttackStat 注入的武器攻击力
// （见 backend-gateway/src/routes/combat.ts L1516），故 ×fixedMult 自动覆盖武器部分，
// 无需在 skillExecutor 内再拆 unit.equipment.weapon。
const legacyBase = Number(uf.base_damage) || Number(uf.damage_modifier_precise) || 0;

// 双定义优先级：若 effect 配置了倍率/固定值，则用「legacyBase × 倍率 + 固定值」覆盖；
// 否则沿用历史 legacyBase（向后兼容，零回归）。
const baseDamage = (dmgEffect && (Number.isFinite(frm) || flat !== 0))
  ? Math.max(0, Math.round(legacyBase * fixedMult + flat))
  : legacyBase;
```

> ⚠️ **武器加成乘算（用户补充，已核实 + 落点优化）**：原 `baseDamage` 仅取 `uf.base_damage`（词条顶层静态值）。经验证 `backend-gateway/src/routes/combat.ts` L1516，网关初始化单位技能时**已将武器攻击力经 `getEquipmentAttackStat` 注入 `uf.base_damage`**。因此倍率直接作用于 `legacyBase`（已含武器加成）即可让高阶武器吃满 `fixed_rate_multiplier`，**无需在 skillExecutor 内重新拆 `unit.equipment`**——方案比初版更简洁且无运行时结构依赖风险。
>
> ⚠️ **双定义优先级（执行新增）**：词条顶层 `base_damage`（静态值）与 effect 维度 `fixed_rate_multiplier×面板+flat_value`（动态式）是两种定义基础伤害的方式。为避免双重计算，约定：**只要该技能任一 damage effect 配置了 `fixed_rate_multiplier`（>0）或 `flat_value`（≠0），即以动态式结果覆盖 `uf.base_damage`**；否则沿用历史静态 `uf.base_damage`。这保证了未配置 effect 倍率的旧词条结算值完全不变。

**注意**：
- `weapon` 字段路径以 `unit.equipment.weapon` 为准；若运行时装备结构为 `unit.equipment` 直接平铺 `melee_bonus`，实施时按真实结构微调取值（可在组装 unit 时统一归一化）。
- `fightService`/网关组装 `unit` 时须确保携带 `equipment.weapon`（damagePipe L75 注释已确认 attacker 含 equipment）。
- 默认 `1.0` + `Math.max(0, ...)` 保证历史未配置词条结算不变，零回归风险。

**验收**：
- 配置某 attack 词条 effect `fixed_rate_multiplier=1.5, flat_value=0` → 靶场基础伤害较未配置提升 50%。
- 手持高阶武器施放该词条 → 伤害包含武器加成被 1.5× 放大（验证武器面板已纳入）。
- 未配置 effect 倍率的旧词条（如 `glossary-skill-config.json` 中 `fixed_rate_multiplier: null` 的）结算值不变。
