> 整合来源：
> 1. 《固定画布与平顶六边形架构变更影响评估报告.md》（以下简称「报告」）
> 2. 关于"伪 3D 是否受平顶/固定画布影响"的代码级讨论（2026-07-22）
> 3. 用户新增三项需求（编辑器平面化 / 战场略缩图栏 / 战场伪 3D 更立体）
>
> 文档目的：把所有**受影响的程序**及其**必须做的修改**精确列清单，作为实施蓝图。

## 0. 背景与需求总览

### 0.1 报告已规划的两条基础改动
- **【A】固定画布**：地图从 `width × height` 动态尺寸改为固定 `100 × 100` + `cells` 集合（见报告 §4.2 / §4.4 / §4.5 / §4.6 / §4.7）。
- **【B】平顶六边形**：尖顶（Even-R，64×72）切换为平顶（Even-Q，72×64），几何中心、顶点生成、邻居公式全部改写（见报告 §3.2.1 / §4.1 / §4.3 / §4.7 / §4.8）。

### 0.2 用户新增三项需求（本次方案重点）
1. **地图编辑器（NewBattlefieldView）不再使用伪 3D，改为平面顶视。**
2. **战斗场景（NewBattleView）保留伪 3D，但新增一个 2D 地图略缩图栏。**
3. **战斗场景的伪 3D 要"更立体"（2.5D 立体感），而非只是倾斜的平面。**

### 0.3 关键判断（来自之前的讨论，结论已验证）
- 固定画布【A】**完全不碰渲染矩阵**，零伪 3D 风险。
- 平顶六边形【B】**会改伪 3D**，因为六边形的形状、倒角顶点、ISO 校准参数三处都和尖顶耦合，需重校准（报告 §8 风险表 + 之前讨论核实）。
- 编辑器目前**实际在用伪 3D**（其 `isoConfig` 取自 `ISO_DEFAULTS`，并带"3D 视角调校"面板与 `saveViewConfig`），与"平面化"诉求相反，必须改造。

## 1. 需求③「更立体」技术路线分析：前端素材 vs 后端跟进

**结论：以"前端渲染技术"为主，"前端美术素材"为辅；后端基本不需要跟进（仅可选持久化配置字段）。**

### 1.1 现状本质
当前伪 3D 是 `HexGridCanvasEngine.vue` 里一个 **2D 仿射变换**（`ctx.transform(ISO.scaleX, ISO.shearY, ISO.shearX, ISO.scaleY, 0, 0)` 等效）把**扁平的六边形**斜切压扁，营造"躺平在地平面"的错觉。单位是用 `unitSpriteResolver` 画的**平面 PNG 精灵**（7 视图）。本质是一个"倾斜的平面"，没有厚度、没有侧面、没有体积。

### 1.2 路线 A（核心，纯前端渲染）—— 挤出式 2.5D 立柱 ★必须
给每个地形格一个**高度 `height`**，渲染时除顶面外，再画出它的**左右两个可见侧面**（带明暗阴影），形成"立体瓷砖/沙盘"体积感。
- 改动点：`hexUtils.js` 新增 `drawIsoHexColumn(...)`（顶面 + 侧面墙 + 双档阴影）；`HexGridCanvasEngine.vue` 新增 `extrude` 开关，地形缓存按 `UNIVERSAL_TERRAIN_MAP[tid].height` 绘制立柱。
- **不依赖任何后端逻辑**，高度值来自前端已定义的 `UNIVERSAL_TERRAIN_MAP`。
- 这是"更立体"的**唯一必要手段**。

### 1.3 路线 B（增强，前端美术素材）—— 等距精灵图
把单位 PNG 从"正面平面图"换成"带光影的 2.5D 等距机甲图"，并给地形侧面贴材质图（岩石/金属纹）。
- 改动点：`unitSpriteResolver.js` 资产命名/锚点扩展；新增贴图资源文件（`/assets/sprites/...`、`/assets/textures/...`）。
- 后端只负责**静态文件托管**（现有 `/assets` 或 `/api/hangar/units/sprites` 已支持），**无新逻辑**。
- 这是"看着更精致"的**可选增强**，不是机制必需。

### 1.4 路线 C（附加，纯前端渲染）—— 光影/地面阴影
单位脚下加投影椭圆、地形顶面加高光渐变、依据 `height` 做环境遮蔽。纯前端。

### 1.5 后端到底要不要动？
- **核心立体效果（路线 A/C）：零后端改动。**
- **唯一可选的后端动作**：把"挤出默认高度 / 是否开启 extrude"持久化进 glossary 配置 JSON（复用现有 `_view` 键，见 §4.9），属于**纯加字段**，后端只存 JSON、不解析、不影响任何战斗逻辑。
- **地形每格高度**：建议直接放在前端 `UNIVERSAL_TERRAIN_MAP`（已是前端真相源），不进 DB，避免前后端双源。若未来要"地图级自定义地形高度"，再在 `maps` 表加 `terrain_height_overrides` 可选 JSON 字段（低优先级）。
- ⚠️ **绝不涉及**：战斗结算、移动寻路、碰撞、坐标契约等后端逻辑。

> **给小组的明确答复**：从**前端渲染（路线 A）入手**就能拿到"更立体"的效果；要更精致再补**前端素材（路线 B）**；**后端无需跟进**（除非你想把立体参数存进配置，那也只是加个 JSON 字段，不改逻辑）。

## 3. 逐项修改清单（按程序）

### 3.1 F1 `hexUtils.js`

**(a) 平顶几何（报告 §4.1 / §3.2.1）**
- 保留 `pointyTopCenter`，新增 `flatTopCenter(q, r, radius, h, v)`。
- 新增顶层开关 `export const FLAT_TOP = true`（或导出 `getHexLayout()`），供引擎与顶点生成统一读取，避免尖顶/平顶两套分支散落。
- `pointyTopToHex` 逆变换需同步支持平顶（`flatTopToHex`）。

**(b) 顶点生成适配平顶（报告 §4.8 + 之前讨论的坑）**
- `drawHexPathDeformed` / `drawIsoHexPath` 的顶点基准角必须随 `FLAT_TOP` 切换：
  - 尖顶：`angle = (π/3)*i - π/2`（顶点在上下）。
  - 平顶：`angle = (π/3)*i`（顶点在左右）。
- ⚠️ **倒角顶点轴必须同步改**：当前 `topFlat/bottomFlat` 压的是上下两个尖点（见 `drawHexPathDeformed` 第 0、3 顶点）；平顶后压的应是**左右**两个尖点，否则瓷砖会被"横着踩扁"而非"斜俯视"。这是之前讨论明确点出的坑。

**(c) 编辑器平面配置（需求①）**
- 新增 `export const PLANAR_CONFIG = { shearX: 0, shearY: 0, scaleX: 1, scaleY: 1, rotation: 0, topFlat: 0, bottomFlat: 0 }`。
- 平面模式下引擎用此配置，`drawIsoHexPath` 的 `isoTransformPoint` 退化为恒等变换 → 顶视平面六边形，点击/悬停逆变换直接还原，无副作用。

**(d) 地形高度表（需求③ 路线 A）**
- 在 `UNIVERSAL_TERRAIN_MAP` 每个地形加 `height` 字段（屏幕深度像素，默认约 `10`）：`mountain: 22, fortress: 16, wall: 24, water: 0, plain: 8, crater: 4, lunar: 8 …`。
- 高度用于挤出立柱；`water` 高度 0 表示"贴地水面"。

**(e) 挤出绘制函数（需求③ 路线 A）★新增（定义于 `hexDraw.js`，见 §3.1g）**
- 新增 `drawIsoHexColumn(ctx, cx, cy, iso, height, topColor)`（落位 `hexDraw.js`）：
  1. 顶面 = 现有 `drawIsoHexPath(...)`（随 `FLAT_TOP` 顶点）。
  2. 底面 = 顶面各顶点沿屏幕 Y 轴下移 `height * iso.scaleY`。
  3. 侧面 = 连接"左前棱"与"右前棱"两个四边形（**平顶=左右两面；尖顶=上下两面**，由 `FLAT_TOP` 决定取哪两条边）。
  4. 阴影：左面 `topColor*0.55`，右面 `topColor*0.38`（双档明暗，体积感来源）。
- 画家算法：调用方须按 **r 升序、q 升序**（远→近）绘制，确保近处侧面覆盖远处顶面。

**(f) ISO 参数重校准（报告 §8 / 之前讨论）**
- `ISO_DEFAULTS`（`shearX/scaleY/rotation/topFlat/bottomFlat`）按平顶重新标定初值；战场端仍静默拉 `_view` 覆盖。
- 建议在 `ISO_DEFAULTS` 旁保留旧尖顶值作注释对照。

**(g) 拆出 Canvas 绘制函数到 `hexDraw.js`（架构解耦·轻量版，见 §9）★新增文件**
- 将 hexUtils 中 4 个带 `ctx` 的绘制函数整体迁移到新文件 `frontend/src/utils/hexDraw.js`：
  - `drawHexPath(ctx, cx, cy)`
  - `drawHexPathDeformed(ctx, cx, cy, cellW, cellH, topFlat, bottomFlat)`
  - `drawIsoHexPath(ctx, cx, cy, iso)`
  - `drawIsoHexPathDeformed(ctx, cx, cy, cellW, cellH, topFlat, bottomFlat, iso)`
- `hexDraw.js` 从 hexUtils **仅 import 纯数学**（`HEX_RADIUS`、`HEX_WIDTH`、`HEX_HEIGHT`、`isoTransformPoint`、`FLAT_TOP` 或 `getHexLayout()` 等），自身不含任何坐标/几何推导，只负责"把数学结果画到 ctx"。
- `hexUtils.js` 迁移后**只保留纯数学**（坐标换算、邻居、ISO 正逆变换、地形表、方向），成为真正零依赖、可在 Node 下 headless 单测的核心。
- 所有原调用点改为 `import { ... } from './hexDraw.js'`：
  1. `HexGridCanvasEngine.vue`（`renderTerrainCache` / `renderTerrainInline` 中的 `drawHexPath` / `drawHexPathDeformed` / `drawIsoHexPath` / `drawIsoHexPathDeformed`）；
  2. **`NewBattleView.vue`**（`drawBattleScene` 中的 `drawHexPath`，共 9 处范围高亮描边：移动/攻击/技能/RoyRoy 部署高亮）——⚠️ 此为方案初稿遗漏的既存调用点，若不补则高亮层会整体失效；
  3. §4 草案新增的 `drawIsoHexColumn`。
- ⚠️ **实施时必须同步改 `NewBattleView.vue` 的 import**（仅此一处额外动作），否则阶段 1 合入后范围高亮全空白/报错。
- 新增的 `drawIsoHexColumn`（§3.1e）也**定义在 `hexDraw.js`**（它是绘制函数，不是数学）。

### 3.2 F2 `HexGridCanvasEngine.vue`（渲染内核，最关键）

**(a) 固定画布 + cells 集合（报告 §4.2）**
- `updateVisibleRange()` 当前用 `props.gridData.width/height`（见 L296-301）。改为：边界来自 `gridData.cells` 集合（含 `q,r` 的 Set），`minQ/maxQ/minR/maxR` 由 cells 实际范围计算（固定 100×100 下即 0..99）。
- `updateVisibleRange` 在 L281-302、L465、L698、L707、L754、L796、L815、L827、L849、L894、L930、L955 多处被调用，均需兼容 cells 来源。

**(b) 平顶邻居 / 高亮（报告 §4.3 / §4.7）**
- 移动范围与战斗高亮调用 `getHexNeighbors` 须返回 **Even-Q** 邻居（平顶）。L535-537 的遍历与高亮判定跟随 `FLAT_TOP` 分支。

**(c) 模式开关（需求① + 内核解耦）★新增**
- 新增 prop `mode: 'planar' | 'iso'`（默认 `'iso'`）。
  - `planar`：内部 `isoConfig` 强制 `PLANAR_CONFIG`，跳过挤出，纯顶视。
  - `iso`：沿用传入 `isoConfig`（战场伪 3D）。
- 新增 prop `extrude: Boolean`（默认 `false`）。为 `true` 时地形缓存改走 `drawIsoHexColumn`。

**(d) 地形缓存支持挤出（需求③）**
- `renderTerrainCache`（L463 附近，逐格 L535-537）增加：
  - 读 `UNIVERSAL_TERRAIN_MAP[cell.terrainId].height`；
  - 若 `extrude` 为真，调用 `drawIsoHexColumn` 而非 `drawIsoHexPath`/`drawHexPathDeformed`；
  - 侧面绘制遵守远→近顺序（当前 `r` 外循环、`q` 内循环已是远→近，保持即可）。
- ⚠️ 性能：挤出后每格像素量增大，确保护缓存命中；缓存 key 需包含 `extrude + FLAT_TOP + ISO` 版本，避免脏缓存串味。

**(e) 点击/悬停命中（报告 §4.2 + 需求③）**
- 命中仍以**顶面中心点**做逆变换（`getHexAtEvent`），挤出只在视觉上"加高"，不改逻辑中心 → 点击精度不受影响。需验证 `pixelToHex` 在平顶下仍正确（§3.1a）。

**(f) 暴露接口已足够（需求② 复用）**
- 引擎已 `defineExpose`：`getVisibleRange()`（L864-866）、`centerGrid`（L874）、`getHexAtEvent`、`zoomIn/Out/Reset`、`redraw`、`offsetX/offsetY/scale/ISO`（L868-876）。略缩图栏直接复用，无需新增暴露。

**(g) 内部收拢 `Camera` 对象（架构解耦·轻量版，见 §9）★内部重构**
- 将引擎内散落的视口状态 `offsetX/offsetY/scale`（L142-144）、`ISO`（L150）、`visibleRange`（视口范围）收拢为一个**轻量级 `Camera` 对象**（普通 reactive/plain object，非 TS class）：
  ```js
  const camera = reactive({
    offsetX: 60, offsetY: 60, scale: 1,
    iso: { ...ISO_DEFAULTS, ...props.isoConfig },   // 原 ISO
    viewport: { width: 0, height: 0 }                // 由 canvas 尺寸填充
  })
  ```
- **仅内部重构，外部组件 API 契约不变**：对外仍通过 `defineExpose` 暴露 `getVisibleRange()/centerGrid/zoomIn/Out/Reset/offsetX/offsetY/scale`（L868-876）——这些是对 `camera` 的访问器，父层（`NewBattleView` / `BattleMinimap`）调用方式**完全不变**。
- 收益：略缩图 `BattleMinimap.vue`（§3.5）直接读取 `camera.viewport` + `getVisibleRange()` 即可绘制视口框与跳转，**无需为需求②额外新建相机抽象**。
- ⚠️ 不做更重的相机系统（无惯性/无动画/无 TS 类型），避免过度设计。

### 3.3 F4 `NewBattlefieldView.vue`（地图编辑器，需求①）

**(a) 默认平面化**
- 当前 `isoConfig` 取自 `ISO_DEFAULTS`（`shearX:0.38…`，伪 3D）。改为：编辑器默认传 `:mode="'planar'"`，或 `:iso-config="PLANAR_CONFIG"`。六边形将以顶视平面显示。

**(b) 删除"3D 视角调校"面板与保存（解耦 `_view`）**
- 删除 L111-118 的 `iso-shear-y` 等滑块 UI 与"💾 保存 3D 视角"按钮。
- 删除 `saveViewConfig`（L631-662）：**这是关键解耦**——它把编辑器视角写入后端 `_view`，而战场 L（NewBattleView）读同一个 `_view` 当伪 3D 参数。编辑器平面化后绝不能再覆盖战场的 `_view`。
- 可选：把编辑器自身视图（如 2D 网格间距微调 `spacingH/V`）保留为本地非持久化状态，不写 `_view`。

**(c) 固定画布 UI（报告 §4.4）**
- 移除 width/height 输入框（报告 §4.4），改为固定 100×100 + `cells` 集合；画笔/拾取边界判定改用 `cells` 集合。
- `updateBattlefield`（L713-715 写 `hex_config`）随后端 schema 变化调整字段（见 §3.6 B2）。

**(d) 保留的部分**
- 地形笔刷、地形库编辑（`loadTerrainDefinitions` L334、`saveTerrainConfig` L371）、地图 CRUD 逻辑不变，仅渲染层面平面化。

### 3.4 F5 `NewBattleView.vue`（战斗场景，需求②③）

**(a) 保留伪 3D + 开启挤出（需求③）**
- `isoConfig` 继续读后端 `_view`（含 `shearX/shearY`），并叠加 `:extrude="true"` 传给引擎，启用 2.5D 立柱。
- 单位绘制（`drawBattleScene` / `drawFn`，L426 引入、`L510` 传入）在挤出模式下：
  - 精灵锚点对齐到该格**顶面中心**（而非平面中心），使单位"站"在立体瓷砖上；
  - 增加脚底投影椭圆（`rgba(0,0,0,0.3)`，随 `height` 上移）；
  - 沿用 `unitSpriteResolver` 七视图（L428）。

**(b) 新增 2D 略缩图栏（需求②）★新增组件**
- 模板中引入 `<BattleMinimap :grid-data="gridData" :cells="cells" :units="battleUnits" :engine="hg" />`。

## 4. 「更立体」实施草案（数学起点，可直接编码）

```
// hexDraw.js  （从 hexUtils 拆出，见 §3.1g）
// 仅从 hexUtils import 纯数学：HEX_RADIUS, isoTransformPoint, FLAT_TOP（或 getHexLayout()）
export function drawIsoHexColumn(ctx, cx, cy, iso, height, topColor) {
  // 1) 顶面（随 FLAT_TOP 顶点）
  drawIsoHexPath(ctx, cx, cy, iso)          // 同文件内（hexDraw.js）
  ctx.fillStyle = topColor
  ctx.fill()

  // 2) 侧面：取"前"两条边（平顶=左/右，尖顶=上/下，由 FLAT_TOP 决定）
  const dy = height * iso.scaleY            // 屏幕深度
  const topPts = hexOutlinePoints(cx, cy, iso)   // 顶面 6 顶点（新增小工具）
  const botPts = topPts.map(p => ({ x: p.x, y: p.y + dy }))
  const sideIdx = FLAT_TOP ? [0,1, 3,4] : [1,2, 4,5]  // 可见两侧棱
  for (const [a, b] of [[sideIdx[0],sideIdx[1]],[sideIdx[2],sideIdx[3]]]) {
    ctx.beginPath()
    ctx.moveTo(topPts[a].x, topPts[a].y)
    ctx.lineTo(topPts[b].x, topPts[b].y)
    ctx.lineTo(botPts[b].x, botPts[b].y)
    ctx.lineTo(botPts[a].x, botPts[a].y)
    ctx.closePath()
    ctx.fillStyle = shade(topColor, a === sideIdx[0] ? 0.55 : 0.38)
    ctx.fill()
  }
}
```
- 画家算法：引擎按 `r` 升序 → `q` 升序 遍历（远→近），每格先画侧面再画顶面。
- `shade(color, k)`：把 RGB 乘 `k` 得到明暗。
- 单位阴影：`ctx.ellipse(cx, cy + dy, rw*0.4, rh*0.18, 0, 0, 2π)`，`fillStyle='rgba(0,0,0,0.3)'`。

> 这套草案让 §7.2 第 26 步"视觉校准"不再是凭感觉调滑块，而是有数学起点。

### 3.11 需求④ 地图素材上传与地表纹理（全局地形素材库）

**目标**：在地图编辑器（`NewBattlefieldView.vue`）的「地形库管理」中，为每种地形上传一张素材图；存为全局资源；战场与编辑器预览按 `terrain id` 自动取用 **CanvasPattern 平铺纹理**；未上传素材的地形回退原纯色填充。2.5D 挤出模式下**仅顶面贴图**，侧面墙仍纯色/渐变，留待后续统一边缘美化（不在本轮）。

**选型（已与用户确认）**：
- 素材归属：**全局地形素材库**——按 `terrain id` 上传，所有地图/战场共享；存进全局词条库 `glossary-skill-config.json` 的 terrain 定义。
- 贴图方式：**CanvasPattern 平铺**（`createPattern(img,'repeat')`），抗六边形拉伸变形。
- 挤出贴图范围：**仅顶面**；侧面后续统一边缘美化（独立后续项）。

**为什么可行（实地事实）**：
- 地形定义是**全局**的：编辑器从 `glossaryAPI.getConfig()` 加载（`loadTerrainDefinitions`），经 `saveTerrainConfig()` 写回 glossary 配置（`current.terrains = JSON.parse(JSON.stringify(editableTerrains))`），每条含 `name/color/move_cost/...`。`material_url` 仅是新增可选字段，无需 DB 迁移。
- 后端图片存储已有成熟模式：`units.ts` 用 `multer` 落盘 `/data/images/`（挂载 `gateway_data` volume，镜像重建不丢）+ `/api/units/views/:filename` 静态服务。地形素材完全可镜像此模式。
- 引擎渲染当前用 `UNIVERSAL_TERRAIN_MAP[terrainId].color` 填充（`renderTerrainCache` L348 / `renderTerrainInline` L543）。替换为「材质优先、纯色回退」即可，且按宪法须把材质表**作为 prop 显式传入**。

**数据流向**：
```
编辑器上传 file(+terrainId)
  → POST /api/terrain/upload → 落盘 /data/images/terrains/<terrainId>.<ext>
  → 返回 url /api/terrain/materials/<terrainId>.<ext>
  → 写入 editableTerrains[key].material_url → saveTerrainConfig() 持久化进 glossary 配置
glossary 配置（含 material_url）
  → NewBattlefieldView / NewBattleView 经 glossaryAPI.getConfig() 加载
  → 构建 terrainMaterials:{[terrainId]:url} → 作为 prop 显式传入 HexGridCanvasEngine
引擎 renderTerrainCache / renderTerrainInline
  → 命中材质且已加载：用 createPattern 填充六边形顶面
  → 否则回退 terrainInfo.color（含加载失败/无素材）
```

**后端改动（新增 `routes/terrain.ts`，挂载 `/api/terrain`）**：
- `POST /api/terrain/upload`：`multer` 单文件（字段名 `file`）+ `terrain` 参数；以 `terrainId` 命名**覆盖式**写 `/data/images/terrains/`；返回 `{ ok:true, url:'/api/terrain/materials/<filename>' }`。复用 `units.ts` 的 `imageUpload` 配置（`gateway_data` volume 持久化）。
- `GET /api/terrain/materials/:filename`：静态服务 `/data/images/terrains/:filename`（同 `units.ts` 的 `/views` 静态段）。
- `app.ts` 注册 `terrain` 路由。无需 DB 迁移。

**前端 API client（`src/api/client.js` 增 `terrainAPI`）**：
- `terrainAPI.uploadMaterial(terrainId, file)`：`multipart/form-data` POST，返回 url。（静态 url 即确定地址，无需额外 GET。）

**前端编辑器（`NewBattlefieldView.vue` · 地形库管理 modal）**：
- 每个地形行增加「上传素材」`<input type="file" accept="image/*">` + 缩略图预览；`change` 时调 `terrainAPI.uploadMaterial` → 把返回 `url` 写入 `editableTerrains[key].material_url` → 触发 `saveTerrainConfig()`（自动持久化新字段）。
- 增加「清除素材」按钮（置 `material_url=null`）回退纯色。
- 编辑器预览：加载 glossary 后构建 `terrainMaterials` 传给引擎，编辑器内即可见地表纹理。

**前端引擎（`HexGridCanvasEngine.vue`）**：
- 新增 prop `terrainMaterials: { type: Object, default: () => ({}) }`（terrainId→url）。**宪法：依赖显式传入，禁幽灵函数/读全局 Store**。
- 新增 `materialImageCache: Map<url, HTMLImageElement>` 与 `ensureMaterialImage(url)`：按需 `new Image()`、`src=url`；**必须**在 `img.onload` 回调里标记 `terrainDirty = true` 并 `scheduleDraw()` 重绘（图片加载是异步的，不触发重绘则材质永不上屏）。异步加载完成前渲染分支**自动回退** `terrainInfo.color`，可防白屏/渲染阻塞；加载失败（`onerror`）同样回退纯色并缓存失败态避免反复请求。
- 渲染（`renderTerrainCache`/`renderTerrainInline`）：算得 `terrainInfo` 后，若 `terrainMaterials[terrainId]` 且对应 Image 已 `complete`：
  - `const pat = ctx.createPattern(img,'repeat'); ctx.fillStyle = pat;` 再 `fillHexPath()`（顶面）。CTM 变换下 pattern 随六边形一起变形，天然贴合等距观感。
  - 否则 `ctx.fillStyle = terrainInfo.color`（回退）。
- `watch(terrainMaterials)` → 预加载新 url → `terrainDirty=true` 重渲。
- 顶面/侧面：挤出模式下顶面用 pattern，侧面墙维持 `terrainInfo.color`/渐变（不在本轮做侧面贴图）。

**前端战场（`NewBattleView.vue`）**：
- 既有 `glossaryAPI.getConfig()` 加载后构建 `terrainMaterials`，传给 `<HexGridCanvasEngine :terrainMaterials="...">`。无额外后端改动。

**回退与健壮性**：
- 无素材 / 图片 404 / 加载失败 → 一律回退 `color`，视觉不崩。
- 图案对齐：默认 pattern 原点随画布，跨格可能轻微错位属可接受 v1；后续可借 `DOMMatrix` 对齐，与「侧面边缘美化」归入同一后续项。

**与既有 §3 的关系**：纯增量，不改动平顶/挤出/相机逻辑；引擎仅新增一个 prop + 一个填充分支，风险隔离。

## 8. 当前前端分层结构（地图编辑器 / 战场场景）

> 本节基于实际模板（`NewBattlefieldView.vue` / `NewBattleView.vue` / `HexGridCanvasEngine.vue`）还原 DOM 分层，作为 §3 修改项的定位参考。两个视图**共用同一个渲染内核** `HexGridCanvasEngine`（`.hex-engine-sandbox` 内部一致），差异只在"外层如何摆放它"与"是否注入伪 3D"。

### 8.1 地图编辑器（NewBattlefieldView）— 可滚动纵向文档流

```
.page-container  (flex flex-col, overflow-y-auto)          ← 整页可滚动，非全屏
├─ header.page-header            标题 + 在线状态
├─ div.map-info-bar              地图名 / 格子数 / 尺寸 / 当前画笔 + 保存·导出·新建·删除·加载
├─ HexGridCanvasEngine           主画布（文档流内 inline，宽 100%）
│    └─ .hex-engine-sandbox
│         ├─ .hex-engine-container > canvas.mainCanvas
│         ├─ .slider-panel        双轴平移滑槽（H/V range）
│         └─ .cursor-hint         悬停坐标提示
│     props: :iso-config="isoConfig"（当前=ISO_DEFAULTS 伪 3D）
│            :use-terrain-cache="false"  @cell-clicked="handleEditorBrush"
├─ div.terrain-palette           地形画笔按钮 + [管理]
├─ div.batch-panel               A1:C5 区间批量修改
├─ div.spacing-bar               水平/垂直间距/偏移系数 + ★3D 倾斜X/Y 滑块 + 💾保存3D视角 + 缩放
└─ 模态层 overlay: 新建地图弹窗 / 自定义地形管理弹窗
```

**特征**
- 外层是**普通纵向文档流**，整页可滚动；画布是流内块元素，不是绝对定位。
- 伪 3D 由 `spacing-bar` 里的 `isoShearX / isoShearY` 滑块**实时驱动**（v-model → isoConfig → 引擎重绘），并有"💾 保存 3D 视角"写回后端 `_view`。
- 浮动层**只有模态框**（overlay），无常驻浮动面板。

**对应需求①的改造点（见 §3.3）**
- `:iso-config` 改为 `PLANAR_CONFIG` → 画布退化为平面顶视。
- `spacing-bar` 内 `iso-group` 滑块 + `iso-save-group` 保存按钮整段删除（解耦 `_view`）。
- 其余 DOM 结构（信息栏 / 画笔 / 批量 / 模态）**完全不变**。

### 8.2 战斗场景（NewBattleView）— 全屏绝对定位 + 浮动卡叠加

```
.dm-battle-layout  (flex flex-row, absolute inset-0, w-full h-full)   ← 全屏，不可滚动
├─ .dm-main  (flex-1 flex flex-col, overflow-hidden)                 ← 中央列
│   ├─ .battle-header           标题 / 阶段 / 阵营 / 第 N 轮
│   ├─ .battle-toolbar          缩放 / 部署·选中徽章 / 结束回合
│   ├─ HexGridCanvasEngine      主画布（填充剩余空间，overflow-hidden）
│   │    └─ .hex-engine-sandbox (canvas + slider-panel + cursor-hint，同编辑器)
│   │     props: :draw-fn="safeDrawBattleScene"（父层画单位）
│   │            :iso-config="isoConfig"（伪 3D）  :use-terrain-cache="false"
│   ├─ .map-legend              absolute bottom-left，pointer-events:none  ← 浮动图例
│   ├─ .dice-overlay            模态：手动投骰
│   └─ .floating-card.floating-faction-panel   absolute 可拖拽 ← 阵营单位框
└─ .floating-card.floating-action-panel        absolute 可拖拽 ← 行动面板 / 技能
```

**特征**
- 外层是**全屏绝对定位**（`absolute inset-0`），画布是底层 **base layer**。
- 所有交互 UI（阵营框 / 行动面板 / 图例 / 投骰）是叠在画布上的**浮动卡**，符合"战棋宪法"浮动层规则：z-index 高于 canvas，空白区 `pointer-events:none` 穿透，仅卡片本身接收事件。
- 单位不单独成层：由父层 `safeDrawBattleScene`（经 `draw-fn`）**直接画在同一张 canvas 上**，与地形共享渲染管线。
- 内核 `.hex-engine-sandbox` 与编辑器**完全一致**（同一组件、同一 `.game-canvas-sandbox` 已拆除历史），故 §8.1 的画布内部结构两视图通用。

**对应需求②③的改造点（见 §3.4 / §3.5）**
- 保留 `:iso-config` 伪 3D，并加 `:extrude="true"` 启用 2.5D 立柱（需求③）。
- **新增浮动层** `.floating-card.battle-minimap`：建议置于 `.dm-main` 内、`absolute` 右下角，`pointer-events:auto`（可交互）、z-index 高于 canvas，承载新增组件 `BattleMinimap.vue`（需求②）。它**独立于**引擎自带的 `.slider-panel` 平移滑槽，是额外的一层信息层。
- 其余浮动面板（阵营框 / 行动面板 / 图例）结构**不变**。

### 8.3 分层结构对照表

| 维度 | 地图编辑器 | 战斗场景 |
|---|---|---|
| 根布局 | `.page-container` 纵向文档流、可滚动 | `.dm-battle-layout` 全屏绝对定位、不可滚动 |
| 画布定位 | 流内 inline 块 | 底层 base layer（填充剩余空间） |
| 伪 3D 注入 | `iso-config=isoConfig`（滑块实时调） | `iso-config=isoConfig`（静默读 `_view`）+ 即将加 `extrude` |
| 单位绘制 | 仅地形，无单位 | 父层 `draw-fn` 同 canvas 绘制 |
| 浮动层 | 仅模态框 | 阵营框 + 行动面板 + 图例 + 投骰 + **（新增）略缩图** |
| 共享内核 | `HexGridCanvasEngine` `.hex-engine-sandbox` | 同左 |
| 本轮改法 | 平面化 + 删 3D 滑块（需求①） | 留伪3D + 加挤出 + 加略缩图（需求②③） |

## 9. 架构解耦决策（轻量版 · 风险隔离）

> 本节记录 2026-07-22 经**实地代码核查**后，关于"顺便做架构重组"的最终决断。原则：**解耦方向正确，但本轮只做低风险、与视觉改造同生共死的轻量重构；重型 Driver/Bridge 抽象延后到独立提交。**

### 9.1 实地核查结论（为什么不全盘采纳"重组提案"）
- `hexUtils.js` **并非已纯净**：含 4 个带 `ctx` 的绘制函数（`drawHexPath` L279 / `drawHexPathDeformed` L403 / `drawIsoHexPath` L459 / `drawIsoHexPathDeformed` L483），且被引擎 `renderTerrainCache` 调用 → 要"零依赖"必须先把它们搬走（即 §3.1g）。
- 引擎**已经基本解耦**：宪法红线（L1-9）已禁止 import 状态机/业务字眼，仅通过 `gridData` prop 收数据；`getVisibleRange()` 已 expose（L281）。"侵入业务数据"的假设不成立；略缩图现在就能复用，不必先抽 Camera 类。
- 前端是**纯 JS**（仅后端 1 个 `.d.ts`），提案的 `interface RenderableCell`（TS）会引入构建摩擦，已否决。

### 9.2 采纳项（已写入实施方案）
| 项 | 内容 | 落地位置 |
|---|---|---|
| ✅ 采纳 1 | 拆分 `hexUtils.js`：4 个 draw 函数 + 新增 `drawIsoHexColumn` 迁至 `hexDraw.js`，hexUtils 保持纯数学 | 阶段 1，§3.1g / §3.1e / §4 |
| ✅ 采纳 2 | 引擎内部 `offsetX/offsetY/scale/ISO/viewport` 收为轻量 `Camera` 对象，**不改外部契约** | 阶段 2，§3.2g |
| ✅ 采纳 3 | 需求④ 地图素材上传与地表纹理：全局地形素材库 + CanvasPattern 顶面平铺 + 纯色回退；新增 `routes/terrain.ts` 与引擎 `terrainMaterials` prop | 阶段 5，§3.11 |
| ✅ 采纳 4 | 阶段 1 合入时同步改 `NewBattleView.vue` 的 `drawHexPath` import（初稿遗漏的调用点）+ 删除死代码 `HexGridCanvas.vue` | 阶段 1，§3.1g / §3.8 |

### 9.3 否决 / 搁置项（明确不在本轮）
- ❌ **不引入** `RenderableCell` 数据桥接接口（TS）→ 保持纯 JS，无 TS 构建摩擦。
- ❌ **不引入** Driver/Bridge 可插拔体系（PixiDriver/GodotDriver）→ 引擎已只吃 `gridData` prop，该抽象解决的是当前不存在的问题（YAGNI）。
- ❌ **不提前泄漏** `isBorder`（100×100 掩码边界）等未来字段到核心接口 → 避免过早耦合未定变更。
- ❌ **不做** Godot/C# 侧"零成本复用"设想 → Godot 不跑 JS，"复用"实为数学重抄，收益被提案夸大；Pixi/Phaser 等 JS 系引擎未来若迁移，本轻量解耦（纯 hexUtils + 数据 prop）已足够支撑。

### 9.4 实施节奏与风险隔离（强制）
- 本轮 **Commit 聚焦**于视觉与逻辑闭环：**平顶几何 + 2.5D 挤出 + 编辑器平面化 + 略缩图栏**。
- 两项轻量重构（hexDraw 拆分 / Camera 收拢）**跟随对应阶段同提交**（阶段 1 / 阶段 2，见 §6），不单独成 PR，避免"半吊子解耦"中间态。
- **重型架构演进（Driver/TS 契约）明确排除在本轮之外**，待视觉改造上线稳定后，作为**独立提交/独立 PR** 评估，绝不与之风险叠加。
- 红线：平顶 + 挤出 + 伪 3D **必须同一提交**（§6 阶段 3），不要把架构重构也塞进这个提交。
