**机甲战棋引擎**
**固定画布 + 填充单元格 + 平顶六边形**
架构变更影响评估报告
2026年7月22日

# 1. 执行摘要
本报告针对您提出的两项架构变更进行全面影响分析：
- 将地图画布固定为 100×100 六边形网格，地图形状由填充的单元格（cells）决定，而非动态 width × height
- 将六边形从尖顶（pointy-topped）切换为平顶（flat-topped）

经全面代码审计，当前系统基于尖顶 Even-R Offset 坐标系构建，地图尺寸由动态 width/height（10–200范围）驱动，单元格采用稀疏存储（仅存有地形的格子）。两项变更涉及前后端共 15+ 个文件，核心数学公式、渲染管线、寻路逻辑、数据库存储、编辑器交互均需协同修改。

**核心结论：**
- 固定 100×100 + 填充单元格模式：可行，但需将边界判定从「矩形范围」全面迁移为「cells 集合成员判定」。此变更本质上是把「地图边界」从 width/height 元数据转移到 cells 数据本身。
- 平顶六边形切换：涉及所有几何公式（中心坐标、像素逆推、邻居方向、顶点绘制、等距变换），工作量显著，但所有公式集中在前端 hexUtils.js 与渲染引擎中，后端仅需更新邻居方向与寻路偏移。
- 两项变更可串行实施：建议先完成固定画布（数据层改动），再切换六边形类型（几何层改动），以降低交叉复杂度。

# 2. 当前架构全景
## 2.1 六边形类型与坐标系
当前系统使用尖顶六边形（pointy-topped），采用 Even-R Offset 坐标系。
| 维度 | 当前值 |
| --- | --- |
| 六边形类型 | 尖顶（pointy-topped） |
| 坐标系 | Even-R Offset（双数行向右错位半格） |
| 单元格宽 | HEX_WIDTH = 64 px |
| 单元格高 | HEX_HEIGHT = 72 px |
| 边心距 | HEX_APOTHEM = 32 px（HEX_WIDTH/2） |
| 外接圆半径 | HEX_RADIUS = 36 px（HEX_HEIGHT/2） |

关键公式（hexUtils.js）：
*中心坐标：x = size * sqrt(3) * q * spacingH + offset；y = size * 1.5 * r * spacingV*
*像素逆推：rFrac = y / (1.5 * size)；qFrac = (x - offset) / (size * sqrt(3))*
*邻居偏移（Even-R）：双数行与单数行的 6 个方向偏移量不同*
## 2.2 地图尺寸与单元格存储
当前采用「动态矩形地图」模式：
| 维度 | 当前实现 |
| --- | --- |
| 地图尺寸 | 动态 width × height（10–200范围，编辑器可选） |
| 单元格存储 | 稀疏存储——只存有地形的格子（Map: "q,r" → terrainId） |
| Canvas 尺寸 | 固定为容器 CSS 像素（与地图尺寸无关） |
| 边界判定 | 矩形边界：0 <= q < width && 0 <= r < height |
| 视口裁剪 | 仅渲染 visibleRange 内的格子（边界受 width/height 限制） |
| 世界尺寸 | 由 width/height 推导（用于居中/缩放） |

## 2.3 渲染管线
渲染管线采用「纯净 Canvas CTM + 等距伪 3D」架构：
1. HexGridCanvasEngine.vue 接收 gridData（含 width、height、cells、topologyParam）
2. 构建 cellMap（"q,r" → cell）用于 O(1) 查找
3. updateVisibleRange：根据 Canvas 视口 + 当前 offset/scale 计算可见 q/r 范围，受 width/height 限制
4. 离屏地形缓存：将 cells 地形绘制到离屏 canvas，主循环仅做 drawImage
5. 主渲染循环：仅遍历 visibleRange 内的格子，绘制地形 + 单位 + 高亮
6. 等距变换：通过 CTM（ctx.transform）+ 逐顶点 isoTransformPoint 实现 3D 效果
## 2.4 寻路系统
寻路在网关层（combat.ts）与 combat-service 层均有实现：
| 层级 | 网关 combat.ts | combat-service |
| --- | --- | --- |
| 边界判定 | 仅检查 cellSet（cells 集合成员） | 检查 cellSet + width/height 矩形边界 |
| 邻居方向 | Even-R 偏移（6方向） | Even-R 偏移（6方向） |
| 范围计算 | max(1, round(rawMob/10)) | Math.floor(mobility/2) |

# 3. 变更设计
## 3.1 固定 100×100 + 填充单元格模式
目标：将画布固定为 100×100 六边形网格，地图形状由 cells 数组中的格子决定。白色/透明区域为「地图外」，不可部署单位、不可移动进入。
### 3.1.1 设计原则
- 画布恒定：渲染引擎始终面对 100×100 的六边形网格坐标空间
- 形状由数据决定：cells 数组中包含的格子即为「地图内」，缺失的格子为「地图外」
- 边界判定迁移：所有「0 <= q < width && 0 <= r < height」判定替换为「cellMap.has(q,r)」或「cellsSet.has(key)」
- 视口裁剪调整：visibleRange 不再受 width/height 限制，而是基于 cells 的 bounding box 或固定 0–99
- 编辑器简化：移除新建地图时的 width/height 输入，画笔在 100×100 画布上自由涂抹
### 3.1.2 对既有稀疏存储的兼容性
当前系统已采用稀疏存储（只存有地形的格子），这与「填充单元格」模式天然兼容。差异仅在于：
- 当前：width/height 定义画布大小，cells 定义哪些格子有地形；无地形的格子默认显示为「moon」（平原）
- 新设计：固定 100×100 画布，cells 定义哪些格子属于地图（有地形）；不在 cells 中的格子为「地图外」（透明/不可达）
这意味着需要引入一个新的概念：「地形类型」与「地图边界」解耦。当前系统中「无地形 = moon」，新设计中「无 cells 条目 = 地图外」。
## 3.2 平顶六边形（flat-topped）
目标：将六边形从尖顶切换为平顶。
### 3.2.1 尖顶 vs 平顶的几何差异
| 维度 | 尖顶（当前） | 平顶（目标） |
| --- | --- | --- |
| 顶点方向 | 顶点在上下，边在左右 | 顶点在左右，边在上下 |
| Offset 类型 | Even-R（行偏移） | Even-Q（列偏移） |
| 宽×高 | 64×72（宽 < 高） | 72×64（宽 > 高） |
| 中心 x 公式 | x = size*sqrt(3)*q + offset | x = size*1.5*q |
| 中心 y 公式 | y = size*1.5*r | y = size*sqrt(3)*r + offset |
| 邻居偏移 | 6方向 Even-R 偏移表 | 6方向 Even-Q 偏移表 |
| 顶点顺序 | 从顶点开始，顺时针/逆时针 | 从边中点开始，顺时针/逆时针 |

### 3.2.2 是否增加工作量？
平顶切换本身不会「额外」增加工作量——因为固定画布与六边形类型是两个正交的变更。但平顶切换涉及的范围广：所有几何公式、顶点绘制、邻居查找、等距变换均需重写。

**关键洞察：**
- 若先完成固定画布（仅改数据层），再切换平顶（仅改几何层），两次变更互不干扰，总工作量 = 两部分之和。
- 若同时进行，需同时处理「固定画布后的边界判定」+「平顶后的坐标偏移」，交叉复杂度增加约 30%。

**建议：串行实施。**

# 5. 需要重新协调的既有内容
## 5.1 数据迁移
现有地图数据全部存储为「width + height + cells」格式。迁移策略：
7. 读取所有现有地图的 width/height/cells
8. 生成新的 cells：将原矩形范围内所有格子（包括无地形的 moon 格子）全部写入 cells 数组
9. 或者：保持现有 cells 不变，前端渲染时默认「无 cells 条目 = 地图外」

**推荐方案：**
方案 B（更干净）——现有 cells 即为地图形状。对于旧地图，前端渲染时将所有在 width×height 矩形内但不在 cells 中的格子视为「平原（moon）」并加入 cells。这样旧地图在固定画布下仍然显示为完整矩形。新地图则通过编辑器自由绘制形状。
## 5.2 现有战斗状态
正在进行的战斗（battleStore 中的状态）包含 map.width/map.height。这些状态在战斗创建时固化，不受地图后续修改影响。但如果重新加载战斗（如断线重连），会从数据库重新读取地图数据。
- 已完成的战斗：无需处理
- 进行中的战斗：若战斗重新加载，可能遇到新旧数据格式不一致。建议在新代码部署后，进行一次性的战斗状态清理或格式升级。
## 5.3 编辑器工作流
当前编辑器工作流：
10. 新建地图 → 选择 width/height → 空白画布 → 画笔涂抹 → 保存
新工作流：
11. 新建地图 → 固定 100×100 画布 → 画笔涂抹（默认全空/地图外）→ 保存

**用户体验变化：**
- 不再有「调整地图大小」的概念——画布恒为 100×100
- 用户需要一种方式标记「地图边界」——可通过一个特殊画笔（如「边界框选」）快速填充大片区域
- 地图保存时体积可能增大（若填充大量格子），但 100×100 = 10,000 格，JSON 存储完全可接受。
## 5.4 前端缓存与状态
frontend/src/stores/ 中可能缓存了地图的 width/height。需要检查：
- battleStore / mapStore 中是否存储了 width/height
- localStorage / sessionStorage 中是否缓存了旧格式
- 路由参数或 query string 中是否传递了 width/height
## 5.5 单元测试
需要检查测试代码中是否硬编码了 width/height 或尖顶六边形的假设：
- combat-service 中的 battleState 测试
- hexUtils 的单元测试（如有）
- 网关路由测试（如有）
## 5.6 地图导出/导入
当前支持 JSON 导出/导入。需要确认：
- 导出格式是否包含 width/height（是 → 新格式需移除或标记 deprecated）
- 导入逻辑是否校验 width/height（是 → 需兼容旧格式）
- Excel/CSV 批量编辑是否依赖 width/height 范围

| 编辑器 UX 退化 | 固定画布后用户可能困惑于「地图外」区域 | 增加视觉提示（地图外格子半透明/网格线区分） |
| 数据膨胀 | 100×100 全填充可能导致 cells 数组达 10,000 条 | 保持稀疏存储；仅地图内格子入数组；JSON 压缩完全可接受 |
| 遗漏边界检查 | 某处代码仍用 width/height 判定，导致异常行为 | 全局搜索所有 width/height 使用点，建立检查清单 |
