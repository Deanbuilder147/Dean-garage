# 技能射程结算问题全链路排查报告

> 现象：只有「距离为 1」的攻击（近战/基础攻击，默认 range 1）才能正常计入伤害结算；
> 超距的技能攻击（射程 > 1）打不出伤害 / 完全不生效。
> 排查日期：2026-07-25
> 结论：根因在**编辑器创建的单位技能缺少稳定 `id`**，导致 `/attack` 技能分支在缺 `skill_id` 时直接 400；
> 叠加 `realRange` 用 `Number()` 解析字符串射程（如 `"1-3"`）会得 `NaN`，与另外两处射程解析器不一致。

---

## 1. 编辑器技能对象缺少 `id`（致命根因）

### 1.1 证据链

**`frontend/src/components/SkillsEditor.vue`** —— 技能对象由 `addSkill` 生成，字段固定为
`{ name, type, attribute, effect, range, special }`，**没有 `id` / `key` / `skill_key`**：

```js
// SkillsEditor.vue addSkill ~L97
function addSkill() {
  skills.value.push({ name: '', type: '近战', attribute: '实体', effect: '', range: '1', special: '' })
}
```

射程输入框是**纯文本**（`type="text"`），所以 `range` 始终是**字符串**：

```vue
<!-- SkillsEditor.vue ~L53 / L80 -->
<input ... type="text" v-model="skill.range" placeholder="射程" />
```

**`frontend/src/views/NewUnitEditorView.vue`** —— 直接把该数组透传给后端：

```vue
<SkillsEditor title="主机体技能" v-model="form.main_skills" :max-slots="3" />  <!-- L126 -->
```

**`backend-gateway/src/routes/units.ts`** —— `createUnit`/`updateUnit` 仅 `JSON.stringify` 序列化，
**不会补 `id`**：

```ts
// units.ts（createUnit ~L93-97）
const skills = JSON.stringify(req.body.skills || [])
// 存入 units.skills 列（TEXT）
```

**`backend-gateway/src/routes/combat.ts`** —— `/attack` 技能分支硬性要求 `skill_id`：

```ts
// combat.ts L938-948
if (attack_type === 'skill') {
  if (!skill_id) {
    res.status(400).json({ success: false, error: 'VALIDATION_ERROR', message: '技能攻击需提供 skill_id' });
    return;                                   // ← 编辑器技能走到这里，技能攻击整体失败
  }
  const owned = (exeCaster.skills || []).find((s: any) => s.id === skill_id);  // 无 id → 找不到
  if (!owned) { res.status(404)...; return; }
}
```

**`frontend/src/views/NewBattleView.vue`** —— 只在 `skill.id` 是 UUID 时才发送 `skill_id`：

```js
// NewBattleView.executeSkillAttack ~L3092
skill_id: (isUUID(skill.id) ? skill.id : undefined)
```

**`backend-gateway/src/services/combatBridge.ts` 的 `toExecutorUnit`（~L628）** —— 透传单位 `skills`，
**不为技能补 `id`**。

### 1.2 后果

- 编辑器创建的单位，其技能对象 **无 `id`** → `executeSkillAttack` 不发送 `skill_id`
  → 网关 `/attack` 技能分支 **400「技能攻击需提供 skill_id」** → 技能攻击**根本不发起**（前端捕获后弹「攻击失败」）。
- 因此该单位**只剩「普通攻击」（基础近战/远程，默认 range 1）能结算伤害**。
- 这正好对应「只有距离为 1 的技能范围才能被正常计入伤害结算」——用户误以为是射程>1 的技能算不出伤害，
  实质是这些技能的攻击请求被 400 拒掉了。

### 1.3 对照：Excel 导入单位为何正常

`excel-schema-normalizer.ts` 的 `mapSkills` **会生成 `id` 并把射程写成数字**：

```ts
// excel-schema-normalizer.ts L194-216
function mapSkills(rawSkills) {
  return rawSkills.map((s) => {
    const { min, max } = parseRange((s as any).range);   // 能解析 "1-3" → {1,3}
    return {
      id: uuidv4(),            // ← 有稳定 id
      ...
      range: max, range_min: min, range_max: max,
      max_range: max, min_range: min,
      cast_range: max,         // ← 数字
      min_cast_range: min,
    }
  })
}
```

所以 Excel 单位的技能攻击能正常带 `skill_id`、射程为数字，`range>1` 能正常结算。
**问题集中在「编辑器创建 / 编辑」的单位**（以及历史上已落库、技能无 `id` 的单位）。

## 2. `realRange` 用 `Number()` 解析字符串射程（脆弱，次级根因）

即便 `skill_id` 问题解决，当前 `realRange` 仍有隐患：

```ts
// combat.ts L951-952
const realRange = Number(owned.cast_range ?? owned.range ?? owned.max_range ?? 1);
const realMin   = Number(owned.min_cast_range ?? owned.min_range ?? 0);
```

- `SkillsEditor` 产出 `range: "1-3"`（用户按效果描述输入 `1-3` / `1~3`）。
- `Number("1-3")` === `NaN` → `inlineDef.cast_range = NaN`。
- 引擎 `_getUniversalFields` 中 `cast_range: cfg.cast_range ?? 1` 不会把 `NaN` 兜底成 1，
  于是 `uf.max_range = NaN`、`uf.cast_range = NaN`。
- 引擎距离校验 `if (uf.max_range || uf.cast_range)`：`NaN || NaN` 为 **falsy** → **跳过距离校验**
  → 射程约束失效（可打任意距离），属于「范围结算」错误的另一面。

> 注意：网关层 `resolveSkillRange.pickNum`（combat.ts ~L693-696）与前端 `getSkillRange`
> （NewBattleView ~L2559-2580）**都能按 `-~/~` 切分取最大/最小**，唯独 `realRange` 用 `Number()`
> 不兼容非纯数字字符串。三处解析器不一致是隐性雷。

## 3. 其它可能相关节点（已排查/复核）

| 节点 | 现状 | 是否致病 |
|------|------|----------|
| 前端 `skillGroups`（NewBattleView 2417-2508） | 直接复用 `unit.skills`，不为技能补 `id`；`selectedAttackSkill?.id === skill.id` 对无 id 技能全 `undefined===undefined` 为真 → 所有技能按钮都高亮 active | 加重定位错觉，但非伤害根因 |
| 引擎 `_getUniversalFields`（skillExecutor.cjs 56-60） | `cast_range: cfg.cast_range ?? 1` 不会回退到 `cfg.range`；`max_range: cfg.max_range ?? cfg.cast_range ?? cfg.range ?? 1` 才回退 | 当前 inlineDef 同时写了 `range` 与 `cast_range`，暂未触发；属脆弱点 |
| 网关 `/attack` 伤害回写 | `if (result && result.triggered !== false)` 才写（`combat.ts` 1050）；引擎 `out_of_range` 时 `triggered:false` → 不写伤害 | 表现层符合预期（无伤害） |
| 部署形态 | 网关 `tsc` 编译后 `node dist/index.js`（`Dist` 在 `docker compose build mecha-gateway` 时生成） | 任何 combat 逻辑修复都**必须重建网关镜像**，仅重建前端无效 |
| 历史存量数据 | 已落库、由编辑器创建的单位：技能无 `id`、`range` 为字符串、无 `cast_range` | 需回填（见修复 5） |

## 4. 根因汇总（按严重度）

1. **【严重】编辑器技能无 `id` → 技能攻击被 400 拒**（`SkillsEditor.vue` 缺 id；`combat.ts:939-942` 必须 `skill_id`；`NewBattleView:3092` 仅 UUID 才发）。这是「只有距离 1 能结算」的直接原因。
2. **【高】`realRange = Number(...)` 对 `"1-3"` 等字符串得 `NaN`**，与另外两处解析器不一致，导致射程约束失效/错乱。
3. **【中】三处射程解析逻辑不统一**（前端 `getSkillRange`、网关 `resolveSkillRange.pickNum`、`combat.ts realRange`），应合并为一个 `parseRangeStr()`。
4. **【中】存量单位数据缺 `id`/`cast_range`**，需回填。
5. **【低】`skillGroups` 不为技能补 `id`**，造成战术框选中态错乱（所有技能按钮同显 active），干扰排错。

## 5. 修复建议

1. **为技能对象补稳定 `id`（核心修复）**
   - `SkillsEditor.vue` 的 `addSkill`：对象加 `id: crypto.randomUUID()`（或 `${Date.now()}-${idx}`）。
   - 加载已有单位技能时若缺 `id` 也补上。
   - 这样 `executeSkillAttack` 会发送 `skill_id`，网关 `owned` 能正确匹配，拿到 `cast_range` → `realRange` 正确 → 超距技能正常结算。
   - 可选更稳方案：网关 `owned` 匹配改为 `s.id === skill_id || s.name === skillKey`（允许按 `name` 兜底），降低对 id 的强依赖。

2. **统一射程解析**（`combat.ts` 内新增并复用）：
   ```ts
   function parseRangeStr(raw: any): { min: number; max: number } {
     if (typeof raw === 'number') return { min: raw, max: raw }
     if (raw == null || raw === '') return { min: 1, max: 1 }
     const nums = String(raw).split(/[-~]/).map(Number).filter(n => !isNaN(n))
     if (!nums.length) return { min: 1, max: 1 }
     return { min: Math.min(...nums) || 1, max: Math.max(...nums) }
   }
   // realRange = parseRangeStr(owned.cast_range ?? owned.range ?? owned.max_range ?? 1).max
   // realMin   = parseRangeStr(owned.min_cast_range ?? owned.min_range ?? 0).min
   ```
   与 `excel-schema-normalizer.parseRange`、`resolveSkillRange.pickNum`、`getSkillRange` 保持同一语义。

3. **`SkillsEditor` 射程输入改造**：拆成「最小/最大」两个 `number` 输入，或保留文本但提交时 `parseRangeStr` 校验，避免 `"1-3"` 这样的字符串直接进库。

4. **引擎 `_getUniversalFields` 防御**：`cast_range: cfg.cast_range ?? cfg.range ?? 1`，避免仅写 `range` 时回退成 1。

5. **存量数据回填**（一次性脚本 / `units.ts` 读取时 Normalize）：
   - 遍历 `units.skills`，对缺 `id` 的技能补 `uuid`；
   - 由字符串 `range` 解析出 `cast_range/range_min/range_max/max_range/min_range/min_cast_range`（数字）。

6. **重新构建并部署网关**：
   ```
   rsync 源码 → docker compose build --no-cache mecha-gateway → up -d --no-deps mecha-gateway
   ```
   （前端无需改动即可先验证；若改了 `SkillsEditor` 则前端也要 build。）

## 6. 验证步骤（修复后）

1. 用**单位编辑器**新建一个机体，主技能设 `类型=远程`、`射程=4`（或 `4-6`）。
2. 进入战斗，选中该单位 → 战术框点该远程技能 → 高亮应显示范围 4。
3. 点击距离 2、3、4 的敌人 → 应各造成正常伤害；点击距离 5+ → 应被拒（out_of_range，无伤害）。
4. 查看 Network：`/attack` 请求带 `skill_id`（UUID），响应 `combat_result.final_damage > 0`。
5. 对照 Excel 导入单位：射程 `1-3` 的技能，距离 1/2/3 都应可命中，距离 4 被拒。
6. 控制台/后端日志：不应再出现 `VALIDATION_ERROR 技能攻击需提供 skill_id`。
