### 1.2 `/api/hangar/factions` — 🔴 404 根因

| 检查项 | 结果 |
|--------|------|
| Nginx 代理 | `location /api/hangar/ → proxy_pass http://mecha-gateway:3006` ✅ |
| Gateway 路由表 | **无 `/api/hangar/` 前缀的路由注册** ❌ |
| 最近似路由 | `units.ts` 使用 `/api/units`（不是 `/api/hangar`） |
| 直连 3006 验证 | `curl localhost:3006/api/hangar/factions` → `{"error":"NOT_FOUND"}` 404 |

**根因**：`app.ts` 第 82 行注册 `app.use(unitRoutes)`，unitRoutes 内部所有端点以 `/api/units` 为前缀。但 Nginx 第 33 行将 `/api/hangar/` 代理至 gateway:3006，且 gateway **完全没有注册** `/api/hangar/` 前缀的任何路由。前端 `hangarAPI.getFactions()` 调用 `/hangar/factions` → Nginx 拼成 `/api/hangar/factions` → Gateway 404 兜底 (`app.ts` 第 155 行)。

### 1.3 `/api/combat/glossary-config` — 🔴 404 根因

| 检查项 | 结果 |
|--------|------|
| Nginx 代理 | `location /api/combat/ → proxy_pass http://mecha-gateway:3006` ✅ |
| Gateway combat 路由 | **仅有带 `:battleId` 参数的路径** ⚠️ |
| 已注册的 combat 路由 | `/api/combat/:battleId/state`, `initialize`, `action-points/consume`, `action-points/:unitId`, `end-turn`, `damage` |
| 是否有无 `:battleId` 的通配路由 | **无** ❌ |
| 直连 3006 验证 | `curl localhost:3006/api/combat/glossary-config` → `{"error":"NOT_FOUND"}` 404 |

**根因**：`combat.ts` 所有端点都是 `/api/combat/:battleId/...` 格式，Express Router 匹配 `/api/combat/glossary-config` 时，`:battleId` 参数虽然能匹配 `glossary-config` 作为 battleId，但后续子路径不匹配。`glossary-config` 作为独立的无战斗上下文端点，未单独注册。

### 1.4 `/api/units`（无尾斜杠）→ 301 重定向 — 🟡 次生问题

| 检查项 | 结果 |
|--------|------|
| Nginx location | `location /api/units/ {`（尾斜杠） |
| 请求 `/api/units`（无尾斜杠） | 不匹配任何 location → 落入 `location / { try_files ... }` → 301 |
| 请求 `/api/units/`（有尾斜杠） | 正常命中 → 返回 401 (需认证) ✅ |
| 外网验证 | `curl https://deanheim.online/api/units` → 301; `curl https://deanheim.online/api/units/` → 401 ✅ |
| 直连 3006 | `curl localhost:3006/api/units` → 200 (Express 无尾斜杠歧视) ✅ |

**根因**：Nginx `location /api/units/` 严格匹配前缀尾斜杠。前端若调用 `/api/units`（不带尾斜杠），Nginx 将其送入 SPA fallback → 301 重定向。Gateway 层面的 Express Router 本身无此问题。**此问题由 Nginx location 语法引起**，是 `/api/units` 端点的前端可达性隐患。

## 排查三：Nginx 安全头与打包指纹审计

### 3.1 CSP 配置

**文件**：`frontend/nginx.conf` 第 5 行
```
add_header Content-Security-Policy "default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob:; connect-src 'self' ws: wss:; font-src 'self';" always;
```

| 指令 | 值 | 评估 |
|---|---|---|
| `default-src` | `'self'` | 严格 |
| `script-src` | `'self'` | 🔴 **缺 `'unsafe-eval'`** |
| `style-src` | `'self' 'unsafe-inline'` | ✅ 允许内联样式 |
| `img-src` | `'self' data: blob:` | ✅ 允许 Data URL |
| `connect-src` | `'self' ws: wss:` | ✅ 允许 WebSocket |
| `font-src` | `'self'` | 严格 |

**CSP 熔断机制分析**：
- `script-src 'self'` 缺少 `'unsafe-eval'` 放行
- Vue.js 运行时模板编译器依赖 `new Function()` / `eval()` 动态执行代码
- CSP 严格模式下浏览器拦截 `eval()` 调用 → 抛 `EvalError`
- 结果：Vue 组件动态渲染失败 → 白屏 / 部分组件挂起

**真机验证**：
- `curl -k 'https://deanheim.online/'` → CSP Header 包含 `script-src 'self'` ✅（无 `unsafe-eval`）
- 同样 CSP 应用于所有 JS 资源请求

### 3.3 附加 Nginx 缓存毒素

**`frontend/nginx.conf` 第 12-14 行**：
```
add_header Cache-Control "no-cache, no-store, must-revalidate" always;
add_header Pragma "no-cache" always;
add_header Expires "0" always;
```

**影响**：这三个 header 通过 `always` 修饰符应用于**所有**响应（包括 `assets/index-*.js` 等带 hash 的不可变静态资源）。正常做法是仅对 HTML 文件禁用缓存，带 hash 的 JS/CSS 应允许长期缓存 (`max-age=31536000, immutable`)。

## 🎯 精准根因定位（按修复优先级）

### 根因 1（最紧急）：前端 API 路径与 Gateway 路由前缀不匹配

- **前端** `client.js` 使用 `/hangar/units` → Gateway 只有 `/api/units`
- **前端** `client.js` 使用 `/hangar/factions` → Gateway 无此路由

### 根因 3：CSP `script-src` 未放行 `'unsafe-eval'`

- `frontend/nginx.conf` 第 5 行，需追加 `'unsafe-eval'`

- 建议增加不含尾斜杠的 location 或使用 rewrite
