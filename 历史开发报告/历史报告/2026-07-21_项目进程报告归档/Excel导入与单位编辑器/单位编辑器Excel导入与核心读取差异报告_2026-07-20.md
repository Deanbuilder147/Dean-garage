# 单位编辑器 Excel 导入 vs 核心读取单位数据 差异分析报告

- 生成时间：2026-07-20
- 分析范围：
  - Excel 导入读取：`mecha-universe-engine/services/hangar-service/src/services/excel-parser.js`、`excel-validator.js`、`config/excel-template.js`、`unit-import-service.js`
  - 前端入口：`mecha-universe-engine/frontend/src/views/NewUnitEditorView.vue`（`importExcel` → `/units/parse-excel`）
  - 核心读取：`mecha-universe-engine/services/combat-service/src/services/unitConverter.js`（`UnitConverter.convert`）

## 一、数据链路总览

```
Excel 文件
  └─ excel-parser.js（按固定单元格模板解析）
        basic: {name, codename, faction, totalPoints}
        units: {主机体, 跟随, 左手, 右手, 其它} 各含 {type, 格斗, 射击, 结构, 机动, skillSlots}
        skills: [{slot, name, type, attribute, effect, range, special, owner}]
  └─ unit-import-service.js（insertUnit 写库，落 columns: main_*, left_*, right_*, extra_*, royroy_*）
        units 表
  └─ combat-service / unitConverter.js（UnitConverter.convert 读取 main_格斗 等列 + *_skills JSON）
        战斗核心单位格式
```

**根本差异**：Excel 是按"固定单元格坐标 + 中文分组名"的**模板式读取**；核心是按"DB 列字段（`main_格斗`/`left_skills` 等带槽位前缀）"的**结构化读取**。两者之间由一个"写库中间层"桥接，桥接过程中发生了字段裁剪与语义映射，导致 Excel 读取到的部分数据在核心侧**不可见或语义被改写**。

---

## 二、具体差异（共 5 处，均属实质性偏差）

### 差异 1：`effect`（技能效果）字段被核心完全忽略
- **Excel 读取**：`excel-template.js` 定义技能列 `effect`(F)，`excel-parser.js` 解析并随 `skills` 入库（`unit-import-service.js` 写入各 `*_skills` JSON 的 `effect` 字段）。
- **核心读取**：`unitConverter._skillToTag` 只取 `skill.name / skill.attribute / skill.range / skill.special / skill.description`，**从不读取 `skill.effect`**。
- **影响**：策划在 Excel "技能效果"列填写的自由文本在战斗核心中**完全丢失**，不会进入技能 Tag。

### 差异 2：`skillSlots`（技能槽位）读取但不存储、核心永不可见
- **Excel 读取**：`excel-template.js` 每个单位行含 `skillSlots`(H 列，0-5)；`excel-validator.js` 还做了 0-5 范围校验（仅 warning）。
- **核心/写库**：`unit-import-service.js` 的 INSERT SQL **没有 skillSlots 列**，该值既不入库也不参与 UnitConverter 任何计算。
- **影响**：Excel 填的槽位数被静默丢弃，核心单位无任何 skillSlots 概念（核心用 `*_skills` 数组长度表达槽位）。

### 差异 3：`totalPoints`（总点数）读取但不存储、核心永不可见
- **Excel 读取**：`excel-template.js` 基本信息 `totalPoints`(C3)，`excel-validator.js` 校验 0-1000（仅 warning）。
- **写库**：`unit-import-service.js` 的 INSERT SQL **没有 total_points 列**，未入库。
- **影响**：Excel "总点数" 是模板要求的字段，但导入后消失，核心无从读取（核心也无 points 概念，派生自 结构×10 等）。

### 差异 4：技能 `type`（自动/手动/被动）读取但核心用 `name` 映射覆盖
- **Excel 读取**：技能 `type`（D 列，取值 自动/手动/被动），入库到 `*_skills` JSON 的 `type`。
- **核心读取**：`UnitConverter._skillToTag` 的 `combatType = TYPE_MAP[name] || 'unknown'`，**完全依据技能 `name` 中文名映射到核心类型**，Excel 的 `type` 字段不参与判定。
- **影响**：若策划在 Excel 把某技能 `name` 填错（不在 TYPE_MAP 的 22 个词内），无论 `type` 填什么，核心都归为 `unknown` 且分类/目标/描述全部兜底；`type` 列对核心毫无约束力。

### 差异 5：`codename`（行动代号）读取入库但核心忽略
- **Excel 读取**：`excel-template.js` 基本信息 `codename`(B3)，入库 `codename` 列。
- **核心读取**：`UnitConverter.convert` 只用 `hangarUnit.name` 作为 `name`，**不引用 codename**（仅前端展示层可能用）。
- **影响**：行动代号在战斗逻辑中无作用，属展示字段差异（程度较轻微，但构成语义不对称）。

## 三、次级/潜在不一致（供参考，未计入主差异数）

- **属性容错映射**：Excel 原样存 `attribute`（如"光束"/"实体"）；核心 `attribute` 解析为 `skill.attribute === '光束' ? 'energy' : skill.attribute === '实体' ? 'kinetic' : (skill.attribute || 'kinetic')`，其它任意值默认 `kinetic`。Excel 填非规范值会在核心侧被静默改写。
- **装备类型合并**：Excel 模板区分 `装甲` 与 `盾牌` 两类；核心 `EQUIP_TYPE_MAP` 将两者都映射为 `armor`，仅 `盾牌` 额外给 `energy` 抗性。Excel 读到的"装甲/盾牌"区分在核心侧部分塌缩。
- **验证器与解析器 owner 命名不一致**：`excel-parser.js` 的 `getSkillOwner` 返回中文（主机体/跟随/左手/右手/其它），而 `excel-validator.js` 的 `getSkillOwner` 返回英文（main/royroy/left/right/extra）。虽因写库层只用解析器的中文 owner 而未造成存储错误，但校验计数与解析口径不一致，属于隐藏隐患。
- **Excel 固定单元格耦合**：解析强依赖 `B2/B3/B4/C3`、单位行 `7-11`、技能行 `14-25`、列 `A-H` 的精确坐标，且只取第一个工作表（`workbook.Sheets[0]`）；核心读取则完全脱离这些坐标，仅依赖 DB 列。一旦模板版式变动（如新增单位槽位），Excel 解析会整体失效或漏读，而核心读取不受影响。

---

## 四、结论

Excel 导入与核心读取在**字段覆盖度**与**语义映射**上共存在 **5 处实质性差异**（effect 丢弃 / skillSlots 不存储 / totalPoints 不存储 / skill type 被 name 覆盖 / codename 核心忽略），差异数 > 3，已按需求生成本报告。

**关键风险**：差异 1–3 属于"Excel 读到了但中间层不落库、核心看不到"的**静默数据丢失**，策划无法从前端感知（导入预览仅警告校验项，不提示字段将被丢弃）。建议在 `unit-import-service.js` 中补列或对策划明确告知，避免配置预期与实际战斗表现脱节。
