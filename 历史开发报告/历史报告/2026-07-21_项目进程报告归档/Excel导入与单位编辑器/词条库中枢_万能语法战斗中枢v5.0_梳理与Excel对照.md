## 一、按游戏场景划分（数据流 5 阶段）

本项目把"词条属性与计算通路"拆分为 5 个相互独立又前后串联的场景。每个场景负责不同的生命周期阶段：

| 场景 | 名称 | 生命周期 | 关键文件 | 职责 |
|---|---|---|---|---|
| **A** | 单位编辑器 | 设计期 | `NewUnitEditorView.vue` | 玩家分配点数、装配技能/装备、产出单位数据 |
| **B** | 词条库中枢 | 配置期（大厅） | `glossary-skill-config.json` + `glossary.ts` | 定义 skills/terrains/damage_kinds/action_types/systems 与 CRUD |
| **C** | 战斗管道 | 结算期 | `damagePipe.cjs` / `skillExecutor.cjs` / `equipmentDurability.cjs` | 把 A 的单位数据 + B 的词条配置投入伤害计算 |
| **D** | 地形与系统机制 | 环境期 | glossary `terrains`(10) / `systems`(3) | 提供地形减伤、高地、暴击、奇袭、迷雾等环境修正 |
| **E** | Excel 设定器导入 | 数据接入期 | 单位编辑器"Excel导入"弹窗 | 把 `作品设定器beta1.xlsx` 解析成场景 A 的表单 |

> 场景 E 是 A 的数据来源之一（也可手工录入）。A 的成果（单位 JSON）经战斗服务反序列化为 `attacker/defender` 对象，再被 C 消费，C 在运算中实时查询 B/D 的配置。

## 二、场景 A：单位编辑器（设计期）

### 2.1 单位结构（6 槽位）
编辑器把一台棋子拆成 **主机体 + 跟随(Royroy) + 左手 + 右手 + 其它** 共 5 类部件（Excel 还单列"其它"，项目合并进 `extra` 槽）：

| 部件 | 点数上限 | HP 公式 | 技能槽数 | 约束 | 额外字段 |
|---|---|---|---|---|---|
| 主机体 `main` | 40 | `结构 × 10` | 3 | 无 | 七视图(0-6 朝向精灵图) |
| 跟随 `royroy` | 25 | `结构 × 3` | 2 | 任一项 ≥ 10 | — |
| 左手 `left` | 15 | （耐久度，非 HP） | 见 §2.3 | — | `damage_kind_modifiers` |
| 右手 `right` | 15 | （耐久度，非 HP） | 见 §2.3 | — | `damage_kind_modifiers` |
| 其它 `extra` | 10(背包)/15 | （耐久度，非 HP） | 见 §2.3 | 载具机动≥10、防具结构≥10 | `damage_kind_modifiers` |

### 2.2 四维属性
每个部件都有 **格斗 / 射击 / 结构 / 机动** 四个维度，从 `0` 累加到该部件点数上限：
```
mainTotal = 格斗+射击+结构+机动  （封顶 40）
mainHP    = 结构 × 10
royroyHP  = 结构 × 3
```

### 2.3 技能槽数量（`getSkillSlots`）
按部件类型固定：
```
武器=1, 防具=1, 载具=2, 背包=0
主机体=3, 跟随=2
```

### 2.4 `damage_kind_modifiers`（Phase 11 装备伤害种类修正）
左右手/其它装备各有一组 5 维修正系数（范围 -5~+5，默认 0），与场景 B 的 `damage_kinds` 一一对应：
```
beam(光束) / kinetic(动能) / explosive(爆炸) / corrosive(腐蚀) / thermal(热熔)
```

## 三、场景 B：词条库中枢（配置期）

### 3.1 配置 5 大块（`glossary-skill-config.json` v5.0）
```
_meta           版本/原则说明
damage_kinds    5 种：kinetic / beam / explosive / corrosive / thermal
action_types    5 种：attack / heal / buff / debuff / passive
skills          9 个非核心 + 6 个硬编码核心
systems         3 个：ambush(奇袭) / fog_of_war(迷雾) / crit(暴击)
terrains        10 种：moon/plain/mountain/water/forest/fortress/ruins/crystal/rubble/city_building
```

### 3.2 Skills 清单
**核心硬编码（只读、不可覆盖，`glossary.ts` 中 `CORE_SKILLS`）**
`melee_strike`(近战打击) / `ranged_shot`(远程射击) / `shield_wall`(护盾壁垒) / `repair`(紧急修复) / `overdrive`(超载驱动) / `beam_cannon`(光束加农炮·地图炮)

**配置内 9 个**
`block`(格挡·近战被动 -2) / `sweep`(扫射·远程扇形) / `throw`(投掷·远程减益) / `execute`(斩杀·近战处决) / `duel`(决斗·特殊) / `snatch`(抢夺·特殊) / `focused_fire`(专注射击·远程+4) / `lucky`(幸运·空投再动) / `reactivate`(再动·击杀追加回合)

> 注意：`counter`(反击) 仅出现在 `campaigns.json` 战役脚本，**未进入 v5.0 中枢配置 skills**。

### 3.3 CRUD 通路（`glossary.ts`）
- `GET /api/combat-glossary/config`：**无认证、全量广播**（游客可读全部技能，含核心）。
- `POST /api/combat-glossary/config`：**仅 admin/dominator**，普通用户 403。
- 合并策略：深度合并 `skills`，但核心技能永不覆盖、不可删；支持 `_delete_skills` 删除非核心技能。小写 `label` 去重。

## 四、场景 C：战斗管道（结算期）

### 4.1 damagePipe.cjs —— 伤害计算 12+1 阶段
```
阶段1  基础攻击力   近战=attacker.melee(格斗) / 远程=attacker.ranged(射击)
阶段2  双方机动值差  DEF_DIFF = attacker.mobility - defender.mobility
阶段3  临时攻击力    = 阶段1 + 阶段2
阶段4  额外值        泛化累加器（buff/外部加成）
阶段5  装备耐久      equipmentDurability 介入
阶段6  防具抗性      
阶段7  地形修正      terrainDefs.damage_kind_modifiers
阶段8  高地优势      height_bonus_per_diff
阶段9  暴击          受 systems.crit 控制 (33.3% / 1.0~1.5)
阶段10 系统机制      systems.ambush / fog_of_war
阶段11 最终封顶      最小 1
阶段12 应用伤害      写入 defender.hp
[+1]  反击/再动等    post 钩子（counter / reactivate / lucky）
```

> **Excel 公式对应**：`阶段1 + 阶段2` 即 Excel「攻击力计算方式 = 格斗数值点数 + 双方机动值差额 / 射击数值点数 + 双方机动值差额」——**概念一致**。

### 4.2 skillExecutor.cjs —— 万能语法
按 `action_type` 路由：`_executeAttackSkill / _executeHealSkill / _executeBuffSkill / _executeDebuffSkill / _executePassiveSkill`，并支持 `supply`(补给)、`scout`(侦察)、`duel`(决斗)、`focused_fire`(专注射击) 等特例。所有技能通过 `universal_fields`（主谓宾定状补插槽）驱动，无硬编码技能名列表。

### 4.3 equipmentDurability.cjs —— 装备耐久
承接 Excel「武器结构×1=耐久度、防具结构×2=HP、载具结构×1=耐久度、背包耐久=5」中"耐久度"语义：装备耐久耗尽触发脱落 / 加成消失。

### 4.4 计算通路示例（近战一次攻击）
```
单位A(格斗=8, 机动=5) 攻击 单位B(机动=3)
→ 阶段1 base=8(melee)
→ 阶段2 DEF_DIFF=5-3=+2
→ 阶段3 temp=10
→ 阶段7 地形(forest beam 0.9 但 kinetic 1.0) 不改
→ 阶段9 crit? 33.3% ×(1.0~1.5)
→ 阶段11 封顶≥1 → 施加到 B.hp
```

### 8.3 差异汇总速查
- **完全一致**：点数预算、技能槽、伤害基础公式、主机体/Royroy HP、装备 DKM 维度。
- **数值偏差（仅存在于两份 Excel 之间）**：`作品设定器beta1.xlsx` 机体 HP=×5，桌面 `战斗规则.xlsx`=×10；项目取 ×10，与 `战斗规则.xlsx` 一致，无需改代码。
- **体系重构 + 术语错配**：伤害种类 2→5；项目装备系统用 `energy` 表示"光束"，与全局 `beam` 不一致（见 §十·10.6）。
- **技能落地度大幅高于初判**：设定器 15 个技能特性 + 战斗规则 10 个特殊词条中，约 20+ 条已在 `unitConverter`+`skillExecutor` 映射并执行；偏差集中在：① 掷骰判定被确定性化（格挡/斩杀/决斗/抢夺/专注射击/幸运）；② 数值微调（全覆式/涂层 -2 vs -3，专注射击 +4 vs +3/+5）；③ 缺失分支（投掷移动-5、双槽约束、决斗同归、幸运 1-2/3-4）；④ 长柄/变形 已映射但效果疑似未执行；⑤ beam↔energy 错配。
- **系统性缺失**：阵营特性 6 项仅"奇袭"有同名不同义实现；地图特征 6 项仅"月面"有近似地形；战术规则 协同/联防/空投生成 完全缺失；防御单元/强化防御 缺失。

### 10.6 关键术语错配：beam ↔ energy（最可能引发运行期 bug）

- **现象**：全局 `glossary-skill-config.json` 与 `damagePipe` 的伤害种类用 **`beam`**（光束）；但 `equipmentDurability.cjs` / `equipManager.cjs` / `combatIntegrator.cjs` 用 **`energy`** 表示光束（`combatIntegrator` 把远程记成 `'energy'`，`equipManager` 的 resistance 类型为 `'kinetic'|'energy'|'explosive'`）。
- **后果**：单位的 `weaponType` 多为 `'beam'`（如 `turnManager.js` 的 `weaponType:'beam'`），传入 `equipmentDurability.applyDamage` 时 `weaponType === 'energy'` 为 **false** → **抗性涂层对光束武器实际不触发**（全覆式装甲查 `kinetic` 则正常）。
- **验证点**：`equipmentDurability.cjs` R140-141 的 `weaponType === 'energy'` 与 `damagePipe` R245/R325 的 `weaponType`（beam/kinetic/...）口径不一致。
- **建议**：统一为 `beam`，或在 `applyDamage` 调用处做 `beam → energy` 归一化，否则 Excel"抗性涂层对光束-3"在线上名存实亡。

## 十一、战斗规则.xlsx 词条修改建议（是否必要 + 怎么做）

### 11.1 先回答：有没有必要重写 Excel 词条？

**结论：有必要，但方向不是"把 Excel 改成和代码一样"，而是"让 Excel 成为可信的单源，并如实标注实现状态"。**

不能无脑照抄代码，因为两类偏差性质完全不同：

| 偏差类型 | 例子 | 该改谁 | Excel 改写策略 |
|---|---|---|---|
| **A. 代码有 bug / 术语错配** | 抗性涂层 `beam` vs `energy`、全覆式/涂层 -3 vs -2 | **改代码** | Excel **保持设计值**（保留 -3、保留"光束"），仅在旁加注"代码当前偏离，待修" |
| **B. 代码有意为之的简化** | 掷骰→固定值（格挡/斩杀/决斗/抢夺/专注射击/幸运） | **设计决策**（保留掷骰 or 接受简化） | Excel 增加"当前实现值"列，保留设计为掷骰，让两份信息共存 |
| **C. 未实现的设计目标** | 阵营 火力覆盖/增援/补给/隐匿、地形 母舰/太空/基地/防御层、战术 协同/联防/空投生成、迷雾占位 | **排期补做 or 暂存 roadmap** | Excel 拆出"规划/未实现"区或加状态列，避免读者误以为已生效 |

> ⚠️ **核心禁忌**：不要用代码的 bug 值去覆盖 Excel 的设计值（例如把"抗性涂层 -3"改成 -2 来"对齐"），那会让设计文档失守、且 bug 被永久固化。

### 11.2 总体修改原则（4 条）

1. **双列法**：每个词条加「设计值」与「当前实现值」两列，差异一目了然，从此不必反复改文档。
2. **状态列**：每列取值 `✅已实现 / ⚠️已简化 / ❌未实现`，一眼看出落地度。
3. **术语映射表**：在 Excel 顶部加一张"Excel↔代码"术语对照，消除 `实体=kinetic`、`光束=beam（≠energy）`、`自动化=special` 这类歧义。
4. **单源声明**：在表头注明"本表为权威，机甲战棋/作品设定器beta1.xlsx 的 ×5 等冲突项以本表 ×10 为准"。

3. **P2（决策）**：确定掷骰类词条"保留概率 or 永久确定性"，统一 Excel 与代码口径；决定奇袭是否改回马克西翁阵营限定。
4. **P3（规划）**：排期实现阵营/地形/协同/联防/空投生成/防御单元，并在 Excel 标记为"规划中"而非"已生效"。

> 一句话：Excel 重写的目标不是"迁就代码"，而是"用双列+状态列把设计意图与实现现状同时钉死"，再回头按 P0→P3 把代码补齐/校准，最终实现双向可追溯。

## 九、结论与建议

1. **两份设计 Excel 在机体 HP 上互相矛盾（非项目问题）**：`作品设定器beta1.xlsx`(×5) 与桌面 `战斗规则.xlsx`(×10) 不一致；项目当前 `*10` 与 `战斗规则.xlsx` 一致，**无需改代码**。建议先统一设计文档（确认哪份为权威），再回头校验导入器是否按 ×10 生成。
2. **伤害种类"超集化" + beam/energy 术语错配**：项目用 5 种 damage_kind 替代 Excel 实体/光束 二分；但装备系统把"光束"记作 `energy` 而非 `beam`（见 §十·10.6），导致**抗性涂层对光束武器实际不触发**。优先级最高的修复点是统一术语（beam→energy 或反之），否则 Excel"抗性涂层对光束-3"线上名存实亡。
3. **技能特性落地度远高于初判，偏差在"确定性化/数值/分支"**：逐条核查（§十·10.1/10.2）显示设定器 15 特性 + 特殊词条 10 条中约 20+ 已通过 `unitConverter`+`skillExecutor` 映射执行。真问题不是"没做"，而是：① 掷骰判定被确定性化（格挡/斩杀/决斗/抢夺/专注射击/幸运）；② 数值微调（全覆式/涂层 -2 vs -3、专注射击 +4 vs +3/+5）；③ 缺失分支（投掷移动-5、双槽约束、决斗同归、幸运 1-2/3-4）；④ 长柄/变形 已映射但效果疑似未执行。**建议优先修 beam/energy 与全覆式/涂层数值，再按需还原掷骰分支。**
4. **系统性缺失集中在阵营/地形/协同/防空投**：阵营 6 项仅"奇袭"有同名不同义实现（且应改为马克西翁阵营限定）；地形 6 项仅"月面"有近似地形（缺 +4 buff）；战术 协同/联防/空投生成 完全缺失；防御单元/强化防御 缺失。建议按玩法价值排期补齐。
5. **迷雾系统是占位**：当前 `fog_of_war` 不改变任何数值，建议尽快接真实命中/视野逻辑，否则该词条有名无实。
