# 战斗核心 · 词条内容计算问题报告

> 生成日期：2026-07-20
> 结论：**否** —— 战斗核心能"读到"词条配置，但**不能完整、准确地按读取的词条内容进行计算**。存在多处"读到了却不用 / 用硬编码覆盖 / 编辑器改了也不生效"的缺陷。
> 核查范围：
> - `services/combat-service/src/services/combatResolver.js`
> - `services/combat-service/src/services/combatCore/skillExecutor.cjs`
> - `services/combat-service/src/services/combatCore/damagePipe.cjs`
> - `services/combat-service/src/services/combatCore/configLoader.cjs`
> 关联报告：`词条编辑器_属性编辑逻辑报告.md`、`词条库中枢_万能语法战斗中枢v5.0_梳理与Excel对照.md`（§十·10.6 beam/energy 错配）

## 一、总体结论

| 能力 | 状态 | 说明 |
|---|---|---|
| 能读取并解析词条配置 | ✅ 是 | `configLoader.getGlossaryConfig()` 每次同步读 JSON，无加载失败 |
| 通用字段驱动计算（base_damage / accuracy_mod / height_bonus / status_effects / damage_kind 等） | ⚠️ 部分 | 仅 `skillExecutor` 的"万能路径"（handleAttack 等）真正消费；`combatResolver` 主路径大量忽略 |
| 完整按配置计算（含伤害种类、专属字段、被动加成） | ❌ 否 | 见下方 7 个问题 |

## 二、问题清单（均附代码证据）

### 🔴 P1 · 技能配置的 `damage_kind` 在主战斗路径被忽略

- **位置**：`damagePipe.cjs` L132 / L277 / L318 / L391；`combatResolver.js` L255–291
- **现象**：`DamagePipe.calculate` 全程以 `attacker.weaponType`（默认 `'kinetic'`）作为伤害种类键来查 `terrainDef.damage_kind_modifiers` / `eq[].damage_kind_modifiers` / `skill.damage_kind_modifiers`。
  ```js
  static _applyTerrainKindModifiers(defender, weaponType, terrainDefs) { ... kindMods[weaponType] ... }  // L240-244
  const weaponType = attacker.weaponType || 'kinetic';  // L277 / L318 / L391
  ```
- **关键**：`combatResolver` 调用 `DamagePipe.calculate` 时（L255），**没有把技能的 `damage_kind` 传进去**。虽然 L250–252 用 `skillExecutor._getUniversalFields(resolvedSkill.type)` 读出了 `skillUf`，但只把 `dice_type / success_line / height_bonus_per_diff / is_manual_roll` 注入管道，**`damage_kind` 被丢弃**。
- **影响**：在编辑器里把某技能的 `damage_kind` 设为 `beam`，对普通攻击结算**毫无作用**——实际生效的是单位的 `weaponType`。词条配置的这一核心字段在主路径是"死字段"。

### 🔴 P2 · `beam` ↔ `energy` 术语错配，涂层对光束永不触发（关联对照报告 §10.6）

- **位置**：`damagePipe.cjs`（用 `beam` / `weaponType`）、`equipmentDurability.cjs`（用 `energy`）
- **现象**：装备"抗性涂层"在 `equipmentDurability` 中判定 `weaponType === 'energy'`；但全局与 `DamagePipe` 的伤害种类键是 `beam`。单位 `weaponType` 多为 `'beam'`（如 `turnManager` 记录）。
- **影响**：`weaponType === 'energy'` 恒为 false → **抗性涂层对光束武器实际永不触发**。同时 P1 中地形/装备 `damage_kind_modifiers` 以 `weaponType` 为键，若单位 `weaponType` 与技能 `damage_kind` 不一致，按 `weaponType` 取修正，进一步忽略技能设定。

### 🟡 P3 · 狙击机动削减硬编码为 2，不读配置

- **位置**：`combatResolver.js` L233–241
  ```js
  if (hasSniper) { sniperMobilityReduction = 2; }   // 字面量 2，未读 glossary
  ```
- **影响**：`sniper` 技能在编辑器里即使配置了 `mobility_reduction`（配置中默认 2，恰巧相等），战斗也只认字面量 2。一旦想调成 3 或 1，编辑器改动**无效**。

### 🟡 P4 · 反击(counter)加成双路径不一致，且一处硬编码 2

- **位置**：`combatResolver.js` L343–348（被动加成提取）vs `skillExecutor.cjs` L532–548（`executeCounter`）
  ```js
  // _extractSkillBonuses 里：
  if (skill.type === 'counter') bonuses.push({ value: 2, bonus_value: 2 });  // 写死 2
  // executeCounter 里：
  const baseBonus = uf.bonus || uf.base_damage || 2;   // 读配置
  ```
- **影响**：同一 `counter` 技能，在主结算被动加成提取路径给固定 +2（**完全忽略配置**），在 `executeCounter` 路径读配置。数值来源分叉、不可预测；编辑器改 counter 的 `bonus/base_damage` 对该主路径**无效**。

### 🟡 P5 · 具名处理器消费的专属字段在编辑器中无控件 → 编辑器改动常不生效

- **位置**：`skillExecutor.cjs` 各 `executeX`（L532–869）
- **现象**：这些处理器从配置读取 `reduction / bonus / damage_multiplier / mobility_reduction / value` 等专属字段（如 `executeBlock` 用 `uf.reduction`，`executeSnatch` 用 `uf.damage_multiplier`，`executeCounter` 用 `uf.bonus`）。
- **影响**：编辑器卡片/向导**不暴露这些字段**（见编辑器报告 §五·5.3），它们停留在配置默认值。于是设计师在编辑器里改 `base_damage` 等通用字段，战斗常按 `uf.bonus || uf.base_damage || 2` 走 `bonus`（配置默认有值）→ **编辑器的改动对战斗无效**。这是"读到配置却不用/用默认覆盖"的典型表现。

### 🟢 P6 · 被动加成提取与技能执行器重复且分叉（维护性隐患）

- **位置**：`combatResolver.js` L314–360（`_extractSkillBonuses`）与 `skillExecutor.cjs` 同名方法
- **现象**：`_extractSkillBonuses` 自己写死 `counter=2`，又调用 `executeAssist/executeBlockade/executeGuard/executeFocusedFire`（这些读配置）。同一技能在两个入口逻辑分叉。
- **影响**：未来调数值需改两处，极易遗漏，且产生 P4 的"counter 双值"问题。

### 🟢 P7 · reactivate/lucky/duel/snatch 等不在被动加成提取中

- **现象**：`_extractSkillBonuses` 仅处理 `assist/blockade/counter/focused_fire/guard/...`，未包含 `reactivate/lucky/duel/snatch`。
- **影响**：若设计师在编辑器新建同类技能，其被动加成不会被主结算提取（仅在特定触发点执行），与"万能语法"宣称的"只认句式不认技能名"不符，存在死角。

## 三、验证中"确认正常"的项（避免误报）

为严谨，下列项经核查**确实读取了配置**，不是问题：
- `executeFocusedFire()`：`uf.base_damage || uf.bonus || 4`（L852）— 读配置，编辑器改 `base_damage` 对专注射击**有效**。
- `executeSnatch()`：`uf.damage_multiplier || 0.5`（L844）— 读配置。
- `executeDuel() / executeStable() / executeSweep() / executeThrow() / executeSupply() / executeAssist() / executeGuard() / executeBlockade() / executeScout()`：均通过 `_getUniversalFields` 读配置字段。
- 通用字段 `base_damage / accuracy_mod / evasion_mod / height_bonus_per_diff / success_bonus_damage / status_effects` 在 `skillExecutor` 万能路径（L218–267）确实参与计算。

## 四、修复建议（按优先级）

| 优先级 | 问题 | 建议动作 |
|---|---|---|
| **P0** | P1 damage_kind 不被主路径采用 | `combatResolver` 调 `DamagePipe.calculate` 时，把 `skillUf.damage_kind` 作为 `weaponType`/ damage_kind 参数传入（或合并单位 `weaponType` 与技能 `damage_kind`），让技能配置真正生效 |
| **P0** | P2 beam/energy 错配 | 统一术语：装备系统 `energy` 改为 `beam`（或 `applyDamage` 入口做 `beam→energy` 归一化），使涂层对光束生效 |
| **P1** | P3 sniper 硬编码 2 | 改为读取 `getSkillConfig('sniper').mobility_reduction`（并让编辑器暴露该字段） |
| **P1** | P4 counter 双路径 | 删除 `_extractSkillBonuses` 里写死的 `value:2`，统一改为调用 `executeCounter` 读取配置值 |
| **P1** | P5 编辑器改了不生效 | 在编辑器为 `reduction/bonus/damage_multiplier/mobility_reduction` 等专属字段补控件（或文档明确"仅 JSON 可改"） |
| **P2** | P6/P7 分叉与死角 | 抽象统一"被动加成提取"逻辑，消除 `combatResolver` 与 `skillExecutor` 重复分支；把 reactivate/lucky/duel/snatch 纳入泛化提取 |
