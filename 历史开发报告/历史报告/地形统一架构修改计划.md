# 地形数据统一架构修改计划

> 编写日期：2026-07-27
> 目标：理顺"自定义地形管理"与各处地形消费方的关系，明确两种统一方案并对比优劣。
> 依据：基于当前代码实测（`backend-gateway`、`frontend`、`services/combat-service`）。

---

## 一、当前的地形情况盘点

### 1.1 地形数据散落在 4 个"真相源"

| 编号 | 真相源 | 文件位置 | 存了哪些字段 | 包含地形数 |
|---|---|---|---|---|
| **S1 画笔调色板** | `UNIVERSAL_TERRAIN_MAP`（前端常量） | `frontend/src/utils/hexUtils.js` | `name / color / cost` | 约 16~21 种 |
| **S2 移动消耗表** | `TERRAIN_COST`（网关硬编码 TS） | `backend-gateway/src/routes/terrainCosts.ts` | `terrainId → number`（wall=99 不可通行） | 21 种 |
| **S3 词条库地形** | `terrains`（glossary 配置 JSON） | `services/combat-service/src/config/glossary-skill-config.json` | `name / color / material_url / move_cost / defense_bonus / is_destructible / max_hp / destroyed_transform_to / damage_kind_modifiers` | 10 种预置 + 用户可扩 |
| **S4 内核消耗表** | `TERRAIN_COST_MAP`（战斗内核常量） | `services/combat-service/src/state/battleState.js` | `terrainId → number` | 约 17 种（历史审计已知缺 6 种） |

> 注意：S1 的 `cost`、S2 的 `TERRAIN_COST`、S3 的 `move_cost` 三者在语义上都是"移动消耗"，但**是三份独立数据**；任何一处改了，另两处不会自动跟随。

### 1.2 数据流向：谁写、谁读

```
                 [ 自定义地形管理 UI ]
                  NewBattlefieldView.vue (editableTerrains)
                          │  saveTerrainConfig()
                          │  仅调用 glossaryAPI.saveConfig
                          ▼
                 ┌─────────────────────────────┐
                 │  S3 glossary-skill-config.json │  ← 唯一被"管理"写到的源
                 └─────────────────────────────┘
                          │
        ┌─────────────────┼───────────────────────┐
        ▼                 ▼                        ▼
  [攻击/掩体路径]    [可破坏地形]            [编辑器 UI 回显]
  skillExecutor      skillExecutor            （读取 S3 回填表单）
  _getTerrainDefenseBonus
  damagePipe (damage_kind_modifiers)
        │
        │  ★ 但"移动"并不读这里！
        ▼
  ┌──────────────────────────────┐
  │ S2 terrainCosts.ts (terrainCost) │ ← 真实移动路径 combat.ts /move
  └──────────────────────────────┘     → tsFindPath → terrainCost(terrainOf)
        ▲
        │  （与 S1 各自硬编码，无自动同步）
  ┌──────────────────────────────┐
  │ S1 hexUtils.js UNIVERSAL_TERRAIN_MAP │ ← 前端画笔 palette / 格子着色
  └──────────────────────────────┘
```

### 1.3 当前"自定义地形管理"实际做了什么

`saveTerrainConfig()`（`NewBattlefieldView.vue:382`）只做一件事：

```382:389:mecha-universe-engine/frontend/src/views/NewBattlefieldView.vue
const { data: current } = await glossaryAPI.getConfig()
current.terrains = JSON.parse(JSON.stringify(editableTerrains))
await glossaryAPI.saveConfig(current)   // 只写 S3
```

后端 `glossary.ts:200` 仅做 `current.terrains = {...current.terrains, ...incoming}` 后 `writeConfig()`。**完全没有触碰 S1 / S2 / S4。**

用户可编辑字段（`editableTerrains` 绑定）已较完整：`name / color / move_cost / defense_bonus / is_destructible / max_hp / destroyed_transform_to / material_url`（另 `seedTerrain` 补 `damage_kind_modifiers` 默认值）。也就是说**UI 已经能编辑"移动消耗"和"防御修正"**，只是写入后各自的生效范围不同（见 1.4）。

### 1.4 已暴露的问题（必须用本文方案解决）

1. **编辑器改 `move_cost` 对真实寻路无效。**
   真实移动走 `combat.ts /move → tsFindPath → terrainCost(terrainOf[nk])`（`combat.ts:157`），读的是 **S2 `terrainCosts.ts`**。glossary 里的 `move_cost` 只被 `skillExecutor._getTerrainMoveCost` 读取，而该方法**不在网关真实移动路径上**。所以你在 UI 调的移动消耗，改的是玩家"看得到但走不到"的值。
2. **编辑器新增的地形，画笔刷不出来。**
   画笔 palette 派生自 S1 `UNIVERSAL_TERRAIN_MAP`（`NewBattlefieldView.vue:152`）。仅写 S3 不会反向补 S1，新地形在 palette 里不存在，无法绘制。
3. **三份"移动消耗"互不同步。** S1.cost / S2.TERRAIN_COST / S3.move_cost 任一处改了都不会联动，极易出现"配置里是 3、寻路里是 1"的偏差。
4. **运行时缓存风险。** S3 经 `configLoader.getGlossaryConfig()` 缓存（进程内单例）。若把 S3 立为唯一真相，必须保证保存后能热刷新缓存，否则"管理里改了、战场仍用旧值"。
5. **S4 `battleState.js` 仍是历史遗留第四份**，需在任一方案中一并对齐或废弃引用。

## 二、方案 A：以地形为基准，统一成单一库（派生读取）

### 2.1 核心思路

> **确立 S3（glossary `terrains`）为唯一真相源。** 其余渠道（画笔 S1、移动 S2、内核 S4）不再各自硬编码，而是**在初始化/加载时从 S3 派生**（运行时生成或启动注入）。

每一个地形在 S3 里长这样（已是现成结构，直接升级为唯一库）：

```jsonc
"plain": {
  "name": "平原",
  "color": "#7a9b4f",
  "material_url": "/api/terrain/materials/plain.png",
  "move_cost": 1,           // ← 移动方读这个
  "defense_bonus": 0,        // ← 掩体减伤读这个
  "is_destructible": false,
  "max_hp": 0,
  "destroyed_transform_to": "plain",
  "damage_kind_modifiers": { "beam":1.0,"kinetic":1.0,"explosive":1.0,"corrosive":1.0,"thermal":1.0 }
}
```

### 2.2 改造清单（文件 × 改动点）

| 文件 | 改动 |
|---|---|
| `backend-gateway/src/routes/terrainCosts.ts` | 删除硬编码 `TERRAIN_COST`；改为从 `getGlossaryConfig().terrains[tid].move_cost ?? 1` 派生（保留 `terrainCost()` 函数签名不变，调用方零改动）。 |
| `backend-gateway/src/routes/combat.ts` | `tsFindPath` 已用 `terrainCost()`，函数签名不变即自动改读 S3。无需改移动逻辑本身。（核实 `terrainOf` 取值正确即可） |
| `frontend/src/utils/hexUtils.js` | `UNIVERSAL_TERRAIN_MAP` 不再硬编码常量；改为运行时 `buildTerrainMap()`：`Object.entries(glossary.terrains).map(([id,d])=>({...d, cost: d.move_cost}))`。前端加载 glossary 后注入。 |
| `frontend/src/views/NewBattlefieldView.vue` | `terrainTypes` / `getTerrainColor` / `seedTerrain` 直接读 S3，去掉对 `UNIVERSAL_TERRAIN_MAP` 的硬编码依赖（仍可保留兜底）。新增地形即时出现在 palette。 |
| `services/combat-service/src/state/battleState.js` | `TERRAIN_COST_MAP` 改为从 `getGlossaryConfig().terrains` 派生，或删除 `getTerrainCost` 改用 gateway 路径；消除第四份。 |
| `backend-gateway/src/routes/glossary.ts` | 保存时**强制热刷新** `configLoader` 缓存（增加 `reloadGlossaryConfig()` 调用），确保"管理保存→战场立即生效"。 |
| `configLoader.cjs` | 增加 `reloadGlossaryConfig()` / 失效缓存接口；支持 `getGlossaryConfig()` 返回最新。 |

### 2.3 方案 A 的运行期读取示意

```
保存：UI → glossaryAPI → S3(json) → reload 缓存
读取：
  移动   combat.ts → terrainCost(tid) → glossary.terrains[tid].move_cost
  掩体   skillExecutor → _getTerrainDefenseBonus → glossary.terrains[tid].defense_bonus
  画笔   NewBattleView → palette 由 glossary.terrains 派生
  可破坏 skillExecutor → glossary.terrains[tid].is_destructible / max_hp
```

## 三、方案 B：以功能为基准，编辑器拆分参数，分库独立保存

### 3.1 核心思路

> **保留 S1/S2/S3（及 S4）各自独立存储**，但把"自定义地形管理"升级为**分发中枢**：用户在统一 UI 里编辑一份表单，`saveTerrainConfig` 按"各 part 需要的字段"拆分，分别写回各自的库。

即 UI 是唯一编辑入口，但落地时**按字段路由**：`move_cost → S2`、`defense_bonus/color/material_url/damage_kind_modifiers/可破坏字段 → S3`、`name/color → S1`。三个库各自保存、各自读取，互不直接派生。

### 3.2 改造清单（文件 × 改动点）

| 文件 | 改动 |
|---|---|
| `backend-gateway/src/routes/terrainCosts.ts` | 由"硬编码常量"改为**可写配置**：`TERRAIN_COST` 改为运行时 `Map`，提供 `setTerrainCost(id, n)` / `loadTerrainCosts(cfg)` 接口；启动时从 S3（或独立 json）载入。 |
| `frontend/src/utils/hexUtils.js` | `UNIVERSAL_TERRAIN_MAP` 改为可写：增加 `syncTerrainPalette(glossaryTerrains)`，把 `name/color` 同步进 palette（`cost` 从 S3.move_cost 取）。 |
| `backend-gateway/src/routes/glossary.ts` | 新增"地形分发"逻辑：接收完整 `terrains` 后，除写 S3 自身外，额外调用 `setTerrainCost(...)` 更新 S2、`syncTerrainPalette(...)` 通知前端重建 S1。 |
| `frontend/src/views/NewBattlefieldView.vue` | `saveTerrainConfig` 改为：① 写 S3；② 调 `terrainAPI.syncPalette()` 或前端本地 `syncTerrainPalette` 重建画笔；③ 移动消耗随 S3 落地后由 S2 接口承接。 |
| `services/combat-service/src/state/battleState.js` | 同样改为可写 `Map`，由分发逻辑同步。 |
| 新增 `terrainCosts` 持久化 | S2 需落盘（如 `terrain-costs.json`）以免重启丢失；S1 前端需落盘（localStorage 或随 glossary 下发）。 |
| `configLoader.cjs` | 增加 S2/S4 的加载与热刷新接口。 |

### 3.3 拆分映射表（UI 字段 → 落地库）

| UI 字段 | 落地库 | 消费方 |
|---|---|---|
| `name` | S1 + S3 | 画笔/UI |
| `color` | S1 + S3 | 画笔/UI |
| `material_url` | S3 | 资源加载 |
| `move_cost` | **S2**（另同步 S3 仅作展示） | 真实移动路径 |
| `defense_bonus` | S3 | 掩体减伤 |
| `is_destructible / max_hp / destroyed_transform_to` | S3 | 可破坏地形 |
| `damage_kind_modifiers` | S3 | 伤害倍率 |

## 四、两套方案对比分析（从修改到使用）

| 维度 | 方案 A（单一库 + 派生） | 方案 B（分库 + 拆分分发） |
|---|---|---|
| **改动范围** | 中。改 6~7 个文件，但大多是"把硬编码改为读 S3"，接口签名尽量保留，调用方零改动。 | 大。需把 S1/S2/S4 从"常量"改造成"可写配置 + 持久化 + 热刷新"，新增落盘文件，改动面更广。 |
| **工作量** | 约 1 个迭代。核心是把 3 份硬编码换成派生函数 + 缓存热刷。 | 约 2~3 个迭代。每处硬编码都要加写接口、加持久化、加同步时序，易出竞态。 |
| **新增/删除地形联动** | 只改 S3 一处，画笔/移动/掩体/可破坏**自动**全部生效（派生）。 | 需保证分发逻辑覆盖 S1/S2/S3/S4 全部，漏一处就出现"能刷不能走"或"能走不能减伤"的半成品。 |
| **运行时一致性** | 天然一致：所有方都从 S3 读，无副本。 | 需主动维护多副本同步；保存失败/部分成功时会出现库与库之间不一致（需事务或回滚）。 |
| **单一真相 vs 多真相** | ✅ 单一真相，易审计、易扩展（加字段只加 S3）。 | ❌ 多真相，需保证 4 份随时相等，长期维护成本高。 |
| **缓存/热刷风险** | 集中在一点：只要 `reloadGlossaryConfig()` 正确，全链路即时生效。 | 分散在 4 处缓存，任何一处忘了热刷都会"管理改了、某方用旧值"。 |
| **前端画笔同步** | 派生源即 S3，新增地形天然进 palette，无需额外动作。 | 需 `syncTerrainPalette` 主动推，若前端缓存未重建则新地形刷不出。 |
| **移动消耗生效** | 改 S3 `move_cost` 即生效（真实路径改读 S3）。**直接修掉当前 1.4-① 的 bug。** | 需把 `move_cost` 正确分发到 S2 并落盘；若只写 S3 不写 S2，bug 依旧。 |
| **防御/可破坏/伤害倍率** | 本就读 S3，无需额外改动，已生效。 | 本就写 S3，已生效；无差别。 |
| **回退/容错** | S3 缺字段时各派生函数给默认值（如 `move_cost ?? 1`），稳健。 | 任一份损坏/缺失需各自兜底，兜底逻辑分散。 |
| **新增"part"的成本**（如将来要加 视野修正/射程修正） | 只在 S3 加字段，各消费方按需读取即可。 | 要新增一份"库"或再加分发分支，架构随功能膨胀。 |
| **风险点** | ① `configLoader` 缓存热刷必须可靠；② S4 `battleState.js` 需确认是否真在路径上，避免漏改。 | ① 多写接口的时序与原子性；② 新增持久化文件带来部署/同步复杂度；③ 前端 palette 与后端 move 表可能短暂漂移。 |
| **使用体验（策划/玩家）** | 在管理里改一处，全战场即时统一表现，心智简单。 | 在管理里改一处"看起来"统一，但底层是分发，出问题难定位。 |

## 五、结论与建议

- **当前最痛的 bug（1.4-① 移动消耗改了无效）和 1.4-②（新地形刷不出）在方案 A 下是"结构性解决"**——因为所有消费方都回到 S3 一个真相源，根本不存在"改了 A 没改 B"的缝隙。
- **方案 B 更接近"最小改动现状"**（保留既有分库结构），但代价是把"多副本一致性"的维护负担永久固化到代码里，且每次新增字段/地形都要手动保证四处同步，长期更易出错。
- **推荐方案 A**：以 S3（glossary `terrains`）为唯一真相源，S1/S2/S4 改为运行时派生，并补上 `configLoader` 热刷新。改动量适中、架构最干净、扩展成本最低，且一次性修掉当前两个已暴露的地形 bug。

> 下一步：若采纳方案 A，可基于本文 2.2 的改造清单直接开工（建议先落地 `terrainCosts.ts` 派生 + `combat.ts` 不动逻辑 + `configLoader` 热刷三件套，验证移动消耗生效后再推进前端 palette 派生）。
