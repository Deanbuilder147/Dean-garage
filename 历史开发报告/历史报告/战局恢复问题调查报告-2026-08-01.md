# 战局恢复问题调查报告

- **日期**：2026-08-01
- **排查对象**：前端「返回上次战斗」入口 + 后端战局状态路由 + 战局持久化缺失
- **关键词**：battlenotfound、f4edae19、03c9bf12、内存战局丢失、localStorage 残留、快照持久化、定时器黑洞、存储膨胀

---

## 一、问题表现（用户可见现象）

1. 用户点击「返回上次战斗」后，浏览器地址栏出现编号 `f4edae19-e49e-4447-9155-26f6d5db1792`，页面请求返回 `BATTLE_NOT_FOUND`。
2. 浏览器 Console / Network 报错信息为：
   `战局 03c9bf12-c86f-4b24-84e2-3fbd172046bd 不存在`（HTTP 404，battlenotfound）。
3. 用户观察到：从房间列表点击某个「正在进行」的对局返回时，系统反而弹出了**阵营选择**（攻击/防守/偷袭/观众），而不是像「返回上次战斗」那样直接回到战场。
4. 二者预期行为应一致（都应直接重连进战场），但实际表现不一致。

---

## 二、显因（直接触发现象的表面原因）

- 前端「返回上次战斗」按钮发起的请求，所携带的房间/战局 ID 来源不可靠：旧逻辑会优先读取 **localStorage 中过期的 roomId**（`f4edae19`），用它去请求房间/战局，而该 roomId 在后端已不存在。
- 后端战局状态路由 `GET /api/combat/:battleId/state`（`backend-gateway/src/routes/combat.ts:742-749`）直接用 URL 中的 `battleId` 去内存 `battleStore` 查找；找不到即返回 404 `战局 ${battleId} 不存在`。
- 报错里出现的 `03c9bf12` 才是请求真正到达后端时携带的 battleId（真战局），但后端内存中已无此战局。

---

## 三、根据现象定位到的真实问题

**结论先行：`f4edae19` 是假目标，`03c9bf12` 才是真战局；真正的问题是「战局内存态不持久化 + 前端恢复逻辑用了过期本地 ID」。**

### 3.1 两个编号的数据库归属（已在服务器容器内 SQLite 核实）

在 `mecha-gateway` 容器的 `/data/mecha-universe.db`（sql.js）中做全表反查：

| 编号 | `rooms` 表 | `battles` 表 | `users.last_room_id` | 判定 |
|------|-----------|-------------|---------------------|------|
| `03c9bf12-c86f-4b24-84e2-3fbd172046bd` | 房号 `904262`、名 `test`、状态 `in_battle`、`battle_id=03c9bf12` | `id=03c9bf12`、`room_id=bc31eec3`、`map_id=migrated-map-10-bb467942`、`status=in_progress` | 实战账号 `dean147` 的 `last_room_id=bc31eec3` | **真战局，确实存在** |
| `f4edae19-e49e-4447-9155-26f6d5db1792` | 无记录 | 无记录 | 无任何用户指向它 | **前端 localStorage 过期残留，数据库查无此号** |

- `03c9bf12` 是后端 `/me` 下发的正确 `lastRoomId`（房间 `bc31eec3`）所关联的 battleId，属于用户当前正在进行的战斗。
- `f4edae19` 是用户**更早一局（早已解散/换房）的房间 roomId**，被浏览器 localStorage 残留下来，被旧恢复逻辑误用。

### 3.2 为什么真战局 `03c9bf12` 会报「不存在」

战局对象只存放在**内存** `battleStore`（一个 Map）中，**未做持久化**：

- `startBattle` 流程会：生成 `battleId`（如 `03c9bf12`）→ 写入 DB 的 `battles` 表和 `rooms.battle_id` → 调 `seedRoomBattle` 把完整战局放进内存 `battleStore`。
- 但**服务重启 / 容器重建**后，内存清空，DB 里却仍留着 `battles` 记录和 `rooms.battle_id`。
- 验证：`GET /api/combat` 返回**空**（内存无任何活跃战局）；gateway 进程启动时间晚于 DB 该战局写入时间 → 印证明战局已随重启蒸发。
- 前端「返回上次战斗」拿 DB 里的 `battle_id=03c9bf12` 请求 `/combat/03c9bf12/state` → 内存查无 → 404。

### 3.3 房间列表点击「战斗中」对局为何弹阵营

`openJoinModal(id)`（`NewBattlefieldSelector.vue`）**无条件**弹出阵营选择模态框，不区分房间是否已开战；而「返回上次战斗」走 `resumeLast → doJoin`，在 `status==='in_battle' && battleId` 时**直接重连**进战场。两条路径逻辑不一致，导致用户看到的行为分裂。

## 四、相关可能的原因（按可能性排序）

1. **【已确认根因 A】前端恢复 ID 来源不可靠**
   - 旧 `onMounted` resume 逻辑：先读 `localStorage.lastRoom`（`status==='waiting'` 才用），回退再读 `localStorage.user.lastRoomId`（首屏占位用户），**没有优先使用后端 `/me` 下发的权威 `lastRoomId`**。
   - 后果：`f4edae19` 这类过期 roomId 被持续复用，指向已不存在的房间。

2. **【已确认根因 B】战局仅存内存、重启即丢**
   - `battleStore` 为内存 Map，服务重启/容器重建后蒸发；DB 残留 `battle_id` 形成「幽灵指针」，前端拿着 DB 的 battleId 必然 404。

3. **【可能原因】历史部署导致的内存清空**
   - 本次排障前有多轮部署重建前端/网关容器（`docker compose build --no-cache` + `up -d`），每次重建都会清空内存战局，但 DB 不回滚 → 放大了「幽灵指针」的出现频率。

4. **【可能原因】localStorage 跨会话污染**
   - 用户浏览器 localStorage 的 `user`（首屏占位）与 `lastRoom`（旧房间）字段，在多局/多房间切换中未被正确清理，旧 roomId 长期残留。

5. **【可能原因】`/me` 下发与首屏占位的时序竞争**
   - 宪法规定「本地 user 仅首屏占位，有 token 即 `/me` 权威覆盖」。`/me` 异步返回前，`userStore.user` 可能是 localStorage 旧值；若 resume 在 `/me` 返回前执行，会短暂命中过期 `lastRoomId`。

## 五、可能还涉及的问题（延伸风险）

1. **【高危】重启后无法恢复任何进行中对局**
   - 只要服务重启过，所有「返回上次战斗」都会 404（内存已空）。这是真实的生产可用性缺陷。
2. **【中危】战局完整态从未落库**
   - `battles` 表仅存 `id / room_id / map_id / status`，没有完整战局态（单位、AP、技能、地形等）。
3. **【中危】`seedRoomBattle` 内存态与 DB 记录脱节**
   - 房间状态（`waiting`/`in_battle`）在内存与外部 DB 同步，但战局实体本身只在内存，状态机存在「房间说在打、战局却没了」的割裂。
4. **【低危】`f4edae19` 类幽灵 ID 仍可能残留在用户浏览器**
   - 已通过修复让 resume 优先用后端值并清理过期 `lastRoom`，但用户本机 localStorage 的 `user.lastRoomId` 若仍残留 `f4edae19`，需强制刷新或清缓存后才彻底消失。
5. **【低危】房间卡片点击「战斗中」的权限/阵营丢失**
   - 改为直接重连后，若该用户此前的阵营/单位在内存战中已丢失（重启导致），重连后可能以空单位进入，需后端 rehydrate 配合才能完整恢复。

## 六、已采取的修复（2026-08-01 已部署，前端资产 index-i0JohLGi.js）

1. **resume 真相源改为后端 `/me` 下发的 `userStore.user.lastRoomId`**（DB 权威、跨浏览器），localStorage 的 `lastRoom` 仅作 `waiting` 房间辅助提示，过期 roomId 一律清除，不再用于 `in_battle` 重连。
2. **房间列表点击「战斗中对局」改为直接重连进战场**（`/battle-pc/<battleId>`），与「返回上次战斗」行为统一，不再误弹阵营选择。

部署链路：rsync → 服务器 `rm -rf dist-dev && npm run build` → `docker compose build --no-cache mecha-frontend && up -d --no-deps mecha-frontend`。验收：8081 入口引用 `assets/index-i0JohLGi.js`。

## 七、根治方案：战局状态持久化与内存重建（三步法 + 三隐患加固）

### 7.1 用户提出的三步拆分（方向正确，予以采纳）

**步骤 1 — 数据库扩容（Schema Update）**
在 `battles` 表加 `state_snapshot`（JSON TEXT 大字段），存活生生的战场数据（单位、AP、技能、地形等）。现表只有基础元数据，缺乏完整战局实体。

**步骤 2 — 状态落库（Snapshotting）**
不能只在内存里跑状态机。在关键动作（部署结束、回合推进 `advanceTurn`、重要技能结算后）把战局状态序列化、快照并 `UPDATE` 进数据库。

**步骤 3 — 内存重建（Rehydration）**
改造报错的 `GET /api/combat/:battleId/state`。内存 `battleStore` 找不到时，**不立刻 404**，而是去 DB 查；有快照则当场反序列化、重新注入 `battleStore`，让战局满血复活。

### 7.2 关键技术判断（决定实现方式）

战局对象**不能直接 `JSON.stringify`**：
- `BattleState.units` 是 `Map<EntityId, BattleUnit>`（`battleStateFactory.ts:345`），不是数组。
- `BattleUnit` 是 `createBattleUnit()` 工厂创建的实例，带计算属性/方法（非纯数据）。
- `battle.map.attributes` 也是 `Map`（`seedRoomBattle` 内 `new Map(...)`）。
- 内存中约 44 处 `battleStore.get(battleId)` 调用都依赖内存命中。

→ 必须做**选择性序列化**（`toPlainState`：Map→数组、剥方法、保留纯数据）与**选择性重建**（`fromPlainState`：复用 `createBattleState` + `createBattleUnit` 工厂恢复类方法），而非黑盒 JSON 往返。

### 7.3 三处用户补充的隐患（已逐条核对代码，确认成立并纳入方案）

#### 🕳 隐患一：定时器黑洞（The Timeout Trap）✅ 成立
- **代码实锤**：奇袭（Surprise）QTE 依赖服务器 10 秒倒计时 `pendingSurprise`，由 `setTimeout` 驱动（`pendingSurprise.timerId`）。代码里已有 `forceSettleOnTimeout(battleId, battle?)`（`combat.ts:1694`）与 `reapStalePending(battle)`（`:1854`：`phase==='waiting' && Date.now() > pend.deadline` 时强制清算）。
- **致命后果**：快照会完美恢复 `pendingSurprise`，但 Node 内存里的 `setTimeout` 随重启灰飞烟灭 → 战局永远卡在奇袭结算，等一个永不超时的倒计时，**死锁**。
- **补充修复方案（采纳）**：`fromPlainState` / 重建逻辑必须做「过期状态清理（State Reconciliation）」：
  - 快照**禁止序列化 `timerId`**（定时器对象无法 JSON 化；重建后 `pend.phase==='waiting'` 但无 timer，正是僵尸态）。
  - 重建后若存在 `pendingSurprise`，用 `reapStalePending` 检测 `Date.now() > pend.deadline`（重启通常几十秒，必超时）→ 调用 `forceSettleOnTimeout` 强制清算，恢复正常回合状态。
  - **关键发现**：`reapStalePending` 函数已存在但当前**没有任何 rehydrate 路径调用它**——本方案在 `fromPlainState` 末尾统一接入即可，零新增代码量。

#### 💾 隐患二：SQLite 存储膨胀（Storage Bloat）✅ 成立
- **代码实锤**：`battles` 是 SQLite 单表（TEXT 列）。一局完整战棋 JSON 可能 500KB~数 MB；数千局累积会拖慢全表查询。
- **补充修复方案（采纳，由「可选」升为「强制」）**：清理强绑定到战斗结算路由。
  - 当 `victoryChecker` 判定结束、`battle.status` 变更为 `finished` 时（end-turn 内 `combat.ts:988` 已置 `finished`），执行终极落库：
    ```sql
    UPDATE battles SET state_snapshot = NULL, status = 'finished' WHERE id = ?
    ```
  - 打完的局只留战绩元数据，庞大 JSON 快照**物理超度**。此步必须写进计划，不可省略。

#### 🔌 隐患三（轻微）：前端 WebSocket 断线重连时差 ✅ 成立
- **代码实锤**：前端 `NewBattleView.vue` `onMounted`（`:3746`）调 `connectBattleSocket`；Socket 重连逻辑已存在。但重连成功后**没有强制重新拉取 `GET /state`**。
- **后果**：服务器重启后所有 WS 连接被切断。玩家若正停在战斗界面（非点「返回」进来），重连后前端 Vue 状态可能与后端「借尸还魂」重建出的新状态时序错位。
- **补充修复方案（采纳）**：前端 socket `onReconnect` / 重连成功后，**必须强制重新拉取一次 `getBattleState`**（即 `refreshState()`），刷新整局内存态，消除错位。

### 7.4 修订后的完整执行计划

**第 0 步：序列化工具（battleStateFactory.ts 或新建 combatSnap.ts）**
- `toPlainState(battle)`：units → 数组、`map.attributes` → 普通对象、剔除函数/循环引用、剔除非序列化字段（`timerId` 等）、保留 round/activeFaction/turnOrder/status/pendingUnits/factionRoles/pendingSurprise（纯数据，不含 timerId）。
- `fromPlainState(plain)`：用 `createBattleState` + `createBattleUnit` 重建合法 `BattleState`（units 回 Map、实例方法恢复、`attributes` 回 Map）。
- `reconcileBattle(battle)`：**隐患一加固点** —— 调 `reapStalePending(battle)` 处理僵尸 `pendingSurprise`。
- `saveBattleSnapshot(battleId, battle)`：`run('UPDATE battles SET state_snapshot=?, snapshot_at=datetime(\'now\') WHERE id=?', [JSON.stringify(toPlainState(battle)), battleId])`（combat.ts 需补 `import { run } from '../db/sqlite.js'`，rooms.ts 已证明 `run` 导出可用）。
- `loadBattleSnapshot(battleId)`：`get('SELECT state_snapshot, snapshot_at FROM battles WHERE id=?')` → `safeParseValue` 返回 plain 或 null。
- `clearBattleSnapshot(battleId)`：**隐患二加固点** —— `run('UPDATE battles SET state_snapshot=NULL, status=\'finished\' WHERE id=?')`。

**第 1 步：Schema 扩容（sqlite.ts）**
- 沿用 `migrateExistingTables()` 的 ALTER 范式，在 `battles` 表加：
  - `state_snapshot TEXT DEFAULT NULL`
  - `snapshot_at TEXT`
- 存量库安全迁移，不影响现有列。

**第 2 步：关键动作落库快照（状态落库）**
在以下锚点动作**成功后**调 `saveBattleSnapshot`：
1. `POST .../end-deployment`（combat.ts:2309 区域）—— 部署结束首张关键快照。
2. `POST .../end-turn`（combat.ts:932，advanceTurn 后 :964）—— **同时检测 victory → 调用 `clearBattleSnapshot`**（隐患二强制清理）。
3. `POST .../attack`（:1013 区域）—— 伤害结算后。
4. `POST .../skill`（:1191 区域）—— 技能结算后。
5. `POST .../move` 及 `pending-units`（:701 区域）—— 单位位置/部署池变更后。
6. `POST .../defend` / `POST .../buff` 等结构变更动作（视代码补点）。
> 性能取舍：只在结构性变更写，不每帧写；锚点动作频率可控。

**第 3 步：内存重建（rehydration，改造 /state 路由）**
`GET .../state`（combat.ts:742）改造：
```
battle = battleStore.get(battleId)
if (!battle) {
  const plain = loadBattleSnapshot(battleId)
  if (plain) {
    battle = fromPlainState(plain)
    reconcileBattle(battle)            // 隐患一：清理僵尸 pendingSurprise
    battleStore.set(battleId, battle)  // 重新注入内存
    console.log('[rehydrate] 从 DB 快照复活战局', battleId)
  } else {
    return 404 BATTLE_NOT_FOUND        // DB 也没有才真 404
  }
}
```
- **统一兜底**：抽 `requireBattle(battleId)` 辅助函数（内存优先 → DB 重建 → 不存在返回 null），替换散落 ~44 处 `battleStore.get` + 404 样板，统一 rehydrate。同时顺手消重。

**第 4 步：前端 WS 重连加固（隐患三）**
- `NewBattleView` 的 `connectBattleSocket` 回调中，增加 `onReconnect` 分支：重连成功即 `refreshState()`（强制 `getBattleState`）一次，刷新整局态。

**第 5 步：部署与验收**
- rsync → 服务器 `docker compose build --no-cache mecha-gateway`（战局在 gateway 镜像内）→ `up -d --no-deps mecha-gateway`。
- 验收（容器内跑）：
  1. 开一局 → 部署 → 推进一回合 → 确认 `battles.state_snapshot` 非空、`pendingSurprise` 无 `timerId`。
  2. **重启 gateway 容器**（模拟崩溃）。
  3. 前端「返回上次战斗」/ 房间列表点头 → `GET /state` 从 DB 重建成功、战场复活、不再 404。
  4. **奇袭 QTE 专项**：开战触发奇袭 → 10 秒内重启 → 重连后确认 `pendingSurprise` 被 `reapStalePending` 强制清算、不卡死锁（隐患一验收）。
  5. 打完一局 → 确认 `state_snapshot` 被置 NULL（隐患二验收）。

### 7.5 风险与缓解

| 风险 | 缓解 |
|------|------|
| R1 快照体积（单局数 MB） | 只在锚点写；`battles` 用 TEXT 存无压力；finished 即清（隐患二） |
| R2 重建后类方法缺失 | 强制 `fromPlainState` + 工厂重建，不裸用 parsed 对象 |
| R3 地图/地形一致性 | 快照冻结开局地图，符合预期 |
| R4 并发写 | 回合制单局串行动作，无冲突 |
| R5 旧战局无快照 | DB 中 `03c9bf12` 这类已存在但无快照的战局，rehydrate 仍 404——**预期且正确**（确无可恢复活态）。**已存在的老战局无法凭空复活，只有本次修复后新开/推进过的战局才支持重启恢复** |
| R6 定时器黑洞（隐患一） | `fromPlainState` 后 `reapStalePending` 强制清算僵尸 `pendingSurprise` |
| R7 存储膨胀（隐患二） | victory 结算强制 `clearBattleSnapshot` |
| R8 前端时序错位（隐患三） | socket 重连成功强制 `refreshState()` |
