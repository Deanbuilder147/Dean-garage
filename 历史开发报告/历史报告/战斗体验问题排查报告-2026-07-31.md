# 战斗体验问题排查报告（2026-07-31）

> 排查范围：后端 `backend-gateway/src/routes/combat.ts`、前端 `frontend/src/views/NewBattleView.vue`、精灵解析 `frontend/src/resolvers/unitSpriteResolver.js`、尺寸映射 `frontend/src/utils/unitSize.js`、绘制 `frontend/src/utils/hexDraw.js`。
> 方式：静态代码精读 + 前端 Playwright 实测（行动画板 bug 已顺带验证修复）。**本报告只排查、不改代码**。

## 一、隐匿（Stealth）

### 1.1 现象：战斗开始时隐匿状态跑到了"防守方"棋子（阵营变马克西翁）
**根因确认（方案 A 语义错位）：**

后端 `combat.ts` 的隐匿资格判定用的是**固有阵营 faction**，不是战术角色 role：
```
combat.ts:2153  isStealthCapableUnit(unitData):
combat.ts:2155    if (String(unitData.faction).toLowerCase() === 'maxion') return true   // ← 固有阵营判定
```
而方案 A 下角色↔阵营映射为：
```
combat.ts:1094  DEFAULT_ROLE_FACTIONS = { attack: 'earth', defense: 'maxion', ambush: 'balon' }
```
即 **defense（防守）角色 → 固有 faction = maxion**。所以"防守方"单位的固有 faction 是 maxion → `isStealthCapableUnit` 直接判 true → `applySpawnStealth` 给该单位打 `stealth=true`。

用户看到的现象完全吻合：
- 场上"防守方棋子阵营变成马克西翁（maxion）"——因为该角色固有 faction 本就是 maxion，而隐匿资格又绑定 maxion，于是"防守方=maxion=隐匿"。
- 阵营单位栏里"偷袭方（ambush）"也显示隐匿——因为 ambush 单位的技能/标签里带 `stealth|隐匿|潜行|偷袭` 正则（第2168行），走的是 `isStealthCapableUnit` 的标签分支，所以单位栏也显示。

**矛盾本质**：设计意图应是"隐匿 = 偷袭方（ambush）专属"，但当前代码把隐匿绑定到了 `maxion`（=defense=防守方）。这是方案 A 双语义改造的遗留错位——`isStealthCapableUnit` 应改为按**战术角色**判断：`resolveRole(factionRoles, faction) === 'ambush'`，而非 `faction === 'maxion'`。

### 1.2 现象：隐匿部署后即生效，无需特地发动
**现状确认（当前即"部署即生效"）：**
```
combat.ts:2171  applySpawnStealth(unit): unit.stealth=true; stealthData={type:'conceal',duration:-1,auto:true}
```
登场即打 `stealth=true`，不耗 AP、不依赖按钮。前端绘制时敌方 stealth 单位不渲染（NewBattleView.vue:2270 `if(isStealth && !isMyUnit && !isGod) return`），友军可见。

**与设计意图的取舍**：
- 若意图是"偷袭方登场即隐（被动天赋）"→ 当前时机正确，只需修 1.1 的资格判定（绑定 ambush role）。
- 若意图是"需主动发动隐匿技能"→ 需移除 `applySpawnStealth` 的自动调用，改为技能触发。
- **建议**：维持"登场即隐"作为偷袭方被动，但把资格从 `maxion` 改为 `ambush` 角色，使"是谁在隐"与阵营单位栏、迷雾一致。

## 二、奇袭（Surprise / 反应奇袭）

### 2.1 现状：前后端均有完整实现，但提示依赖轮询且未经实测走通
**战斗核心（combat.ts）：**
- `maybeInterceptSurprise`（1662）：攻击时若找到反应者（findSurpriseReactors），挂起 `pendingSurprise`（10s 倒计时，`SURPRISE_TIMEOUT_MS=10000`）。
- `resolveSurpriseChoice`（1721）：锁定反应者选择 replace/counter/giveup，鉴权绑定 ownerId。
- `forceSettleOnTimeout`（1693）：超时强制清算恢复原攻击。
- `getStateView`（287）展开 battle，`pendingSurprise` 随 state 下发。

**前端展示（NewBattleView.vue）：**
- `surpriseUI`（767）+ QTE 弹窗（490-498）：⚡反应奇袭！发动/反击/放弃按钮 + 倒计时。
- `screenToneOn`（768/771）：全端暗绿滤镜，依赖 `battleState.value?.surprise || pendingSurprise`。
- `watch`（3561）：监听 `battleState.value?.surprise || battleState.value?.pendingSurprise` → `openSurprise(s)`。
- `ambushAlert`（3020）：`if(resp?.ambushed)` 触发伏击红屏警报。

### 2.2 疑似"没有提示"的可能原因（待实测确认）
1. **轮询链路脆弱**：`watch` 依赖 `battleState.value?.pendingSurprise`，而 `battleState` 由 `refreshState`→`normalizeBattleState` 刷新。`normalizeBattleState`（1152）只处理 units 数组、`return state` 原样返回，顶层 `pendingSurprise` 字段被保留——**理论上能收到**。但 Gateway 无 WS 推送（combat.ts:1317 注释明确），完全靠前端 `getStateView` 轮询；若轮询间隔 > 10s 或攻击后未立即刷新，QTE 可能错过/闪烁。
2. **`ambushed` 路径**：`ambushAlert`（3020）依赖攻击响应 `resp.ambushed`，但真实奇袭走 `pendingSurprise` 路径（响应 `interrupted:true, surprise:...`），`resp.ambushed` 可能未在该响应里置 true → 红屏警报不触发。
3. **反应者条件苛刻**：`findSurpriseReactors`（1358）要求反应者未 debt-lock 且在触发条件内；若对局中从未满足，则奇袭永不触发 → 用户"没看到提示"实为"没触发"。

**结论**：奇袭功能在代码层完整，但提示是否真正弹出需**实测**（制造一次"守方被攻"触发 reactor）验证轮询与 QTE 联动。当前静态排查无法 100% 确认提示失效，需用户配合实测或我方构造对局。

## 三、画面

### 3.1 坐标层级：确保坐标数值越大越靠前
**现状：已实现（基于屏幕 Y 的画家算法，间接满足"越大越靠前"）**
```
NewBattleView.vue:2250-2257
  unitsWithScreenY = allUnits.filter(u=>u.q!==undefined).map(...)
    .sort((a,b)=> a.screenY - b.screenY)   // Y小(远)先绘，Y大(近)后绘→覆盖在上
NewBattleView.vue:2266  forEach 按序绘制，后画者覆盖先画者
```
排序键是 **ISO 变换后的屏幕 Y**（`screenY = oy + s*(scaleY*flatX + shearY*flatY)`），非原始 q/r。默认 `shearY>0` 时 `flatX`(≈col)、`flatY`(≈row) 越大 screenY 越大 → 在默认视角下"行/列数值越大越靠前"成立。地形层（HexGridCanvasEngine:436-437/791-792）同样按 r→q 远→近绘制，与单位层一致。

**结论**：当前视角下满足需求。风险点：若后续改 `shearY=0` 或特殊 ISO 参数，靠近/远关系需重验。建议保持，无需改。

### 3.2 血条归零：自动消失 + 阵营栏变灰不可点
**现状：缺失（Canvas 与阵营栏均无死亡处理）**
- Canvas 绘制循环（2266-2466）遍历 `unitsWithScreenY`，**无 `hp<=0`/`dead` 过滤**，仅隐匿单位提前 return。HP=0 时血条宽度 0 但棋子本体仍画在场上。
- `allUnits`（1844-1849）直接映射 `battleState.value?.units`，无死亡过滤。
- 阵营栏卡片（模板 148-167）：`@click` 始终绑定 `selectUnitById`，**无 `:disabled`、无 hp 判断**；CSS（4240-4259）无 `.dead` 灰度样式。
- 全文件搜 `hp<=0`/`.dead`/`isDead` **0 命中**。

**修复点（待实施）**：
- 绘制前过滤：`unit.hp<=0 || unit.dead` 跳过（或 `allUnits` 计算属性过滤）。
- 卡片模板加 `:class="{dead:(unit.hp||0)<=0}"` + 点击守卫；CSS 加 `.faction-unit-card.dead{opacity:.4;filter:grayscale(1);cursor:not-allowed;pointer-events:none}`。
- 后端 `getStateView` 是否标记 `dead`：击杀后需确认 unit 带 `hp:0` 或 `dead:true`（建议后端在扣血归零时置 `dead=true` 并保留单位以便前端读取）。

### 3.3 xl 大小棋子模糊
**现状：问题存在（源图固定小尺寸 + 1.5x 拉伸 + 未控制平滑）**
- 尺寸系数：`unitSize.js:6` `SIZE_RENDER_SCALE={s:.82,m:1,l:1.22,xl:1.5}`。
- xl 目标尺寸 ≈ 源图 56 × 1.5 ≈ 84px（再乘视口 scale），而源图固定 `DEFAULT_RENDER_W=48/H=56`（`unitSpriteResolver.js:50-51`），不随 xl 提升分辨率。
- 全仓库搜 `imageSmoothingEnabled` **0 命中**——默认双线性插值放大 → 模糊。

**修复点（待实施）**：
- 为 xl（及 l）预置 2x 高分辨率源图或动态按 sizeScale 提升 `_buildTexture` 渲染尺寸。
- 绘制 xl 前显式 `ctx.imageSmoothingEnabled` 控制（像素风用 false，写实风用高质量 true）。

### 3.4 结算扣血：血条平滑移动 + 双方残余显示
**现状：缺失（瞬时跳变 + 结算弹窗无双方血条）**
- Canvas 血条（2453-2462）：每帧按当前 `hpPct` 直接 `fillRect`，无补间。
- 阵营栏血条（156 + CSS 4282-4285 `.fu-fill`）：仅 `{height:100%;display:block}`，**无 `transition`** → 宽度瞬变。
- 结算弹窗（475-483 `.victory-overlay`）：只显示 `winner/condition/message`，**无双方残余 HP 条**。`AttackReportModal`（486）是否含残余血条需进一步核实。

**修复点（待实施）**：
- 阵营栏 `.fu-fill.hp` 加 `transition: width .3s ease`。
- Canvas 血条引入 `displayHp` 中间值做 lerp 补间（现有 `unitLerpState` 插值引擎可复用）。
- 结算弹窗遍历参战/存活单位，按阵营展示残余 HP 条（攻击方 + 防守方）。
