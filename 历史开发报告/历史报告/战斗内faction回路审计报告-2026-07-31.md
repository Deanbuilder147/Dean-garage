# 战斗内 faction 回路审计报告

> 日期：2026-07-31
> 范围：`backend-gateway/src`（网关战斗路由 + `battleStateFactory.ts`）、`services/combat-service/src`（结算服务）
> 结论先行：**战斗内被 overloaded 成两类 faction，且只有"回合门控"读对了类型，其余所有技能/敌我/胜利/可见性逻辑都读的是"固有阵营"，没有读取"轮转角色(攻击/防守/偷袭)"。** 这正是你发现的问题：战斗里真正该被传递、被技能消费的 faction，应该是 `attack/defense/ambush` 这三种轮转角色，而不是棋子自身的 `earth/maxion/balon`。

---

## 一、两类 faction 的定义

| 名称 | 取值 | 来源 | 用途 |
|---|---|---|---|
| **固有阵营 (intrinsic faction)** | `earth` / `maxion`(即 maxon) / `balon` / `neutral` | 单位库、房间部署、`unit.faction`、`state.current_faction`、`factionRoles` 的 **key** | 棋子所属的"势力"标签，纯展示/数据归属 |
| **轮转角色 (rotation role)** | `attack` / `defense` / `ambush`（攻击/防守/偷袭） | `activeFaction`、`factionTurnOrder`、`factionRoles` 的 **value**、`resolveRole(...)` 的返回 | 战斗内驱动"谁的回合、谁能动、谁和谁一队" |

两者映射（`battleStateFactory.ts`）：
- `LEGACY_FACTION_TO_ROLE` (L47-52)：`earth→attack`、`maxion→defense`、`balon→ambush`。
- `resolveRole(factionRoles, faction)` (L58-63)：优先用 `battle.factionRoles[faction]`，否则走 legacy 映射，否则回退 `attack`。
- `battle.factionRoles` 由准备房 `rooms.ts` 的 `assignedFaction → assignedRole` 推导写入（如 `{earth:'attack', maxion:'defense', balon:'ambush'}`）。

**关键事实**：`createBattleUnit` (`battleStateFactory.ts:180-228`) 在构建 `BattleUnit` 时只写了 `faction: params.faction`（固有阵营），**没有写 `role` 字段**。因此每个部署进战场的棋子对象上，只有 `unit.faction`（固有），没有 `unit.role`（轮转）。网关在判定回合时用 `resolveRole(battle.factionRoles, unit.faction)` 即时还原成角色；但结算服务的各个 `.cjs` 模块拿不到 `battle.factionRoles` 上下文，只能直接读 `unit.faction`（固有阵营）。

## 二、战斗内 faction 数据流总览

```
准备房 rooms.ts: assignedFaction(固有) + assignedRole(轮转)
        │  构建 pendingUnit: { faction: assignedFaction, role: assignedRole }
        ▼
seedRoomBattle → battle.factionRoles{固有→轮转}, battle.factionTurnOrder[轮转...], battle.activeFaction(轮转)
        │
deploy-unit → createBattleUnit → BattleUnit { faction: 固有, (无 role) }
        │
┌─────── 网关 combat.ts（即时 resolveRole 还原）───────┐
│  /move /attack /action /react /royroy /回收 门控       │  ✅ 读"轮转角色"
│  canIssueCommand: resolveRole(factionRoles,f)===activeFaction │
└───────────────────────────────────────────────────────┘
        │
┌─────── combat-service 各模块（直接读 unit.faction）────┐
│  victoryChecker / combatResolver / skillExecutor        │  ❌ 读"固有阵营"
│  aiStrategies / reactionHandlers(cover,zoc) / factionSkillRegistry │
│  turnManager(isUnitVisible,getActiveUnits)              │
└───────────────────────────────────────────────────────┘
```

## 四、致命 mismatch 汇总（按严重度）

1. **【高】阵营技能发错**：`factionSkillRegistry` 与前端面板按**固有 faction** 发技能，而非单位在战斗中的轮转角色。单位拿到的是"势力技能"而非"攻击/防守/偷袭"技能——这正是你发现的问题。
2. **【高】胜负判定按固有阵营**：`victoryChecker` 用 `unit.faction`（固有）归并阵营、返回 `winner='earth'` 等。一旦角色与固有 faction 非 1:1，胜负错且前端展示缺映射。
3. **【高】掩护 / ZOC 按固有阵营**：`cover.cjs` / `zoc_block.cjs` 按固有 faction 找友军、组共线直线。同角色不同固有 faction 的单位无法互相掩护 / 形成 ZOC。
4. **【中】支援 / 侦察友军判定**：`combatResolver.getSupportUnits` / `skillExecutor` scout 按固有 faction 找友军，友军判定错误。
5. **【中】AI 敌我判定**：`aiStrategies` 按固有 faction 找敌/友，可能误击"同角色真队友"或漏判敌人。
6. **【中】可见性**：`turnManager.isUnitVisible` 按固有 faction 判友军可见（若网关走此路径）。

**根因**：`BattleUnit` 在 `createBattleUnit` (`battleStateFactory.ts:205`) 只写 `faction`（固有），**未写 `role`（轮转）**；网关用 `resolveRole` 即时还原角色做门控，但结算服务各模块无 `factionRoles` 上下文，直接读 `unit.faction`（固有），于是整体落回"固有阵营"语义。

**为何现在没炸**：线上"正常 3 方各一固有 faction"配置下，`factionRoles` 是 1:1 映射（earth↔attack 等），所以"固有 faction 相同"恰好等于"角色相同"，上述 mismatch 被掩盖。一旦准备房出现：同一角色下多单位、或不同角色共享固有 faction、或裁判临时调阵营，就会暴露实质 bug。

## 五、推荐修复方案（统一为"轮转角色即战斗阵营"）

**方案 A（推荐，最小侵入、向后兼容）**：
1. `battleStateFactory.ts`：`CreateBattleUnitParams` 增加 `role?: string`；`createBattleUnit` 写入 `role: params.role ?? resolveRole(params.factionRoles, params.faction)`。`combat.ts` 在 `deploy-unit` 调 `createBattleUnit` 时，把 `resolveRole(battle.factionRoles, unitData.faction)` 作为 `role` 传入（combat.ts 已有 `battle.factionRoles`）。
2. 结算服务各"友军/敌军/胜负/可见性"判定统一改成比较 `unit.role`：
   - `victoryChecker.cjs`（L30/L60-105）→ `u.role`
   - `combatResolver.js:390`、`skillExecutor.cjs:1080`、`cover.cjs:32`、`zoc_block.cjs:26` → `u.role`
   - `aiStrategies.cjs`（L82/178/246/191）→ `u.role`
   - `turnManager.js`（L509 可见性、L496 可行动单位）→ `u.role`
3. `factionSkillRegistry.cjs` 改为以 `attack/defense/ambush` 为 key（或 `getFactionSkill/getUnitSkills` 用 `unit.role` 查表）；前端 `NewBattleView.getFactionSkills` 改用 `unit.role`。
4. `victoryChecker` 的 `winner` 返回轮转角色（attack/defense/ambush），前端做映射展示。

**方案 B（不推荐）**：在网关把 `BattleUnit.faction` 直接覆盖成 `role`（入战即用 attack/defense/ambush 作 faction）。会丢失固有 faction 展示信息，且需同步改 `factionSkillRegistry` 的 key，改动面更大。

**验收口径**：
- 部署后每个 `BattleUnit` 同时带 `faction`（固有，展示）与 `role`（轮转，逻辑）。
- 同一轮转角色下的两个单位（即使固有 faction 不同），在掩护 / ZOC / 支援 / 侦察 / AI 敌我 / 胜负判定中互为队友。
- 前端"阵营技能"面板按当前角色（攻击/防守/偷袭）展示对应技能，而非按固有 earth/maxion/balon。
