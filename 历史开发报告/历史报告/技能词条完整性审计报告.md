## 〇、技能 ↔ 词条关系模型（依据设计文档）

设计表确立的层级关系是：

```
技能类型（4类）                可选词条（每技能选 1 项）
─────────────────────────────────────────────────────
近战 melee   实体/光束二选一     反击 · 格挡 · 长柄 · 补给(双槽)
远程 ranged  实体/光束二选一     扫射 · 投掷 · 稳定 · 狙击
自动化 automation 实体/光束二选一 助攻 · 守护 · 阻碍 · 侦察(双槽)
特殊加成 special               全覆式装甲 · 抗性涂层 · 变形
```

- **技能类型**决定：① 属性选择（实体/光束）② 攻击力计算方式（近战=格斗+机动差额；远程=射击+机动差额；自动化=随条件触发）。
- **词条**是挂在技能上的特效（每个技能从其类型池里选 1 个）。代码中一个单位的 `skills[]` 里每个元素的 `type` 字段就是词条 id。
- 权威中文→英文映射在 `services/combat-service/src/services/unitConverter.js` 的 `TYPE_MAP`（注释明确"匹配 Excel 技能表：反击/格挡/长柄/补给/扫射/投掷/稳定/狙击/助攻/守护/阻碍/侦察"）。

## 一、问题 1：现有"技能引用词条"程序的问题排查

### P1【最严重】9 个设计词条在词条库缺失，引擎取词失败
引擎通过 `getSkillConfig(type)` / `_getUniversalFields(type)`（`skillExecutor.cjs`）读词条配置。这 9 个词条在 `glossary.skills` 段不存在 → 返回 `null`：

- **`counter`（反击）→ 完全失效**：`skillExecutor.cjs:284` 用 `if (target && target.hp>0 && getSkillConfig('counter'))` 做**布尔门控**，词条缺失即整个反击机制永不触发（这正是此前多份报告"反击永关"的根因）。
- 其余 8 个（polearm/supply/stable/sniper/assist/guard/blockade/scout）：引擎有处理函数，但取不到词条 → **回退到代码硬编码默认值**降级运行，数值与设计文档可能不符（如 assist 默认 +3、guard 默认 -5、blockade 默认 -5、scout 默认 evasion+2，恰好与设计一致属巧合，无法通过词条库调参）。

### P2【规范不一致】category 词汇表三层互相矛盾
同一个"技能类型"概念，三套代码用了三套词：

| 层 | 取值 | 出处 |
|---|---|---|
| 设计文档 | 近战 / 远程 / 自动化 / 特殊加成 | 用户提供的设计表 |
| 词条库契约（规范） | `melee / ranged / automation / support` | `frontend/src/contracts/skillContract.js`、`glossary-excel-validator.ts`(`VALID_CATEGORIES`) |
| 战斗转换层 | `melee / ranged / auto / special` | `unitConverter.js _getSkillCategory` |
| 现网词条库数据 | `melee / ranged / special` | `glossary-skill-config.json` |

具体矛盾：
- **`auto` ≠ `automation`**：战斗层用 `auto`，规范用 `automation`，二者不相等。
- **`special` 不在规范枚举内**：契约 `SKILL_CATEGORIES` 无 `special`，校验器对 `category=special` 既警告"已归为 melee"又报"非法 category"，前端 `validateSkill` 也判非法。**但现网词条库有 5 个技能（execute/duel/snatch/lucky/reactivate）正用 `category:"special"`** —— 现网数据自带规范冲突，一旦走 Excel 导入/前端编辑校验就会报错或被静默改成 melee。
- **`support` 规范有、战斗无**：契约支持 `support` 类别，但战斗 `_getSkillCategory` 不产生它。
- 设计文档的「自动化」词条（assist/guard/blockade/scout）规范 category 应为 `automation`，但因词条整体缺失，现网无从体现。

**向下兼容策略（评审补充·已采纳）**：统一目标枚举为契约四值 `melee/ranged/automation/support`，但改动必须做**双向容错**，避免旧对局/单位快照反序列化失败：
- `unitConverter._getSkillCategory` 改为 `case 'auto': case 'automation': return 'automation';`，并将 `special` 归并到 `support`（保留 `special` 仅作展示、校验层放行）。
- 校验器 `glossary-excel-validator.ts` 的 `VALID_CATEGORIES` 增加 `'auto'/'special'` 为**兼容别名（警告不报错）**，使现网 5 个 `special` 技能（execute/duel/snatch/lucky/reactivate）与历史单位 JSON 不被拦截。
- 引擎 `_getUniversalFields` 读 `cfg.category || 'melee'`，旧快照里 `category:'auto'/'special'` 仍能被正常反序列化（仅展示文案差异），无需改。

### P3 特殊加成不属于 skills 词条体系（且变形未实现）
- `full_armor`(全覆式装甲) / `coating`(抗性涂层) 在 `combatResolver.js:111/123`、`damagePipe.cjs:337` 以**装备/耐久槽位**（`['full_armor','coating','shield_gen','reactive_armor']`）参与 `EquipmentDurability.applyDamage` 减伤并扣耐久。这是"加成"而非"技能"，结构上（获得条件/加成对象/目标属性/加成数值/耐久度）也塞不进现有 skills schema —— **不应录入 skills 段**。
- `transform`(变形) 在战斗逻辑里**完全未实现**（代码中所有 transform 都是地形 `destroyed_transform_to`，与变形无关）。

### P4 "选 1 项"约束无程序强制
单位 `skills[]` 可挂任意数量词条，无"每个技能类型限选 1 词条"的引擎/校验约束。属数据录入纪律，录入时需人工遵守。

### P5 已存在 3 词条的 category 与 attack_stat 一致性
block(category=melee, attack_stat=melee)、sweep(ranged/ranged)、throw(ranged/ranged) 均自洽，近战用格斗、远程用射击，与设计文档攻击力计算方式一致。新增词条时需保持 `category` 与 `attack_stat` 同步。

## 二、问题 2：如何按"现有词条库规范"录入设计文档词条

### 2.1 录入路径（三选一，推荐 A）
- **A. GlossaryView.vue 结构化 CRUD**：填表后 `POST /api/combat-glossary/config`，前端 `serializeSkillToContract` 会同时产出"新契约字段 + 旧镜像字段"，零回归兼容引擎 `_getUniversalFields`。**最稳妥**。
- **B. Excel 导入**：经 `glossary-excel-parser.ts` 解析 + `glossary-excel-validator.ts` 校验（列：key/name/category/target_scope/cast_range_min/max/skill_shape/damage_kind/base_damage/action_type/type/has_dice/dice_type/dice_branches…）。
- **C. 直接编辑 `glossary-skill-config.json` 的 `skills` 段**（需同时满足两套字段，见下）。

### 2.2 必须遵守的规范枚举
| 字段 | 合法值 |
|---|---|
| `category` | `melee` / `ranged` / `automation` / `support`（**不要用 special/auto**） |
| `damage_kind` | `kinetic` / `beam` / `explosive` / `corrosive` / `thermal` |
| `action_type` | `attack` / `heal` / `buff` / `debuff` / `passive` |
| `type` | `active` / `passive` |
| `attack_stat` | `melee` / `ranged` / `max` |
| `skill_shape` | `single` / `fan` / `linear` / `concentric` |
| `target_scope` | `enemy` / `ally` / `enemy_equipment` / `ally_equipment` |
| `dice_type` | `4` / `6` / `8` / `10` / `12` / `20` |

> 引擎 `_getUniversalFields` 实际读取的是**旧字段**（`reduction`/`bonus`/`value`/`evasion_mod`/`cast_range`/`base_damage`/`success_bonus_damage` 等），所以录入时**两套字段都要给**（新契约供校验/展示，旧字段供引擎结算）。

### 2.5 特殊加成（不入 skills）
`full_armor`/`coating` 已是装备耐久体系，保持现状；`transform` 在战斗逻辑里**完全未实现**，三者**不录入 skills 段**。
- 如确需词条化，应为"加成"单独建一类 schema（含 获得条件/加成对象/目标属性/加成数值/耐久度）。
- **评审补充·变形短期替代方案**：若策划希望短期内可见"变形"效果，可将其定义为一个**切换形态 Buff 技能**（消耗 1 动作点、-3 基础攻击、+3 机动/移动力），直接复用现有 `buff` 机制（`action_type:"buff"`，用 `value` 或 `-base_damage`+`bonus` 表达），无需开发"多形态机体数据替换系统"。此项为**独立可选**，不纳入本次 9 词条。

### 2.6 评审补充点落实（用户审阅 3 条优化·已核对引擎源码）
1. **cast_range 必为标量（已修正）**：引擎 `_getUniversalFields`（`skillExecutor.cjs:67`）直接 `cfg.cast_range ?? 1` 当数字用；若 `cast_range` 为对象，`dist > cast_range` → `NaN` 比较恒为 false → 距离检查形同虚设。网关 `resolveSkillRange`（`combat.ts:639`）的 `pickNum` 仅处理 `number|string`，遇对象返回 `undefined` → **静默跳过射程校验**（不崩溃，但射程拦截失效）。故 2.4 全部改为 `cast_range`(标量)+`min_cast_range`(标量)，已剔除所有 `{min,max}` 对象。
2. **supply `heal` 公式字符串（已修正）**：引擎**无任何公式解析器**（`reduction/bonus/value/base_damage` 均为 `?? 0` 直接取数）；且 `executeSupply`（`skillExecutor.cjs:700-703`）**根本不读 `heal` 字段**，回血量硬编码为 `unit.melee + success_bonus_damage`。故 2.4 删除 `heal:"melee*1"`，仅保留 `success_bonus_damage`（可调）。同理 `extra_range_cardinal`/`initCounter`/`slots`/`reveal_area` 均被引擎忽略，已从草稿删除（计数 5/3/3 实际由 `initAssistCounter`/`initGuardCounter`/`initBlockadeCounter` 硬编码，数值恰与设计表一致）。
3. **transform 短期 Buff 替代（已记录）**：见 2.5 末段，作为独立可选项，待你决定是否纳入。

### 2.7 前端 UI 渲染校验（scout.cast_range=0 的展示风险·评审补充）
- 核对 `NewBattleView.vue` 技能卡片渲染：`getActiveSkillTooltip`（805-833 行）仅对 `focused_fire/sweep/throw/directional_beam` 有特殊文案，**scout 走 `default` 分支返回 `skill.description`** → tooltip 显示正常（2.4 草稿 description 已写明"暴露敌方3×3区域并自身闪避+2"）。
