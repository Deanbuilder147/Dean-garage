## 二、四个修复明细

### 修复 1【P0】AI 距离计算：曼哈顿 → 立方距离（`aiIntegration.cjs`）

**问题**：`getDistance` 用 `|dq|+|dr|`（偏移坐标曼哈顿距离），对六边形是错的；`isInRange` 读 `attacker.attack_range`（单位无此字段，恒为 `undefined`→`1`），导致 AI 永远按射程 1 行动，且距离误判。

**改动**：
- 新增模块级 helper（与后端 `hexDistanceOffset` 同公式）：
  ```js
  function evenROffsetToCube(q, r) {
    const x = q - (r - (r & 1)) / 2;
    const z = r;
    const y = -x - z;
    return { x, y, z };
  }
  ```
- `isInRange`：`const range = attacker.attack_range || 1;` → `const range = attacker.range || attacker.currentStats?.range || 1;`
- `getDistance`：改用立方距离 `(|dx|+|dy|+|dz|)/2`。

### 修复 2【P0】AI 范围判定：用 `hexDistance` 且字段名 `range`（`aiStrategies.cjs`）

**问题**：`findEnemiesInRange`（基类 + `BalancedStrategy` + 另一子类共 3 处）及 `findBestMoveTarget` 攻击范围判定，均用 `manhattanDistance` 与 `unit.attack_range || 1`。讽刺的是同文件第 9 行已存在正确的 `hexDistance`，却未被采用。

**改动**：
- 全部 `manhattanDistance(unit.position, enemy.position)`（攻击范围相关调用点，5 处）→ `hexDistance(...)`。
- 全部 `unit.attack_range || 1`（4 处）→ `unit.range || unit.currentStats?.range || 1`。
- **保留** `manhattanDistance` 定义与导出：测试文件 `phase8-ai-system.test.cjs` 仍断言其原值，未破坏。

### 修复 3【P1】前端 glossary 技能高亮字段读取（`NewBattleView.vue`）

**问题**：`getSkillRange`/`getSkillRangeMin` 只认 `skill.range`/`skill.range_min`/`skill.category`，不认 glossary 技能实际携带的 `cast_range`/`max_range`/`min_cast_range`。`skillGroups` 透传的 glossary 技能对象无 `range` 字段，于是高亮回退到 `selectedUnit.range`（单位基础射程），与后端 `resolveSkillRange` 读 `max_range` 在"技能射程 ≠ 单位射程"时产生偏差。

**改动**：重写两函数，按优先级读取 `range / range_max / max_range / cast_range`（支持数字、`"1-3"` 字符串、`{min,max}` 对象）与 `min_cast_range / min_range / range_min`，与后端 `resolveSkillRange` 完全对齐。

### 修复 4【P2】前端死代码清理（`NewBattleView.vue`）

**问题**：`attackRangeHexes`（声明后从未填充）及其红色高亮块（约原 1831-1840 行）永不触发，属冗余死代码。

**改动**：删除 `const attackRangeHexes = new Set()` 声明及红色高亮绘制块。攻击范围实际由 `skillRangeHexes`（黄色环）正确呈现，功能无缺失。

## 七、二次仔细复查与补漏（2026-07-24 晚）

用户要求"仔细检查"，复查中发现**上一轮修复本身引入了符号错误**，并暴露两处既有攻击范围 bug。已修复并重新部署。

### 7.1 复查发现的真实问题

1. **【严重·我引入】`aiIntegration.evenROffsetToCube` 符号写反**
   我上一轮新写的 helper 用了 `x = q - (r - (r & 1)) / 2`，但后端真值 `hexDistanceOffset`/`offsetToAxial` 用的是 `q - (r + (r & 1)) / 2`。两者在**偶数行巧合相等、奇数行算错距离**。

2. **【严重·既有】`aiStrategies.hexDistance` 缺 offset→axial 转换**
   原公式 `(|dq|+|dr|+|d(q+r)|)/2` 直接把**偏移坐标**当**轴向坐标**套用，对偏移坐标本身就是错的（且此前该函数未被调用，是被我上一轮改成调用才暴露）。

3. **【严重·既有】`damagePipe.calculateHexDistance` 根本不存在**
   `factionSkillRegistry.cjs` 在阵营技能 AoE 半径判定处（行 82/220/315）调用 `DamagePipe.calculateHexDistance(...)`，但 `damagePipe.cjs` 从未定义该方法 → 阵营技能一旦触发 AoE 必抛 `TypeError` 崩溃。

> **为何上一轮漏掉**：上一轮冒烟测试恰好只用了偶数行样本 `(0,0)→(1,2)`，三种公式巧合一致，掩盖了奇数行的分歧。本次改用含奇数行的多组样本才暴露。

### 7.2 修复

- `aiStrategies.cjs` `hexDistance` 重写为正确的 Even-R offset→axial→cube（`q - (r + (r & 1)) / 2`，取 `max`）。

## 八、伤害结算机动差公式（路由链路延伸，2026-07-25）

用户确认原公式 `小计 = 基础攻击力 + 骰子 + 高地` 缺少"双方机动值差"项，并补充三条规则。本期在 `/attack` 与 `/skill` 路由 → `skillExecutor._executeAttackSkill` 链路接入机动差计算。

### 8.1 用户定义规则

1. **机动差方向**：攻方机动高 → 增伤；守方机动高 → 减伤（即 `攻击力 - 双方机动值差`）。
2. **攻击方优势封顶**：攻方机动优势带来的增伤 **最高 +4**；若 `机动差 > 4`，实际取 `4`。
3. **防御方优势无上限**：守方机动高导致的减伤 **不设上限**。
4. **武器机动叠加**：若攻击来源为**武器类装备**，攻击方有效机动需叠加该武器机动值。

### 8.2 路由链路改动

| 链路 | 位置 | 改动 |
|---|---|---|
| 武器机动解析 helper | `combat.ts` 模块级 `computeWeaponMobilityBonus`（紧随 `resolveSkillRange`） | 新增。扫描 `exeCaster.equipState` 中 `type==='武器'` 的条目，取其 `mobility`；武器来源判定：`skillSlot` 为空（基础 melee/ranged 攻击）或属于武器槽 `left/right/extra`。按 `slot` 匹配具体武器，否则汇总所有武器机动。 |
| `/skill` 路由注入 | `combat.ts` `/skill`（exeCaster/exeTarget 解析后、executeUniversalSkill 前） | 由 `exeCaster.skills` 找到 owned 技能的 `slot`，调用 helper，将 `weaponMobility` / `isWeaponAttack` 注入 `context`。 |
| `/attack` 路由注入 | `combat.ts` `/attack`（executeUniversalSkill 前） | 基础攻击 `slot=null`（武器来源）；技能攻击取 `exeCaster.skills` 中 `skill_id` 对应 `slot`，调用 helper 注入 `context`。 |
| 引擎消费 | `skillExecutor.cjs` `_executeAttackSkill` | 读 `context.weaponMobility` / `context.isWeaponAttack`：攻击方有效机动 `attMob = 机体机动 + (武器来源? 武器机动 : 0)`；`mobilityMod = attMob - 守方机动`；若 `mobilityMod > 4` 封顶为 `4`（仅攻击方优势封顶，防御方优势 `<0` 不动）。 |

### 8.3 公式

```
攻方有效机动 attMob = 机体机动 + (武器来源 ? 武器机动 : 0)
机动差修正 mobilityMod = attMob - 守方机动
  if mobilityMod > 4: mobilityMod = 4        // 攻击方优势增伤封顶 +4
  // 若 mobilityMod < 0（守方优势减伤）则不封顶
小计 subtotal = 基础攻击力(baseDamage) + mobilityMod + 骰子(diceBonus) + 高地(heightBonus) + ...
```

`formula[]` 明细新增独立步骤「机动差修正」，desc 显示 `攻方机动(机体X+武器Y) - 守方机动 Z = N（封顶/无上限）`，前端 `AttackReportModal` 动态遍历自动呈现。

### 8.4 验证（node 实测）

| 场景 | 攻方机动 | 守方机动 | 武器 | 期望 mobilityMod | 实际 |
|---|---|---|---|---|---|
| 普通攻击 攻10/守5 | 10 | 5 | 0 | 封顶 → +4（原式 5→4） | +4 ✅ |
| 武器攻击 机体2+武器6=8 / 守5 | 2(+6) | 5 | 6 | +3 | +3 ✅ |
| 机体攻击 攻2/守5（减伤） | 2 | 5 | 0 | −3 不封顶 | −3 ✅ |
| 机体攻击 攻2/守30（巨额减伤） | 2 | 30 | 0 | −28 不封顶 | −28 ✅ |
| 武器攻击 机体1+武器3=4 / 守5 | 1(+3) | 5 | 3 | −1 | −1 ✅ |
