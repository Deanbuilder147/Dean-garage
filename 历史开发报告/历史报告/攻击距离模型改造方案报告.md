## 一、你的原始设计（复述，用于对齐）

| 层 | 规则 |
| --- | --- |
| **基础距离（按攻击类型）** | 近战 = **1 格**；远程 = **3 格**；自动化 = 类似 buff，**对自己释放（0 格 / self）** |
| **词条修饰（叠加在基础上）** | 近战词条：`长柄` +1 格；远程词条：`稳定` +1 格、`狙击` 距离变成 **4~6 格**的范围、**投掷** 对 **1~3 格内某点**造成以其为中心的 **1 格半径 AoE（落点 AoE）**；`扫射` 维持**原本的扇形 AOE**（形态不变） |

## 二、当前战斗逻辑"取距"的真实链路（实测代码）

取距不是一个地方决定的，而是**三处各取所需**，且权威方是前端：

1. **前端 `getSkillRange` / `getSkillRangeMin`**（NewBattleView.vue L2562-2617）——**合法目标的唯一权威闸门**。
   - 技能有 `range/range_max/max_range/cast_range` 字段 → 直接用（数字 / `"1-3"` 字符串 / `{min,max}`）。
   - 这些字段都没有时回退：`melee → 1`；`ranged/auto → unit.range || 2`。
   - 基础普通攻击（`skill=null`）→ `unit.range || 1`，**不区分近战/远程**。

2. **后端 `combat.ts` `/attack` 内联定义**（L980-1010、L1050-1110）。
   - 技能攻击：`realRange = owned.cast_range ?? owned.range ?? owned.max_range ?? 1`（**直接读单位 Excel 技能自带数值，覆盖词条库**）。
   - 基础攻击：`rangeVal = currentStats.range ?? (at==='ranged' ? 2 : 1)`（远程默认 **2**，不是 3）。

3. **结算端 `skillExecutor._executeAttackSkill`**（L203-212）距离校验——**已被注释移除**，注释写明"射程判定统一由前端 `getSkillRange + validTargets` 门控完成"。所以后端现在**不再校验距离**，完全信任前端选中的目标。

**词条库**（glossary-skill-config.json）当前存的是**绝对数值**：
- `polearm`(长柄) `category:melee, cast_range:2`
- `stable`(稳定) `category:ranged, cast_range:4`
- `sniper`(狙击) `category:ranged, cast_range:6, min_cast_range:4` → 4-6
- `sweep`(扫射) `category:ranged, cast_range:2, max_range:2, sector_angle:60, mode:deterministic_sweep, aoe_radius:0` → **扇形 2 格**（即你要维持的"原本扇形 AOE"，与现状一致，**无需改**）
- `throw`(投掷) `category:ranged, cast_range:3, min_cast_range:1, aoe_radius:1` → **1-3 + AoE 1**（这正是你描述的"对 1-3 距离内某点造成以其为中心 1 格半径范围伤害"的落点 AoE 形态，已符合，**无需改**）

## 三、冲突分析（逐条）

### 冲突 A：基础距离按攻击类型（近战1/远程3/自动0）根本没实现
- 当前远程默认是 `unit.range || 2`（前端回退）或 `currentStats.range ?? 2`（后端基础攻击），**没有任何地方把"远程"硬编码成 3**。
- `category` 字段虽已存在于词条库（melee/ranged/auto），但只用于伤害类型与选靶，**从未用于推导基础距离**。
- 影响：若单位 `range=2`，远程攻击实际只有 2 格；若 `range=4`，远程攻击变成 4 格——与"远程恒为 3"的设想不符。

### 冲突 B：词条是"绝对数值"，不是"基础 + 修饰"的组合
- `长柄=2`、`稳定=4`、`狙击=4-6` 都已是**最终结果值**，没有"melee基础1 + 长柄+1"这种可组合结构。
- 后果：**脆弱**。若你以后把"远程基础"从 3 改成 4，`稳定` 不会自动变成 5，必须手动改词条库每个数值。反之若想调长柄为 +2，也要逐条改。
- 这与你"基础由类型定、再按词条修饰"的设计**语义相反**——你要的是**组合解析**，现在是**写死**。

### 冲突 C：扫射 / 投掷 形态已符合，无机制冲突（更正）
- 经你最新确认：**扫射维持原本的扇形 AOE**，而"对 1-3 距离内某点造成以其为中心 1 格半径范围伤害"的**落点 AoE 形态属于投掷**。
- 当前词条库：`扫射` = 60° 扇形、最远 2 格（即"原本扇形 AOE"，**与你要的一致，无需改**）；`投掷` = 1-3 + aoe_radius 1（**正是落点 AoE 形态，也已符合，无需改**）。
- 结论：**之前报告误将投掷的形态归给扫射，并据此判定"扫射机制完全不同"——此为误判，现更正：扫射与投掷的形态当前均已符合你的设计，二者是并列的两种远程词条（扇形 AOE vs 落点 AoE），不存在需要重写的机制冲突。**

### 冲突 D：自动化/buff 不是 self(0)
- 你要"自动化类似 buff，对自己释放（0 格）"。
- 当前前端 `getSkillRange` 对 `auto` 回退到 `unit.range || 2`，**不是 0/self**；后端 `supply` 词条 `cast_range:1`（邻接友军），属于"auto 但可指向邻接"，并非纯 self。
- 影响：纯自身 buff（如 D-field 守护类）当前可能被误当成有射程的技能。需明确：auto + `target_scope:self` → 0；auto + 邻接友军（如补给）→ 保留其显式距离 1。

### 冲突 E：生产优先级——内联 Excel 射程覆盖词条库
- `combat.ts` 用 `owned.cast_range ?? ...` 优先取**单位自带数值**，词条库被架空。
- 若改造成"基础+词条修饰"组合模型，**必须让词条（或"攻击类型+词条"的解析结果）成为唯一真相**，否则组合逻辑只在词条库生效、线上仍用 Excel 老数值，等于没改。

### 冲突 F：狙击是"替换"不是"叠加"，不能和稳定共存
- 你要的 `狙击` = 远程距离**变成** 4-6（替换基础 3）。这是 `range_override`（min4/max6），与 `稳定`(+1) 是**互斥的两种远程词条**，不能同时叠成 5-7。当前词条库把狙击存成绝对 4-6，语义上已是 override，但缺乏"与稳定互斥"的显性约束。

### 冲突 G（次要）：基础攻击不分近远程
- 前端 `getSkillRange(null)`（普通攻击）一律 `unit.range || 1`；后端基础远程默认 2、近战 1。**普通远程攻击应是 3**，当前偏短。

## 五、改造方案（可落地）

### 5.1 新增统一取距核心函数 `resolveSkillRange(skill, glossary)`（单真相）
放到前后端都能用的共享模块（建议 `combat-service/src/services/combatCore/skillRangeResolver.cjs`，前端通过 `createRequire` 或复制一份纯函数复用）。

```js
const BASE = { melee: 1, ranged: 3, auto: 0 };
function resolveSkillRange(skill, glossary) {
  const entry = glossary[skill.glossaryKey] || {};
  const cat = skill.category || entry.category || 'melee';
  const base = BASE[cat] ?? 1;
  // 1) 替换型（狙击/投掷）：显式 min/max 覆盖
  if (entry.range_override) {
    return { min: entry.range_override.min, max: entry.range_override.max,
             aoe_radius: entry.aoe_radius || 0 };
  }
  // 2) 修饰型（长柄+1 / 稳定+1）
  const bonus = entry.range_bonus || 0;
  const max = base + bonus;
  const min = (cat === 'auto') ? 0 : (entry.min_cast_range ?? 0);
  // 3) 投掷特例（落点 AoE）：reach 1-3 + 落点 AoE1
  if (entry.is_drop_aoe) {
    return { min: entry.reach_min ?? 1, max: entry.reach_max ?? 3,
             aoe_radius: entry.aoe_radius ?? 1, shape: 'drop_aoe' };
  }
  return { min, max, aoe_radius: entry.aoe_radius || 0 };
}
```

### 5.2 词条库 schema 扩展（glossary-skill-config.json）
给每个词条加 `range_rule` 字段，取代"靠 cast_range 猜含义"：
- `长柄`：`{ "range_bonus": 1 }`（melee 基础1 → 2）
- `稳定`：`{ "range_bonus": 1 }`（ranged 基础3 → 4）
- `狙击`：`{ "range_override": { "min": 4, "max": 6 }, "requires_unmoved": true }`
- `投掷`：`{ "is_drop_aoe": true, "reach_min": 1, "reach_max": 3, "aoe_radius": 1 }`（落点 AoE 形态）
- `扫射`：`{ "range_override": { "min": 0, "max": 2 }, "sector_angle": 60 }`（维持原本**扇形 2 格**，作为固定距离词条，不参与"远程基础3+0"——即保持原样不变）
- `补给`：`{ "range_override": { "min": 1, "max": 1 } }`（auto 基础0，但**仅可指向邻接友军 range=1，禁止对自己释放**——与前端 `target_scope:ally` 双保险，底层数据模型同样排除 self，不再用 min:0 自相矛盾）
- 反应类（反击/格挡/…）：维持原 `cast_range` 作为反应触发距离，不参与攻击基础距离。

> 旧 `cast_range` 字段保留为**回退默认值**，仅在缺少 `range_rule` 时启用，保证老数据不崩。

### 5.3 前端 `getSkillRange` / `getSkillRangeMin` 改造（NewBattleView.vue）
- 优先调用 `resolveSkillRange`；仅当无词条解析结果时，才回退到现有的"读 range/cast_range 字段"逻辑。
- 删除 `ranged/auto → unit.range || 2` 的回退，改为经 `resolveSkillRange` 得到基础 3 / 0。
- 普通攻击（`skill=null`）：依据玩家选择的近战/远程，分别返回 1 / 3（不再是 `unit.range||1`）。
- **扫射选靶 UI 维持原样**：扫射是扇形 AOE，前端原本就画扇形，无需重写；投掷的落点 AoE 选靶 UI 本已存在，也无需改。

### 5.4 后端 `combat.ts` 内联定义 + 距离校验回归
- `realRange` 不再直接读 `owned.cast_range`，改为 `resolveSkillRange(owned, glossary)` 的结果；内联 Excel 数值降级为"缺失词条时的回退"，**消除冲突 E**。
- 在 `_executeAttackSkill` 恢复距离断言（用解析出的 `{min,max}`），使后端自洽——即使前端门控被绕过也不会出现超距结算（防御性，不破坏现有正常流程）。

### 5.5 扫射 / 投掷 机制（无需重写）
- 经更正：**扫射维持原扇形 AOE**（`deterministic_sweep` 分支保留），**投掷已是落点 AoE**（`aoe_radius:1` 邻域取法本就存在）。二者均无需改动，本节原"扫射机制重写"计划**取消**。

### 5.6 自动=self、远程基础=3 的默认值修正
- `auto` 基础 0；`target_scope:self` 的技能 distance 校验跳过（自身必中）。
- 基础远程攻击默认 3（combat.ts `at==='ranged' ? 3 : 1`）。

### 5.7 数据迁移映射（现有技能 → 新 schema）
| 现有词条 | 新 range_rule |
| --- | --- |
| polearm cast_range2 | base melee1 + bonus1 |
| stable cast_range4 | base ranged3 + bonus1 |
| sniper 4-6 | override{4,6} |
| throw 1-3,aoe1 | override{1,3}, aoe1 |
| sweep 扇形2 | range_override{0,2}, sector60（维持原样，固定2格） |
| supply cast1 | override{1,1}（仅邻接友军，禁 self） |
| counter/block/… | 维持反应距离不变 |

## 八、自动化技能落地方案与条件触发架构（2026-07-27 追加）

> 本章在第五章（攻击距离 `auto=self 0`）基础上，进一步解决"自动化技能发动后**如何真正生效**"以及"未来**条件化自动技能**如何在不重构的前提下扩展"。包含两件事：① 你已拍板的 assist/guard 语义；② 在 Buff/Status 重构与 damagePipe 结算中**预留条件触发（Conditional Triggers）扩展性**。

### 8.1 语义拍板：assist/guard = 被动常驻但限量 N 次

经你确认，assist/guard/blockade 这一族"自动化"技能采用如下语义：

- **激活即生效**：玩家对自己发动该技能后，立即进入"常驻生效"状态，无需再次确认。
- **用完即停**：按"剩余次数（counter）"消耗，次数耗尽自动失效。
- **再次发动才能再次行动**：要恢复效果，必须**重新发动一次该技能**（重新建立 counter），而非自动续期。

这澄清了此前"持续回合 vs 限量次数"的歧义——**assist/guard/blockade 是"次数制（counter）"，不是"回合制（duration）"**。注意：这并不排斥"某些自动化技能用回合制"，二者是**两个正交维度**（见 8.3）。为表达清晰，定义 Buff/Status 的两个轴：

| 轴 | 取值 | 说明 | 当前适用 |
| --- | --- | --- | --- |
| **消耗模型 consumption.mode** | `counter` / `duration` | 次数制 vs 回合制 | assist/guard/blockade = `counter`；阵营 buff = `duration` |
| **触发条件 trigger.type** | `unconditional` / `conditional` | 无条件 vs 条件匹配 | 当前 assist/guard = 无条件；未来"仅近战受击减伤" = 条件 |

### 8.2 现状审计：为什么当前生产路径里自动化技能"没生效"

（基于本轮代码核查，仅作背景，落地计划见 8.8）

- **配置层已具备**：glossary-skill-config.json 中 `assist/guard/blockade` 均为 `category:auto`、`target_scope:self`，计数逻辑 `executeAssist/executeGuard/executeBlockade` 也写好了。
- **致命缺口（生产路径未接线）**：
  - **A. 激活不持久化**：网关 `POST /api/combat/:battleId/skill` 调用 `executeUniversalSkill` → `_executeBuffSkill`，后者只返回 `{buff_value}` 不写回施法者单位；`/skill` 路由回写逻辑也只动目标 HP，**caster 单位上没有任何状态残留**。
  - **B. 攻击/受击不消费**：真实路径 `executeUniversalSkill → _executeAttackSkill` 完全不调用 `executeAssist/executeGuard`，两者是死代码（仅存在于一条平行测试路径 `combatResolver` 中，且该路径用 `increment=false` 导致计数器永不递减）。
  - **C. 模型割裂**：旧 `BuffManager` 用 `attack_buff / attack_buff_turns` 等**扁平标量**存储，无法承载 counter、condition、trigger 等结构化信息——这正是需要重构的根本原因。

结论：积木（计数逻辑、词条语义、damagePipe 输入接口）基本齐全，**本次重构核心是"建立结构化 Buff 模型 + 把消费接线到真实路径"**，并非从零造轮子。

### 8.3 统一 Buff/Status 数据结构（预留 `condition` / `trigger_type`）

**旧模型局限**：`BuffManager` 用 `unit.attack_buff / defense_buff / mobility_buff` 三个标量 + 对应 `_turns` 字段，只能表达"3 种固定类型 + 回合倒计时"，无法表达：
- 次数制 counter（assist/guard 需要）；
- 条件触发（仅近战/特定伤害类型才生效）；
- 同一单位叠加多个同类但不同条件的 buff。

**新模型**：将单位 buff 改为**列表化 `statusEffects` 数组**，每个实例是结构化对象。单位上新增 `unit.statusEffects = []`（旧标量保留为回退，保证老数据不崩）。

```js
// 统一 Buff/Status 实例结构（statusEffects 数组元素）
{
  id: 'st_20260727_assist_01',     // 实例唯一 ID（同技能再次发动 = 新实例）
  source: 'assist',                // 词条库 glossary key
  label: '助攻',
  action_type: 'attack_buff',      // 修饰类型：attack_buff / defense_buff / mobility_buff / ...
  value: 3,                        // 数值大小（增伤 + / 减伤 - / 机动修正 ±）

  // —— 消耗模型（consumption）——
  consumption: {
    mode: 'counter',               // 'counter' 次数制 | 'duration' 回合制
    remaining: 5,                  // 剩余生效次数（counter）或剩余回合（duration）
    max: 5                         // 初始值（前端进度条显示用）
  },

  // —— 条件触发（trigger / condition）——【本版核心扩展性预留】——
  trigger: {
    type: 'unconditional',         // 'unconditional' | 'conditional'
    attack_type: null,             // 触发所需攻击方攻击类型：['melee'] / ['ranged'] / ['melee','ranged']；null=不限
    damage_kind: null              // 触发所需伤害类型：['beam','kinetic','explosive',...]；null=不限
  },

  // 生效方向（枚举，三选一）：
  //   'attack'               = 自身发动攻击时生效（assist 增伤）
  //   'defense'              = 自身受击时生效（guard 减伤）
  //   'attack_debuff_target' = 自身发动攻击时，对【目标】施加 Debuff（blockade 削弱目标机动）
  //   —— 'attack'/'defense' 修饰的是"自身"，'attack_debuff_target' 修饰的是"被攻击的目标"
  applies_on: 'attack'
}
```

> **关键扩展点**：`trigger` 字段即你要求的 `condition` / `trigger_type`。未来任何"条件化自动技能"只需在词条库配置 `trigger:{type:'conditional', attack_type:[...], damage_kind:[...]}` 即可落地，**无需改动匹配引擎与 damagePipe**（见 8.4 / 8.5）。

### 8.4 条件触发匹配引擎（ConditionTrigger Matcher）

独立纯函数工具（建议放 `combat-service/src/services/combatCore/conditionTrigger.cjs`），供 damagePipe 与 BuffManager 共用：

```js
/**
 * 判定某 buff 是否被本次攻击触发
 * @param {Object} buff - statusEffects 元素（含 trigger 字段）
 * @param {Object} ctx  - { attack_type:'melee'|'ranged', damage_kind:'beam'|'kinetic'|... }
 * @returns {boolean}
 */
function matchTrigger(buff, ctx) {
  const t = buff.trigger || { type: 'unconditional' };
  if (t.type !== 'conditional') return true;            // 无条件：始终匹配
  const atOk = !t.attack_type || t.attack_type.includes(ctx.attack_type);
  const dkOk = !t.damage_kind  || t.damage_kind.includes(ctx.damage_kind);
  return atOk && dkOk;                                   // 攻击类型 AND 伤害类型 同时命中
}
```

匹配规则一览：

| buff.trigger | 攻击方 attack_type | 攻击方 damage_kind | 是否触发 |
| --- | --- | --- | --- |
| `unconditional` | 任意 | 任意 | ✅ 总是 |
| `conditional, attack_type:['melee']` | melee | 任意 | ✅ |
| `conditional, attack_type:['melee']` | ranged | 任意 | ❌ 不触发 |
| `conditional, attack_type:['melee'], damage_kind:['beam']` | melee | beam | ✅ |
| `conditional, attack_type:['melee'], damage_kind:['beam']` | melee | kinetic | ❌ 不触发 |
| `conditional, damage_kind:['kinetic']` | 任意 | kinetic | ✅ |

> **不触发 = 既不减免/增加伤害，也不扣减层数**（这是"条件触发"与"无条件"的本质区别：无条件 buff 每次命中都消耗，条件 buff 只在命中条件时消耗）。

### 8.5 damagePipe 结算集成（结算伤害与扣减层数前做匹配校验）

**原则（契合战斗宪法"单向数据管道"）**：damagePipe 保持**纯函数**——只读取输入、返回计算结果与"应扣减的 buff 列表"，**不主动修改任何单位状态**；真正写回 `statusEffects` 的是调用方（`skillExecutor` / `combat.ts`）。

**新增阶段（插入在现有阶段之间，全部基于 `unit.statusEffects` + `matchTrigger`，绝不回退到 `executeAssist/executeGuard/executeBlockade` 等写死函数）**：

- **阶段 1.5（攻击方对目标机动削弱匹配）**：在阶段 2（机动值差）之前，遍历**攻击方** `statusEffects` 中 `applies_on:'attack_debuff_target'` 的条目，用 `matchTrigger(buff, {attack_type, damage_kind})`（以**攻击方**的攻击/伤害类型为上下文）过滤；命中者将其 `value` 作为机动削弱量累加到 `mobilityDebuff`，并从 `config.defender_effective_mobility` 中扣减（即 `effectiveDefMobility = max(0, defMobility - sniperReduction - mobilityDebuff)`）。命中的 blockade 实例 id 同样进入 `result.triggered_status`。这是 blockade「下几次使对方机动-5」的唯一落点——它走 `attack_debuff_target`，而非 `attack`/`defense`。
- **阶段 3.5（攻击方增伤匹配）**：`_calcExtraValues(attacker)` 累加 bonuses 时，对 `applies_on:'attack'` 的 buff 先过 `matchTrigger(buff, {attack_type, damage_kind})`，仅命中者计入。`attacker.bonuses` 改为从 `unit.statusEffects` 派生（过滤 `action_type` 与 `applies_on:'attack'`）。
- **阶段 8.5（防御方减伤匹配）**：`_calcDefense` / `_calcArmorReduction` 读取 `defender.buffs`（派生自 `unit.statusEffects`，过滤 `applies_on:'defense'`）时，先用 `matchTrigger` 过滤——仅条件命中的 guard 类减伤生效。
- **阶段 12.5（产出待扣减列表）**：damagePipe 在返回结果中附加：

```js
result.triggered_status = [
  // 所有在本轮结算中被"命中条件且被实际使用"的 statusEffects.id
  // 含 applies_on 三种方向：attack(assist) / defense(guard) / attack_debuff_target(blockade)
  'st_20260727_assist_01',
  'st_20260727_guard_03',
  'st_20260727_blockade_02'
];
```

调用方在拿到 `final_damage` 并回写 HP 后，遍历 `result.triggered_status` 调用 `BuffManager.consumeStatus(unit, id)`（counter 模式 `remaining--`，归零则移除；duration 模式不在此处扣减，留给 `tickBuffs` 在回合末处理）。

> 注意：damagePipe 的 `attack_type` 与 `damage_kind` 输入**已经存在**（`config.attack_type`、`config.damage_kind`），无需新增接口；只需把 `defender.buffs` 从旧的标量求和升级为"结构化 statusEffects + 条件过滤"，即可实现匹配校验。**整套增伤/减伤/削机动逻辑统一由 `unit.statusEffects` 遍历 + `matchTrigger` 动态提取，彻底废弃 `executeAssist/executeGuard/executeBlockade` 等硬编码函数**（见 8.8 Phase 5）。

### 8.6 端到端示例：『仅在受到近战攻击时，下 2 次受击伤害减免』

词条库新增（或现有 `guard` 扩展为可带 trigger 的泛化形态）：

```json
{
  "guard_melee": {
    "label": "近战守护",
    "category": "auto",
    "target_scope": "self",
    "action_type": "buff",
    "consumption": { "mode": "counter", "remaining": 2, "max": 2 },
    "trigger": { "type": "conditional", "attack_type": ["melee"], "damage_kind": null },
    "applies_on": "defense",
    "value": 5
  }
}
```

激活后单位 `statusEffects` 产生实例：`{ ..., value:5, consumption:{mode:'counter',remaining:2,max:2}, trigger:{type:'conditional',attack_type:['melee']}, applies_on:'defense' }`。

结算走查：

| 来袭攻击 | 条件匹配？ | 伤害处理 | counter 变化 |
| --- | --- | --- | --- |
| 敌方近战（melee） | ✅ 命中 | 该次伤害 -5 | 2 → 1 |
| 敌方近战（melee） | ✅ 命中 | 该次伤害 -5 | 1 → 0（效果耗尽，自动移除） |
| 敌方远程（ranged） | ❌ 不命中 | 不减伤、不消耗 | 维持 0（已耗尽）/ 或中途的剩余值不变 |
| 敌方光束近战（melee, beam） | ✅ 命中（damage_kind 未限） | 该次伤害 -5 | 递减 |

> 此示例**完全由 `trigger` 配置驱动**，匹配引擎与 damagePipe 无需为它写任何特例代码——这正是本架构"预留扩展性"的落地形态。

**blockade（阻碍）的落点**：`blockade` 词条配置 `applies_on:'attack_debuff_target'`、`value:-5`、`consumption:{mode:'counter',remaining:3,max:3}`。当你发动攻击时，阶段 1.5 用**攻击方**的攻击/伤害类型匹配，命中则从目标有效机动中扣 5，并随本次攻击把该实例计入 `triggered_status` 扣减一次（剩余 3→2→1→0）。它**不**走 `attack`（不增伤）、也**不**走 `defense`（不减伤），只走 `attack_debuff_target`——这正是上一版遗漏、本次补齐的生效方向。

### 8.7 与攻击距离模型的衔接

- 第五章已解决 `auto = self(0)` 的取距问题（自动化技能对自己释放、无射程门槛）。
- 本章解决"**发动之后如何真实生效 + 如何条件化**"——两者正交：取距决定"能否选目标"，Buff 模型决定"发动后产生什么状态、何时消耗"。未来设计具体条件技能时，只需在词条库配 `trigger` + `consumption`，并复用本章引擎。

### 8.8 实施顺序（待你确认后展开为完整计划）

1. **Phase 1 — 统一 Buff/Status 数据结构**：单位新增 `statusEffects` 数组；旧 `attack_buff/_turns` 标量保留为回退。定义 `statusEffects` 元素 schema（含 `consumption` + `trigger`）。
2. **Phase 2 — ConditionTrigger 匹配引擎**：新建 `conditionTrigger.cjs`，实现 `matchTrigger(buff, ctx)` 纯函数（8.4）。
3. **Phase 3 — BuffManager 列表化重构**：新增 `addStatus / getMatchingStatus(unit, ctx, applies_on) / consumeStatus(unit, id) / tickStatus(unit)`；旧标量 API 改为读 `statusEffects` 的兼容壳。
4. **Phase 4 — damagePipe 条件集成**：阶段 1.5（blockade 机动削弱）/ 3.5（assist 增伤）/ 8.5（guard 减伤）统一用 `matchTrigger` 过滤；阶段 12.5 产出 `result.triggered_status`（保持纯函数，不写状态）。
5. **Phase 5 — 真实路径接线（彻底废弃 `executeAssist/executeGuard/executeBlockade` 旧函数）**：
   - **激活持久化**：`/skill` 路由对 `action_type:buff/debuff` 的技能，由 `_executeBuffSkill` 依据词条库配置（value / consumption / trigger / applies_on）**生成 `statusEffects` 实例**并写回 caster（或 target）单位；不再只返回裸 `buff_value`。
   - **攻击消费（统一遍历 `statusEffects` + `matchTrigger`，不调用任何 `executeXxx` 写死函数）**：`_executeAttackSkill` 改为：
     1. 攻击前：用 `BuffManager.getMatchingStatus(attacker, {attack_type, damage_kind}, 'attack')` 提取增伤，并入 finalDamage；
     2. 攻击前：用 `getMatchingStatus(attacker, {attack_type, damage_kind}, 'attack_debuff_target')` 提取机动削弱，传入 `config.defender_effective_mobility`；
     3. 受击前：用 `getMatchingStatus(defender, {attack_type, damage_kind}, 'defense')` 提取减伤，并入防御；
     4. 结算后：拿 `result.triggered_status` 调 `BuffManager.consumeStatus` 扣减被命中的层数（assist/guard/blockade 全走同一通道）。
   - 增伤、减伤、削机动**三件事全部动态提取**，与技能名彻底解耦——未来新增任何条件技能都不必改 `_executeAttackSkill`。旧 `executeAssist/executeGuard/executeBlockade` 函数从 `skillExecutor.cjs` 删除。
6. **Phase 6 — 前端反馈**：buff 条显示"剩余 N 次 / 剩余 N 回合" + 条件标签（如"仅近战"）。
7. **Phase 7 — E2E 验证**：沙盒战局验证 ①assist 增伤且 5 次后停 ②guard 减伤且 3 次后停 ③条件技能仅命中时生效与消耗 ④再次发动可恢复。

> **前置依赖**：自动化技能落地（Phase 1–7）与第五章攻击距离改造相互独立，可并行；但 Phase 4 的 damagePipe 集成建议与第五章同一次发布，避免半接入状态。
