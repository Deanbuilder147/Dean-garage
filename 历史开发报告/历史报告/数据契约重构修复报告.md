## 一、第一步：A5 胜利条件现网死链修复（防腐层）

### 1.1 根因（已代码确权）
- 前端整备室 `NewPreparationRoom.vue` 发送扁平形状：`{ conditions:[...], hold_round, target_q, target_r }`。
- 核心消费端 `victoryChecker.cjs` 实际读取 `vc.facility.{q,r,hp,faction,attacker,holder}`（L53/100/137）。
- **字段名错位 → `facility` 恒为 `undefined` → `destroy_facility` 与 `hold_position` 永不触发**（战局无法结算 = 现网卡死）。这就是 A5 由 MEDIUM 升 HIGH 的活 bug。

### 1.2 修复（网关防腐层，零侵入核心结算）
`combat.ts` 新增 `normalizeVictoryConditions(body)`，**在写入 `battle` 元数据前**合成引擎期望的 `facility`：

```js
function normalizeVictoryConditions(body) {
  const conditions = Array.isArray(body?.conditions) ? body.conditions.slice() : [];
  const vc = { ...body, conditions };
  const needFacility = conditions.includes('destroy_facility') || conditions.includes('hold_position');
  if (needFacility) {
    const toNum = (v) => (v === undefined || v === null || v === '' ? undefined : Number(v));
    const q = toNum(body.target_q ?? (body.facility && body.facility.q));
    const r = toNum(body.target_r ?? (body.facility && body.facility.r));
    const hp = typeof body.facility_hp === 'number' ? body.facility_hp
             : (body.facility && typeof body.facility.hp === 'number' ? body.facility.hp : 100);
    vc.facility = { q, r, hp,
      faction: body.facility_faction ?? (body.facility && body.facility.faction),
      attacker: body.facility_attacker ?? (body.facility && body.facility.attacker),
      holder:   body.facility_holder   ?? (body.facility && body.facility.holder),
      owner:    body.facility_owner    ?? (body.facility && body.facility.owner),
      capturer: body.facility_capturer ?? (body.facility && body.facility.capturer) };
  }
  return vc;
}
```

路由体改为 `(battle as any).victoryConditions = normalizeVictoryConditions(conditions);`。

### 1.3 关键防御点
- **`hp` 默认正值（100）**：设施须被攻击至 `hp<=0` 才获胜，避免开局即胜（自爆）。
- **不覆盖未来扩展**：若 payload 已带 `facility`，以其为准。
- **前端补齐 hold_position 坐标**：`NewPreparationRoom.vue` 新增坚守坐标输入，并在提交时透传 `facility_attacker`（攻击方阵营 `roleFactions.attack[0]`）/ `facility_holder`（防守方 `roleFactions.defense[0]`）。

### 1.4 顺带修复的 hold_position 前置契约
`victoryChecker.hold_position` 读取 **顶层 `u.q`/`u.r`** 判定占位，但 `createBattleUnit` 只暴露 `position.{q,r}`。为不让防腐层白做，在 `createBattleUnit` 暴露顶层 `q/r`（与 `position` 同源），并在 `combat.ts` 移动路由更新位置时同步 `unit.q/unit.r`。

### 1.5 验收
`data-contract-tests.cjs` 断言：
- `destroy_facility` + `facility.hp<=0` → 攻击方获胜 ✅
- `destroy_facility` + `facility.hp>0` → 不误判 ✅
- 旧形状（无 `facility`）→ 永不被触发（**死链复现，印证修复价值**）✅
- `hold_position` + 友军占位 + 轮次达标 → 坚守方获胜 ✅

> ⚠️ **已知后置依赖**：`destroy_facility` 要真正取胜，还需存在一条「削减 `facility.hp`」的路径（当前引擎无设施伤害动作）。防腐层已让条件可被引擎正确读取与判定，削减设施 HP 的触发动作列入后续迭代。

## 二、🔴 第一梯队：高危系统锁死防御

### A3 · 阵营安全兜底锁（`factionSkillRegistry.cjs`）
- **原状**：`getFactionInfo(faction)` 未知阵营返回 `null`；若未来任一逻辑段读取 `.color`/`.id`/`.skills` 会抛 `TypeError` 致 `/attack` 500。
- **修复**：未知阵营返回与已知阵营**同构**的安全结构 `{ id, name, style:'未知', description:'', skills:{}, buff:{} }`。
- **保留**：`getFactionSkills` 未知返回 `[]`（必须保持数组，否则破坏 `.forEach`）—— 不动。
- 测试：`getFactionInfo('my_custom')` 非 null、`skills` 为对象、`getFactionSkills('my_custom')` 为 `[]`、已知 `earth` 正常 ✅

### A2 · 坐标 Key 大一统（新建 `hexKey.cjs`）
- **新建** `services/combat-service/src/services/combatCore/hexKey.cjs`，导出唯一真相源 `getHexKey(q,r) => q + ',' + r`。
- **收敛调用点**：
  - 网关 `buildTerrainMap`（地形字典 → 防月面回退）
  - `skillExecutor.cjs` 全部地形读取（掩体减伤、移动成本、友军集合）共 4 处
  - 网关 `deploy_royroy` 占用格判定
  - 移动路由 `unit.position` 同步
- 前端 `hexUtils.js` 同步导出 `getHexKey`（availability，调用方后续统一）。
- 测试：`getHexKey(3,4)==='3,4'` ✅

### A1 · 射程二次断层回归守卫（`battleStateFactory.ts`）
- **原状（历史 bug，已于 2026-07-24 修复）**：`range` 仅存 `currentStats.range`，前端读顶层 `selectedUnit.range` 读不到。
- **加固**：`createBattleUnit` 中顶层 `range` 与 `currentStats.range` **双向同步**，任一缺失即回退另一来源（再兜底 1）：
  ```js
  currentStats: { ...params.currentStats, range: params.currentStats?.range ?? (params.range ?? 1) },
  range: params.range ?? params.currentStats?.range ?? 1,
  ```
- `CreateBattleUnitParams` 新增可选 `range?: number` 字段。

## 三、🟡 第二梯队：中等风险数据归一化

### A8 · Royroy 阵营透传（`combat.ts` /action deploys）
- `deploy_royroy` 部署时强制透传母机：`roy.faction = host.faction; roy.ownerId = host.ownerId;`
- `RoyroyState` 类型新增 `faction?` / `ownerId?`，确保未来被纳入 AoE/ZOC/友军识别时不再读 `undefined`。

### A4 · 词条标量校验 + 死字段标注（`glossary.ts`）
- 新增 `normalizeSkillForSave(key, raw)`：
  - `cast_range` 必须标量数字（对象/数组会致 NaN 比对失效），缺失兜底 1；
  - `trigger` 字段标为**死字段**（仅被 `_getUniversalFields` 读出，无调度逻辑）—— 保留但强制为字符串，非空值 `console.warn` 提醒维护者勿作分派键。
- `POST /config` 合并非核心词条时统一走该归一化。

### A7 · 部署池装备形状 sanitize（`combat.ts` /pending-units）
- 新增 `sanitizeEquipment(equipment)` + `DKM_KEYS = ['kinetic','beam','explosive','corrosive','thermal']`：
  - 非普通对象 → `{}`；
  - 每个槽位携带的 `damage_kind_modifiers` 归一为 5 个标准伤害类型的数值对象（缺失补 0、非数 coerce 0）。
- 落库前 `pendingUnits.map(u => ({ ...u, equipment: sanitizeEquipment(u.equipment) }))`，防范减伤功能因脏数据失效。
