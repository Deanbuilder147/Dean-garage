# 机动（Mobility）字段系统性修复报告

> 日期：2026-07-23
> 范围：`mecha-universe-engine` 前端 `NewBattleView.vue` + 后端 `backend-gateway/src/battleStateFactory.ts`
> 状态：**已定位根因 + 已实施系统性修复 + 已部署**

---

## 1. 现象

用户反馈：在战场上查看 `weirdnova` 棋子时，行动面板的「机动」一栏显示为 `?`。

经排查确认，`?` 出现在**部署阶段面板**（`selectedDeployUnit.mobility || '?'`）与**战场阶段面板**（`selectedUnit.mobility || selectedUnit['机动'] || '?'`）两处。`weirdnova` 只是最先暴露的个例——其根因是系统性的字段语义断层，绝非单一棋子数据问题。

---

## 2. 根因（系统性，而非单棋子的数据错误）

**「机动」在整套系统里没有唯一权威字段**，同一概念分散在至少 4 类命名/位置中：

| 来源 | 字段 | 说明 |
|------|------|------|
| 后端 `currentStats` | `mobility` | 战斗单位顶层机动（createBattleUnit 透传） |
| 后端 `currentStats` | `speed` | 移动力总预算，前端 `moveRange` 实际取自它 |
| hangar 数据 `attributes.parts` | `机动`（中文字段，分部位） | 真实来源：`主机体.机动` + `其它(载具).机动` + … |
| hangar 数据顶层 | `mobility` / `机动` / 旧 `main_机动` | 不同历史版本遗留的扁平字段 |

而前端两条显示链路**只读 `mobility` 与 `机动` 两个字段**：
- 部署面板：`selectedDeployUnit.mobility || '?'`
- 战场面板：`selectedUnit.mobility || selectedUnit['机动'] || '?'`
- `normalizeBattleState`（`NewBattleView.vue`）只把 `attack/defense/range/shield/armor/maxHp` 从 `currentStats` 提到顶层，**从不处理 `mobility`**。

**运行态数据实证**（服务器 gateway SQLite `units` 表，共 12 个单位）：
- 仅 **1/12** 个单位的 `stats` JSON 含 `mobility` 字段；
- **11/12** 个单位（含 weirdnova）的 `stats` 只有 `speed`/`range` 等，没有 `mobility`；
- weirdnova 的真实机动藏在 `attributes.parts`：`主机体.机动=10`、`其它(载具).机动=10`（合计 20），而顶层既无 `mobility` 也无 `机动`。

**读链命中不了任何来源 → 回退到 `?`**（部署面板）；战场内则因 `createBattleUnit` 的 `mobility = currentStats.mobility ?? 0`，对缺 `mobility` 的单位统一显示错误的 `0`。

### 为什么是 weirdnova 最先暴露？
它刚好满足「三重缺失」：`stats` 无 `mobility`、顶层无 `机动`、且其显示链路不会去读 `attributes.parts.*.机动`。其它多数单位因 `stats` 中碰巧写了 `mobility`/`speed` 而侥幸显示，属于**掩埋的同类缺陷**——一旦移动到只含 `parts.机动` 的数据路径，同样会 `?` 或 `0`。

---

## 3. 影响范围（不止 weirdnova）

- **部署阶段面板**：所有缺少顶层 `mobility` 的棋子 → `?`（11/12 单位潜在命中）。
- **战场阶段面板**：所有缺少 `stats.mobility` 的棋子 → 显示错误的 `0`（同样 11/12 单位）。
- 移动高亮依赖 `moveRange || mobility || 机动 || 3`，缺字段时退到魔法数字 `3`，与面板数值不一致。

---

## 4. 修复方案（已实施）

核心思想：**建立唯一权威解析器 `resolveMobility`，覆盖所有已知来源；在「数据进入显示前」的每一道边界都做一次归一化**。这样无论单位数据来自哪一版 schema，都不会再出现 `?` 或错误的 `0`。

### 4.1 解析优先级（单一真相）
```
mobility = stats.mobility
         ?? stats.speed            // 移动力总预算，与 moveRange 一致
         ?? Σ attributes.parts.*.机动   // 分部位中文合计
         ?? 顶层 mobility / 机动 / main_机动
         ?? 0
```
> 语义约定：`speed` 被视作移动力总预算（与 `moveRange` 同源），`mobility` 优先于 `speed`；`parts.机动` 合计作为最终兜底。weirdnova 实际解析结果 = `speed=3`（与其移动范围一致）。
> 若希望「机动」显示部件合计 20，只需把 `Σ parts.机动` 提到 `speed` 之前（一行调整）。

### 4.2 改动清单
1. **后端 `battleStateFactory.ts` · `createBattleUnit`**
   - 新增 `sumPartsMobility(parts)`：累加 `attributes.parts` 中每个部件的 `机动`/`mobility`。
   - `mobility` 与 `moveRange` 改为 `currentStats.mobility ?? currentStats.speed ?? sumPartsMobility(parts) ?? 0`。
   - 效果：**从源头**保证战场单位拥有正确机动，前端即使不归一化也不会 `0`。

2. **前端 `NewBattleView.vue`**
   - 新增 `resolveUnitMobility(raw)`（与后端同源逻辑），兼容 `stats.mobility / stats.speed / attributes.parts.*.机动 / 顶层 mobility / 机动 / main_机动`。
   - `normalizeBattleState`：对每个单位 `u.mobility = resolveUnitMobility(u)`；`u.moveRange` 缺失时回退到 `u.mobility`。
   - `loadDeployPool`：后端 API 分支与 hangar 回退分支都对部署池单位做 `mobility` 归一化。
   - 显示层：部署面板 `selectedDeployUnit.mobility ?? '—'`、战场面板 `selectedUnit.mobility ?? selectedUnit['机动'] ?? '—'`，彻底移除 `?` 兜底（归一化后不会再触发，仅留 `—` 作为极端兜底）。

### 4.3 为何其它棋子不会再出现
解析器对任意来源取「第一个存在的数值」；只有当一个单位 `stats` 与 `parts` 与所有顶层字段**全无**机动信息时，才回退到 `0`（不再是 `?`）。这从结构上封死了「字段名不匹配即 `?`」的整类缺陷。

## 6. 后续建议（可选增强）

1. **统一字段契约**：在长期规划中，建议后端在 `createBattleUnit` 时把「机动」写入一个**固定顶层字段**（如始终 `mobility`），并让 hangar 入库时把 `parts.机动` 合计回填进 `stats.mobility`，从源头消灭多命名并存。
2. **回归防护**：建议加一个前端单元测试，断言 `resolveUnitMobility` 对四类来源（mobility / speed / parts.机动 / 顶层 机动）均能正确取值，防止此类字段断层复发。
3. **同类隐患扫描**：`attack/defense/range/shield` 虽已由 `normalizeBattleState` 提到顶层，但部署阶段面板仍直接读 `selectedDeployUnit.attack` 等原值；建议部署面板也走同一归一化，避免部署期出现同类 `?`。
