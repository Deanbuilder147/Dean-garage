## 二、引擎现状的三个关键事实（实现前必读）

### 事实 1：`trigger` 字段目前是"死字段"，但这不是障碍而是机会

`skillExecutor.cjs:62` 把 `cfg.trigger` 读进万能字段后，**再无任何代码消费它**。斩杀/抢夺/决斗/幸运/再动的执行函数全部已写好（`skillExecutor.cjs:913-990`），但全项目搜索确认**零调用点**。

这意味着：**你的表格里"发动阶段"这一列，恰好就是引擎缺失的那一层。** 我们不需要发明新架构，只需要把你表格的"发动阶段"列变成真正的调度器。

### 事实 2：真正干活的结算路径只有一条，钩子落点非常集中

生产环境真实结算链路（已核实）：

```
前端 → POST /api/combat/:battleId/attack (combat.ts:803)
     → executeUniversalSkill (skillExecutor.cjs:149)
     → switch(action_type) 五谓语之一
     → 回写 currentStats.hp (combat.ts:915-930)
```

你的 10 条词条里，**7 条的钩子都能挂在 `/attack` 路由的前后两个点上**（攻击宣言前 / 伤害回写后），不需要侵入引擎内部。回合类挂 `/end-turn`（combat.ts:486 的 `isNewRound` 分支），移动类挂 `tsFindPath`（combat.ts:92）。

### 事实 3：已有一个"接线成功"的范本可以照抄——反击（counter）

```javascript
// skillExecutor.cjs:284 —— 全项目唯一真接线的反应钩子
if (target && target.hp > 0 && getSkillConfig('counter')) {
    const counterRes = this.executeCounter(target, unit, ...);
}
```

模式 = **"词条存在即门控 + 在结算管线固定位置硬编码调用"**。本报告的方案就是把这个模式**泛化成注册表**，让 10 条词条复用同一套机制，而不是再写 10 个 if。

### 二·补.2 最致命的架构偏差

**实时 `/attack` 的伤害是 `_executeAttackSkill` 内联算的（`finalDamage = baseDamage + diceBonus + heightBonus`，`skillExecutor.cjs:278`），完全不调用 `DamagePipe.calculate`（已验证 `skillExecutor.cjs` 内 0 调用）。** 连锁结论：

1. **抗性（resistance）目前在实时攻击里 100% 不生效**——`damagePipe` 的减免逻辑只活在 `combatResolver`（死路径）和废弃的 `combatIntegrator` 里。要让抗性生效，必须让实时伤害路径读取 `damage_kind_modifiers`。
2. **`skillRegistry` 的加成（`focused_fire` 等）在 `/attack` 基础攻击里不生效**——`/attack` 直连 `executeUniversalSkill`，后者内部不调 `getBonusExtractor`。只有硬编码的 `counter`（`skillExecutor.cjs:284` 直接 `executeCounter`）生效。
3. **击杀判定点**在 `combat.ts` 写回 `writeBackTarget.currentStats.hp` 之后（约 L915-930），`_executeAttackSkill` 内部拿到的是 `toExecutorUnit` **副本**，改 `target.hp` 不会回写真实战局。

### 二·补.4 前后系统衔接与数据流核对

实时 `/attack` 数据流（新效果必须落在真实对象上）：
```
combat.ts /attack
  → exeCaster = toExecutorUnit(caster)   // 副本
  → exeTarget = toExecutorUnit(tu)       // 副本（改它不回写！）

### 二·补.5 关键架构纠正（替代报告原"从零建 TriggerEngine"）

不另建 `TriggerEngine`，改为**在实时主链路挂 H2（伤害已结算）钩子**，复用现有 `EffectExecutor`/`ConditionEvaluator`：

1. **抗性**：在 `skillExecutor._executeAttackSkill` 伤害公式处，调用一次 `DamagePipe._calcArmorReduction`（或抽出纯函数）读 `defender.skills/装备` 的 `damage_kind_modifiers`；补 glossary `resistance`/装甲配置。代价最小，近乎纯配置。
2. **专注射射**：在 `_executeAttackSkill` 内加 `focused_fire` 判定（持有 + 未移动 + ranged）→ 调用 `executeFocusedFire`（模型按报告改成 +3/+5）。
3. **斩杀**：`combat.ts` 写回 hp 后、检测 `0<hp<5` → 调 `executeExecute`（重写对齐报告扁平阈值 + 掷骰>剩余HP）→ 命中置 `hp=0` + 日志 + 广播 `executed`。

（旧 `combatIntegrator`/`hookChain` 整套保持废弃、勿碰，避免引入第二套活链路。）

### 二·补.6 执行前必须锁定的 6 处偏差

6. execute/reactivate 必须作用真实 battle unit + 前端新增广播字段。

## 三、总体架构方案：TriggerEngine（触发引擎层）

### 3.1 设计原则（与你现有"侧词条系统"同构）

你现有的词条库是"小枚举段 + 引用"结构（`damage_kinds`/`action_types` 被 skills 引用）。本方案原样复制这个思路，新增一层：

```
glossary-skill-config.json 新增侧词条段：
┌─────────────────────────────────────────────────┐
│ "trigger_types": {                              │
│   "post_melee_damage":  { "label": "近战结算后" },│

### 3.3 调度器实现（新文件，约 150 行）

新建 `services/combat-service/src/services/combatCore/triggerEngine.cjs`：

```javascript
// 核心形态（示意，非最终代码）
class TriggerEngine {
    // 一次性声明全部事件枚举通道（关键补充：即使第一期只实现 H2，亦在类定义时声明 H1/H2/H3，
    // 后续二期《决斗》H1、《抢夺》H3 只需向 REACTION_HANDLERS 注册表填 Handler，无需改动类结构）
    static HOOKS = { H1: 'on_target_selected', H2: 'on_damage_resolved', H3: 'on_damage_pre_write', H4: 'on_round_start', H5: 'on_unit_turn_start', H6: 'on_move_path', H7: 'on_defense_calc' };
    // 在钩子点被调用：扫描战场上所有单位的技能，
    // 找出 cfg.trigger === hookName 且条件满足的词条，逐一执行对应 handler
    fire(hookName, context) {
        const results = [];
        for (const unit of context.allUnits) {
            for (const skill of unit.skills || []) {
                const cfg = getSkillConfig(skill.key || skill.type);
                if (!cfg || cfg.trigger !== hookName) continue;
                const handler = REACTION_HANDLERS[cfg.reaction_type];
                if (handler && this._checkCondition(cfg, unit, context)) {
                    results.push(handler(cfg, unit, context));
                }
            }
        }
        return results;
    }
}
// 反应处理器注册表（与 skillRegistry.cjs 同款思路）
REACTION_HANDLERS = {
    lethal:      ..., // 斩杀形状：阈值检查 + 掷骰 vs HP → 致死
    duel:        ..., // 决斗形状：双方掷骰比大小
    steal:       ..., // 抢夺形状：条件 + 掷骰 + 装备转移
    extra_turn:  ..., // 再动形状：AP 重置 + 防连锁标记
    airdrop_drop:..., // 空投形状：随机坐标生成装备 token
    ...
};
```

**关键收益**：你现在写死的 `executeExecute/executeSnatch/executeDuel` 从"没人调用的孤儿方法"变成"注册表里的形状处理器"；以后再设计"血量低于 X 时触发 Y"类词条，只是填 JSON。

### 卡片 1：斩杀（execute）—— 工作量：小

- **你的规则**：近战伤害结算后，目标剩余 HP<5 → 掷 1d6，点数>剩余血量 → 直接斩杀。
- **与现有配置的分歧**：JSON 现写 `hp_threshold_percent:10`（百分比）且无骰子。**建议按你的表格改**：阈值改绝对值 5，加掷骰判定。
- **落点**：H2 钩子（`/attack` 伤害回写后）。
- **配置改造**：
  ```json
  "execute": {
    "trigger": "post_melee_damage",
    "reaction_type": "lethal",
    "attack_stat": "melee",           // 仅近战（你表格注明"近战武器"）
    "condition": "target_hp_below",
    "condition_value": 5,
    "dice_type": "1d6",
    "success_rule": "roll_gt_target_hp",
    "effect": "instant_kill"
  }
  ```
- **改动清单**：① 改 JSON 词条；② TriggerEngine 注册 `lethal` 处理器；③ `/attack` 回写后调 `triggerEngine.fire('post_melee_damage', ...)`；④ 前端结算弹窗加"斩杀掷骰"展示行。
- **注意**：必须排除"目标已 HP=0"的情况（已死不再斩），且只有攻击方持有该词条时才触发（技能归属检查）。
- **防守逻辑（关键补充）**：① 若目标受击后剩余 HP `≤ 0`（已致死 / 溢出伤害），**直接走常规死亡结算、跳过斩杀判定**，不弹斩杀窗、不写斩杀日志，避免对已死单位重复触发；② 进入掷骰的阈值统一为 `0 < HP < 5`（即 HP∈{1,2,3,4}）；③ HP=1 时 1d6 出 2~6 即斩杀（成功率 83.3%），HP=4 时需出 5~6（33.3%），完全符合"点数 > 剩余血量"规则与设计预期。
- **投产核查修正（关键）**：① 模型冲突——旧 `executeExecute`（`skillExecutor.cjs:913`）用 `hp_threshold_percent`（百分比，配置 `hp_threshold_percent:10`），与报告"扁平 HP<5 + 掷骰点数>剩余HP"模型完全不同，落地须重写对齐报告；② 落点修正——斩杀判定必须放在 `combat.ts` 写回 `writeBackTarget.currentStats.hp` **之后**（约 L915-930），且作用在**真实 battle unit** 而非 `toExecutorUnit` 副本，命中后置 `hp=0` + 写日志 + 广播 `executed:true`（前端需新增该字段，否则无感知）。

### 卡片 3：抢夺（snatch）—— 工作量：中大

- **你的规则**：某次伤害值 > 被攻击者携带武器的攻击值 → 攻击者**可选择**掷骰：<4 失败；>3 伤害减半（向下取整）+ 获得该武器。
- **三个子问题**：
  1. **判定**：伤害值 vs 防御方**主手武器攻击值**。建议统一走 `getMainHandAttack(unit)` 辅助函数读取权威值（实现时归一化 `equipManager` 的 `right_hand_melee/ranged` 与 `tagProcessor` 的 `equipment.left_hand.attack` 两处命名不一致的读取源，避免主手左右槽定义分裂）；若主手为空则取 `equipState` 中最高一件武器的攻击值兜底。（建议取最高一件武器的攻击值，多件时让你选）。
  2. **可选择**：这意味着攻击方要看到一个"是否发动抢夺？"的交互——前端确认框，类似决斗。
  3. **武器转移（三层同步，关键修正）**：攻击结算实际由**两套并行数据**驱动，只改 `equipState` 会出现"展示换枪但结算仍用旧枪"的分裂，必须**三层同步**：
     - **A. 扁平字段（真正决定伤害加成）**：`unit.right_hand_type` / `unit.right_hand_melee` / `unit.right_hand_ranged`（被 `equipManager.getWeaponBonus` 读取，L46-49）。攻击方填武器值，防御方置 `right_hand_type=null`（清空加成）；**只动嵌套对象不改这里，伤害加成不会变**。
     - **B. 嵌套对象 `unit.equipment` 的主手槽**（决定 `attack` 值与 `damage_kind_modifiers`，被 `tagProcessor.getWeaponAttack`、`damagePipe` 读取）。同步写入攻击方、清空防御方，避免旧 `attack`/抗性残留。
     - **C. `equipState` 数组**（机动值与前端展示）：防御方移除该武器、攻击方推入。
     三层缺一不可；完成后在战局状态落一条 `equipment_transfers` 日志供前端刷新。
- **对局生命周期（重要约束，关键修正）**：抢夺产生的一切装备归属变更**仅存活于内存态战局（battleState）**，**严禁回写玩家的数据库仓库 / 整备室**。战局结束后内存态释放、整备室装备自动恢复原状（不持久化、不回流）。实现上所有替换只操作 `battleState` 内的 `equipment`/`equipState` 镜像，永不触碰 `userInventory` / 整备室写入接口。
- **默认武器兜底 / 徒手占位符（关键防守点）**：降级防御方主手时，**扁平字段** `right_hand_type` 置 `null`（清空攻击加成，`getWeaponBonus` 有 `unit.right_hand_type === 'weapon'` 守卫，不会触发 `Cannot read property 'range' of null` 空指针）；**但嵌套对象 `unit.equipment.right_hand` 绝不能传 `null`**——后续 `damagePipe` 或 `tagProcessor` 访问 `.attack` 或 `.damage_kind_modifiers` 会触发 `Cannot read property of null`。必须给一个**纯净的徒手占位对象** `{ type: 'unarmed', attack: unit.melee, damage_kind_modifiers: { kinetic: 0, beam: 0 } }`（可按需补 `melee`/`ranged`/`destroyable` 等字段），即"扁平字段清空 + 嵌套对象保持徒手占位"双保险。
- **攻击范围即时重算（关键防守点）**：三层数据同步（equipState + 扁平 `right_hand` + 嵌套 `equipment.right_hand`）完成后，**必须立即调用一次 `recalculateUnitStats(unit)`**。现状/风险：现有 `combat.ts` 与前端逻辑中单位 `range` 主要由当前主手武器决定；若玩家 A 抢走玩家 B 主手长枪（射程 2~3）、B 降级为徒手（射程 1），不重算则 `currentStats.range` 仍显示 3、下一击高亮圈错乱。重算后防守方 `currentStats.range` 从 3 降为 1、攻击方更新为新枪射程。前端同步：网关 `combat_result` 响应包除 `equipment_transfers` 日志外，需**同时带上双方更新后的 `currentStats`**，强制前端刷新两者的 `skillRangeHexes` 高亮圈。
- **落点**：H3 钩子（伤害回写**前**，因为成功时伤害减半要改变回写值）。
- **配置**：
  ```json
  "snatch": {
    "trigger": "on_damage_pre_write",
    "reaction_type": "steal",
    "condition": "damage_gt_target_best_weapon_attack",
    "dice_type": "1d6",
    "success_line": 4,
    "success_damage_multiplier": 0.5,
    "success_effect": "transfer_target_weapon"
  }
  ```
- **改动清单**：① steal 处理器（判定+掷骰+减半）；② **三层同步装备转移逻辑**（攻击方 `equipState` 数组 + 扁平字段 `right_hand_type/melee/ranged` + 嵌套 `equipment` 主手槽 同时写入；防御方三层对应清空/降级为徒手占位 + 写 `equipment_transfers` 日志；全程仅内存态）；③ 前端"是否抢夺"确认 + 装备栏/主副手刷新；④ 整备室/单位详情只读内存态镜像、不触发任何写库动作。

### 卡片 6：再动（reactivate）—— 工作量：小

- **你的规则**：击杀敌军 → 立即再进行一个额外回合，不可连续触发。
- **落点**：H2（伤害回写后检测 target.hp===0）。
- **实现**：攻击者 AP 立即重置（MOVE+ATTACK 各发还 1 次），并打 `reactivated_round: 当前round` 标记；同 round 内再次击杀不再触发（`no_consecutive` 字段已现成）。
- **改动清单**：① 注册 `extra_turn` 处理器（查 AP 服务重置 + 标记）；② `/attack` H2 钩子调用；③ 前端行动条"再动！"高亮提示。
- **与现有代码关系**：`canReactivate(killConfirmed, lastReactivation)` 可以直接被处理器复用。
- **投产核查修正（🚨 硬阻塞）**：实时 `/attack` 虽能检测到击杀，但 `turnManager.js` 对 `extraTurn`/`grantExtraTurn`/`canActAgain` **0 命中**——实时回合推进完全不支持额外回合。`EffectExecutor.handleGrantExtraTurn` 设的 `targetUnit.extraTurn=true` 只在废弃的 `combatIntegrator` 子系统里有效。因此再动是四者中**唯一必须扩展 `turnManager`** 的：击杀后给 `casterUnit` 打 `extraTurn/canActAgain` 标志，`turnManager` 推进回合时识别该标志让该单位再行动一次，且不连续二次触发（`no_consecutive`）。`canReactivate`（`skillExecutor.cjs:988`）的 `killConfirmed && !lastReactivation` 守卫可直接复用。
- **turnManager 最小侵入改动（关键防守点）**：第一期改 `turnManager.js` **不需要重构整套回合切换逻辑**。只需在 `advanceTurn` 或 `endCurrentTurn` 方法中**优先判断 `currentUnit.extraTurn === true`**：若为真，则将 `extraTurn` 置回 `false`（防连续触发 `no_consecutive`）、重置该单位 `actionPoints`、并**跳过队列切换**，继续将行动权赋给该单位。如此可接通实时额外回合而零破坏旧代码。

### 卡片 7：援助（建议改 key 为 `cover`）—— 工作量：大（10 条中最复杂）

- **你的规则**：视距内友军受击时，你可放弃下回合一个行动：①弃移动→瞬移到攻防之间任意格并分担 5 伤；②弃战斗→对攻击方造成 5 反击伤害。
- **为什么复杂**：它是**唯一需要在"别人的回合、别人的攻击结算中途"插入你决策**的词条。引擎当前是"请求-响应"一次性结算，没有"挂起等第三方确认"的概念。
- **需要新建的"反应窗口"状态机（含 10s 服务端倒计时，关键修正）**：
  ```
  A 攻击 B → 网关检测到 C 持有 cover 且 C 在视距内
    → 不立即完成结算，生成 pending_reaction（存 battle 状态），并启动 10s 服务端倒计时
    → 前端 C 玩家（或 DM）看到"是否援助？"窗口（①/②/放弃）
    → C 在 10s 内选择 → 网关继续结算（①瞬移 C+分担 5 伤 / ②C 对 A 造成 5 伤 / ③正常结算）
    → 标记 C 下回合对应行动已放弃
    → 【超时】10s 内无响应 → 服务端自动按"放弃援助"继续推进后续结算，
        并通过 WebSocket 广播该结果（攻击方请求不会被长时间挂起）
  ```
  > **超时必要性（关键修正）**：联机 / 对局模式下，若被援助方长时间不操作，攻击方的 WebSocket / HTTP 请求会一直阻塞在 pending_reaction，导致超时卡死。10s 服务端倒计时是强制推进的兜底，超时即放弃，不依赖客户端应答。
- **需你拍板的定义**（见六-4）：①"视距范围"具体=？（建议先用 C 自身武器射程或固定 6 格）；②"攻防之间任意格"= A 与 B 连线上的空格，还是 B 周围一圈？
- **可复用参考**：`CombatResolver.resolveReinforcement`（combatResolver.js:418）已有"邻近单位分担 80% 伤害"的静态实现，分担伤害的写法可以照抄，差异只在触发方式（它是 1 格被动，你是视距+主动选择）。
- **分期建议**：放最后一期，且第一版可先做"DM 人工代答"模式（反应窗口只弹给 DM），降低联机交互复杂度。
- **断线重连防护（关键防守点，第四期）**：`battleState.pendingReaction` 需记录 `expireAt: Date.now() + 10000`。服务端 `setTimeout` 定时器只作为触发器，**实际超时校验以 `Date.now() > expireAt` 为准**，防止事件循环阻塞导致 `setTimeout` 推迟。若 10s 倒计时期间被援助方 F5 刷新 / 网络断开重连，必须能从服务端拉到 `pendingReaction` 快照并正确恢复倒计时弹窗——状态以 `expireAt` 为权威，不因重连重置。

### 卡片 8：空投（airdrop）—— 工作量：中大（全新子系统）

- **你的规则**：第 2 轮起，每轮 DM 掷骰决定生成武器/防具数量 → 随机坐标生成；坐标上有单位则该单位回合开始触发《幸运》。
- **落点**：H4（`/end-turn` 的 `isNewRound` 分支，round>=2 时）。
- **数据模型（groundItems 地面掉落物实体，关键修正）**：原方案 `spawn_items` 只回消息不落地，是虚构状态。必须在 `battleState` 显式补全 `groundItems` 结构作为"地面掉落物实体"：
  ```javascript
  battleState.groundItems = {
    // key = `${q},${r}`
    "3,-2": { q: 3, r: -2, items: [{ name, type:'武器'|'防具', def:{...} }], faction: null, spawned_round: 3 }
  }
  ```
  > 注意：当前 `effectExecutor.handleSpawnItems` 只 `return { type:'spawn_items', ... }` 不写回 battleState。本期必须让其真正把物品写入 `groundItems`（落地），`airdrop.cjs` 的 `spawn_items` 词条才有意义。
- **JSON Key 安全性（关键防守点，第三期）**：`groundItems` 字典 key 必须使用**标准化的 `getHexKey(q, r)`**（即 `${q},${r}`）生成器函数，**严禁在不同模块手动拼字符串**（如 `${q}_${r}` 或 `${q}:${r}`），避免后端存储与前端 Canvas 渲染遍历时读不到 Key。同格叠加用数组 `items: [...]`（设计优良）：同一格第二次掉落或有多个物品时直接 `push` 到数组末尾；单位踩上去可一次性捡起该格全部物品或弹窗选择拾取。
- **流程**：
  1. `isNewRound && battle.round >= 2` → 掷 1d6 得数量 N；
  2. 从战局地图候选格随机选 N 格，候选格必须满足 **reroll 平地规则**（见下）；
  3. 每格从装备池随机一件武器/防具，写入 `battleState.groundItems[key]`（**真正落地**，不再是消息占位）；
  4. **掩体与落点规则（reroll 策略，关键修正）**：空投生成时若判定目标格为**高山、深水区等不可通行 / 高掩体地形**（地形 `move_cost` 趋近不可达或标记 `is_cover` / 高掩体），**直接重刷坐标**，确保只掉落在可平稳拾取的平地（Clear / 可通行地形）。实现上循环重试选格，直到命中平地或达到重试上限（上限内仍无平地则跳过本次空投并记日志）。
  5. **拾取判定**：单位回合开始时（或移动结束后）若站在 `groundItems` 格 → 装备进入其 `equipState`（并同步旧 `equipment` 槽位，见卡片 3 的双槽位约束）+ 获得"空投增益"标记 → H5 触发《幸运》掷骰。
- **DM 手动 vs 自动（需拍板，见六-3）**：建议服务器自动掷骰+完整日志，DM 可在面板修改结果（项目已有 `is_manual_roll` 字段的雏形，语义即"DM 人工掷骰"）。
- **改动清单**：① 空投生成器（combatCore 新文件 ~120 行）写入 `battleState.groundItems`；② end-turn 钩子（H4）按 reroll 平地规则选格；③ 拾取检测（/move 成功后 + 回合开始）写 `equipState` + 旧 `equipment` 槽位；④ **Canvas 道具 Token 绘制层**（见下方"Canvas 渲染补充"）；⑤ 前端地图空投图标渲染 + DM 空投面板；⑥ 装备池来源（复用现有装备数据）。
- **Canvas 渲染补充（关键修正）**：前端此前**没有任何地面道具 Token 绘制层**（`hexDraw.js` 仅地形与立柱，渲染循环不遍历 items）。本期需：① 在 `hexDraw.js` 新增 `drawGroundItemToken(ctx, x, y, iso, item)`，绘制掉落物图标/光环；② 在 `HexGridCanvasEngine.vue` 渲染循环插入**独立的道具渲染层**。绘制顺序必须严格遵守画家算法：
  ```
  地形层  →  地面道具 Token 层 (groundItems)  →  范围 / 高亮层  →  机体单位层
  ```
  （道具在地形之上、单位之下，确保单位永远覆盖道具，高亮范围不被道具遮挡。）

### 卡片 9：联防（blockade_line）—— 工作量：中

- **你的规则**：三个同阵营单位并列时，敌对阵营单位不得从并列单位**中间穿过**，需绕行。
- **技术翻译（几何纠偏，关键修正）**：原方案把"三单位并列"简化为"3 个及以上单位两两相邻成链"，**存在几何漏洞**——在六边形 Axial（轴向）坐标系下，"成链"会包含品字形 / 折线排列，导致一个没有中间缝隙的三机小队也被误判为阻断了周边路径。因此**改为严格共线判定**：算法必须校验单位在 `(q, r, s)` 三轴坐标系下的**共线向量（Collinear Vectors）**。
- **实现（严格共线 ZOC 边阻塞）**：
  ```javascript
  // tsFindPath 邻居扩展处（combat.ts:121 附近）新增：
  // 仅当 3 个单位在 (q,r,s) 轴向方向上处于同一直线且连续排列时，
  // 敌方试图穿越其相邻"公共边格"(Edge-crossing) 才禁止穿越：
  //   - 取 cur→next 这条边；
  //   - 若存在一敌对联防单位 A、B 共线且 cur/next 落在其"相邻公共边"两侧，则 continue
  // 非共线的品字形/折线排列一律不阻断（仅天然占位阻塞仍生效）
  ```
- **"共线"判定（Axial 三轴）**：把每个单位坐标转为立方坐标 `(q, r, s=-q-r)`，对同阵营单位两两求方向向量；只有满足"三点共线（向量叉积为 0）+ 沿同一轴线连续（相邻格间距=1 且中间无空挡）"才构成有效联防链。每回合移动后重算一次各阵营的"共线联防链"，供寻路查询。
- **前端同步**：移动高亮 BFS（前端 `moveRangeHexes`）必须实现**同一共线规则**，否则出现"高亮能点但后端拒绝"。建议把 `isCollinearBlockade(cur, next, units)` 抽成前后端共享纯函数放 `hexUtils.js` 同款位置（遵守宪法第 2 条：数学真理单源）。
- **配置**：
  ```json
  "blockade_line": {
    "trigger": "on_move_path",
    "reaction_type": "zoc_block",
    "formation": "collinear",        // 关键修正：严格共线，非 chain
    "formation_min": 3,
    "scope": "enemy_only"
  }
  ```
- **地图边缘 / 越界格保护（关键防守点，第四期）**：严格共线判定需计算 `s = -q - r` 轴向向量叉积。`isCollinearBlockade(cur, next, units)` 在取 `cur→next` 的"两侧公共边格"时，若一侧格超出地图边界（Dijkstra 邻居扩展遇 `null` 越界格），**只需判断留存在地图内的那一侧是否被联防阵型封锁即可**，防止越界格返回 `undefined` 导致数组报错抛崩溃（尤其三机联防队紧贴地图边缘如 `(0,0),(0,1),(0,2)` 时）。

### 卡片 10：抗性（resistance）—— 工作量：极小（数据入口为主）

  if (attackerWeaponType === defenderResistance) return WEAPON_COUNTER_PENALTY; // = -2

  1. 装备数据加字段 `resist_kind: 'kinetic'|'beam'|...`（整备室配防具时声明）；

- **投产核查修正（🚨 关键）**：原报告称"机制已存在 90%"有误导——`damagePipe._calcArmorReduction`/`_calcWeaponPenalty` 确实实现了减免，但**实时 `/attack` 的伤害是 `_executeAttackSkill` 内联算的（`skillExecutor.cjs:278`），完全不调用 `DamagePipe.calculate`**（已验证 `skillExecutor.cjs` 内 0 调用）。因此抗性 `damage_kind_modifiers` 减免在实时攻击里**当前根本不生效**。落地必须：① 在 `_executeAttackSkill` 伤害公式处插入一次减免计算（或改调 `DamagePipe.calculate`）；② 补 glossary `resistance`/装甲槽（`full_armor`/`coating` 等）`damage_kind_modifiers` 配置——经全文搜索，glossary **当前没有这些词条配置**，是缺失而非"已存在 90%"。

## 八、验收标准（每期 DoD）

- **第一期**：① 穿动能抗性甲的单位被动能攻击时结算 -2；② 专注射击攻击后 MOVE 消失且骰点 1-4/5-6 分别 +3/+5；③ 近战把目标打进 HP<5 后出现斩杀掷骰，点数>HP 目标即死；④ 击杀者当回合 AP 重置且本回合再次击杀不再触发。

## 附录 E：多 Agent 任务分工策划方案（2026-07-25）

> 目的：在「一次性完成 10 条词条全部任务」的目标下，评估"调用现有 agent"还是"部署定制化子 agent"，并给出可落地的分工、职责、协作流程。本方案已吸收「二·补」投产前核查结论——真实编辑集中在 `combat.ts` / `skillExecutor.cjs` 实时路径，因此把"集中冲突文件"拆成"文件天然隔离"是并行的前提。

### E.1 子 Agent 部署能力确认

- 工具层：`Task`（派生子 agent）/ `team_create`（组建异步团队）均已具备，可**自主部署**子 agent，无需人工逐次触发。
- 现有可用子 agent：仅 `code-explorer`（**只读探索**，无写码权限）。
- 结论：写码类任务必须"部署定制化子 agent"（团队模式成员，受任务简报驱动、可写码）；只读类任务可"调用现有 agent"。

### E.2 现有 agent vs 定制化子 agent：评估与决策

| 任务类型 | 用现有 / 定制 | 理由 |
|---|---|---|
| 前置代码考古 / 锚点复核（只读 diff、行号确认） | **现有 `code-explorer`** | 不写码，只读探索正是其强项，零风险 |
| 后置交叉联调审查（只读比对偏差、回归检查） | **现有 `code-explorer`** | 只读审查作为质量闸，不污染代码 |
| 一切写码（钩子、handler、glossary、Vue、新模块） | **定制化子 agent**（团队模式） | `code-explorer` 无写码权限，本任务 80%+ 是写码 |
| 构建 / rsync 部署 / 运行测试 | **定制化 `INT` agent** | 是命令执行（非编辑），由收口 agent 统一做 |

**最终决策（混合策略）**：

1. 主导力量是**定制化写码子 agent**（F 基础 + B1~B8 各卡 + INT 集成）。
2. 现有 `code-explorer` 仅在两个**只读**环节被调用：`ARCH`（前置勘察）与 `REV`（后置审查），作为质量闸。
3. **不采用"纯现有 agent"方案**（它写不了码）；**也不采用"全定制化无协调"方案**（会在 `combat.ts` / `skillExecutor.cjs` / `glossary` 巨型文件上撞车）。

### E.3 动手前必须做的改造：把"集中冲突文件"拆成"文件天然隔离"

基于「二·补」核查，朴素并行会在 `combat.ts`(52KB)、`skillExecutor.cjs`、`glossary`(16KB)、`NewBattleView.vue`(154KB) 上撞车。按以下四招拆开，**让 F 之外的 agent 一律不碰这四个巨型文件**：

1. **反应 handler 按文件拆分**：`combatCore/reactionHandlers/{lethal,steal,duel,extra_turn,lucky_roll,zoc_block,cover,airdrop_drop}.cjs`，引擎启动时 `require` 整个目录。每卡 agent 拥有自己的 handler 文件，互不冲突。
2. **内联减免抽成独立模块**：`combatCore/damageModifiers.cjs`，`resistance` / `focused_fire` 各占一个导出函数；`skillExecutor._executeAttackSkill` 内只留**一个调用点** `applyDamageModifiers(...)`。B2 只在 `damageModifiers.cjs` 内写，不碰 `skillExecutor.cjs` 主体。
3. **glossary 分片加载**：每卡一个 `glossary.fragments/{execute,duel,snatch,focused_fire,lucky,reactivate,cover,blockade_line,airdrop,resistance}.json`，加载器合并。避免 10 个 agent 改同一份 16KB JSON。
4. **前端拆子组件**：`frontend/src/components/battle/reactions/{ExecuteDialog,DuelDialog,SnatchDialog,LuckyRoll,CoverWindow,AirdropIcon,ReactivateBanner}.vue`，各卡 agent 只建自己的子组件，**绝不改 `NewBattleView.vue` 本体**。

> 效果：冲突面从 3 个巨型文件收敛到仅 **F 独占**的 `combat.ts` 调用点（一次性插入）+ `skillExecutor.cjs` 调用点（一次性插入）。其余 agent 全部落在隔离文件。

### E.5 协作流程（同步屏障 + 分支策略）

1. **分支策略（本地工作树）**：F 在 `base` 分支完成 E.3 改造并提交；每个 B 从 F 的提交切 `feature/<card>` 分支独立开发；INT 把各 `feature/*` 合并回集成分支并解冲突。→ 单卡出问题可单独 revert，不污染其他卡。

4. **依赖串行**：`ARCH → F →（B1/B2/B3/B4/B5/B7/B8 并行）→ B6（等 B5）→ INT → REV`。
5. **部署收口**：部署是**末段一次性动作**，由各 B 完成、INT 统一执行 `rsync` + `docker compose build` + `up -d`。不在各 agent 内部分散部署，避免镜像反复重建与 db 孤儿冲突。
