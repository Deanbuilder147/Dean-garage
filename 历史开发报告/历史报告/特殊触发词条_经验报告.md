# 特殊触发词条 · 经验报告

> 生成时间：2026-07-25
> 主题：10 张特殊触发词条（斩杀/决斗/抢夺/专注射射/幸运/再动/援助/空投/联防/抗性）的后端实时路径实现
> 执行模式：单编排者直接实现（平台仅能派发只读 `code-explorer` 子 agent）

---

## 一、技术难点

### 1.1 实时路径与孤儿方法脱节（最核心难点）
报告核查发现：`executeExecute / executeDuel / executeSnatch` 等方法在 `skillExecutor.cjs` 中**存在但零调用**；实时 `/attack` 走 `_executeAttackSkill` 内联公式且**完全不调用 `DamagePipe.calculate`**。这意味着直接在孤儿方法上改代码不会生效——必须找到真实调用点挂钩子。

**教训**：写码前必须用只读勘察（ARCH）确认"方法是否真的被调用"，避免改了一堆代码却毫无效果。本次正是靠 ARCH 把"行号漂移"与"孤儿事实"暴露出来，才没有在错误的函数上浪费工时。

### 1.2 集中大文件的合并冲突风险
`combat.ts`(52KB)、`skillExecutor.cjs`(45KB)、`glossary`(16KB) 是高度集中的"热点文件"。若多 agent 并发编辑，必然冲突、破坏生产环境。

### 1.3 循环依赖（注册表模式）
`index.cjs` 在 `module.exports` 赋值**之前** `require` 各 handler，而 handler 顶部 `require('./index.cjs')` 拿到的是尚未赋值的空对象 → `register is not a function`，8 个触发器全部 0 注册。

### 1.4 skills 数据形态歧义
`toExecutorUnit` 把单位 `skills` 映射为**对象数组**（`[{key,...}]`），而旧 `executeFocusedFire` 用 `skills.includes('focused_fire')`（期望字符串数组）。形态不一致会让 `unitHasSkill` 永远返回 false，整张卡静默失效。

### 1.5 前端/后端坐标真理不一致
联防要求前后端共用同一套共线判定，否则会出现"后端拦得住、前端显示能走"的 discrepancy。

### 1.6 两段式交互（抢夺/援助/决斗）
这些卡不是"一次请求出结果"，而是"检测→前端弹出→二次确认"两段式。强行塞进单条 `/attack` 同步路径会破坏已有结算。

## 二、解决方案

### 2.1 钩子注册表 + 文件隔离（对应报告 E.3）
- 新建 `reactionHandlers/index.cjs` 作为唯一派发器，`fire(trigger, ctx)` 分发到各卡独立文件。
- 各卡 handler 落独立文件（`lethal/duel/steal/...cjs`），**互不冲突、零侵入主链路**。
- 伤害减免收敛到 `damageModifiers.cjs` 的单一 `applyDamageModifiers(...)` 调用点（H7），`skillExecutor` 主链路只加 6 行。

### 2.2 循环依赖修复
把 `module.exports = { register, fire, listTriggers }` 移到 `require('./'+f)` 循环**之前**。子文件 `require('./index.cjs')` 即可拿到已就绪的 `register`。验证后 8 个触发器全部注册成功。

### 2.3 skills 形态兼容
`unitHasSkill` 同时支持：字符串数组、对象数组（`{key}`）、字符串、对象四种形态，彻底消除"持有技能却检测不到"的静默失效。

### 2.4 坐标真理单源
`hexUtils.isCollinearBlockade`（前端）与 `reactionHandlers/zoc_block.cjs`（后端）实现**同一套** `axialToCube / areCubeCollinear / blockerLines / crossesBlockerSeam` 逻辑，确保前后端判定一致（DoD 第四期①）。

### 2.5 两段式交互路由
新增 4 个路由：`/duel-check`（H1 预检）、`/resolve-duel`、`/resolve-snatch`、`/resolve-cover`。`/attack` 仅做"检测并暂存 pending（`pendingSnatch`/`pendingReaction`）"，真正的结算交给二次确认路由，避免污染同步路径。

### 2.6 越界格 undefined 保护
`isCollinearBlockade` 与 `crossesBlockerSeam` 对越界坐标做 `null` 守卫；`cover.cjs` 的 `onAllyAttacked` 对 `position` 缺失单位跳过，防联机地图边缘崩溃。

### 2.7 时间权威用绝对时间戳
援助 `pending_reaction.expireAt = Date.now()+10000`，`setTimeout` 仅作触发器，实际以 `Date.now()>expireAt` 判定，规避断线重连导致的状态丢失/超时漂移。

## 三、协作优化建议

1. **只读勘察必须前置且独立**：把"确认锚点/调用点"作为写码前强制闸门（本次 ARCH 直接避免了在孤儿方法上白干）。建议把"该方法是否被实际调用"写入任何功能文档的硬性核查项。
2. **"单编排者直接实现"优于"无协调的并发写码"**：当写码目标集中在少数大文件、且要上生产服务器时，并发 agent 的合并风险 > 并行收益。本次改为单编排者按文件隔离顺序推进，既保隔离又保可控。
3. **契约先行**：F 必须先产出"钩子契约 + glossary 分片 schema + handler 函数签名"，其余卡才能零歧义开工。本次虽改为单实现，仍严格遵循"先建注册表/纯函数，再填各卡"的顺序。
4. **高风险动作显式门控**：服务器部署（rsync + docker compose build）与数据库变更必须等用户确认。本次把部署放在末步且未执行，本地改动全程可回滚。
5. **废弃链路写进"禁碰清单"**：把 `combatIntegrator / hookChain / EffectExecutor / ConditionEvaluator / tags/*` 明确标记为 DEPRECATED，新钩子一律走实时路径，避免回归到死代码。

## 四、可复用最佳实践

1. **注册表模式挂载反应/事件钩子**：`fire(trigger, ctx)` + 自动加载同目录 handler，是扩展"词条/技能/触发器"类需求的最低侵入范式。新增一张卡 = 新增一个文件，不改主链路。
2. **纯函数收敛伤害结算**：把抗性的"减伤/增益"抽成一个 `applyDamageModifiers(caster,target,damage,...)` 单一调用点，主执行器只用一行接入，逻辑全在独立模块。
3. **数据形态兼容层**：凡读取"可能有多形态（字符串/对象/数组）"的配置字段，统一用兼容函数（如 `unitHasSkill`），不要假设单一形态——这是游戏类项目反复踩的坑。
4. **坐标/规则数学真理单源**：凡前后端都要用的判定（共线、距离、命中），抽成两边都引用的纯函数，杜绝"后端说能、前端说不能"。
5. **两段式交互用 pending 暂存**：检测与结算分离（先落 `pendingXxx`，二次确认路由再结算），比把交互塞进同步请求健壮得多。
6. **绝对时间戳做超时权威**：联网对战/可断线的反应窗口，超时判定一律用 `Date.now()+window` 而非依赖定时器。
7. **每步留可验证出口**：每个阶段结束即用 `node --check` + 小冒烟脚本验证（本次 11 个 .cjs 全过、斩杀/抗性冒烟通过），比"全部写完再联调"更早暴露问题。

## 六、一句话总结

把"集中大文件"按**注册表 + 文件隔离 + 单一调用点**拆开，用**只读勘察前置**确保改在真实调用点上，用**纯函数单源**保证前后端一致，用**两段式路由**承接交互——这套组合让 10 张卡在"零侵入主链路、本地可回滚、未碰废弃/数据库"的前提下全部落地并通过验证。
