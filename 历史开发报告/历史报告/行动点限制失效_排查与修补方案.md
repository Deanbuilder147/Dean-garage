# 行动点（AP）限制失效 · 排查与修补方案报告

> 生成时间：2026-07-27
> 现象：每个棋子在其行动回合中，不点待机就能**无限次**移动 / 无限次战术（攻击 / 技能）。
> 预期：每个棋子每轮回合只能进行 **1 次移动行动 + 1 次战术行动**。

---

## 一、结论（先把话说清楚）

行动点系统（action_points）**数据层是正确的**，问题出在 **两层都没"接上"**：

1. **后端权威层没消费**：`/move`、`/attack` 路由执行动作后，从不调用 `consumeActionPoint` / 不校验 `hasActionPoints`。所以哪怕前端被绕过（直接调 API），后端也允许无限移动、无限战术。
2. **前端展示层没禁用**：按钮禁用依赖从不存在的旧布尔字段 `has_moved` / `has_acted`（后端从未写入、前端 normalize 也从不派生），这两个值永远是 `undefined` → `:disabled` 恒为 `false` → 按钮永不置灰。

> 误区澄清：我曾怀疑是 `actionPoints`（驼峰）与 `action_points`（下划线）字段名不一致导致系统彻底失效。经核对 **`createBattleUnit` 内部已把传入的驼峰 `actionPoints` 统一重命名为下划线 `action_points` 写入单位**（`battleStateFactory.ts:189`）。所以单位确实携带正确的 `action_points = {MOVE:1, ATTACK:1}`，`/state` 也正常返回它。字段名**不是**本次 bug 的根因，请勿据此误改。

## 二、根因逐层定位（附代码坐标）

### 数据层（✅ 正常，仅记录）
| 位置 | 内容 |
|---|---|
| `battleStateFactory.ts:31` | `DEFAULT_ACTION_POINTS = { MOVE:1, ATTACK:1 }` |
| `battleStateFactory.ts:189-191` | `createBattleUnit` 写入 `action_points`（下划线，正确） |
| `battleStateFactory.ts:384` | `consumeActionPoint(unit, action, amount)` 读 `unit.action_points` |
| `battleStateFactory.ts:395` | `hasActionPoints(unit, action, amount)` 读 `unit.action_points` |
| `combat.ts:142` | `advanceTurn` 在 `isNewRound` 调 `resetAllActionPoints` —— 每"新一轮"（所有阵营各轮一遍 = 每个棋子再次轮到自己）统一重置满点 ✅ 重置时机正确，无需改 |

### 失效点 ①：后端 `/move` 路由不消费 MOVE（核心）
`backend-gateway/src/routes/combat.ts:1755` 起：
- L1763-1769 只做了"阵营轮转门控"（NOT_YOUR_TURN 校验）。
- L1790-1793 直接改 `unit.position` 并 `unit.q/r` 同步。
- L1808-1814 返回成功。**全程无任何 `hasActionPoints(unit,'MOVE')` 校验，也无 `consumeActionPoint(unit,'MOVE',1)` 调用。**
- 结果：同一单位可反复移动，MOVE 点永远停在 1。

### 失效点 ②：后端 `/attack` 路由不消费 ATTACK（核心）
`backend-gateway/src/routes/combat.ts:1056` 起：
- L1164-1177 调 `executeUniversalSkill` 结算。
- L1180-1198 回写血量 / 反击 / statusEffects。
- L1255-1279 返回成功。**同样无 `hasActionPoints` 校验、无 `consumeActionPoint(unit,'ATTACK',1)`。**
- 结果：同一单位可无限攻击 / 无限放技能，ATTACK 点永远停在 1。

### 失效点 ③：前端按钮禁用依赖死字段
| 位置 | 表达式 | 问题 |
|---|---|---|
| `NewBattleView.vue:161` | `:disabled="unit.has_moved"` | `has_moved` 后端从不写、前端从不派生 → `undefined` → 永不禁用 |
| `NewBattleView.vue:287` | `:disabled="selectedUnit.has_moved"` | 同上（战术面板移动按钮） |
| `NewBattleView.vue:329` | `:disabled="selectedUnit.has_acted"` | `has_acted` 同上 → 战术按钮永不禁用 |
| `NewBattleView.vue:1059` 附近 | `:disabled="selectedUnit.has_acted"` | 防御 / 待机按钮也依赖死字段 |

前端 `normalizeBattleState`（L1045）遍历单位时，**从未**由 `action_points` 派生 `has_moved` / `has_acted`。而前端其实能拿到 `selectedUnit.action_points`（下划线，来自 `/state`），却完全没用它。

### 失效点 ④：`/consume-ap` 是"死端点"
`combat.ts:658` 的 `POST /action-points/consume` 实现了消费逻辑，但**前端从不调用它**（前端 `executeMove`/`executeAttack` 只 `refreshState()`，不消费）。即便调用，也因 ①② 后端路由自身不校验而形同虚设。本方案将改为"后端路由内直接消费"，该端点可保留作运维查询用，不再依赖前端主动扣。

### 次要问题 ⑤：防御 / 待机未"终结"单位行动
- `combat.ts:1650` `wait` 分支设 `standby=true`（全员待机自动跳阵营），但**不清零 / 消费 `action_points`** → 先点待机仍可继续移动 / 战术。
- `defend` **根本没有后端分支**：前端 `executeAction('defend')` → `combatAPI.action(..., {actionType:'defend'})` 落到 `combat.ts:1752` 返回 `400 UNKNOWN_ACTION`，且被前端 `try/catch` 静默吞掉 → 防御当前是**纯视觉空壳**（只打日志 `+15 护盾` + 放防御姿态动画，不加任何护盾、不改状态、不消耗 AP）。
- 用户直觉（2026-07-27 拍板）："点防御 = 结束该棋子行动 + 获得持续减伤"。修复见 **P3**。

## 三、修补方案（权威 + 展示双重修复）

### P0 — 后端 `/move` 校验并消费 MOVE（核心）
在 `combat.ts` `/move` 路由：
- 门控之后、`unit.position = ...`（L1790）之前，插入校验：
  ```ts
  if (!hasActionPoints(unit, 'MOVE')) {
    return res.status(400).json({ success: false, error: 'NO_MOVE_AP', message: '移动行动点已用完（每轮回合仅 1 次移动）' });
  }
  ```
- 成功回写之后、`res.json`（L1808）之前，插入消费：
  ```ts
  consumeActionPoint(unit, 'MOVE', 1);
  ```
（`consumeActionPoint` / `hasActionPoints` 已在 `combat.ts:21-22` 导入，无需新增 import。）

### P1 — 后端 `/attack` 校验并消费 ATTACK（核心）
在 `combat.ts` `/attack` 路由：
- `executeUniversalSkill` 调用之前（L1160 之前），插入校验 `casterUnit`：
  ```ts
  if (!hasActionPoints(casterUnit, 'ATTACK')) {
    return res.status(400).json({ success: false, error: 'NO_ATTACK_AP', message: '战术行动点已用完（每轮回合仅 1 次战术）' });
  }
  ```
- 回写段之后（`applyStatusEffectsWriteback` 之后，L1198 之后、`res.json` L1255 之前），插入消费：
  ```ts
  consumeActionPoint(casterUnit, 'ATTACK', 1);
  ```
- 注意：普通攻击与技能攻击都走 `/attack`（前端 `executeAttack`/`executeSkillAttack` → `combatAPI.attack`），所以一处消费即覆盖两类战术行动。

### P2 — 前端由 `action_points` 派生 `has_moved` / `has_acted`（最小改动、零模板改动）
在 `NewBattleView.vue` 的 `normalizeBattleState`（L1045-1079）循环内，增加派生：
```js
// 行动点 → 旧布尔按钮字段（保持模板 :disabled 逻辑不变）
if (u.has_moved === undefined) u.has_moved = (u.action_points?.MOVE ?? 1) <= 0;
if (u.has_acted === undefined) u.has_acted = (u.action_points?.ATTACK ?? 1) <= 0;
```
这样现有模板按钮（L161 / 287 / 329 / 1059）**无需任何改动**即自动生效：移动 1 次后 `MOVE=0 → has_moved=true` 移动按钮置灰；战术 1 次后 `ATTACK=0 → has_acted=true` 战术 / 防御 / 待机按钮置灰。移动 / 攻击成功后 `refreshState()` 自动拉取新 `action_points`，按钮实时禁用。
> 前端不再需要调用 `/consume-ap`（后端已在 P0/P1 直接消费）。

### P3 — 防御 / 待机终结单位行动（贴合用户"点防御/待机即结束"的直觉）

#### 需求（用户 2026-07-27 拍板）
1. 「防御」= 清零该单位 `action_points` + 结束其本轮回合（与「待机」同等语义）。
2. 「防御」额外赋予：**直到该单位下个自己的回合开始，每次受到的伤害值 -3**。

#### 需求 2 可行性结论：✅ 可 100% 走现有管道实现，无需新减伤引擎
- 现有伤害管道 `DamagePipe.calculate`（`services/combat-service/src/services/combatCore/damagePipe.cjs`）在 `_calcDefense` 中会把 `BuffManager.getMatchingStatus(defender, trigCtx, 'defense')` 命中的 statusEffect 的 `value` 累加进 `guardVal`，最终从总伤害里扣除：
  ```js
  const defenseBuffs = this._sumBuffs(defender.buffs || [], 'defense') + guardVal; // guardVal=匹配'defense'的statusEffect.value之和
  const total = baseDefense + defenseBuffs + coverBonus + terrainDefenseBonus + ...;
  const finalDamage = Math.max(0, attack - total); // guardVal 即 -N 减伤
  ```
- 这与已上线的 `guard` 技能机制**完全一致**：`guard` 也是往受击方写入一条 `applies_on:'defense'` 的 statusEffect，攻击结算时自动减伤。防御动作只需复用同一套「`defense` statusEffect」，**不需要新增任何减伤公式**。
- 差异点：`guard` 用 `consumption.mode:'counter'`（命中 N 次后消失）；防御动作需要「持续到下次自己回合开始」的时间维度 → 用 `duration` + 新一轮清除（见下），而非 counter。

#### 后端 `/action` 路由改动
**(a) `wait` 分支（L1658 之后）补清零**：执行完 `standby=true` 后，追加 `unit.action_points = { MOVE: 0, ATTACK: 0 }`，保证待机后不可再移动 / 战术。
```ts
(u as any).standby = true;
u.action_points = { MOVE: 0, ATTACK: 0 };   // 待机 = 终结该单位本轮
const advanced = maybeAutoAdvance(battle);
```

**(b) 新增 `defend` 分支**（在 `wait` 分支之后、`deploy_royroy` 之前插入）：
```ts
if (actionType === 'defend') {
  const { unit_id } = params || {};
  const u = battle.units.get(String(unit_id));
  if (!u) return res.status(404).json({ error: 'UNIT_NOT_FOUND' });
  if (battle.activeFaction && resolveRole(battle.factionRoles, u.faction) !== battle.activeFaction) {
    return res.status(400).json({ error: 'NOT_YOUR_TURN', message: `当前行动阵营为 ${battle.activeFaction}` });
  }
  // ① 清零行动点（终结本轮，与待机同语义）
  u.action_points = { MOVE: 0, ATTACK: 0 };
  // ② 标记 standby（走现有全员待机自动跳阵营逻辑）
  (u as any).standby = true;
  // ③ 写入「防御姿态」减伤 statusEffect（value=3，applies_on='defense'）
  u.statusEffects = Array.isArray(u.statusEffects) ? u.statusEffects : [];
  u.statusEffects = u.statusEffects.filter((s) => s.source !== 'defend_action'); // 去重，避免连点叠加
  u.statusEffects.push({
    id: `defend_${u.id}_${Date.now()}`,
    source: 'defend_action',
    label: '防御姿态',
    action_type: 'defense_buff',
    value: 3,                                   // 每次受击 -3
    consumption: { mode: 'duration', remaining: 1, max: 1 },
    trigger: { type: 'unconditional', attack_type: null, damage_kind: null },
    applies_on: 'defense',                      // 关键：与 guard 同源，攻击结算自动减伤
  });
  const advanced = maybeAutoAdvance(battle);
  return res.json({ success: true, actionType, unit_id, standby: true, advanced,
    activeFaction: battle.activeFaction, round: battle.round, turn: battle.turn, message: '进入防御姿态' });
}
```

#### 过期挂钩（「直到下个自己回合开始」）
- 在现有 `applyNewRoundEffects(battle)`（`combat.ts:116`，于 `isNewRound` 时调用）里**追加一步**：清除所有单位 `source === 'defend_action'` 的 statusEffect。
- 语义对齐：本项目是阵营轮转模型，每个单位的「自己的回合」在每个 `isNewRound`（新一轮开始、AP 统一重置处）重新到来；在 `isNewRound` 清除 = 精确等价于「直到该单位下个自己的回合开始」。
```ts
function applyNewRoundEffects(battle) {
  // ...现有 fireReaction('on_round_start') 等
  if (Array.isArray(battle.units)) {
    for (const u of battle.units) {
      if (Array.isArray(u.statusEffects)) {
        u.statusEffects = u.statusEffects.filter((s) => s.source !== 'defend_action');
      }
    }
  }
}
```
- 不采用 counter 方案：会让它在每次受击扣 1 层变成「抗 N 次」，与「持续到回合开始」语义不符。

#### 前端改动
- `NewBattleView.vue` 的 `executeAction('defend')`：去掉 `try/catch` 吞错，改为 await 真实调用；成功后在本地把该 unit 的 `action_points` 同步为 `{MOVE:0,ATTACK:0}`（与后端一致），并触发 `normalizeBattleState` 重算 `has_moved/has_acted` 置灰。保留现有 `setUnitVisual(..., 'defend')` 防御姿态动画。
- 按钮禁用逻辑继续由 P2 的 `action_points` 派生（防御后 AP=0 → 移动/攻击按钮自动置灰）。

| --- | --- |

| `frontend/src/views/NewBattleView.vue` | `executeAction('defend')` 接真实后端、同步 AP、去 swallow 错误 |

### P4 — 回合重置（✅ 已正确，仅复核）
`advanceTurn`（L142）在 `isNewRound` 调 `resetAllActionPoints`，每"新一轮"所有单位恢复 `{MOVE:1, ATTACK:1}`，符合"每个棋子自己的轮回 1 移动 + 1 战术"。无需改动。

## 四、验证方法
1. **单元层**：启动战局 → 某单位先移动 1 次，`GET /action-points/:unitId` 应返回 `action_points.MOVE=0, canMove=false`；再调 `POST /move` 应返回 `NO_MOVE_AP`。
2. **战术层**：攻击 1 次后 `ATTACK=0, canAttack=false`；再调 `POST /attack` 返回 `NO_ATTACK_AP`。
3. **前端层**：刷新后移动按钮 / 战术按钮在对应点用完后自动置灰；点待机 / 防御后（P3 后）两者均置灰。
4. **防御减伤层**：点防御后，敌方对该单位发起攻击，结算伤害应比无防御时少 3（`guardVal` 计入）；下个自己回合开始（新一轮 / AP 重置）后，再次受击伤害恢复、statusEffects 中 `defend_action` 已清除。
4. **回合恢复**：该阵营轮完一圈回到本阵营（新一轮），`action_points` 回到 `{MOVE:1, ATTACK:1}`。
5. 部署：gateway 重新 `docker compose build --no-cache mecha-gateway` 并 `up -d --no-deps mecha-gateway`；本方案**不涉及前端 dist 之外的逻辑改动以外的特殊构建**（仅 `NewBattleView.vue` 一处，需在服务器 `npm run build` 后重建 frontend 镜像）。

## 五、影响面与风险
- **影响**：修复后所有战棋单位严格受"1 移动 + 1 战术 / 轮回"约束，符合 SRW 类战棋直觉；任何依赖"无限移动 / 无限攻击"的玩法或测试脚本会失效（属预期）。
- **风险**：低。仅新增校验 + 消费，不改动结算公式；旧布尔字段 `has_moved`/`has_acted` 仅新增派生，不删除（兼容模板）。
- **已确认的设计点（2026-07-27 拍板）**：防御 / 待机均"终结单位行动"（清零 `action_points` + `standby`）。防御额外赋予「持续到下次自己回合开始、每次受击 -3」的减伤（复用现有 `defense` statusEffect 管道，见 P3）。

## 六、与"词条参数"排查的关系
本次行动点 bug 与你在排查的**词条参数填写问题**是**两条独立链路**：
- 词条参数（glossary-skill-config.json 的 `applies_on` / `consumption` / `trigger` 等）影响的是**技能效果结算**（增伤 / 减伤 / 层数扣减），已由上一轮部署落地；
- 行动点（action_points.MOVE/ATTACK）影响的是**单位能执行几次移动 / 战术的基础权限**，与词条无关。
两者可并行排查，互不干扰。
