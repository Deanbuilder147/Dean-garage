# 骰子系统收拢计划报告（含接口调整 + 前端设计预想）

> 文档版本：v1.0　|　日期：2026-07-29　|　范围：mecha-universe-engine 战斗引擎掷骰逻辑 + 前端参数配置
> 结论先行：**现无统一投骰服务**。曾经的中央服务 `DiceEngine.cjs` 已于 Phase 4 废除，掷骰动作被重复实现 **7+ 处**，每份只返回裸点数，点数含义由各自业务系统解释。本报告给出"收拢为单一 `diceService.cjs`"的方案，并附**每个程序的接口调整清单**与**前端骰子参数配置页的设计预想**。

---

## 0. 背景与现状结论

- 曾经存在中央投骰服务 `DiceEngine.cjs`（封装海豹骰子 dicescript VM，支持 `"1d6"`/`"2d6+3"` 表达式，导出了 `defaultEngine` 单例）。该服务已于 Phase 4 废除（`damagePipe.cjs:22` 注释：`DiceEngine.cjs 已于 Phase 4 废除，直接使用 Math.random()`），全仓已无业务代码 `require` 它。
- 废除后**未建立统一替代**，导致"掷骰"这一基础动作被各处图省事**各自重写**，形成违反 DRY 的架构债。
- 关键认知（已与用户确认）：七份实现**都是"哑函数"**（只吐裸点数），**没有任何一份内置业务含义**；"点数→倍率/加成/分支/成功"的解释层在业务系统的配置表里，与 `rollDice` 被复制几份无关。因此收拢时**业务语义层一行不用动**，只需把"掷骰动作"收口。

**重要语义冲突（收拢前必须先解决）**：
- 同一"掷骰"语义，出现三种入参约定：`faces=6`（数）、`diceType=6`（数，名不对）、`diceStr="1d6"`（字符串）。`branchEvaluator` 把 `dice_type` 当**面数 number**，而 `skillContract.js` 也把 `dice_type` 归一化为 number（L170），但 `skillExecutor._rollDice` / 前端 `rollDice` 却吃**表达式字符串**——同名字段两种解释并存，是收拢的最大陷阱。

## 2. 目标架构：统一 `diceService.cjs`（单例）

以已废的 `DiceEngine.cjs` 为蓝本，新建轻量、纯 `Math.random` 的中央服务（不再依赖 dicescript VM，保持 Phase 4 后的简化方向）。

```js
// services/combat-service/src/services/combatCore/diceService.cjs
class DiceService {
  constructor() { this.config = defaultDiceConfig(); }
  /** 统一入口：expr 可为 'NdM' 字符串或纯面数 number（默认 1d6） */
  roll(expr = '1d6') { /* 解析 → 逐骰累加 */ }
  /** 返回每个骰子的具体点数（用于显示/动画） */
  rollDetails(expr = '1d6') { /* number[] */ }
  /** 多次掷同一表达式 */
  rollMany(expr, n) { /* number[] */ }
  /** 掷骰并判定 */
  check(expr, operator, threshold) { /* boolean */ }
  /** 整数区间随机（替代裸 Math.random，用于暴击倍率等） */
  rangeInt(min, max) { /* integer in [min,max] */ }
  /** 从 /api/dice-config 热加载全局参数 */
  loadConfig(cfg) { this.config = { ...this.config, ...cfg }; }
}
module.exports = new DiceService();
```

设计要点：
- **唯一解析器**：`roll()` 内部统一把 `number` 当"面数"、把 `"NdM"` 当"表达式"，消除 §1 的三种签名分歧。
- **配置外置**：`rollMult[6]`、`critThreshold/Min/Max`、`availableDiceTypes`、`focusedFireRanges`、`manualRollDefault` 全部从 `config` 读取（§5），使"前端随时调参"成立。
- **纯函数、无副作用**：保持"哑服务"定位，业务语义仍在调用方。

## 3. 各程序接口调整清单（重点）

> 原则：先建 `diceService.cjs` → 各文件**改为引用 `DiceService`**，旧 `rollDice` 函数保留一版 `deprecated` 别名做过渡，降低回滚风险。

### 3.1 `damagePipe.cjs`
- L59 `static rollDice(faces=6)` → 内部改 `return DiceService.roll(faces)`（或整函数改为转发别名）。
- L66-67 `checkCrit()`：`this.rollDice(6) >= CRIT_THRESHOLD` → `DiceService.check('1d6', '>=', this.config.critThreshold)`。
- L197 暴击倍率 `CRIT_MIN + Math.random()*(CRIT_MAX-CRIT_MIN)` → 改为读 `DiceService.config.critMin/critMax`（`rangeInt` 或直接保留 random 但读配置），`CRIT_MIN/MAX/THRESHOLD` 常量下沉到 diceConfig。
- L404 手动摇骰内联循环 `Math.random()` → `DiceService.roll(diceType)`（已支持多骰累加）。
- **连带文件** `factionSkillRegistry.cjs`：L392 `DamagePipe.rollDice(this.params.dice_sides)`、L453 `DamagePipe.rollDice(10)` → 改为 `DiceService.roll(...)`；需在该文件顶部 `require('./diceService.cjs')`，并删除对 `DamagePipe.rollDice` 的依赖。

### 3.2 `branchEvaluator.cjs`
- L16 `rollDice` 导出函数 → 内部改 `DiceService.roll(diceType)`；或直接移除导出，由调用方改用 `DiceService.roll`。
- 调用方 `skillExecutor.cjs` L688 `BranchEvaluator.rollDice(uf.dice.dice_type)` → `DiceService.roll(uf.dice.dice_type)`（此处 `dice_type` 为面数 number，与 `roll()` 的 number 入参约定一致，无需改业务语义）。

### 3.3 `skillExecutor.cjs`
- 移除 L773 `_parseDice` + L776 `_rollDice`（纯重复实现）。
- L789 手动摇骰 `this._rollDice(diceType)` → `DiceService.roll(diceType)`。
- **L362 `ROLL_MULT` 硬编码梯度** `[0.6,0.7,0.8,0.9,1.0,1.1]` → 抽入 `DiceService.config.rollMult`，弹窗"投骰倍率"读取 `config.rollMult[_roll-1]`（此项即前端可调的核心参数，见 §6）。

### 3.4 `hookChain.cjs`
- L169 `rollDice(sides=6)` 方法 → 内部改 `DiceService.roll(sides)`；检查 HookChain 内部所有掷骰调用点一并替换。

### 3.5 `tagProcessor.cjs`
- L18 `rollDice(sides=6)`、L170 `executeDice(diceConfig)` → 内部改 `DiceService.roll(diceConfig.sides)`。
- 注意：`executeDice` 的 `diceConfig.sides` 与 `DiceService.roll` 入参对齐（面数 number）。这些效果处理器多为历史孤儿（execute/snatch/duel 等运行时零调用），可**保留但统一走服务**，或借机标注清理。

### 3.6 `NewBattleView.vue`（前端）
- L3120 `parseDiceType` + L3125 `rollDice` → 改为调用前端轻量镜像 `src/utils/diceUtil.js`（语义与后端 `DiceService.roll` 对齐，保证手动摇骰动画与引擎一致）。
- 手动摇骰动画（L3119-3194）逻辑保留，仅把本地 `rollDice` 调用换为 `diceUtil.roll`。

### 3.7 `damageModifiers.cjs`
- L71 `applyFocusedFire` 内联 `Math.random()` → `manualDice != null ? manualDice : DiceService.roll(6)`。
- `dice_ranges` / `bonus_pct` 配置（现读 `glossary-skill-config.json`）可一并纳入 diceConfig，使前端卡片可编辑（§6 卡片4）。

## 4. 配置落库方案（让"随时调参"成立）

- 新增后端全局配置 `diceConfig`，来源建议：**`glossary-skill-config.json` 新增 `systems.dice` 段**（复用现有配置加载链路），或独立 `dice-config.json` 置于 `/app/data/`（容器软链，遵循部署红线）。
- 字段草案：
  ```json
  {
    "rollMult":        [0.6, 0.7, 0.8, 0.9, 1.0, 1.1],
    "critThreshold":   5,
    "critMin":         0.8,
    "critMax":         1.5,
    "availableDiceTypes": [4, 6, 8, 10, 12, 20],
    "focusedFireRanges": [
      { "min": 1, "max": 1, "bonus_pct": 0.20 },
      { "min": 2, "max": 5, "bonus_pct": 0.50 },
      { "min": 6, "max": 6, "bonus_pct": 1.00 }
    ],
    "manualRollDefault": { "successLine": 4, "bonusDamage": 0, "enabled": false }
  }
  ```
- 网关 `combat.ts` 新增：
  - `GET /api/dice-config` → 回读当前 `DiceService.config`
  - `PUT /api/dice-config` → 校验后 `DiceService.loadConfig(body)` 并落盘（热更新，无需重启容器）
- 部署提示：combat-service 打包进 gateway 镜像，配置在 `/app/data`；仅重建 `mecha-gateway` 即生效（**严禁动 `mecha-battle-db`**）。

## 5. 前端设计预想：骰子参数配置页 / 卡片

### 5.1 定位与路由
- 新增 `frontend/src/views/DiceConfigView.vue`，路由 `/dice-config`，侧边栏 `TheSidebar` 新增入口「🎲 骰子工坊」。
- **与 `GlossaryView`（词条编辑）职责分离**：Glossary 管"每个技能配什么骰 / 分支判定"，本页管"骰子引擎的**全局参数**"（倍率梯度、暴击、骰面库、专注射射档位、手动摇骰默认）。两者通过 `availableDiceTypes` 联动（本页决定 Glossary 下拉可选面数）。

### 5.2 页面结构（卡片式布局）
复用 GlossaryView 已有的 `param-row` / `wiz-input` 样式与 `contracts/skillContract.js` 的 `DICE_TYPES` 常量（`L66`），保持视觉一致。

| 卡片 | 内容 | 控件 |
|------|------|------|
| **卡片1 投骰倍率梯度** | `rollMult[6]`（骰点1~6 → 倍率） | 6 个滑块/数字输入，右側实时显示折线或柱状曲线 |
| **卡片2 暴击配置** | `critThreshold` / `critMin` / `critMax` | 数字输入（触发骰点、倍率区间上下限） |
| **卡片3 骰面库** | `availableDiceTypes` | 4/6/8/10/12/20 多选开关（影响 Glossary 下拉与手动摇骰可选面） |
| **卡片4 专注射射档位** | `focusedFireRanges` | 可增删行的 min/max/bonus_pct 编辑器 |
| **卡片5 手动摇骰默认** | `manualRollDefault` | `successLine`、`bonusDamage`、全局 `enabled` 开关 |
| **卡片6 实时掷骰模拟器** | 本地验证 | 选骰面+次数 → 调 `diceUtil.rollMany` 掷骰并画分布直方图，确认参数生效 |

### 5.3 数据流向
```
DiceConfigView  --GET-->  /api/dice-config  -->  DiceService.config
      | 双向绑定编辑
      |  --PUT-->  /api/dice-config  -->  DiceService.loadConfig() + 落盘
```
- **即时生效范围**：新开战斗 / 新一次结算立即读新参数；**进行中战斗已加载进内存的单位状态不回滚**（仅后续结算生效）——需在页面注明提示。

### 5.4 复用现有资产
- 样式与控件：参考 `GlossaryView.vue` 的 `wiz-field` / `param-select` / `param-input`（L184-192、L489-560）。
- 手动摇骰动画：`NewBattleView.vue` L3119-3194 保留，仅把 `rollDice` 换成本地 `diceUtil`。
- 前端轻量镜像：`src/utils/diceUtil.js` 实现与后端 `DiceService.roll` 完全一致的解析（number→面数、`"NdM"`→表达式），保证前后端掷骰语义零偏差。

### 5.5 不做的事（边界）
- 不动各业务系统的"点数→含义"解释层（ROLL_MULT 表、dice_branches、effects 等），它们仍由各自系统负责。
- 不恢复 dicescript VM 依赖；保持纯 `Math.random` 实现（延续 Phase 4 简化方向）。

## 6. 实施步骤与风险

1. **Step 1** 新建 `diceService.cjs`（后端单例）+ `src/utils/diceUtil.js`（前端镜像），并写单测验证 `roll` 对 number / `"NdM"` 两种入参一致。
2. **Step 2** 按 §3 顺序逐个文件替换为 `DiceService`，旧 `rollDice` 保留 `deprecated` 别名过渡一版。
3. **Step 3** 抽 `ROLL_MULT` / `CRIT_*` 常量进 `diceConfig`，加 `GET/PUT /api/dice-config`（combat.ts）。
4. **Step 4** 新建 `DiceConfigView.vue` + 侧边栏入口 + 路由 `/dice-config`。
5. **Step 5** 部署：rsync 源码 → 服务器 `frontend npm run build` → `docker compose build --no-cache mecha-gateway mecha-frontend` → 大小写对账（红线 #7）。
6. **风险与对策**
   - **`dice_type` 语义分歧**（number 面数 vs `"NdM"` 字符串）：以 `DiceService.roll` 统一解析为唯一真理；`branchEvaluator`/`skillExecutor` 调用处入参已经是 number，无需改业务。
   - **前后端解析一致性**：前端 `diceUtil` 必须镜像后端 `roll`，避免手动摇骰动画与引擎结果不一致。
   - **进行中战斗热更新**：仅新结算生效，页面需提示。

---

## 7. 验收标准

- 全仓 grep 战斗结算路径内 `Math.random()` 归零（除 `diceService.cjs` / `diceUtil.js` 内部）；`rollDice` 仅 `diceService` 定义一处。
- `DiceEngine.cjs` 旧文件可删除（或保留仅作注释参考）。
- 前端「骰子工坊」可改 `rollMult` / `crit*` 并即时影响**新开战斗**的结算与弹窗（投骰倍率项随之变化）。
- 手动摇骰动画与后端掷骰结果一致（同一 `dice_type` 同分布）。
