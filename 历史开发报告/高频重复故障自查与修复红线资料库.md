## 红线 #1: Canvas 离奇白屏/黑屏/不显示

### 发生次数: ≥5 次 (Phase 9, 12, 16, 18-B, 18-C)

### 典型症状

- Canvas 区域全黑、全白、或显示为透明空白
- 控制台无报错，或报错信息完全无关
- 仅在某些操作序列后出现（如：从整备室出击 → Canvas 不显示）
- F5 刷新后可能恢复，但下次操作又消失

### 排查公式

```
Canvas不显示 = 
    CSS孤儿选择器导致Flex布局破裂
  | Vue路由守卫重定向导致 nextTick 时序失效
  | Canvas尺寸为 0 (宽/高未初始化)
  | drawBattleScene 静默抛异常
  | terrainMap/cells 数据格式不兼容
```

### 子类 A: CSS 孤儿选择器破坏 Flex 布局

**发生**：Phase 16 (HexGridCanvas 不显示)  
**根因**：`.log-entry.log-move` 等 7 个选择器缺少 `{ }` 规则块，后续选择器在第2个空缺处被吞并，导致 Flex 容器失效。  
**自查诊断**：
1. 打开浏览器 DevTools → Elements → 检查 Canvas 父容器 computed width/height 是否为 0
2. 搜索 scoped style 中所有含空格但无 `{` 的选择器行
3. 在 Vue SFC 的 `<style scoped>` 中运行 `grep -n '^\.[a-z-]*\.[a-z-]*\s*$'` 检查悬挂选择器

**标准修复范式**：
```css
/* ❌ 错误：悬挂选择器 */
.log-entry.log-move     ← 缺乏 { } 规则块
.log-entry.log-attack

/* ✅ 修复：删除所有空选择器，或补全 { } */
```

### 子类 B: Vue 路由守卫重定向导致 nextTick 时序失效

**发生**：Phase 18-C (整备室出击 → 战场 Canvas 黑屏)  
**根因**：`router.push('/battle/' + id)` → `redirectByDevice` 中间件 → `/battle-pc/:id` // 触发完整路由生命周期 → onMounted / watch / nextTick 竞争 → Canvas init 被跳过  
**自查诊断**：
1. 在 `onMounted` 中打印 `console.log('[Canvas] canvas element:', canvasRef.value)`
2. 检查 `document.querySelector('canvas')` 是否存在且尺寸 > 0
3. 在 route guard 中打印 `console.log('[Router] redirect:', from, '→', to)`

**标准修复范式**：
```javascript
// ❌ 错误：通过中间件重定向，多一次路由生命周期
router.push('/battle/' + battleId)  // → guard → /battle-pc/:id

// ✅ 修复：硬导航直达目标路由
router.push('/battle-pc/' + battleId)
```

### 子类 C: drawBattleScene 静默抛异常

**发生**：Phase 18-B (screenY 公式错误 → NaN → 绘制失败)  
**根因**：`drawBattleScene` 内部某行抛异常，但 HexGridCanvas 的 drawFn 调用可能被吞没  
**自查诊断**：
1. 在 `drawBattleScene` 开头和结尾添加 try/catch 打印
2. 在 HexGridCanvas 组件的 `draw()` 函数中打印 `console.log('[Canvas] redraw OK, w=', ctx.canvas.width)`

**标准修复范式**：
```javascript
// Phase 14 标准错误边界 (NewBattleView.vue:598-618)
function safeDrawBattleScene(ctx, opts) {
  try {
    drawBattleScene(ctx, opts)
  } catch (e) {
    console.error('[CanvasCRASH]', e.message)
    // 在 Canvas 上绘制红色错误提示
    ctx.fillStyle = '#ff4444'
    ctx.fillText('⚠ 渲染异常，请刷新页面', ctx.canvas.width / 2, 40)
    throw e
  }
}
```

### 子类 D: terrainMap / cells 格式不兼容

**发生**：Phase 13 (旧地图 terrain 格式 → 新格式不兼容)  
**根因**：后端返回的 terrain 值是字符串 `"mountain"` 而非对象 `{ terrain_id: "mountain", ... }`  
**自查诊断**：
1. 在 `sanitizeBattlefieldCells()` 中打印 `typeof cell.terrain`
2. 对 `battleState.terrain` 执行 `Object.values(terrain).every(v => typeof v === 'object')`

**标准修复范式**：
```javascript
// 必须在 onMounted 的 try/catch 外侧调用
sanitizeBattlefieldTerrain()   // 清洗 battleState
sanitizeBattlefieldCells()     // 显式 cells 校验
// terrainMap 二次清洗
Object.entries(terrainMap).forEach(([key, val]) => {
  if (typeof val === 'string') terrainMap[key] = sanitizeTerrainCell(val)
})
```

## 红线 #2: 部署/出击时数据链熔断

### 发生次数: ≥4 次 (Phase 13, 14, 18-A, 18-C)

### 典型症状

- 从整备室/大地图/战役沙盒出击 → 战场白屏/黑屏
- 控制台报错: `Cannot read property 'kinetic' of null/undefined`
- 错误堆栈指向 `damagePipe.cjs` 或 `skillExecutor.cjs`
- 仅出现在某些单位的战斗中（装备不全的单位）

### 排查公式

```
数据链熔断 = 
    unit.equipment 为 null/undefined
  | unit.equipment.left_hand 为 null
  | unit.equipment.left_hand.damage_kind_modifiers 缺失
  | damage_kind_modifiers 缺少 kinetic/beam/explosive/corrosive 中的某个 key
```

### 子类 A: 整备室/沙盒提交前未经 DKM 清洗

**发生**：Phase 14, 18-C (整备室出击 → damagePipe 爆炸)  
**根因**：`selectedUnits` 直接从格纳库取出提交给后端，`equipment.left_hand/right_hand/other` 三槽位可能为 null。战场侧虽然也有 `sanitizeUnitEquipment` 补给线，但在 `damagePipe._calcArmorReduction` 执行时可能还未完成清洗。  
**自查诊断**：
1. 在 `POST /api/combat/:id/pending-units` 的 body 中打印 `JSON.stringify(units[0].equipment)`
2. 检查是否存在 `"left_hand": null` 或 `"damage_kind_modifiers": null`
3. 在 `damagePipe._calcArmorReduction` 的 `for (const slot of [...] )` 循环中加 `if (!eq) continue`

**标准修复范式（双防线策略）**：

```javascript
// === 防线 1: 源头清洗 (整备室/战役沙盒提交前) ===
// 在 NewPreparationRoom.vue / CampaignView.vue 中
const selectedUnits = availableUnits.filter(u => ids.includes(u.id))
selectedUnits.forEach(u => sanitizeUnitEquipment(u))  // 强制清洗三槽位
fetch('/api/combat/' + id + '/pending-units', {
  body: JSON.stringify({ units: selectedUnits })
})

// === 防线 2: 战场侧清洗 (onMounted 初始化后) ===
// 在 NewBattleView.vue 中
sanitizeAllUnitsEquipment()
if (deployPool.value?.length > 0) {
  deployPool.value.forEach(u => sanitizeUnitEquipment(u))
}
```

### 子类 B: 全局 DKM 清洗规范

**sanitizeUnitEquipment 标准实现**（所有模块必须同构）：
```javascript
function sanitizeUnitEquipment(unit) {
  if (!unit || typeof unit !== 'object') return unit
  unit.equipment = unit.equipment || {}
  const slots = ['left_hand', 'right_hand', 'other']
  slots.forEach(slot => {
    if (!unit.equipment[slot] || typeof unit.equipment[slot] !== 'object') {
      unit.equipment[slot] = {
        damage_kind_modifiers: { kinetic: 0, beam: 0, explosive: 0, corrosive: 0 }
      }
    } else {
      const dkm = unit.equipment[slot].damage_kind_modifiers
      if (!dkm || typeof dkm !== 'object') {
        unit.equipment[slot].damage_kind_modifiers = { kinetic: 0, beam: 0, explosive: 0, corrosive: 0 }
      } else {
        const kinds = ['kinetic', 'beam', 'explosive', 'corrosive']
        kinds.forEach(k => { if (!(k in dkm)) dkm[k] = 0 })
      }
    }
  })
  return unit
}
```

## 红线 #3: 坐标错位与视觉漂移

### 发生次数: ≥3 次 (Phase 9.7, 16, 18-B)

### 典型症状

- 棋子渲染位置与鼠标选中的六角格不一致（偏移约 6-7 行）
- 平移/缩放后棋子"飞"出格子
- 等距视角下 X/Y 轴发生倾斜
- 不同缩放级别下偏移量不恒定

### 排查公式

```
坐标漂移 = 
    screenY 公式混入 flatX 分量 (CTM 约束违反)
  | zoomReset 锚点用 .x/.y 而非 .wx/.wy (CTM 坐标与 flat 坐标混淆)
  | hexUtils 常量硬编码而非统一导入 (HEX_WIDTH=64, HEX_HEIGHT=72)
  | pixelToHex/hexToPixel 内部混入非 1.0 倍率 (缩放旁路污染)
```

### 子类 A: screenY 混入 flatX 分量（7行漂移经典内鬼）

**发生**：Phase 18-B (最严重的一次)  
**根因**：`NewBattleView.drawBattleScene` 中两处 screenY 公式违反了 CTM 矩阵约束：

```
CTM = ctx.transform(scaleX, 0, shearX, scaleY, 0, 0)
         ↓
   newX = scaleX * flatX + shearX * flatY
   newY =        0 * flatX + scaleY * flatY  ← b=0 是强制约束!
```

旧代码错误地将 `shearY` 纳入 Y 轴：`screenY = oy + s * (iso.shearY * flatX + iso.scaleY * flatY)`  
→ `shearY * flatX = 0.44 * 312 = 137` 像素 → 除以 `scaleY * 1.5 * 36 = 21` 像素/行 → **恰好 6.5 行脱靶**

**自查诊断**：
1. 打印 `flatX = getUnitDrawFlat(unit)` 的值，估算 `flatX / (1.5 * HEX_RADIUS)`
2. 在 screenY 公式中检查是否出现任何 flatX 项
3. 验证：在 `r=0` 行部署一个棋子，肉眼确认其是否与格顶线对齐

**标准修复范式**：
```javascript
// ✅ 正确：screenY 仅依赖 flatY（严格遵循 CTM 的 b=0 约束）
const screenX = ox + s * (iso.scaleX * flatX + iso.shearX * flatY)
const screenY = oy + s * (iso.scaleY * flatY)

// ❌ 错误：Y 轴混入 flatX 分量
const screenY = oy + s * (iso.shearY * flatX + iso.scaleY * flatY)
```

### 子类 B: 坐标转换净化原则

**来自 Phase 9.7 终极宪法的核心红线**：

1. **hexUtils.js 是唯一数学真理**：`HEX_WIDTH=64, HEX_HEIGHT=72` 统一从 hexUtils 导入，**严禁任何文件硬编码**
2. **pixelToHex/hexToPixel 保持 1.0 标准倍率绝对纯净**：缩放/平移/等距压缩必须在核心公式外部进行矩阵逆运算
3. **渲染时**：2D标准坐标 → 乘scale → 加offset → (若3D则Y*0.5) → 绘制
4. **点击时**：鼠标像素 → 减offset → 除scale → (若3D则Y/0.5) → 核心公式逆推

### 子类 C: CTM 矩阵成员对照表

| 矩阵成员 | 值 (等距基准) | 含义 | 可混入Y轴? |
|----------|-------------|------|-----------|
| `scaleX` | 1.00 | X轴水平缩放 | 否（仅X） |
| `b` | **0** | **强制为0** | **如果非0则CTM定义被违反** |
| `shearX` | 0.25 | X轴剪切(纵深感) | 否（仅X） |
| `scaleY` | 0.39 | Y轴垂直压缩 | **是（唯一合法Y分量）** |

### 红线 #4: 独立渲染未复用标准六角格管线 (≥2次 · Phase 19, 19-D)

#### 典型症状

- 剧情模式/编辑模式使用了独立的 HTML `<table>` 或 div 网格渲染代替标准 `<HexGridCanvas>`
- 点击事件走独立路线的 `handleCellClick(q,r)` 而非 `@hex-click` 逆矩阵事件
- 不使用 `drawBattleScene` 而手动拼接 `getCellStyle` / `getCellClasses` 逐格样式
- 不同模式下坐标计算逻辑不一致，导致视觉漂移或拾取错位

#### 排查公式

```bash
# 检查是否存在独立 Table 渲染
grep -n '<table\|getCellClass\|getCellStyle' frontend/src/views/*.vue

# 检查是否缺少 HexGridCanvas 导入
grep -c 'HexGridCanvas' frontend/src/views/*.vue
# 预期: 所有战斗/编辑视图均为 ≥1
```

#### 子类诊断

| 子类 | 症状 | 诊断 |
|------|------|------|
| **A: Table 替代 Canvas** | 使用 `<table>` / `<td>` 渲染六角格 | 废除 Table，挂载 `<HexGridCanvas>` + `:draw-fn` |
| **B: 硬编码单位数据** | 玩家单位写死在代码中而非从格纳库加载 | 导入 `hangarAPI`，`selectCampaign` 时异步拉取 |
| **C: 触控事件失联** | `handleCellClick` 独立实现而非复用 `@hex-click` | 使用 `onHexClick({ q, r })` 处理画布事件 |
| **D: 防爆清洗缺失** | deploy 前单位未经过 `sanitizeUnitEquipment` | 出征前强制调用清洗，确保 DKM 三槽位齐备 |

#### 标准修复范式

**一式: 废除 Table，挂载 Canvas**
```vue
<!-- ❌ 错误 -->
<table>
  <tr v-for="r in height"><td v-for="q in width" :style="getCellStyle(q,r)">
     ...
  </td></tr>
</table>

<!-- ✅ 正确 -->
<HexGridCanvas
  ref="hexGrid" mode="battle"
  :grid-width="battleState?.width || 20"
  :grid-height="battleState?.height || 30"
  :draw-fn="safeDrawBattleScene"
  @hex-click="onHexClick"
/>
```

**二式: 实现 safeDrawBattleScene**
```javascript
function drawBattleScene(ctx, { hlQ, hlR } = {}) {
  // 使用 hexUtils 标准公式绘制六角格 terrain + units
  // Even-R: px = ox + q * HEX_WIDTH * 0.75
  //         py = oy + r * HEX_HEIGHT + (q%2 ? HEX_HEIGHT/2 : 0)
}
function safeDrawBattleScene(ctx, h) {
  try { drawBattleScene(ctx, h) } catch(e) {
    console.error('[Canvas] 绘制异常:', e)
  }
}
```

**三式: 打通格纳库数据链**
```javascript
import { hangarAPI } from '@/api/client'

// 沙盒中异步加载
const res = await hangarAPI.getUnits()
hangarUnits.value = res.data?.units || []

// 出征前清洗
playerUnits.forEach(u => sanitizeUnitEquipment(u))
```

**四式: onHexClick 事件路由**
```javascript
function onHexClick({ q, r }) {
  const unit = battleState.value.units.find(u => u.q===q && u.r===r)
  if (unit) {
    unit.faction === 'earth' ? selectUnit(unit) : selectTarget(unit)
  } else if (selectedUnitId.value) {
    selectedTargetPos.value = { q, r }
  }
}
```

1. **绝对禁止**在任何战斗/编辑视图中使用 HTML Table 替代 Canvas
2. **绝对禁止**硬编码玩家单位 — 所有友军必须从格纳库 API 动态加载

### 红线 #5: 异步动态组件挂载导致数据时序脱节 (≥1次 · Phase 20)

#### 典型症状

- 动态组件挂载后 Canvas 只露面板不露地图（地面六角格不渲染）
- 控制台无报错或仅有 `battleState.cells` 为 undefined 的静默日志
- 发生在沙盒/容器模式下，`battleState` 通过 emit/props 异步传入子组件
- F5 刷新后偶尔正常，但下次从父容器传入数据时又复发

#### 排查公式

```
时序脱节 =
    onMounted 中 getBattleState 在异步数据到达前完成
  | 父组件通过 emit('state-refreshed') 传入 battleState → 子组件无 watch
  | campaignApi.getBattleState 返回延迟 > 500ms
  | sanitizeBattlefieldCells() 在 onMounted 内已执行 → cells 为空
  → 后续 battleState.cells 到达时 Canvas 无重绘信号触发
```

#### 自查诊断

1. 在 `onMounted` 中打日志确认 `battleState.value?.cells?.length`
2. 确认是否存在对 `battleState` 的 deep watch（搜索 `watch.*battleState`）
3. 检查 `HexGridCanvas` 是否在 `battleState` 为空时正确渲染空地图而非完全消失
4. 在 `<script setup>` 中打印 `console.log('[MountTrace] battleState:', battleState.value)`

#### 标准修复范式

```javascript
// ✅ 刚性时序修复：deep watch + immediate + sanitize 三重保障
watch(() => battleState.value, (newDynamicState) => {
  if (newDynamicState && newDynamicState.cells && newDynamicState.cells.length > 0) {
    console.log('[TimeSync] 检测到异步地图数据源到达，立刻触发 cells 洗涤管线')
    sanitizeBattlefieldCells(newDynamicState.cells)
    // terrainMap 二次清洗
    if (terrainMap && typeof terrainMap === 'object') {
      Object.entries(terrainMap).forEach(([key, val]) => {
        if (typeof val === 'string') terrainMap[key] = sanitizeTerrainCell(val)
        else if (val && typeof val === 'object' && !val.terrain_id) terrainMap[key] = sanitizeTerrainCell(val)
      })
    }
    if (hexGrid.value) { hexGrid.value.draw() }  // 刚性逼迫画布重绘
  }
}, { deep: true, immediate: true })
```

#### 为什么不能用 onMounted 一次性清洗

`onMounted` 仅保证组件 DOM 已挂载，不保证**异步数据**已到达。在以下场景下 onMounted 的清洗发生在数据就绪前：

| 场景 | 数据延迟 | onMounted 时序 |
|------|---------|----------------|
| 剧情沙盒通过 props 传入 battleState | 0–2000ms | 清洗发生在 state 注入前 |
| 父组件 emit('state-refreshed') | 500–3000ms | 清洗发生时 cells 为空 |
| campaignApi.getBattleState 网络延迟 | 1000–5000ms | try 块内清洗失败，catch 分支未清洗 |

**结论**：`onMounted` 是必要条件，但不是充分条件。必须追加 deep watch 作为时序保险。

#### 关键严禁行为

1. **绝对禁止**仅依赖 `onMounted` 执行 `sanitizeBattlefieldCells()` 而不设 watch 兜底
2. **绝对禁止**在 watch 中仅判断 `battleState.value` 存在而不检查 `cells.length > 0`
3. **绝对禁止**在 watch 回调中省略 `hexGrid.value.draw()` 重绘调用

| Phase | 故障描述 | 触发条件 |
|-------|----------|----------|

### 红线 #6: 双层主标签嵌套引发时序坍塌 (≥1次 · Phase 20-B)

#### 典型症状

- DOM 树上出现 `/html/body/div/div/main/div/main/div[3]` 等离奇多层 `<main>` 嵌套路径
- Canvas 尺寸测绘瘫痪 — `getBoundingClientRect()` 返回 0 或异常值
- Flex 布局腰斩 — 子组件高度塌陷为 0，地图完全不加载
- 仅出现在有外层布局容器（如 App.vue 的 `<main>`）页面的动态组件中

#### 排查公式

```
双层 main 嵌套 =
    App.vue / 布局组件中已有 <main class="main-content"> 包裹 router-view
  | 子组件内部又声明了 <main class="dm-main"> 作为独立主内容区
  → 两处 <main> 在 DOM 中形成父子级联
  → 浏览器 Flex 布局上下文中 <main> 可能争夺主轴空间
  → 内层 Canvas 的 computed width/height 因弹性容器塌缩而变为 0
```

#### 自查诊断

1. 打开浏览器 DevTools → Elements → 在 DOM 树中搜索 `<main`，计数是否 > 1
2. 逐层检查父组件布局：`App.vue` / 布局 wrapper / 路由视图
3. 检查 Canvas 容器 computed style：若 `width=0` 或 `height=0`，说明 Flex 已解体
4. 在每个 `<main>` 出现位置打印 `console.trace()` 确认组件来源

#### 标准修复范式

```html
<!-- ❌ 错误：子组件用 <main>，与 App.vue 的 <main> 形成双层嵌套 -->
<!-- App.vue -->
<main class="main-content">
  <router-view />     ← 渲染 CampaignView → NewBattleView
</main>

<!-- NewBattleView.vue -->
<div class="dm-battle-layout">
  <main class="dm-main">   ← 第二个 <main>！与 App.vue 冲突
    <HexGridCanvas />
  </main>
</div>

<!-- ✅ 正确：子组件内部降级为 <div>，全局仅保留一个 <main> -->
<!-- NewBattleView.vue -->
<div class="dm-battle-layout">
  <div class="dm-main">    ← <div> 替代 <main>，语义不受影响
    <HexGridCanvas />
  </div>
</div>
```

#### 修剪手术标准流程

1. **定位**: `grep -n '<main'` 扫描全量 `.vue` 文件，列出所有 `<main>` 声明
2. **溯源**: 确认每个 `<main>` 所在的组件层级 — 最终渲染路径上是否多个 `<main>` 共存
3. **降级**: 保留**最外层**布局的 `<main>`（如 App.vue），将**所有内层** `<main>` 改为 `<div>`
4. **CSS 平移**: 确保 `<div>` 沿用原 `<main>` 的全部 class，不丢失任何样式规则
5. **验收**: DevTools Elements 面板确认页面有且仅有 1 个 `<main>` 标签

#### 关键严禁行为

1. **绝对禁止**在任何 `<router-view>` 的子页面中使用 `<main>` 标签（若外层已有 `<main>`）
2. **绝对禁止**在有外层 Flex/Grid 布局的容器内嵌套第二个 `<main>`
3. **绝对禁止**将 Canvas 容纳在多个 `<main>` 嵌套的 DOM 子树中 — Canvas 尺寸测绘将瘫痪

#### 历史故障记录

| Phase | 故障描述 | 触发条件 |
|-------|----------|----------|
| 20-B | App.vue `<main>` + NewBattleView `<main>` 双层嵌套 → Flex 腰斩 → Canvas 尺寸 0 | CampaignView 通过 router-view 渲染在 App.vue `<main>` 内，NewBattleView 自含 `<main>` |

### 红线 #8: UUID 序列化排异致 [object Object] 级联崩溃 (≥1次 · Phase 21)

#### 典型症状

- 控制台爆出 100+ 个运行时错误，全部追溯至同一根源
- API 请求路径出现 `/api/campaign/[object Object]/state`
- Vue 模板中 `battleState.cells` 为 undefined，触发 `v-for` / `map()` / `slice()` 等渲染爆炸
- 错误集中在组件 `onMounted` 阶段，因为 `fetch()` / `axios.get()` URL 为非法 `[object Object]`

#### 排查公式

```
UUID 序列化排异 =
    props.campaign_battle_id 传入的是 Object 而非 String
  | computed 计算属性直接透传，未做 String() 强制转换
  | API 适配器 _cid 闭包捕获了原始 Object，URL 拼接时隐式调用 .toString()
  → Object.toString() 返回 "[object Object]"
  → 所有 API 请求发往非法 URL → 返回 HTML / 500
  → battleState.value 赋值失败或赋值空对象
  → Template 内 v-for / computed 基于 undefined 计算
  → 123 个 Runtime Error 级联爆炸
```

#### 自查诊断

1. `console.log(typeof props.campaign_battle_id, props.campaign_battle_id)` → 若输出 `object`，立即告警
2. 在所有 API 调用的 URL 拼接处（`/campaign/${_cid.value}/state`）打临时日志确认值类型
3. 搜索 `[object Object]` 在 Network 面板的请求 URL 中
4. 检查所有 `computed` 返回值是否强制 `String()` 包装

#### 标准修复范式

```javascript
// ✅ 刚性防御清洗器
const FORBIDDEN_IDS = new Set(['[object Object]', 'undefined', 'null', ''])
function sanitizeBattleId(raw) {
  const s = String(raw ?? '')
  if (FORBIDDEN_IDS.has(s)) {
    console.error(`[Anti-Explode] 截获非法战场指针 "${s}" (type=${typeof raw})，强行重定向兜底`)
    return '1'  // 刚性指向默认 SQLite 1号地基
  }
  return s
}

// ✅ activeBattleId 入口清洗
const activeBattleId = computed(() => {
  if (props.is_campaign && props.campaign_battle_id) {
    return sanitizeBattleId(props.campaign_battle_id)
  }
  return sanitizeBattleId(route.params.id)
})

// ✅ _cid 同步清洗 (campaignApi 内部 URL 拼接依赖此值)
const _cid = computed(() => sanitizeBattleId(props.campaign_battle_id))
```

#### 模板级防护：v-if 安全空气墙

```html
<!-- ✅ 数据未 100% 就绪前，绝对禁止模板渲染 -->
<div v-if="battleState && battleState.cells && battleState.cells.length > 0" class="dm-battle-layout">
  <!-- 正常战场内容 -->
</div>
<div v-else class="dm-battle-layout dm-battle-loading">
  <!-- 骨架屏：数据未就绪时绝对不执行任何 v-for / computed 循环 -->
  <div class="loading-spinner" />
  <p>[ BATTLEFIELD_DATA_INITIALIZING ]</p>
</div>
```

#### onMounted 数据链刚性冲洗

```javascript
// ✅ 数据赋值后立刻执行三重清洗
battleState.value = data.battle || data
sanitizeAllUnitsEquipment()     // 单位装备 DKM 四槽位清洗
sanitizeBattlefieldCells()      // 地形 cells 标准化清洗 ← Phase 21 追加
```

#### 关键严禁行为

1. **绝对禁止** `computed` 直接透传 props 值而不经 `sanitizeBattleId()` 清洗
2. **绝对禁止** `battleApi.getBattleState(activeBattleId)` 在 `activeBattleId` 未清洗前执行
3. **绝对禁止** Template 内直接对 `battleState.cells` 进行 `v-for` 遍历而不设 `v-if` 守卫
4. **绝对禁止** 任何 API URL 拼接中直接使用未经 `String()` 包装的 Object 类型值
5. **绝对禁止** `localStorage.setItem(key, obj)` 直接投喂原生 Object — 必须 `JSON.stringify(obj)` 全量序列化 (Phase 21-B)
6. **绝对禁止** `JSON.parse(localStorage.getItem(key))` 不检查 `[object Object]` 即直接使用 — 必须先过毒化检测 (Phase 21-B)
7. **绝对禁止** 将 Vue 响应式 Proxy 对象直接塞入 API 请求体 — 必须 `JSON.parse(JSON.stringify(obj))` 过水解耦 (Phase 21-D)
8. **绝对禁止** 在 campaignApi 中硬编码 `/campaign/` 前缀 — 必须经由 `_routePfx` 多态分流器智能路由 UUID/剧本号 (Phase 21-E)

